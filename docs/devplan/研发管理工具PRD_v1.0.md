## 1. 文档概述

### 1.1 文档目的

本文档基于公司《需求开发流程》流程图，定义研发管理工具的产品需求，覆盖**需求管理、开发任务管理、测试管理、发版上线管理、报表统计**五大业务域，作为产品设计、开发、测试、验收的依据。

### 1.2 建设背景与目标

当前需求与测试管理依赖线下流转，存在记录缺失、进度不透明、质量不可控、数据难统计等问题。本工具的建设目标（对应流程图"好处"）：

1. **电子记录**：全流程线上化，不缺项、不漏项、易统计；
2. **质量把控**：需求评审、详细设计评审、测试把关、上线验证多级质量控制点线上固化；
3. **进度透明**：进度一目了然，尤其是各干系人自己关心的进度。

### 1.3 考核指标（系统必须支撑的数据度量）

| 序号 | 考核点 | 数据来源模块 |
| --- | --- | --- |
| 1 | 软件需求申请单数量 | 需求管理 |
| 2 | 需求设计工作量 | 需求管理（设计工时填报） |
| 3 | 需求设计按时完成情况 | 需求管理（计划/实际时间对比） |
| 4 | 开发任务测试单数量 | 测试管理 |
| 5 | 测试工作量 | 测试管理（测试工时填报） |
| 6 | 测试用例覆盖率 | 测试管理（用例关联需求） |
| 7 | 项目与运维提报 bug 数量 | 需求管理/Bug 管理（按来源统计） |

## 3. 核心业务流程

### 3.1 总体流程概览

```
需求收集（4类来源）→ 需求提交 → 需求审批 →（讨论会评审）→ 需求分析设计
→ 需求设计评审 → 开发排期 → 任务分解 → 详细设计 → 详细设计评审 → 开发
→ 测试执行 → 测试通过 → 质量确认 → 操作指导书编制 → 状态自动完成
→ 发起人验收 → 发版计划 → 脚本封包/上线资料 → 审阅 → 数据进出申请
→ 上线申请 → 上线执行 → 上线验证 → 试运行跟进 → 结束
```

### 3.2 需求管理流程

**需求来源（四类，均需形成需求描述后提交《软件需求申请单》）：**

| 来源 | 提交人 | 前置动作 |
| --- | --- | --- |
| 迭代需求 | 总工/产品经理 | 整理迭代需求，形成需求描述 |
| 客户需求/bug（交付） | 总监/项目经理/实施人员 | 接收并过滤客户需求/bug，形成需求描述 |
| 客户需求/bug（运维） | 运维服务人员 | 接收并过滤客户需求/bug，形成需求描述 |
| 售前项目需求 | 售前人员 | 进行项目设计，形成需求/新硬件描述 |

**审批链路：**

1. 交付中心提交的需求：先由**总监/项目经理**在《软件需求申请单》中审批；
2. 统一由**产品经理/总工**进行需求合理性审批：
   - 不合理 → 驳回并填写驳回原因（流程退回发起人）；
   - 合理 → 判断是否需要需求讨论会评审：
     - 需要 → 需求发起人员/领导/产品**每周四线下需求讨论会**评审，不通过则结束/退回，通过则进入设计；
     - 不需要 → 直接进入设计；
3. **产品经理**进行需求分析设计（产出需求设计）；
4. **领导**进行需求设计评审：
   - 评审不通过 → 退回重新设计；
   - 评审通过 → 进入开发排期；
5. **开发经理**了解需求并进行开发排期；**产品经理**跟进排期计划（重点：跟进时间风险）；
6. **需求发起人**查看需求设计和排期计划（重点：描述清晰的需求内容、期望的时间节点）。

### 3.3 开发管理流程

1. **开发经理**在《软件需求申请单》中分解形成《开发任务单》（重点：任务分解和各任务的排期）；
2. **开发人员**在《开发任务单》中进行详细设计；
3. **领导**在《开发任务单》中进行详细设计评审：驳回 → 重新设计；通过 → 进入开发；
4. **开发人员**进行开发，完成后提交测试。

### 3.4 测试管理流程

1. **测试人员**在需求设计阶段即介入，了解需求设计、准备测试（编写测试用例）；
2. 开发完成后，测试人员在《开发任务单》中**按测试用例进行测试**，并在《测试任务单》中记录测试结果；
3. 测试判断：
   - 不通过 → 驳回，并**关联测试任务单中的 bug 数量**；
   - 通过 → 测试人员在《开发任务单》中通过测试；
4. **测试原则**：bug 优先；测试 bug 不隔人天（当日 bug 当日处理）；
5. **产品经理**在《软件需求申请单》中确认开发质量（重点：细节质量把控、整体质量把控）；
6. **测试人员**根据《软件需求申请单》编制操作指导书；
7. **系统自动**在《软件需求申请单》中更新需求状态为"完成"；
8. **需求发起人**查看需求完成情况，并进行验收测试。

### 3.5 发版上线流程

1. **技术经理**确定发版计划（现阶段按发版管理，后续推进迭代版本制定）；
2. **测试人员**进行数据库脚本封包；
3. **开发人员**发版并准备上线资料（**升级包、上线操作说明、回滚方案**三件套）；
4. **所有人员（或各部门负责人）**审阅上线资料；
5. **开发人员**在《数据进出申请》中进行申请和发版；
6. **项目经理/实施人员**在《上线申请单》中确认上线时间并提交申请；
7. 《上线申请单》审批通过；
8. **运维人员或甲方信息人员**按照时间和上线资料操作上线；
9. 是否操作成功：
   - 否 → 按回滚方案执行**回滚**；
   - 是 → **实施人员/测试人员**进行上线后验证（升级完成前后半小时数据和功能持续正常）；
10. 是否验证通过：是 → **实施人员**进行试运行阶段跟进 → 结束。

### 3.6 需求状态机

| 状态 | 触发动作 | 下一状态 |
| --- | --- | --- |
| 草稿 | 提交 | 待审批 |
| 待审批 | 审批驳回 | 已驳回 |
| 待审批 | 审批通过 | 待评审/设计中 |
| 已驳回 | 重新提交 | 待审批 |
| 待评审 | 讨论会通过 | 设计中 |
| 设计中 | 设计提交评审 | 设计评审中 |
| 设计评审中 | 评审不通过 | 设计中 |
| 设计评审中 | 评审通过 | 排期中 |
| 排期中 | 排期确认 | 开发中 |
| 开发中 | 开发完成提测 | 测试中 |
| 测试中 | 测试驳回 | 开发中 |
| 测试中 | 测试通过+质量确认 | 待验收 |
| 待验收 | 发起人验收通过（系统自动更新完成） | 已完成 |
| 已完成 | 纳入发版 | 已发布 |

## 4. 功能需求

### 4.1 功能架构

```
研发管理工具
├── 需求管理模块（软件需求申请单）
├── 开发任务模块（开发任务单）
├── 测试管理模块（测试任务单/用例/bug）
├── 发版上线模块（发版计划/数据进出申请/上线申请单）
├── 文档管理（操作指导书、上线资料）
├── 报表统计模块（考核看板/明细表）
├── 待办中心与消息通知
└── 系统管理（用户/角色/权限/流程配置）
```

### 4.2 需求管理模块（《软件需求申请单》）

#### 4.2.1 功能列表

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| REQ-01 | 需求创建与提交 | P0 | 支持四类来源入口，自动生成申请单编号 |
| REQ-02 | 需求描述 | P0 | 需求内容、期望时间节点必填（重点控制项） |
| REQ-03 | 多级审批 | P0 | 交付中心需求先经总监/项目经理审批；统一经产品经理/总工合理性审批，驳回必填原因 |
| REQ-04 | 讨论会评审 | P0 | 标记"需讨论会评审"的需求纳入每周四讨论会议题池，记录评审结论 |
| REQ-05 | 需求分析设计 | P0 | 产品经理在线编制需求设计，支持附件 |
| REQ-06 | 需求设计评审 | P0 | 领导评审，通过/不通过，不通过退回重新设计 |
| REQ-07 | 开发排期 | P0 | 开发经理排期（计划开始/完成时间），产品经理可跟进、标注时间风险 |
| REQ-08 | 排期计划查看 | P0 | 需求发起人可查看需求设计和排期计划 |
| REQ-09 | 状态自动更新 | P0 | 测试通过且质量确认后，系统自动更新需求状态为"完成" |
| REQ-10 | 验收测试 | P1 | 需求发起人在线验收并记录结论 |

#### 4.2.2 《软件需求申请单》字段设计

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 申请单编号 | 自动生成 | 是 | 规则：REQ-YYYYMMDD-XXX |
| 需求标题 | 文本 | 是 | 简要描述 |
| 需求来源 | 枚举 | 是 | 迭代需求/客户需求(交付)/客户需求(运维)/售前项目需求 |
| 关联客户/项目 | 文本/关联 | 否 | 来源为客户需求时建议填写 |
| 需求描述 | 富文本 | 是 | 重点：描述清晰的需求内容 |
| 期望完成时间 | 日期 | 是 | 重点：期望的时间节点 |
| 发起人/发起部门 | 自动 | 是 | 取登录人信息 |
| 是否需讨论会评审 | 布尔 | 是 | 默认否 |
| 需求设计 | 富文本+附件 | 是 | 产品经理编制 |
| 需求设计工作量 | 数值(人日) | 是 | 考核点 |
| 计划设计完成时间/实际完成时间 | 日期 | 是 | 考核点：按时完成情况 |
| 开发排期计划 | 关联任务 | 是 | 开发经理填写 |
| 审批记录 | 列表 | 自动 | 审批人/时间/结论/意见 |
| 当前状态 | 枚举 | 自动 | 见 3.6 状态机 |
| 关联开发任务单 | 关联 | 自动 | 一对多 |
| 验收结论 | 枚举+文本 | 否 | 通过/不通过 |

## 5. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 常规操作响应 ≤ 2s；报表查询 ≤ 5s；支持 200+ 并发用户 |
| 安全 | 角色权限最小化；审批操作留痕不可篡改；上线资料等敏感附件加密存储；满足内外网隔离要求 |
| 内外网协同 | 甲方现场（内网）与公司（外网）数据交换需有明确的同步/导入导出机制 |
| 可用性 | 表单填报有校验提示；待办入口突出；支持移动端审批（如采用钉钉方案） |
| 扩展性 | 表单与流程引擎化，支持后续新增表单类型与流程而无需定制开发 |
| 可追溯 | 需求→任务→用例→bug→版本全链路双向追溯 |

## 6. 技术实现方案评估（对应流程图"实现方案"）

| 方案 | 说明 | 优势 | 风险/限制 |
| --- | --- | --- | --- |
| 方案一：钉钉流程 | 基于钉钉审批流+表单搭建 | 移动端审批便捷、推广成本低 | **报表查看能力需确认**（流程图已标注该疑虑）；复杂状态机与追溯能力弱 |
| 方案二：新平台自定义表单+报表平台 | 自研/低代码平台自定义表单，对接报表平台 | 表单流程可定制、报表能力强、数据自主可控 | 建设周期与投入较大 |
| 方案三：免费 SaaS 管理平台 | 如 PingCode 等 | 开箱即用、专业研发管理能力 | 数据在外部平台，内外网协同与定制报表受限 |

**建议**：以方案二为目标架构（表单引擎+流程引擎+报表平台），MVP 阶段可借助方案三快速验证流程；涉及甲方内网场景需专项设计内外网协同方案。

## 8. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 内外网协同方案未明确 | 上线/数据进出环节线上化受阻 | 三期前完成专项方案评审；过渡期支持线下单据线上补录 |
| 钉钉方案报表能力不足 | 考核指标无法自动统计 | 选型阶段 POC 验证报表能力，不达标则采用方案二 |
| 表单配置与实际流程不符 | 流程执行走样 | 上线前按本 PRD 3.x 流程逐节点 UAT；表单字段配置评审（参考 openproject 配置） |
| 干系人职责不清 | 审批积压、待办不明 | 系统内置各表单流程与干系人职责说明页，待办明细按角色清晰呈现 |
| 用户习惯改变阻力 | 数据回线下 | 以"进度一目了然"为卖点推广；管理层以系统数据为考核唯一口径 |
