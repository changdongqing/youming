## 0. 文档说明

本文档以《研发管理工具PRD_v1.0.md》为基本需求，结合 youming 项目现有技术栈（pig 微服务框架 + pig-ui Vue3 前端 + PostgreSQL + Flyway），输出可直接指导开发的详细设计计划，覆盖：总体架构、模块设计、数据库设计、接口设计、前端设计、状态机与流程引擎设计、非功能设计、实施与排期计划。

### 0.1 设计原则

1. **复用优先**：最大化复用 pig 已有的用户/角色/权限/字典/文件/审批骨架，避免重复造轮子。
2. **引擎化**：表单字段可配置、流程节点可配置，支撑 PRD"扩展性"要求（新增表单类型与流程无需定制开发）。
3. **全链路追溯**：需求→任务→用例→bug→版本，主键与外键双向关联，任一节点可上溯/下钻。
4. **渐进交付**：一期 MVP 聚焦主流程线上化，二三期补齐发版上线、考核看板、内外网协同。
5. **约定优于配置**：状态机、编号规则、审批链路以约定内置为默认值，表单/流程引擎仅做例外覆盖。

### 0.2 与 pig 框架的复用关系

| pig 能力 | 复用方式 | 说明 |
| --- | --- | --- |
| pig-upms（用户/角色/菜单/部门/字典） | 直接复用 | 六部门组织架构 = upms 的 `sys_dept`；系统角色 = `sys_role`；权限码 = `sys_menu.permissions` |
| pig-common-security | 直接复用 | OAuth2 资源服务器、`@HasPermission` 权限注解、`SecurityUtils` 获取当前用户 |
| pig-common-data | 直接复用 | MyBatis-Plus、分页 `Page`、`R<T>` 统一响应、Flyway 迁移机制 |
| pig-common-feign | 直接复用 | 服务间调用（如任务单回写需求单状态） |
| pig-common-log + `@SysLog` | 直接复用 | 审批操作留痕不可篡改 |
| pig-common-oss | 直接复用 | 上线资料三件套、需求设计附件、详细设计附件加密存储 |
| pig-common-excel | 直接复用 | 报表导出 |
| pig-gateway | 直接复用 | 路由 `/admin/rm/**` 转发到研发管理模块 |

> 新增业务统一收敛到独立模块 **`pig-rm`**（Research Management），与 `pig-ontology` 并列，避免污染 upms 主干。

## 2. 领域模型与状态机设计

### 2.1 领域模型（聚合根）

```
Requirement（需求申请单） ──1:N──> DevTask（开发任务单）
DevTask ──1:N──> TestTask（测试任务单）
TestTask ──1:N──> Bug
TestTask ──N:1──> TestCase（测试用例）
TestCase ──N:1──> Requirement（用例关联需求，支撑覆盖率统计）
Requirement ──N:N──> ReleasePlan（发版计划，通过 release_item 关联）
ReleasePlan ──1:N──> ReleaseArtifact（上线三件套）
ReleasePlan ──1:1──> OnlineApply（上线申请单）
ReleasePlan ──1:1──> DataAccessApply（数据进出申请）
OnlineApply ──1:N──> OnlineExecution（上线执行记录，含回滚）
OnlineApply ──1:1──> OnlineVerify（上线验证）
OnlineVerify ──1:N──> TrialRunIssue（试运行问题）

ApprovalRecord（审批记录） ──N:1──> 任意单据（bill_type + bill_id）
OperationLog（操作日志，复用 SysLog）
```

### 2.4 状态机引擎设计

采用**枚举驱动 + 事件方法 + 配置覆盖**的轻量方案，不引入 Activiti：

```java
public enum RequirementEvent {
    SUBMIT,              // 提交
    APPROVE_PASS,        // 审批通过
    APPROVE_REJECT,      // 审批驳回
    RESUBMIT,            // 重新提交
    REVIEW_PASS,         // 讨论会通过
    REVIEW_FAIL,         // 讨论会不通过
    DESIGN_SUBMIT,       // 设计提交评审
    DESIGN_REVIEW_PASS,  // 设计评审通过
    DESIGN_REVIEW_FAIL,  // 设计评审不通过
    SCHEDULE_CONFIRM,    // 排期确认
    DEV_COMPLETE,        // 开发完成提测
    TEST_PASS,           // 测试通过（含质量确认）
    TEST_REJECT,         // 测试驳回
    ACCEPT,              // 验收通过
    RELEASE              // 纳入发版
}
```

状态转移规则以**静态转移表** + **数据库配置覆盖**实现：

- 默认转移表硬编码在 `RequirementStateMachine`（见 §6）。
- `rm_flow_node` 表可覆盖默认审批人/下一状态，实现"流程配置"（SYS-03）。
- 非法转移抛出 `StateMachineException`，前端拦截提示。

### 5.2 页面设计要点

#### 5.2.1 软件需求申请单（核心页面）

- **列表页**：支持按来源（四类）、状态、发起人、时间区间筛选；列表展示编号、标题、来源、状态（带状态色标）、期望完成时间、发起人；状态列点击进入详情。
- **表单页**：依据 `rm_form_field_config` 动态渲染字段；"需求描述"使用 wangeditor 富文本；"期望完成时间"日期选择器（重点控制项，标红必填）。
- **详情页**：分四个 Tab：
  1. 基本信息（表单字段只读）
  2. 审批记录（时间线，复用 pig 已有时间线组件风格）
  3. 需求设计（富文本展示 + 附件下载）
  4. 关联开发任务（列表，可跳转任务单详情）
- **状态流转可视化**：详情页顶部以步骤条（el-steps）展示当前状态在状态机中的位置。
- **操作按钮随状态变化**：如"待审批"状态显示"审批通过/驳回"按钮（仅审批人可见）；"设计中"显示"提交设计评审"按钮（仅设计人可见）。按钮可见性同时由前端状态判断 + 后端权限码双重控制。

#### 5.2.2 待办中心

- 顶部按待办类型分组统计（待审批 N / 待设计 N / 待评审 N / 待开发 N / 待测试 N / 待验收 N）。
- 列表展示：标题、单据类型、单据编号、待办类型、截止时间（超期标红）、操作（去处理→跳转对应单据）。
- 区分"执行人员待办"与"管理人员待办"两个 Tab（对应 PRD"执行人员和管理人员查阅待办明细清晰"）。

## 6. 状态机与流程引擎详细设计

### 6.1 状态机引擎实现

```java
/**
 * 需求状态机（默认转移表，可被 rm_flow_node 配置覆盖）
 */
@Component
public class RequirementStateMachine {

    // 转移表：(当前状态, 事件) -> 目标状态
    private static final Map<StatusEvent, RequirementStatusEnum> TRANSITIONS = Map.ofEntries(
        entry(of(DRAFT, SUBMIT), PENDING_APPROVAL),
        entry(of(PENDING_APPROVAL, APPROVE_PASS), PENDING_REVIEW),  // 默认需讨论会；可配置跳过
        entry(of(PENDING_APPROVAL, APPROVE_REJECT), REJECTED),
        entry(of(REJECTED, RESUBMIT), PENDING_APPROVAL),
        entry(of(PENDING_REVIEW, REVIEW_PASS), DESIGNING),
        entry(of(PENDING_REVIEW, REVIEW_FAIL), REJECTED),
        entry(of(DESIGNING, DESIGN_SUBMIT), DESIGN_REVIEW),
        entry(of(DESIGN_REVIEW, DESIGN_REVIEW_PASS), SCHEDULING),
        entry(of(DESIGN_REVIEW, DESIGN_REVIEW_FAIL), DESIGNING),
        entry(of(SCHEDULING, SCHEDULE_CONFIRM), DEVELOPING),
        entry(of(DEVELOPING, DEV_COMPLETE), TESTING),
        entry(of(TESTING, TEST_REJECT), DEVELOPING),
        entry(of(TESTING, TEST_PASS), PENDING_ACCEPTANCE),
        entry(of(PENDING_ACCEPTANCE, ACCEPT), COMPLETED),
        entry(of(COMPLETED, RELEASE), RELEASED)
    );

    public RequirementStatusEnum transit(RequirementStatusEnum current, RequirementEvent event) {
        RequirementStatusEnum next = TRANSITIONS.get(of(current, event));
        if (next == null) {
            throw new StateMachineException(
                "非法状态转移: " + current + " + " + event);
        }
        return next;
    }
}
```

**配置覆盖**：`rm_flow_node` 表的 `next_node_pass`/`next_node_reject` 字段可覆盖默认转移目标。`FlowService` 在执行转移前先查询配置，配置存在则用配置值，否则用默认表。

### 6.2 审批流程引擎

```
单据提交
  → FlowService.resolve(flowCode, billId)
    → 查询 rm_flow_node 获取当前节点的审批人(approver_type + approver_ref)
      → ROLE: 查 sys_role + sys_user_role 取角色下用户
      → DEPT_LEADER: 查 sys_dept.leader 取部门负责人
      → USER: 直接取用户
      → INITIATOR_LEADER: 取发起人所在部门负责人
    → 为每个审批人生成 rm_todo（待审批）
    → 审批人操作后写 rm_approval_record
      → 结论 PASS: 流转到 next_node_pass
      → 结论 REJECT: 流转到 next_node_reject，生成驳回待办给发起人
```

**PRD 审批链路落地**（`rm_flow_node` 种子数据）：

| 流程 | 节点 | 审批人类型 | 审批人引用 | 通过→下一节点 | 驳回→下一节点 |
| --- | --- | --- | --- | --- | --- |
| REQUIREMENT_FLOW | DELIVERY_APPROVAL | DEPT_LEADER | （发起人部门） | PRODUCT_APPROVAL | — |
| REQUIREMENT_FLOW | PRODUCT_APPROVAL | ROLE | rm_product_approver | REVIEW_OR_DESIGN | REJECTED |
| REQUIREMENT_FLOW | REVIEW | ROLE | rm_reviewer | DESIGN | REJECTED |
| REQUIREMENT_FLOW | DESIGN | ROLE | rm_designer | DESIGN_REVIEW | — |
| REQUIREMENT_FLOW | DESIGN_REVIEW | ROLE | rm_leader | SCHEDULE | DESIGN |
| REQUIREMENT_FLOW | SCHEDULE | ROLE | rm_dev_manager | DEVELOPING | — |

> 注：交付中心需求走 `DELIVERY_APPROVAL` 节点，其他来源直接从 `PRODUCT_APPROVAL` 开始（由流程引擎根据 `source` 跳过首节点）。

### 6.3 自动流转与事件驱动

| 自动事件 | 触发条件 | 实现 |
| --- | --- | --- |
| 状态自动完成 | 测试通过 AND 产品经理质量确认 | `TestTaskService.pass()` + `RequirementService.qualityConfirm()` 联合判断，满足后 `StateMachine.transit(TESTING, TEST_PASS)` |
| 测试任务单生成 | 开发完成提测 | `DevTaskService.submitTest()` 调用 `TestTaskService.create()` |
| 待办生成 | 每次状态流转 | `FlowService` 在流转后自动创建对应角色待办 |
| 待办关闭 | 单据状态变更 | 旧节点待办批量标记 CANCEL |

## 7. 关键业务逻辑设计

### 7.1 编号生成

统一编号服务 `CodeGenerator`，基于 Redis 原子递增：

```java
public String next(String prefix, String datePattern) {
    String date = LocalDate.now().format(DateTimeFormatter.ofPattern(datePattern));
    String key = "rm:seq:" + prefix + ":" + date;
    Long seq = redisTemplate.opsForValue().increment(key);
    redisTemplate.expire(key, 2, TimeUnit.DAYS);
    return prefix + "-" + date + "-" + String.format("%03d", seq);
}
// 示例：next("REQ", "yyyyMMdd") → "REQ-20260729-001"
//      next("DEV", "yyyyMMdd") → "DEV-20260729-001"（或按需求单内序号）
```

### 7.2 测试用例覆盖率统计

覆盖率定义：已关联用例的需求数 / 需求总数（按状态筛选，如"开发中"及以上）。

```sql
SELECT
    COUNT(DISTINCT r.id) AS total_req,
    COUNT(DISTINCT CASE WHEN c.id IS NOT NULL THEN r.id END) AS covered_req,
    ROUND(COUNT(DISTINCT CASE WHEN c.id IS NOT NULL THEN r.id END)::numeric
          / NULLIF(COUNT(DISTINCT r.id), 0) * 100, 2) AS coverage_rate
FROM rm_requirement r
LEFT JOIN rm_test_case c ON c.requirement_id = r.id AND c.del_flag = '0'
WHERE r.del_flag = '0'
  AND r.status IN ('DEVELOPING','TESTING','PENDING_ACCEPTANCE','COMPLETED','RELEASED')
  AND r.tenant_id = #{tenantId}
```

### 7.3 当日 bug 提醒（bug 不隔人天）

Quartz 定时任务 `BugDailyReminderJob`，每日定时扫描：

```sql
SELECT * FROM rm_bug
WHERE status IN ('NEW','IN_PROGRESS')
  AND create_date = CURRENT_DATE
  AND assignee_id IS NOT NULL
```

为每个处理人生成 `rm_notify`（类型 `BUG_DAILY`），前端待办中心高亮展示当日未处理 bug。

### 7.4 超期预警

Quartz 定时任务 `OverdueWarningJob`：

- 扫描 `rm_requirement`：`expect_complete_date < CURRENT_DATE AND status NOT IN ('COMPLETED','RELEASED')` → 生成超期通知。
- 扫描 `rm_dev_task`：`plan_end_date < CURRENT_DATE AND status NOT IN ('已完成')` → 通知开发经理。
- 扫描 `rm_todo`：`due_time < NOW() AND status = 'PENDING'` → 标记超期，前端标红。

### 7.5 上线验证逻辑

验证清单 `checklist` 以 JSON 存储，包含：

```json
{
  "items": [
    {"key": "data_normal", "label": "数据持续正常（升级前后半小时）", "result": "PASS"},
    {"key": "function_normal", "label": "功能持续正常", "result": "PASS"}
  ],
  "halfHourVerified": true
}
```

验证通过条件：所有 item result = PASS 且 `verify_end_time - verify_start_time >= 30min`。

### 7.6 上线失败回滚

`rm_online_execution.result = FAIL` 时：

1. 自动创建回滚待办给操作人（`todo_type = ROLLBACK`）。
2. 回滚完成后记录 `is_rollback = '1'` + `rollback_remark`。
3. 上线申请单状态回退为"已回滚"，不进入验证流程。
4. 通知发版计划相关人员。

## 11. 内外网协同方案（三期专项）

### 11.1 场景

- 甲方现场（内网）部署一套，公司（外网）部署一套。
- 上线执行在甲方内网，但审批/排期/设计在公司外网。

### 11.2 方案设计

采用**定时数据同步 + 离线导入导出**双模式：

| 模式 | 适用场景 | 实现 |
| --- | --- | --- |
| 定时同步 | 内外网有受控网络通道 | Quartz 定时任务，通过接口增量同步单据数据（按 `update_time` 增量拉取），冲突以 `update_time` 最新为准 |
| 离线导入导出 | 内外网完全隔离 | 系统提供"导出数据包"（JSON 打包单据+附件元数据）和"导入数据包"功能，人工通过 U 盘等介质传输 |

**数据包格式**：

```json
{
  "packageId": "PKG-20260729-001",
  "exportTime": "2026-07-29T10:00:00",
  "source": "EXTERNAL",
  "bills": [
    {"billType": "REQUIREMENT", "billId": 123, "data": {...}, "attachments": ["url1","url2"]}
  ]
}
```

**冲突处理**：导入时按 `billType + billId` 匹配，存在则比对 `update_time`，最新覆盖；不存在则新增。

> 三期前完成专项方案评审，过渡期支持线下单据线上补录（PRD 风险对策）。

## 13. 开发规范约定

### 13.1 后端规范

- 包名：`com.pig4cloud.pig.rm`（biz）/ `com.pig4cloud.pig.rm.api`（api）
- Controller 路径前缀：`/rm/`
- 实体继承 `MybatisBaseEntity`（含审计字段），使用 `@TableName`/`@TableId`
- Service 继承 `ServiceImpl<Mapper, Entity>` + 自定义 `XxxService` 接口
- 事务：`@Transactional` 标注在 Service 方法，涉及状态流转的方法必须事务
- 异常：业务异常抛 `CheckedException`（pig 内置），全局异常处理器统一捕获
- 日志：关键操作 `@SysLog`，调试日志 `@Slf4j` + `log.debug`

### 13.2 前端规范

- 组件采用 `<script setup lang="ts">`
- API 函数命名：`fetchXxxList` / `getXxxObj` / `addXxx` / `putXxx` / `delXxx`
- 页面权限：`v-auth="'rm_xxx'"` 指令控制按钮/操作可见性
- 状态色标：草稿灰、待审批橙、进行中蓝、已完成绿、已驳回红、已发布紫（统一枚举映射）
- 表单校验：Element Plus `el-form` rules + 必填项红色星号

### 13.3 提交规范

沿用 AGENTS.md 约定：

```
feat(rm): 需求管理模块-需求申请单 CRUD 与审批流
fix(rm): 测试驳回未关联 bug 数量问题
docs(rm): 研发管理详细设计文档
```

每完成一个独立功能模块提交一次（细粒度提交）。
