## 一、评审结论

**通过（Pass），附修订建议。**

文档以"可行性高、代码改动极小、以配置+DDL 转换为主"为核心结论，经源码核验属实，不阻塞立项执行。工作量估算 2–3 人周（迁移）+ 4 人天（Flyway）合理偏保守，留有缓冲。

最关键的三个技术论断全部经核验成立：

1. **手写 SQL 零重写** —— 18 个 Mapper XML、8 个含手写 SQL，MySQL 专有函数扫描 0 命中（`IF/FIND_IN_SET/GROUP_CONCAT/DATE_FORMAT/IFNULL/NOW()/SUBSTRING_INDEX/${}` 均无）。✅
2. **主键应用层雪花** —— `AUTO_INCREMENT` 在 `db/pig.sql` 仅 1 处（`gen_field_type`），业务实体普遍 `IdType.ASSIGN_ID`。✅
3. **审计字段应用层兜底** —— `MybatisPlusMetaObjectHandler.updateFill` 实现了 `updateTime` 兜底；`ON UPDATE CURRENT_TIMESTAMP` 共 11 处可安全移除。✅

这三条是整个迁移"低风险"判断的基石，基石稳固。

## 三、问题清单（按严重度）

### 🟠 应修订（Should-fix）—— 2 项

#### S1. 文件路径笔误（02 文档第 13 节索引）

`02-迁移详细设计.md` 第 463 行：

```
| Quartz 配置 | `pig-visual/pig-codegen/src/main/resources/quartz-config.yml` |
```

**实际路径**：`pig-visual/pig-quartz/src/main/resources/quartz-config.yml`（`pig-quartz` 不是 `pig-codegen`）。

文档自身 4.4 节写对了（`pig-visual/pig-quartz/...`），仅 13 节索引笔误。影响：迁移时按错路径找配置文件会扑空。

**修订**：将索引行改为 `pig-visual/pig-quartz/src/main/resources/quartz-config.yml`。

#### S2. updateTime 的 @TableField 注解表述与实际不符（03 文档第 89 行）

`03-DDL转换映射参考.md` 第 89 行：

> 迁移后需验证实体 updateTime 字段标注了 `@TableField(fill = FieldFill.INSERT_UPDATE)`

**实际**：`SysUser.java` 的 `updateTime`（L99 附近）标注的是 `@TableField(fill = FieldFill.UPDATE)`，**不是 `INSERT_UPDATE`**。

为何结论仍成立：`MybatisPlusMetaObjectHandler.insertFill`（L26-37）对 `updateTime` 做了 `fillValIfNull` 兜底（insert 时若为空则填当前时间），所以 INSERT 场景由 handler 兜底而非注解驱动；UPDATE 场景由 `FieldFill.UPDATE` 注解 + `updateFill` 双保险。**结论（应用层兜底 update_time）正确，但"需验证 INSERT_UPDATE 注解"的表述会误导开发者去改注解。**

**修订**：改为"验证实体 updateTime 字段标注了 `@TableField(fill = FieldFill.UPDATE)`，且 insert 场景由 `MybatisPlusMetaObjectHandler.insertFill` 兜底（已实现）"。避免有人误改成 `INSERT_UPDATE` 引入非预期行为。

### 🟡 建议补强（Nice-to-have）—— 6 项

#### N1. 基线脚本与 pgloader 的执行顺序需二选一并固化

04 文档第 5 节给了"空库+全量基线"和"存量库 baseline"两条路径，并在 5.2 末尾推荐"空库 + pgloader `WITH data only`"。但 02 文档 7.1 又写 pgloader `WITH include drop, create tables, create indexes`（即 pgloader 自己建结构）。**两处口径冲突**：

- 02-7.1：pgloader 建结构 + 迁数据（`create tables`）
- 04-5.2：Flyway 建结构 + pgloader 只迁数据（`data only`）

若 Flyway 已接管结构，pgloader 再 `create tables` 会与 Flyway 基线脚本冲突（要么表已存在报错，要么 pgloader 建的表结构与 Flyway 不一致）。

**建议**：统一为"Flyway 建结构（基线脚本）→ pgloader `WITH data only` 迁数据 → 校验行数"。在 02-7.1 与 04-5.2 互相引用说明这一点，删去 pgloader `create tables` 选项，或明确标注"仅在不采用 Flyway 时用 pgloader 建结构"。

#### N2. `gen_field_type` 的 bigserial + setval 方案需注意雪花残留值

03 文档第 136 行 `SELECT setval('gen_field_type_id_seq', 1634915190321451010, true)`。该值是历史 AUTO_INCREMENT 残留（接近雪花量级，远超 int 范围但 bigint 可容）。setval 到这个值后，后续 `bigserial` 自增会从该值+1 起，**继续在雪花量级区间分配 id**。

风险：若未来 `gen_field_type` 由应用层（非 DB 自增）插入，id 可能与 DB 自增序列冲突。pig 当前对该表是 DB 自增还是应用赋值，需确认。文档默认"维护者手工/脚本插入"，但未核实 `GenFieldType` 实体的 `@TableId` 类型。

**建议**：迁移前核实 `GenFieldType` 实体主键策略；若是 `ASSIGN_ID` 则 PG 侧用 `bigint`（无序列）即可，无需 `bigserial`/`setval`，与 48 张业务表一致。若是 `AUTO`（DB 自增）才需 `bigserial`。这一核实应在 P1 前完成。

#### N3. Nacos PG 支持成熟度是最大外部风险，应有 PoC 验收门禁

01 文档将 Nacos PG 列为"中"风险，04 文档 9 节也提到。但 Nacos 官方对 PG 的支持历史上是社区插件（`nacos-datasource-pg`），不同 Nacos 版本成熟度差异大。文档说"确认 Nacos 版本的 PG 支持成熟度"，但未给验收标准。

**建议**：在 P2（外部组件适配）增加 Nacos PG PoC 子任务，验收门禁：①Nacos 以 PG 启动无报错；②8 条种子配置导入成功；③配置下发与 `@RefreshScope` 动态刷新正常；④历史配置版本（his_config_info）可查。任一不通过则触发"回退 MySQL Nacos"决策点（02-11 回滚方案已有，衔接此门禁）。

#### N4. Druid wall 过滤器对 PG DDL 的拦截需在 Flyway 基线前验证

04 文档 9 节风险表提到 wall 可能拦 `CREATE FUNCTION`/`CREATE TRIGGER`。03 文档 3.1 的触发器备选方案也含 `CREATE FUNCTION`。若基线脚本（V20260706.01/02/03）中任何 DDL 被 wall 拦，应用启动即失败。

**建议**：①在 P5 联调首日先用一条含 `CREATE FUNCTION`/`COMMENT ON`/`CREATE INDEX` 的探针脚本过 Druid 验证 wall 行为；②若被拦，按 04-8.2 为 Flyway 配独立无 wall 的 DataSource（给出具体 `@FlywayDataSource` 配置示例），或在 wall config 显式放行 DDL 类型。

#### N5. 隐式逗号连接（ANSI-89）虽兼容，建议借迁移机会改 JOIN

02 文档 3.1 提到 6 处隐式连接（`FROM a,b WHERE a.id=b.aid`）PG 可执行，建议改 `JOIN ON`。评审赞同：ANSI-89 在 PG 下虽能跑，但①易因遗漏连接条件产生笛卡尔积；②执行计划不如显式 JOIN 清晰；③与代码生成器产出的新代码风格不一致。迁移是统一代码风格的低风险窗口。

**建议**：作为 P5 的可选子项，把这 6 处改写为 `JOIN ... ON`，纳入回归。非阻塞，但收益大于成本。

#### N6. 时间戳命名约定的"规划日"定义需防歧义

04 文档 3.1/12 节定义 `{yyyyMMdd}` 为"规划日，非提交日"。但实际开发中"规划日"模糊——是需求评审日？PR 起草日？为避免同日多人冲突靠 `.seq`，但跨日时若有人用提交日有人用规划日，会出现 `V20260720.01` 早于 `V20260719.01` 的乱序（虽 out-of-order=false 会报错暴露，但仍需人工改号）。

**建议**：明确"规划日 = PR 起草日（本地分支创建迁移脚本当日）"，并在 CI 预检加一条规则：脚本日期不得早于该分支 base 之后已合入的最新脚本日期，否则 fail。把"靠 .seq 兜底"升级为"CI 兜底"。
