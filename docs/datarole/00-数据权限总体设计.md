## 1. 现状分析

### 1.1 当前权限模型

youming 基于 pig 框架，当前**仅具备功能权限（菜单/按钮级）**，不具备行级数据权限：

```
用户 ──┬── sys_user_role ── 角色 ── sys_role_menu ── 菜单(permission 字符串)
       │                                        └── 菜单/按钮功能权限
       └── sys_user_dept ── 部门（parent_id 自引用树）
            └── sys_user.dept_id（主部门，冗余字段）
```

- **功能权限**：Controller 方法标注 `@HasPermission("sys_role_add")`，由 `PermissionService.hasPermission()` 校验当前用户的 authorities（来自 `sys_menu.permission` 字符串）。
- **行级数据权限**：**完全不存在**。所有用户只要拥有功能权限，就能查询到全表数据。例如拥有 `sys_role_view` 的普通用户可以分页看到全部角色，拥有 `sys_user_view` 的用户可以看到所有部门的用户。

### 1.2 已有的可复用基础设施

| 基础设施 | 位置 | 复用方式 |
|----------|------|----------|
| `UserContext` SPI | `pig-common-core/.../context/UserContext.java` | 扩展接口，增加 `getDeptIds()` 等方法 |
| `UserContextHolder` | `pig-common-core/.../context/UserContextHolder.java` | 数据权限拦截器注入此接口获取当前用户，**不反向依赖 security** |
| `PigUser` | `pig-common-security/.../service/PigUser.java` | 已携带 `deptId`、`deptIds`、`roleIds`，无需改造 |
| `MybatisPlusConfiguration` | `pig-common-data/.../mybatis/MybatisPlusConfiguration.java` | 在 `mybatisPlusInterceptor()` Bean 中追加 `DataScopeInnerInterceptor` |
| `SysDeptServiceImpl.listDescendant()` | `pig-upms-biz/.../impl/SysDeptServiceImpl.java` | 递归 `parent_id` 获取子部门，可复用于"本部门及以下" |
| 部门树 `parent_id` 自引用 | `sys_dept` 表 | PostgreSQL 递归 CTE 替代内存递归，提升性能 |
| Flyway 迁移机制 | `pig-common-data/.../db/migration/` | 新增 `V23__data_scope.sql` |

### 1.3 核心痛点

1. **无行级隔离**：任何有查询权限的用户可看全表数据。
2. **无按部门过滤能力**：部门字段存在但从未用于查询过滤。
3. **无角色级数据范围配置**：`sys_role` 表无 `data_scope` 字段，无法按角色配置可见数据范围。
4. **部门子树查询低效**：`listDescendant()` 全表加载到内存递归，部门量大时有性能风险。

## 2. 设计目标

### 2.1 功能目标

支持 **5 种数据范围（Data Scope）**，以角色为单位配置，用户多角色取**最宽范围**：

| 编码 | 名称 | 含义 |
|------|------|------|
| `1` | 全部数据 | 不附加任何过滤条件 |
| `2` | 自定义数据 | 仅可见指定部门集合的数据（通过 `sys_role_dept` 关联表配置） |
| `3` | 本部门数据 | 仅可见用户主部门（`sys_user.dept_id`）下的数据 |
| `4` | 本部门及以下 | 可见用户主部门及其所有子部门（递归）的数据 |
| `5` | 仅本人 | 仅可见当前用户创建（`create_by = username`）的数据 |

> **多角色规则**：用户拥有多个角色时，取各角色数据范围的**并集**（最宽范围）。例如角色A=本部门、角色B=自定义[部门X]，最终用户可见 = 本部门 ∪ 部门X。若任一角色为"全部数据"，则最终为"全部数据"。

### 2.2 非功能目标

| 维度 | 目标 |
|------|------|
| **性能** | 数据权限过滤通过 SQL 条件注入实现，不加载全表到内存；部门子树查询使用 PG 递归 CTE + 缓存 |
| **侵入性** | 对现有业务代码零侵入——通过 MyBatis 拦截器 + 注解声明式接入，不需要手写过滤条件 |
| **可配置性** | 角色数据范围通过管理后台 UI 配置，无需改代码 |
| **可跳过** | 提供 `@DataScope(disabled = true)` 或编程式 `DataScopeContext.disable()` 跳过过滤（管理员/内部任务场景） |
| **安全性** | SQL 注入防护——部门 ID 列表参数化绑定，不拼接字符串；拦截器仅对标注了 `@DataScope` 的查询生效 |
| **兼容性** | 现有无注解的查询完全不受影响；单体版 `pig-boot` 和微服务版均可用 |

### 2.3 不在本次范围内

- 多租户隔离（Tenant）——pig 开源版已声明不含，后续单独立项
- 列级数据权限（字段脱敏/隐藏）——后续单独立项
- 数据权限的导入/导出——后续迭代

### 3.2 核心数据流

以"查询用户列表"为例，展示数据权限的完整执行链路：

```
1. HTTP 请求: GET /admin/user/page?username=xxx
   │
2. Controller: SysUserController.getPage(page, sysUser)
   │  方法或 Mapper 接口标注 @DataScope(deptAlias = "ud", userAlias = "u")
   │
3. MyBatis 执行查询，触发拦截器链:
   │  PaginationInnerInterceptor → DataScopeInnerInterceptor → OptimisticLocker
   │
4. DataScopeInnerInterceptor.beforeQuery():
   │  a. 检查当前 MappedStatement 是否标注了 @DataScope
   │  b. 检查 DataScopeContext 是否被 disabled（跳过）
   │  c. 通过 UserContextHolder.get() 获取当前用户上下文
   │  d. 调用 DataScopeProcessor 解析当前用户的数据范围:
   │     - 从缓存/DB 读取用户各角色的 data_scope 配置
   │     - 多角色取最宽范围，计算出最终的 (scopeType, deptIds) 
   │  e. 根据 scopeType 构建 SQL 条件片段:
   │     - scope=1(全部): 不追加条件
   │     - scope=2(自定义): AND ud.dept_id IN (:deptIds)
   │     - scope=3(本部门): AND ud.dept_id = :userDeptId
   │     - scope=4(本部门及以下): AND ud.dept_id IN (递归CTE子树)
   │     - scope=5(本人): AND u.create_by = :username
   │  f. 使用 JSqlParser 解析原 SQL，将条件注入到 WHERE 子句
   │
5. 改写后的 SQL 发送到 PostgreSQL 执行:
   SELECT u.* FROM sys_user u
   LEFT JOIN sys_user_dept ud ON u.user_id = ud.user_id
   WHERE u.del_flag = '0'
     AND ud.dept_id IN (1, 2, 3, 5)   -- ← 数据权限注入的条件
   ORDER BY u.create_time DESC
   │
6. 返回过滤后的结果集
```

### 3.3 技术选型

| 决策点 | 选型 | 理由 |
|--------|------|------|
| SQL 改写方式 | MyBatis-Plus `InnerInterceptor` + JSqlParser | 与现有 `MybatisPlusConfiguration` 一致；MP 原生支持，无需额外框架 |
| 注解声明 | 自定义 `@DataScope` 注解 | 声明式、可标注在 Mapper 方法或 Service 类上，零代码侵入 |
| 用户上下文获取 | `UserContextHolder` SPI（已有） | 避免 `pig-common-data` 反向依赖 `pig-common-security` |
| 部门子树查询 | PostgreSQL 递归 CTE（`WITH RECURSIVE`）+ Redis 缓存 | 避免全表内存递归；CTE 走索引，缓存降低 DB 压力 |
| 角色数据范围缓存 | Spring Cache + Redis（`@Cacheable`） | 角色数据范围变更频率低，适合缓存；已有 Redis 基础设施 |
| 多角色取最宽 | 内存计算（取并集） | 角色数量有限（通常 < 10），内存计算无性能问题 |

### 5.2 `@DataScope` 注解

```java
@Target({ElementType.METHOD, ElementType.TYPE})
@Retention(RetentionPolicy.RUNTIME)
@Documented
public @interface DataScope {
    /** 部门表的别名，例如 "ud" 或 "d" */
    String deptAlias() default "d";
    /** 用户表的别名，例如 "u" */
    String userAlias() default "u";
    /** 部门字段名，默认 dept_id */
    String deptField() default "dept_id";
    /** 是否禁用数据权限（管理员场景） */
    boolean disabled() default false;
}
```

### 5.3 拦截器注册

在 `MybatisPlusConfiguration.mybatisPlusInterceptor()` 中追加：

```java
// 数据权限拦截器（须在分页拦截器之后、乐观锁之前）
DataScopeInnerInterceptor dataScopeInterceptor = new DataScopeInnerInterceptor(dataScopeProcessor);
interceptor.addInnerInterceptor(dataScopeInterceptor);
```

### 5.4 多角色取最宽范围规则

```
用户角色集合 = [角色A(scope=3,本部门), 角色B(scope=2,自定义[1,2]), 角色C(scope=5,本人)]

解析过程:
  1. 若任一角色 scope=1(全部) → 最终 scope=1，直接返回（短路）
  2. 收集所有 scope=2 的自定义部门 ID → customDeptIds
  3. 收集所有 scope=3/4 的标记 → needDept / needDeptAndChild
  4. 收集所有 scope=5 的标记 → needSelf
  5. 合并:
     - finalDeptIds = customDeptIds
     - if needDept → finalDeptIds += userDeptId
     - if needDeptAndChild → finalDeptIds += 递归子树(userDeptId)
     - if finalDeptIds 非空 → 最终: dept_id IN (finalDeptIds) [AND/OR self condition]
     - if needSelf → 追加 OR create_by = username
  6. 若 finalDeptIds 为空且 needSelf → 仅本人
  7. 若 finalDeptIds 为空且 !needSelf → 无数据（返回 1=0）
```

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 拦截器误拦截无注解查询 | 全局查询异常 | 拦截器仅对标注 `@DataScope` 的 Mapper 方法/类生效；无注解直接放行 |
| JSqlParser 对复杂 SQL 解析失败 | 查询报错 | 限制 `@DataScope` 仅用于标准 SELECT；提供降级开关 |
| 部门闭包表维护不一致 | 子树查询遗漏 | 闭包表由触发器或 Service 层事务维护；定期校验脚本 |
| 内部 Feign 调用无用户上下文 | 拦截器 NPE | `UserContextHolder.get()` 返回 null 时直接放行（视为系统调用） |
| 性能退化（IN 列表过大） | 慢查询 | 自定义部门数上限校验；子树查询走缓存；监控 IN 列表长度 |
| 存量角色行为变更 | 现有角色突然看不到数据 | `data_scope` 默认值 `'1'`（全部数据），存量角色行为不变 |

## 9. 术语表

| 术语 | 英文 | 说明 |
|------|------|------|
| 数据权限 | Data Scope / Data Permission | 行级数据可见性控制，基于部门/用户维度 |
| 功能权限 | Functional Permission | 菜单/按钮级操作权限，控制"能否做" |
| 数据范围 | Data Scope Type | 数据权限的级别：全部/自定义/本部门/本部门及以下/本人 |
| 闭包表 | Closure Table | 预存储树形结构所有祖先-后代关系的表，用于高性能子树查询 |
| 递归 CTE | Recursive CTE | PostgreSQL `WITH RECURSIVE` 语法，用于递归查询树形结构 |
