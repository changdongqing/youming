## 1. UserContext SPI 扩展

### 1.1 现状

当前 `UserContext` 接口（`pig-common-core`）仅暴露 3 个方法：

```java
public interface UserContext {
    String getUsername();
    Long getDeptId();
    List<Long> getRoleIds();
}
```

数据权限引擎需要额外获取：
- `getUserId()` — 用于"仅本人"场景的 `create_by` 关联（当 create_by 存的是 userId 时）
- `getDeptIds()` — 用户关联的全部部门（多部门场景，`sys_user_dept`）

### 1.2 扩展后的接口

```java
// pig-common-core/.../context/UserContext.java

public interface UserContext {

    /**
     * 用户名（用于 create_by = username 条件）。
     */
    String getUsername();

    /**
     * 用户 ID。
     */
    Long getUserId();

    /**
     * 主部门 ID（sys_user.dept_id）。
     */
    Long getDeptId();

    /**
     * 用户关联的全部部门 ID 列表（sys_user_dept，含主部门）。
     * <p>用于多部门用户的数据权限过滤。
     */
    List<Long> getDeptIds();

    /**
     * 角色 ID 列表。
     */
    List<Long> getRoleIds();
}
```

**向后兼容性**：新增 `getUserId()` 和 `getDeptIds()` 方法。由于 `UserContext` 是接口，新增方法会导致编译错误。提供 **default 实现** 保证不破坏现有实现：

```java
public interface UserContext {

    String getUsername();

    Long getDeptId();

    List<Long> getRoleIds();

    // === 新增方法（default 保证向后兼容）===

    /**
     * 用户 ID，默认返回 null（旧实现不提供）。
     */
    default Long getUserId() {
        return null;
    }

    /**
     * 全部部门 ID 列表，默认返回仅含主部门的列表（旧实现降级）。
     */
    default List<Long> getDeptIds() {
        Long deptId = getDeptId();
        return deptId != null ? List.of(deptId) : Collections.emptyList();
    }
}
```

> **设计决策**：使用 `default` 方法而非直接新增抽象方法。这样：
> 1. 现有的 `PigUserContextAdapter` 不会编译报错（但需要覆写新方法以提供真实数据）。
> 2. 第三方扩展（如果有）不会被迫立即实现新方法。
> 3. 数据权限引擎调用 `getUserId()` / `getDeptIds()` 时，旧实现降级返回 null / 单部门，功能受限但不报错。

## 2. PigUserContextAdapter 适配层改造

### 2.1 现状

```java
public class PigUserContextAdapter implements UserContext {
    private final PigUser delegate;

    @Override public String getUsername() { return delegate.getUsername(); }
    @Override public Long getDeptId() { return delegate.getDeptId(); }
    @Override public List<Long> getRoleIds() { /* 从 authorities 解析 */ }
}
```

### 2.2 改造后

```java
// pig-common-security/.../context/PigUserContextAdapter.java

public class PigUserContextAdapter implements UserContext {

    private final PigUser delegate;

    public PigUserContextAdapter(PigUser delegate) {
        this.delegate = delegate;
    }

    @Override
    public String getUsername() {
        return delegate.getUsername();
    }

    @Override
    public Long getUserId() {
        return delegate.getId();
    }

    @Override
    public Long getDeptId() {
        return delegate.getDeptId();
    }

    @Override
    public List<Long> getDeptIds() {
        // PigUser 已携带 deptIds（全部部门，含主部门）
        List<Long> deptIds = delegate.getDeptIds();
        return deptIds != null ? deptIds : Collections.emptyList();
    }

    @Override
    public List<Long> getRoleIds() {
        // 优化：直接从 PigUser.getRoleIds() 获取，不再从 authorities 解析
        List<Long> roleIds = delegate.getRoleIds();
        if (roleIds != null && !roleIds.isEmpty()) {
            return roleIds;
        }
        // 降级：从 authorities 解析（兼容旧逻辑）
        return delegate.getAuthorities()
                .stream()
                .map(GrantedAuthority::getAuthority)
                .filter(authority -> StrUtil.startWith(authority, SecurityConstants.ROLE))
                .map(authority -> Long.parseLong(
                        StrUtil.removePrefix(authority, SecurityConstants.ROLE)))
                .toList();
    }
}
```

**优化点**：
- `getRoleIds()` 优先使用 `PigUser.getRoleIds()`（已由 `PigUserDetailsService.convertUserDetails()` 填充），避免重复解析 authorities。
- `getDeptIds()` 直接使用 `PigUser.getDeptIds()`（已由 `convertUserDetails` 从 `UserInfo.getDeptList()` 填充）。
- `getUserId()` 暴露 `PigUser.getId()`。

### 2.3 数据填充链路验证

```
登录流程:
  1. PigUserDetailsService.convertUserDetails(UserInfo info)
  2.   → new PigUser(
           info.getUserId(),                          // ← id
           info.getUsername(),
           info.getRoleList().stream()
               .map(SysRole::getRoleId).toList(),     // ← roleIds
           info.getDeptId(),                          // ← deptId (主部门)
           info.getDeptList().stream()
               .map(SysDept::getDeptId).toList(),     // ← deptIds (全部部门)
           info.getPostList()...,
           ...
       )
  3. SecurityContextHolder 设置 PigUser 为 principal
  4. DataScopeProcessor → UserContextHolder.get() → PigUserContextAdapter(PigUser)
     → getUserId() / getDeptId() / getDeptIds() / getRoleIds() 全部可用 ✅
```

**结论**：`PigUser` 已携带数据权限所需的全部字段（id, roleIds, deptId, deptIds），**无需改造登录链路**，仅需扩展 `UserContext` 接口和适配器。

### 3.3 SysRoleDataScopeHandler 实现

```java
package com.pig4cloud.pig.admin.service.impl;

import cn.hutool.core.collection.CollUtil;
import com.baomidou.mybatisplus.core.toolkit.Wrappers;
import com.pig4cloud.pig.admin.api.entity.SysRole;
import com.pig4cloud.pig.admin.api.entity.SysRoleDept;
import com.pig4cloud.pig.admin.mapper.SysDeptMapper;
import com.pig4cloud.pig.admin.mapper.SysRoleDeptMapper;
import com.pig4cloud.pig.admin.mapper.SysRoleMapper;
import com.pig4cloud.pig.common.data.datascope.handler.DataScopeHandler;
import com.pig4cloud.pig.common.data.datascope.model.DataScopeType;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.cache.annotation.Cacheable;

import java.util.*;
import java.util.stream.Collectors;

/**
 * 数据范围解析 SPI 实现。
 *
 * <p>由 pig-upms-biz 提供，封装角色数据范围查询和部门子树查询。
 * 结果带 Spring Cache 缓存，减少 DB 访问。
 *
 * @author youming
 */
@Slf4j
@RequiredArgsConstructor
public class SysRoleDataScopeHandler implements DataScopeHandler {

    private final SysRoleMapper roleMapper;
    private final SysRoleDeptMapper roleDeptMapper;
    private final SysDeptMapper deptMapper;

    /**
     * 查询指定角色集合的数据范围类型。
     *
     * <p>缓存 key 使用 roleIds 的 hashCode，变更时通过 @CacheEvict 清除。
     */
    @Override
    @Cacheable(value = CacheConstants.DATA_SCOPE_ROLE, key = "T(java.util.Objects).hash(#roleIds)")
    public List<DataScopeType> getDataScopeTypes(List<Long> roleIds) {
        if (CollUtil.isEmpty(roleIds)) {
            return Collections.emptyList();
        }

        List<SysRole> roles = roleMapper.selectBatchIds(roleIds);

        // 按入参顺序返回，缺失的角色默认 ALL（安全降级）
        Map<Long, DataScopeType> scopeMap = roles.stream()
                .collect(Collectors.toMap(
                        SysRole::getRoleId,
                        r -> DataScopeType.of(r.getDataScope()),
                        (a, b) -> a));

        return roleIds.stream()
                .map(id -> scopeMap.getOrDefault(id, DataScopeType.ALL))
                .toList();
    }

    /**
     * 查询角色自定义数据范围关联的部门 ID 集合。
     */
    @Override
    @Cacheable(value = CacheConstants.DATA_SCOPE_CUSTOM_DEPT, key = "T(java.util.Objects).hash(#roleIds)")
    public Set<Long> getCustomDeptIds(List<Long> roleIds) {
        if (CollUtil.isEmpty(roleIds)) {
            return Collections.emptySet();
        }

        List<SysRoleDept> list = roleDeptMapper.selectList(
                Wrappers.<SysRoleDept>lambdaQuery()
                        .in(SysRoleDept::getRoleId, roleIds));

        return list.stream()
                .map(SysRoleDept::getDeptId)
                .collect(Collectors.toSet());
    }

    /**
     * 查询指定部门的全部子部门 ID（含自身）。
     * <p>使用 PostgreSQL 递归 CTE，结果带缓存。
     */
    @Override
    @Cacheable(value = CacheConstants.DATA_SCOPE_DEPT_TREE, key = "#deptId")
    public Set<Long> getDeptAndChildren(Long deptId) {
        if (deptId == null) {
            return Collections.emptySet();
        }
        Set<Long> result = new HashSet<>(deptMapper.selectDeptAndChildren(deptId));
        return result;
    }
}
```

## 4. 多角色取最宽范围规则详解

### 4.1 规则定义

用户可能拥有多个角色，每个角色配置不同的数据范围。**多角色取并集（最宽范围）**，而非交集。

| 规则 | 说明 |
|------|------|
| **短路规则** | 若任一角色为 ALL(1)，最终为 ALL，不附加任何条件 |
| **部门合并** | 所有 CUSTOM 角色的自定义部门 ∪ 所有 DEPT 角色的主部门 ∪ 所有 DEPT_AND_CHILD 角色的主部门子树 |
| **本人合并** | 若任一角色为 SELF(5)，最终需要追加 `create_by = username` 条件 |
| **部门 ∪ 本人** | 部门条件与本人条件之间用 `OR` 连接（取并集） |

### 4.2 场景示例

**场景 1**：用户拥有 [角色A(本部门), 角色B(自定义[部门10,部门20])]

```
解析:
  - 角色A: DEPT(3) → visibleDeptIds += userDeptId (假设=1)
  - 角色B: CUSTOM(2) → visibleDeptIds += {10, 20}
  - 无 SELF 角色 → selfOnly = false
  - 无 ALL 角色 → 不短路

最终 SQL 条件: AND ud.dept_id IN (1, 10, 20)
```

**场景 2**：用户拥有 [角色A(本部门及以下), 角色B(仅本人)]

```
解析:
  - 角色A: DEPT_AND_CHILD(4) → visibleDeptIds += 子树(1) = {1, 2, 3, 4}
  - 角色B: SELF(5) → selfOnly = true
  - 无 ALL 角色 → 不短路

最终 SQL 条件: AND (ud.dept_id IN (1, 2, 3, 4) OR u.create_by = 'zhangsan')
```

**场景 3**：用户拥有 [角色A(全部数据)]

```
解析:
  - 角色A: ALL(1) → 短路，直接返回 skip=true

最终 SQL 条件: 无（不附加任何条件）
```

**场景 4**：用户拥有 [角色A(仅本人)]，且 SQL 无部门 JOIN

```
解析:
  - 角色A: SELF(5) → selfOnly = true
  - visibleDeptIds 为空

最终 SQL 条件: AND u.create_by = 'zhangsan'
```

**场景 5**：用户拥有 [角色A(自定义[])] — 自定义但未选任何部门

```
解析:
  - 角色A: CUSTOM(2) → customDeptIds = {} (空)
  - visibleDeptIds = {} (空)
  - selfOnly = false

最终 SQL 条件: AND 1=0 (无可见数据)
```

### 4.3 算法伪代码

```
function resolve(userContext, roleIds):
    if roleIds is empty:
        return DENY_ALL  // 1=0

    scopeTypes = handler.getDataScopeTypes(roleIds)

    // 短路：任一角色为 ALL
    if ANY(scopeTypes == ALL):
        return SKIP  // 不附加条件

    visibleDeptIds = empty set
    selfOnly = false

    // 收集 CUSTOM 部门
    customDeptIds = handler.getCustomDeptIds(roleIds)
    visibleDeptIds.addAll(customDeptIds)

    // 收集 DEPT / DEPT_AND_CHILD
    userDeptId = userContext.getDeptId()
    if ANY(scopeTypes == DEPT_AND_CHILD) AND userDeptId != null:
        visibleDeptIds.addAll(handler.getDeptAndChildren(userDeptId))
    else if ANY(scopeTypes == DEPT) AND userDeptId != null:
        visibleDeptIds.add(userDeptId)

    // 收集 SELF
    if ANY(scopeTypes == SELF):
        selfOnly = true

    return DataScopeRule(visibleDeptIds, selfOnly, username)
```

### 4.4 边界情况处理

| 边界情况 | 处理 | 理由 |
|----------|------|------|
| 用户无角色 | 返回 `1=0`（不可见任何数据） | 安全降级 |
| 用户主部门为 null | DEPT/DEPT_AND_CHILD 跳过 | 不追加部门条件，仅靠其他范围 |
| 自定义部门列表为空 | visibleDeptIds 不追加 | 仅靠其他范围或返回空集 |
| 所有范围都为 SELF | `AND create_by = username` | 仅本人 |
| 角色 data_scope 为非法值 | `DataScopeType.of()` 降级为 ALL | 安全降级（避免误拒） |

## 5. 管理员/超管特殊处理

### 5.1 方案 A：角色配置（推荐）

管理员角色（如 `ROLE_ADMIN`）的 `data_scope` 配置为 `1`（全部数据）。由于短路规则，管理员用户自动跳过过滤。**无需额外代码**。

### 5.2 方案 B：role_code 白名单（可选增强）

```java
// DataScopeProcessor 中增加白名单判断

private static final Set<String> ADMIN_ROLE_CODES = Set.of("ROLE_ADMIN", "ROLE_SUPERADMIN");

public DataScopeRule resolve() {
    // ... 获取用户上下文 ...

    // 管理员白名单检查
    List<String> roleCodes = getRoleCodes(userContext.getRoleIds());
    if (roleCodes.stream().anyMatch(ADMIN_ROLE_CODES::contains)) {
        return DataScopeRule.builder().skip(true).build();
    }

    // ... 正常解析 ...
}
```

> **推荐方案 A**：通过角色配置而非硬编码白名单。方案 B 作为可选增强，适合需要"无论角色怎么配，管理员始终看全部"的刚性需求场景。

### 5.3 方案 C：userType 判断

`PigUser` 已有 `userType` 字段（`UserTypeEnum.TOB`）。如果未来引入 `SUPER_ADMIN` 类型，可在 `DataScopeProcessor` 中判断：

```java
if (UserTypeEnum.SUPER_ADMIN.getStatus().equals(userContext.getUserType())) {
    return DataScopeRule.builder().skip(true).build();
}
```

## 6. 性能分析

### 6.1 单次查询开销

| 步骤 | 操作 | 开销 | 缓存命中后 |
|------|------|------|-----------|
| 获取用户上下文 | `UserContextHolder.get()` | ~0ms（ThreadLocal） | — |
| 查询角色 data_scope | `SELECT data_scope FROM sys_role WHERE role_id IN (...)` | ~2ms | ~0ms |
| 查询自定义部门 | `SELECT dept_id FROM sys_role_dept WHERE role_id IN (...)` | ~2ms | ~0ms |
| 递归 CTE 查子树 | `WITH RECURSIVE ...` | ~5ms（100 部门） | ~0ms |
| JSqlParser 改写 SQL | 内存解析 + 注入 | ~1ms | ~1ms |
| **合计** | | **~10ms** | **~1ms** |

### 6.2 缓存命中率优化

- 角色数据范围缓存 key = `roleIds.hashCode()`：同一用户的每次查询命中同一缓存。
- 部门子树缓存 key = `deptId`：同部门用户共享缓存。
- 缓存 TTL 10~30 分钟，角色/部门变更时主动清除。

**预期命中率**：> 95%（角色和部门变更极低频）。

### 6.3 SQL 注入条件对查询计划的影响

数据权限注入的 `AND dept_id IN (...)` 条件：
- 走 `sys_user_dept.dept_id` 索引（已有 PK 索引 `(user_id, dept_id)`，需确认是否有 `(dept_id)` 单列索引）
- IN 列表长度通常 < 50（部门数量），PG 优化器能高效处理

**建议索引**：

```sql
-- sys_user_dept 已有 PK(user_id, dept_id)，但按 dept_id 查需要反向索引
CREATE INDEX IF NOT EXISTS idx_user_dept_dept_id ON sys_user_dept (dept_id);
```

## 7. 数据一致性保障

### 7.1 缓存与 DB 一致性

| 操作 | 缓存失效策略 | 一致性窗口 |
|------|-------------|-----------|
| 修改角色数据范围 | `@CacheEvict(allEntries=true)` 清除 `data_scope:role` 和 `data_scope:custom_dept` | ~0s（同步清除） |
| 新增/删除/移动部门 | `@CacheEvict(allEntries=true)` 清除 `data_scope:dept_tree` | ~0s（同步清除） |
| 用户登录 | 角色范围从缓存读取 | 缓存 miss 时查 DB |
| 用户角色变更 | 清除该用户相关缓存 | 重新登录后生效 |

### 7.2 分布式缓存一致性

微服务版多实例共享 Redis 缓存，`@CacheEvict` 通过 Redis pub/sub 广播失效，一致性有保障。

单体版 `pig-boot` 单实例，无此问题。
