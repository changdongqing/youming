> 数据权限扩展的 DDL 变更、Flyway 迁移脚本、索引设计、ER 关系

| 类型 | 对象 | 变更 |

| ALTER TABLE | `sys_role` | 新增 `data_scope` 列 |

## 2. DDL 详细设计

### 2.1 sys_role 新增列

```sql
-- sys_role 新增 data_scope 列
ALTER TABLE sys_role ADD COLUMN data_scope char(1) DEFAULT '1' NOT NULL;

COMMENT ON COLUMN sys_role.data_scope IS '数据范围：1=全部数据, 2=自定义数据, 3=本部门数据, 4=本部门及以下, 5=仅本人';
```

**设计说明：**

- `char(1)` 而非 `int`：与 `sys_role.del_flag` 等 pig 现有字段风格保持一致（`char(1)` 标识位）。
- `DEFAULT '1' NOT NULL`：存量角色默认"全部数据"，**行为完全不变**，保证向后兼容。
- 不使用枚举类型（PG `CREATE TYPE`）：避免 Flyway 迁移和后续修改枚举值的复杂度，保持与 pig 风格一致。

### 2.2 sys_role_dept 关联表

```sql
CREATE TABLE sys_role_dept (
    role_id bigint NOT NULL,
    dept_id bigint NOT NULL,
    PRIMARY KEY (role_id, dept_id)
);

COMMENT ON TABLE sys_role_dept IS '角色-部门关联表（角色数据范围为"自定义"时使用）';
COMMENT ON COLUMN sys_role_dept.role_id IS '角色ID';
COMMENT ON COLUMN sys_role_dept.dept_id IS '部门ID';

-- 索引：按 dept_id 反查（查询某部门被哪些角色引用时使用）
CREATE INDEX idx_role_dept_dept_id ON sys_role_dept (dept_id);
```

**设计说明：**

- 与 `sys_role_menu`（role_id + menu_id）结构完全对称，保持一致性。
- 仅当 `sys_role.data_scope = '2'`（自定义）时此表数据生效；其他范围此表对该角色的记录应被清理。
- 主键 `(role_id, dept_id)` 天然唯一，不需要额外唯一索引。
- `idx_role_dept_dept_id` 反查索引：当部门被删除时，需要清理引用该部门的角色-部门关联。

### 2.3 sys_dept_closure 闭包表

```sql
CREATE TABLE sys_dept_closure (
    ancestor   bigint NOT NULL,
    descendant bigint NOT NULL,
    depth      integer NOT NULL DEFAULT 0,
    PRIMARY KEY (ancestor, descendant)
);

COMMENT ON TABLE sys_dept_closure IS '部门闭包表：预存储所有祖先-后代关系，用于高性能子树查询';
COMMENT ON COLUMN sys_dept_closure.ancestor IS '祖先部门ID';
COMMENT ON COLUMN sys_dept_closure.descendant IS '后代部门ID';
COMMENT ON COLUMN sys_dept_closure.depth IS '距离（0=自身, 1=直接子级, 2=孙级...）';

-- 索引：按祖先查所有后代（"本部门及以下"场景使用，高频）
CREATE INDEX idx_dept_closure_ancestor ON sys_dept_closure (ancestor);

-- 索引：按后代查所有祖先（权限向上追溯场景）
CREATE INDEX idx_dept_closure_descendant ON sys_dept_closure (descendant);
```

**设计说明：**

| 对比维度 | 现状 `parent_id` 递归 | 闭包表 `sys_dept_closure` |
|----------|----------------------|---------------------------|
| 查询子树 | `SysDeptServiceImpl.listDescendant()` 全表加载 + 内存递归 | `SELECT descendant FROM sys_dept_closure WHERE ancestor = ?` 一次查询 |
| 查询复杂度 | O(N) 全表扫描 + 内存递归 | O(log N) 索引扫描 |
| 部门量大时 | 性能差（千级部门明显） | 性能稳定 |
| 维护成本 | 零维护 | 需在部门增删改时同步维护 |

**闭包表维护策略：**

采用 **Service 层事务维护**（不用数据库触发器，因为 pig 跨数据库兼容，且触发器难以追踪）：

```
新增部门 D (parent=P):
  1. INSERT (D, D, 0)  -- 自身
  2. INSERT (A, D, depth+1) FOR EACH (A, P, depth) IN closure  -- P 的所有祖先 → D

删除部门 D:
  1. DELETE FROM closure WHERE descendant = D  -- 删除所有指向 D 的记录
  2. DELETE FROM closure WHERE ancestor = D     -- 删除 D 作为祖先的记录（可选，视级联策略）

移动部门 D 到新 parent=P_new:
  1. 删除 D 子树与 D 旧祖先子树的交叉关系
  2. 插入 D 子树与 P_new 祖先子树的新关系
```

> 详见 [02-后端核心框架设计.md](02-后端核心框架设计.md) 中的 `DeptClosureService` 实现。

### 2.4 替代方案：PostgreSQL 递归 CTE（不建闭包表）

如果不希望引入闭包表的维护成本，可以使用 PG 原生递归 CTE：

```sql
-- 查询部门 ID = ? 的所有子部门（含自身）
WITH RECURSIVE dept_tree AS (
    SELECT dept_id, parent_id FROM sys_dept WHERE dept_id = #{deptId}
    UNION ALL
    SELECT d.dept_id, d.parent_id
    FROM sys_dept d
    INNER JOIN dept_tree t ON d.parent_id = t.dept_id
    WHERE d.del_flag = '0'
)
SELECT dept_id FROM dept_tree;
```

**对比结论：**

| 维度 | 闭包表 | 递归 CTE |
|------|--------|----------|
| 查询性能 | 极快（索引扫描） | 中等（递归扫描，但有索引） |
| 维护成本 | 高（增删改同步） | 零维护 |
| 部门层级深度 | 无限制 | PG 递归深度限制（默认 100，可调） |
| 适用场景 | 部门量大(>500) + 频繁子树查询 | 部门量小(<500) + 变更频繁 |

**推荐方案**：youming 初期部门量不大，**优先使用递归 CTE**（零维护），并在 `DataScopeProcessor` 中增加 Redis 缓存（TTL 5 分钟）。当部门量增长到 500+ 时，再引入闭包表。数据库 DDL 中预留闭包表建表语句但**注释掉**，作为后续优化储备。

## 5. 索引设计汇总

| 表 | 索引名 | 列 | 用途 |
|----|--------|----|----|
| `sys_role_dept` | (PK) | (role_id, dept_id) | 主键，按角色查部门 |
| `sys_role_dept` | `idx_role_dept_dept_id` | (dept_id) | 按部门反查角色（部门删除时清理） |
| `sys_dept_closure` | (PK) | (ancestor, descendant) | 主键 |
| `sys_dept_closure` | `idx_dept_closure_ancestor` | (ancestor) | **高频**：查某部门的所有后代 |
| `sys_dept_closure` | `idx_dept_closure_descendant` | (descendant) | 查某部门的所有祖先 |

> `sys_role.data_scope` 列基数极低（5个值），**不需要索引**。查询时 `data_scope` 总是与其他条件联合使用，走其他索引。

## 6. 数据迁移与兼容性

### 6.1 存量数据兼容

| 存量对象 | 迁移行为 | 兼容性 |
|----------|----------|--------|
| 现有角色 | `data_scope` 默认 `'1'`（全部数据） | ✅ 行为不变，仍可查看全部数据 |
| 现有用户-角色关系 | 无需变更 | ✅ 不受影响 |
| 现有用户-部门关系 | 无需变更 | ✅ 不受影响 |
| `sys_role_dept` | 新表，初始为空 | ✅ 无存量数据问题 |

### 6.2 回滚方案

```sql
-- 回滚 V23
DROP TABLE IF EXISTS sys_role_dept;
-- DROP TABLE IF EXISTS sys_dept_closure;  -- 如果启用了闭包表
ALTER TABLE sys_role DROP COLUMN IF EXISTS data_scope;
```

Flyway 不支持自动回滚（社区版无 undo），上述脚本需手动执行。由于 `data_scope` 默认值 `'1'` 使存量角色行为不变，即使回滚也不会丢失数据。
