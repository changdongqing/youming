## 1. 角色数据范围管理 API

### 1.1 Controller 新增端点

在 `SysRoleController` 中新增数据范围的查询和保存接口：

```java
// pig-upms-biz/.../controller/SysRoleController.java

/**
 * 查询角色的数据范围配置
 * @param roleId 角色ID
 * @return 数据范围信息（scope 类型 + 自定义部门列表）
 */
@GetMapping("/data-scope/{roleId}")
@HasPermission("sys_role_datascope")
public R getDataScope(@PathVariable Long roleId) {
    return R.ok(sysRoleService.getDataScope(roleId));
}

/**
 * 保存角色的数据范围配置
 * @param vo 数据范围配置
 * @return success/fail
 */
@SysLog("修改角色数据范围")
@PutMapping("/data-scope")
@HasPermission("sys_role_datascope")
@CacheEvict(value = {CacheConstants.DATA_SCOPE_ROLE, CacheConstants.DATA_SCOPE_CUSTOM_DEPT}, allEntries = true)
public R saveDataScope(@RequestBody @Valid RoleDataScopeVO vo) {
    return R.ok(sysRoleService.saveDataScope(vo.getRoleId(), vo.getDataScope(), vo.getDeptIds()));
}
```

### 1.2 RoleDataScopeVO

```java
// pig-upms-biz/.../api/vo/RoleDataScopeVO.java

package com.pig4cloud.pig.admin.api.vo;

import io.swagger.v3.oas.annotations.media.Schema;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;

import java.util.List;

 * 角色数据范围配置 VO
```

### 1.3 SysRoleService 新增方法

```java
// pig-upms-biz/.../service/SysRoleService.java（接口新增）

/**
 * 查询角色数据范围配置
 * @param roleId 角色ID
 * @return 数据范围 VO
 */
RoleDataScopeVO getDataScope(Long roleId);

/**
 * 保存角色数据范围配置
 * @param roleId 角色ID
 * @param dataScope 数据范围编码
 * @param deptIds 自定义部门列表（仅 dataScope=2 时有效）
 * @return 是否成功
 */
Boolean saveDataScope(Long roleId, String dataScope, List<Long> deptIds);
```

```java
// pig-upms-biz/.../service/impl/SysRoleServiceImpl.java（实现）

@Override
public RoleDataScopeVO getDataScope(Long roleId) {
    SysRole role = this.getById(roleId);
    if (role == null) {
        throw new RuntimeException("角色不存在");
    }

    RoleDataScopeVO vo = new RoleDataScopeVO();
    vo.setRoleId(roleId);
    vo.setDataScope(role.getDataScope() != null ? role.getDataScope() : "1");

    // 仅当自定义范围时查询关联部门
    if ("2".equals(vo.getDataScope())) {
        List<Long> deptIds = roleDeptMapper.selectList(
                Wrappers.<SysRoleDept>lambdaQuery()
                        .eq(SysRoleDept::getRoleId, roleId))
                .stream()
                .map(SysRoleDept::getDeptId)
                .toList();
        vo.setDeptIds(deptIds);
    }

    return vo;
}

@Override
@Transactional(rollbackFor = Exception.class)
@CacheEvict(value = {CacheConstants.DATA_SCOPE_ROLE, CacheConstants.DATA_SCOPE_CUSTOM_DEPT}, allEntries = true)
public Boolean saveDataScope(Long roleId, String dataScope, List<Long> deptIds) {
    // 1. 更新角色数据范围
    SysRole role = new SysRole();
    role.setRoleId(roleId);
    role.setDataScope(dataScope);
    roleMapper.updateById(role);

    // 2. 先删除旧的关联部门
    roleDeptMapper.delete(Wrappers.<SysRoleDept>lambdaQuery()
            .eq(SysRoleDept::getRoleId, roleId));

    // 3. 仅自定义范围时保存新关联
    if ("2".equals(dataScope) && CollUtil.isNotEmpty(deptIds)) {
        List<SysRoleDept> list = deptIds.stream().map(deptId -> {
            SysRoleDept rd = new SysRoleDept();
            rd.setRoleId(roleId);
            rd.setDeptId(deptId);
            return rd;
        }).toList();
        // 批量插入
        list.forEach(roleDeptMapper::insert);
    }

    return Boolean.TRUE;
}
```

## 2. 用户列表接入数据权限（完整示例）

### 2.1 现状分析

当前用户分页查询的 XML（`SysUserMapper.xml` → `getUserVosPage`）：

```sql
SELECT u.* FROM sys_user u
<if test="query.deptId != null">
    INNER JOIN sys_user_dept ud ON u.user_id = ud.user_id AND ud.dept_id = #{query.deptId}
</if>
WHERE u.del_flag = '0'
  AND u.username LIKE ...
ORDER BY u.create_time DESC
```

**问题**：
1. 仅当 `query.deptId` 非空时才 JOIN `sys_user_dept`，否则没有部门别名 `ud`。
2. 数据权限拦截器需要稳定的 `ud.dept_id` 列引用。

### 2.2 改造方案：始终 LEFT JOIN sys_user_dept

```xml
<!-- 改造后的 getUserVosPage -->
<select id="getUserVosPage" resultMap="baseResultMap">
    SELECT
    <include refid="userColumns"/>
    FROM
    sys_user u
    <!-- 始终 LEFT JOIN，确保数据权限拦截器能引用 ud.dept_id -->
    LEFT JOIN sys_user_dept ud ON u.user_id = ud.user_id
    <if test="query.deptId != null and query.deptId != ''">
        AND ud.dept_id = #{query.deptId}
    </if>
    WHERE
    u.del_flag = '0'
    <!-- 用户名模糊查询 -->
    <if test="query.username != null and query.username != ''">
        <bind name="usernameLike" value="'%' + query.username + '%'"/>
        AND u.username LIKE #{usernameLike}
    </if>
    <!-- 手机号模糊查询 -->
    <if test="query.phone != null and query.phone != ''">
        <bind name="phoneLike" value="'%' + query.phone + '%'"/>
        AND u.phone LIKE #{phoneLike}
    </if>
    <!-- 防止一个用户多部门导致重复行 -->
    GROUP BY u.user_id
    ORDER BY u.create_time DESC
</select>
```

**关键改动**：
1. `INNER JOIN` → `LEFT JOIN`：确保无部门用户也能被查询到（当数据范围为 ALL 时）。
2. 始终 JOIN：即使 `query.deptId` 为空也 JOIN，保证 `ud` 别名存在。
3. `GROUP BY u.user_id`：防止用户多部门导致重复行（`sys_user_dept` 一个用户可能多行）。

### 2.3 Mapper 方法标注 @DataScope

```java
// pig-upms-biz/.../mapper/SysUserMapper.java

@Mapper
public interface SysUserMapper extends MPJBaseMapper<SysUser> {

    // === 标注 @DataScope，启用数据权限过滤 ===
    @DataScope(deptAlias = "ud", userAlias = "u", deptField = "dept_id", createByField = "create_by")
    IPage<UserVO> getUserVosPage(Page page, @Param("query") UserDTO userDTO);

    // 其他方法无注解，不受数据权限影响
    UserVO getUserVo(@Param("query") UserDTO userDTO);

    // 导出全量数据时跳过数据权限
    @DataScope(deptAlias = "ud", userAlias = "u", disabled = true)
    List<UserVO> getUserVoList(@Param("query") UserDTO userDTO, @Param("ids") Long[] ids);

    UserVO getUserVoById(Long id);
}
```

### 2.4 效果验证

假设用户 zhangsan（deptId=1）拥有角色A（data_scope=4，本部门及以下），部门树为：

```
部门1（总公司）
├── 部门2（技术部）
│   ├── 部门5（前端组）
│   └── 部门6（后端组）
└── 部门3（市场部）
```

**改写后的 SQL**：

```sql
SELECT u.user_id, u.username, u.dept_id, ...
FROM sys_user u
LEFT JOIN sys_user_dept ud ON u.user_id = ud.user_id
WHERE u.del_flag = '0'
  AND ud.dept_id IN (1, 2, 3, 5, 6)    -- ← 数据权限注入：部门1及其全部子部门
GROUP BY u.user_id
ORDER BY u.create_time DESC
```

## 3. 通用接入模式

### 3.1 有部门字段的业务表

youming 业务表普遍有 `dept_id` 或 `create_by` 字段。接入数据权限的标准模式：

```java
// 1. Mapper 方法标注 @DataScope
@DataScope(deptAlias = "t", userAlias = "t")
List<SomeEntity> selectPage(Page page, @Param("query") SomeQuery query);
```

```xml
<!-- 2. XML 中确保有对应别名 -->
<select id="selectPage" resultType="SomeEntity">
    SELECT t.* FROM some_table t
    WHERE t.del_flag = '0'
    <!-- 数据权限拦截器会追加: AND t.dept_id IN (...) 或 AND t.create_by = 'xxx' -->
</select>
```

### 3.2 无 JOIN 的简单查询

如果业务表自身有 `dept_id` 列（无需 JOIN 部门关联表），直接使用表别名：

```java
@DataScope(deptAlias = "t", userAlias = "t")
List<SomeEntity> selectList(@Param("query") SomeQuery query);
```

拦截器注入条件：`AND t.dept_id IN (...)`

### 3.3 需要 JOIN 部门关联表的查询

如果业务表没有 `dept_id` 但需要通过用户关联部门：

```xml
<select id="selectPage" resultType="SomeEntity">
    SELECT t.* FROM some_table t
    LEFT JOIN sys_user_dept ud ON t.create_by_user_id = ud.user_id
    WHERE t.del_flag = '0'
</select>
```

```java
@DataScope(deptAlias = "ud", userAlias = "t")
List<SomeEntity> selectPage(Page page, @Param("query") SomeQuery query);
```

拦截器注入条件：`AND ud.dept_id IN (...)`

### 3.4 编程式跳过数据权限

```java
// 场景：管理员导出全量数据 / 定时任务数据同步
try (DataScopeContext ignored = DataScopeContext.disable()) {
    List<SysUser> allUsers = userMapper.selectList(Wrappers.emptyWrapper());
    // 此查询不附加数据权限条件
}
```

### 3.5 注解式跳过数据权限

```java
// Mapper 方法级跳过
@DataScope(disabled = true)
List<SysUser> selectAllForExport();
```

## 4. pig-rm 业务模块接入示例

youming 的 RM（需求管理）模块有大量业务表。以典型业务表为例：

### 4.1 需求列表查询接入

假设 `rm_requirement` 表有 `dept_id` 和 `create_by` 字段：

```java
// pig-rm/.../mapper/RmRequirementMapper.java

@Mapper
public interface RmRequirementMapper extends MPJBaseMapper<RmRequirement> {

    @DataScope(deptAlias = "r", userAlias = "r")
    IPage<RmRequirement> selectPage(Page page, @Param("query") RmRequirementDTO query);
}
```

```xml
<!-- RmRequirementMapper.xml -->
<select id="selectPage" resultType="RmRequirement">
    SELECT r.* FROM rm_requirement r
    WHERE r.del_flag = '0'
    <if test="query.title != null and query.title != ''">
        AND r.title LIKE CONCAT('%', #{query.title}, '%')
    </if>
</select>
```

### 4.2 注意事项

| 事项 | 说明 |
|------|------|
| MPJ Join 查询 | 使用 `MPJLambdaWrapper` 时，`deptAlias` 需与 join 的别名一致 |
| 子查询 | `@DataScope` 仅对最外层 SELECT 的 WHERE 子句注入条件，不影响子查询 |
| UNION 查询 | JSqlParser 对 UNION 的支持有限，建议避免在 UNION 查询上标注 `@DataScope` |
| 嵌套 ResultMap | 使用 `<collection>` 嵌套查询时，数据权限仅作用于主查询，不作用于嵌套查询 |

## 5. 接入检查清单

接入数据权限时，逐项确认：

- [ ] SQL 中是否存在 `@DataScope` 注解指定的别名（`deptAlias` / `userAlias`）
- [ ] SQL 中是否存在对应字段（`deptField` / `createByField`）
- [ ] LEFT JOIN 是否会导致重复行 → 需要加 `GROUP BY` 或 `DISTINCT`
- [ ] 导出/全量查询是否标注了 `disabled = true` 或使用 `DataScopeContext.disable()`
- [ ] 定时任务/Feign 调用路径是否无用户上下文 → 拦截器会自动放行（null check）
- [ ] 管理员角色 `data_scope` 是否配置为 `1`（全部数据）
- [ ] 缓存是否在角色/部门变更时正确清除

## 6. 常见问题（FAQ）

### Q1: 标注了 @DataScope 但过滤条件没有生效？

**排查步骤**：
1. 确认 `DataScopeInnerInterceptor` Bean 已注册（检查 `DataScopeConfiguration`）
2. 确认拦截器在 `MybatisPlusInterceptor` 链中（查看启动日志）
3. 确认 Mapper 方法上确实标注了 `@DataScope`（而非类级注解，类级注解需要 Mapper 接口本身有注解）
4. 确认当前用户有角色且角色 `data_scope` 不是 `1`（全部数据会短路）
5. 开启 SQL 日志，查看实际执行的 SQL 是否包含过滤条件

### Q2: SQL 中报错"column ud.dept_id does not exist"？

**原因**：`@DataScope` 指定的 `deptAlias` 在 SQL 中不存在。

**解决**：
- 确认 SQL 中有对应别名的 JOIN 或表别名
- 如果是 `LEFT JOIN sys_user_dept ud`，则 `deptAlias = "ud"`
- 如果是直接查 `sys_dept d`，则 `deptAlias = "d"`

### Q3: 用户多部门导致查询结果重复？

**原因**：`sys_user_dept` 中一个用户多行（多部门），LEFT JOIN 导致笛卡尔积。

**解决**：在 SQL 中加 `GROUP BY u.user_id` 或 `DISTINCT`。

### Q4: 内部 Feign 调用报 NPE？

**原因**：Feign 调用无用户上下文，`UserContextHolder.get()` 返回 null。

**解决**：拦截器已处理 null check，返回 `skip=true` 自动放行。如果仍报错，检查是否在非查询方法（如 insert/update）上误标了 `@DataScope`。

### Q5: 如何临时查看全部数据（调试场景）？

```java
// 编程式跳过
try (DataScopeContext ignored = DataScopeContext.disable()) {
    List<SysUser> all = userMapper.selectList(Wrappers.emptyWrapper());
}
```

### Q6: 数据权限是否影响 INSERT/UPDATE/DELETE？

**不影响**。`DataScopeInnerInterceptor` 仅实现 `beforeQuery`，不拦截写操作。数据权限控制的是"能看到什么数据"，不控制"能修改什么数据"。写操作权限由 `@HasPermission` 功能权限控制。

> 如果需要写操作也受数据权限控制（例如只能修改本部门的数据），需要在 Service 层手动校验，或后续增加 `beforeUpdate` 拦截。

### Q7: 递归 CTE 在数据量大时性能如何？

PostgreSQL 递归 CTE 在 `parent_id` 上有索引时性能良好。`sys_dept` 表通常不超过千级，递归深度不超过 10 层，CTE 查询在毫秒级。配合 Redis 缓存（TTL 10 分钟），实际 DB 查询频率极低。

如果部门量超过 5000+，建议启用闭包表方案（见 [02-后端核心框架设计.md](02-后端核心框架设计.md) 第 12 节）。
