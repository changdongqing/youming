### 1.1 结论

本模块必须补充，但应采用与当前关系模型相容的**“工作区 + 不可变发布快照”**方案，而不是在现有表上伪装出并不存在的多版本并行能力。

核心结论：

1. `ont_entity_type`、`ont_data_property`、`ont_object_property`、`ont_axiom_rule` 等现有表仍表示一个本体工程的**当前工作区**。
2. 发布版本是对工作区 TBox/规则/扩展依赖的**不可变检查点**，用于比较、审计、导出和恢复计划。
3. **实例 ABox 不进入本体版本快照**。IoT/业务实例是持续变化的数据，把全部实例塞入每个版本会导致快照爆炸，也混淆“本体版本”和“业务数据备份”。实例只通过迁移计划和迁移作业与 Schema 版本关联。
4. 首期使用**全量规范化 JSONB 快照**，不使用链式增量快照。全量快照更容易校验、比较和恢复，PostgreSQL JSONB 可由 TOAST 压缩；增量链会放大恢复失败风险。
5. “回滚”不是把 `current_version_id` 指回旧版本，也不是直接覆盖关系表和删除实例；正确做法是：从历史快照生成**恢复计划**，应用到工作区，完成实例迁移和校验后，再发布一个新的更高版本。
6. 当前表结构不支持同一工程多个并行活动分支。并行分支/命名图/不同项目固定使用不同版本属于后续能力；首期可通过复制为不同本体工程实现隔离。

### 1.2 对原设计的关键修正

| 原设计问题 | 修正 |

## 2. 领域模型与边界

### 2.1 名词

| 名词 | 定义 |
|---|---|
| 工作区（Working Copy） | 当前关系表中的可编辑本体 Schema 与实例数据 |
| 候选版本（PREPARED） | 已冻结快照和差异，但尚未激活为当前发布版本 |
| 已发布版本（PUBLISHED） | 已通过校验并成为过当前版本的不可变快照 |
| 当前版本 | `ont_ontology_project.current_version_id` 指向的已发布版本 |
| 迁移计划 | 描述工作区 Schema 变化后实例断言如何调整的声明式规则 |
| 迁移作业 | 对迁移计划的一次实际执行，包含进度、失败明细和校验结果 |
| 恢复计划 | 由历史版本快照与当前工作区比较生成的正向变更计划；执行后发布新版本 |

### 2.2 快照范围

版本快照必须包含：

- 本体工程标识、ontology IRI、版本 IRI。
- 命名空间依赖清单。
- 实体类型、标签、继承、不相交、等价关系。
- 数据属性、标签、枚举、值域/必填/唯一/单位等约束元数据。
- 对象属性、标签、domain、range、功能性/对称性/传递性等语义。
- 公理与规则及其目标。
- 扩展模块绑定和扩展资源引用。
- 使用到的单位 IRI/编码依赖清单。
- 快照格式版本 `snapshotFormatVersion`。

版本快照不得包含：

- `ont_entity_instance` 全量实例。
- `ont_instance_data_value` 和 `ont_instance_object_relation` 全量数据。
- 校验报告、导入导出日志、SPARQL 查询日志。
- 用户、角色、菜单和设备凭证。
- 高频 IoT 遥测和时序数据。

### 2.3 工作区限制

现有模块 04～11 的写接口直接修改工作区，并没有 Draft Branch。为避免“未发布破坏性 Schema 已影响在线实例”，首期治理要求：

- 对破坏性 Schema 变更使用维护窗口。
- 候选版本 PREPARED 后，受影响 Schema 元素和实例写入进入维护锁。
- 迁移与全量校验通过前不得激活候选版本。
- 若需要真正的并行草稿/发布分支，应另行设计带版本有效期的表模型或命名图，不在本期通过 JSON 快照冒充。

#### 2.3.1 工作区状态转换

`ont_ontology_project.workspace_status` 状态机：

```text
EDITABLE ──prepare(BREAKING)──▶ MIGRATING ──migration SUCCEEDED + validation pass ──▶ EDITABLE(activate)
  │                               │                                                         │
  │                          migration FAILED/CANCELLED                                     │
  │                               ▼                                                         │
  │                          MIGRATING(cancel) ──▶ EDITABLE                                  │
  │                                                                                         │
  └──prepare(非 BREAKING)──▶ EDITABLE(直接 activate，不变状态) ──────────────────────────┘
```

| 当前状态 | 含义 | 允许 |
|---|---|---|
| `EDITABLE` | 正常可编辑 | 所有模块 04～11 的写操作；prepare |
| `PREPARED` | 候选版本已冻结但未激活（用于工作区锁定语义） | 查询、取消候选版本后回到 EDITABLE |
| `MIGRATING` | 正在执行实例迁移 | 只读；迁移作业查询/取消；激活被拒绝 |

> 注意：非 BREAKING 的 prepare + activate 在同一流程内完成，`workspace_status` 不经过 `MIGRATING`。只有 BREAKING 变更需要迁移作业时才进入 `MIGRATING`。`PREPARED` 状态用于锁定语义：prepare BREAKING 候选版本时设为 `PREPARED`，创建迁移作业后转为 `MIGRATING`。

#### 2.3.2 跨模块写入保护

模块 04～11 的 Service 写方法应调用 `WorkspaceStatusGuard.assertEditable(ontologyId)` 在事务内校验工作区状态。`MIGRATING` 状态下所有 Schema 元素和实例写入被拒绝（返回 `R.failed("工作区正在迁移中，写入已锁定")`）。首期通过在现有 Service 方法中追加一行调用实现，不需要 AOP。

## 3. 版本语义

### 3.1 版本号

- 发布版本采用 SemVer 主版本格式 `MAJOR.MINOR.PATCH`。
- 首期只发布稳定版本，不开放预发布后缀。
- 新版本必须严格大于本工程历史最大已发布版本。
- 版本号比较必须使用 SemVer 解析器，不允许字符串比较。实现引入 `com.github.zafarkhaja:java-semver:0.10.2`（Maven Central），用 `SemVer.valueOf(versionNumber).compareTo(priorSemver) > 0` 校验严格递增。版本号格式校验用 `SemVer.valueOf` 解析，异常即格式不合法。

建议规则：

| 变化 | 版本建议 |
|---|---|
| 删除类/属性、公理语义收紧、IRI 变更、datatype 变更、domain/range 收窄、必填约束增强 | MAJOR |
| 新增可选类/属性、增加不影响旧实例的扩展 | MINOR |
| 标签、定义、注释、排序、非语义错误修复 | PATCH |

### 3.2 兼容性判定

兼容性由系统根据 diff 计算，发布者可以把等级调得更严格，但不能把 `BREAKING` 人工降为 `BACKWARD_COMPATIBLE`。

| 兼容性 | 含义 |
|---|---|
| `PATCH_ONLY` | 不改变可执行语义，通常仅标签/定义/注释变化 |
| `BACKWARD_COMPATIBLE` | 旧实例仍满足新 Schema，新增内容为可选或扩展性变化 |
| `BREAKING` | 旧实例可能失效，必须提供迁移计划并重新校验 |

以下至少判为 BREAKING：

- IRI 删除或变更（IRI 重命名按“删除旧 IRI + 新增新 IRI”处理）。
- 数据类型改变、枚举收窄、最大长度/数值范围收窄。
- `minCount`/必填约束增强。
- 对象属性 domain/range 收窄。
- 新增不相交关系导致既有实例冲突。
- 删除实例正在使用的属性或实体类型。

### 3.3 OWL 版本声明

工程需增加：

- `ontology_iri`：本体标识 IRI，例如 `http://example.org/standard-ontology`。
- `version_iri_base`：版本 IRI 基础，例如 `http://example.org/standard-ontology/version/`。

发布 `1.2.0` 后：

```turtle
<http://example.org/standard-ontology> a owl:Ontology ;
  owl:versionIRI <http://example.org/standard-ontology/version/1.2.0> ;
  owl:priorVersion <http://example.org/standard-ontology/version/1.1.0> ;
  owl:backwardCompatibleWith <http://example.org/standard-ontology/version/1.1.0> .
```

`owl:incompatibleWith` 只在确有依据时输出。`PATCH_ONLY` 不自动等同于某个 OWL 兼容性谓词。

## 4. 数据模型

### 4.1 本体工程扩展

```sql
ALTER TABLE ont_ontology_project
  ADD COLUMN IF NOT EXISTS ontology_iri varchar(512),
  ADD COLUMN IF NOT EXISTS version_iri_base varchar(512),
  ADD COLUMN IF NOT EXISTS current_version_id bigint,
  ADD COLUMN IF NOT EXISTS workspace_status varchar(16) NOT NULL DEFAULT 'EDITABLE',
  ADD COLUMN IF NOT EXISTS workspace_revision bigint NOT NULL DEFAULT 0;

ALTER TABLE ont_ontology_project
  ADD CONSTRAINT ck_ont_project_workspace_status
  CHECK (workspace_status IN ('EDITABLE', 'PREPARED', 'MIGRATING'));

CREATE UNIQUE INDEX IF NOT EXISTS uk_ont_project_ontology_iri
  ON ont_ontology_project (ontology_iri)
  WHERE del_flag = '0' AND ontology_iri IS NOT NULL;

COMMENT ON COLUMN ont_ontology_project.ontology_iri IS '本体标识IRI，如 http://example.org/standard-ontology';
COMMENT ON COLUMN ont_ontology_project.version_iri_base IS '版本IRI基础路径，如 http://example.org/standard-ontology/version/';
COMMENT ON COLUMN ont_ontology_project.current_version_id IS '当前已发布版本ID，引用ont_ontology_version.id，初始为空';
COMMENT ON COLUMN ont_ontology_project.workspace_status IS '工作区状态：EDITABLE/PREPARED/MIGRATING';
COMMENT ON COLUMN ont_ontology_project.workspace_revision IS '工作区修订号，每次语义写入递增，用于乐观锁校验';
```

**实体类同步修改**：`OntOntologyProject.java` 需新增对应 5 个字段（`ontologyIri`、`versionIriBase`、`currentVersionId`、`workspaceStatus`、`workspaceRevision`），每个字段添加 `@Schema(description = "...")`，保持与现有实体注解风格一致。

- `current_version_id` 初始可空，首次真实基线发布后填写。
- `workspace_status` 由模块 04～11/14 的写服务共同校验；`MIGRATING` 时受影响 Schema 和实例写入必须拒绝。实现方式见 §2.3.2 `WorkspaceStatusGuard`。
- `workspace_revision` 在每次工作区语义写入事务中递增，候选版本记录准备时的 revision；激活时 revision 不一致则拒绝。递增 SQL 使用乐观锁模式：
  ```sql
  UPDATE ont_ontology_project
  SET workspace_revision = workspace_revision + 1, update_time = now()
  WHERE id = ? AND workspace_revision = ? AND del_flag = '0'
  ```
  返回影响行数为 0 表示并发冲突，写入需重试或拒绝。
- `ontology_iri` 和 `version_iri_base` 必须为绝对 IRI，不得以 `#` 作为版本号拼接位置。版本 IRI 拼接规则：`version_iri_base + version_number`，例如 `http://example.org/standard-ontology/version/1.2.0`。

### 4.2 本体版本表 `ont_ontology_version`

COMMENT ON TABLE ont_ontology_version IS '本体版本表，存储不可变Schema快照及发布元数据';
COMMENT ON COLUMN ont_ontology_version.id IS '主键ID（雪花算法）';
COMMENT ON COLUMN ont_ontology_version.ontology_id IS '本体工程ID';
COMMENT ON COLUMN ont_ontology_version.version_number IS '语义版本号 MAJOR.MINOR.PATCH';
COMMENT ON COLUMN ont_ontology_version.version_iri IS '版本IRI，version_iri_base+version_number';
COMMENT ON COLUMN ont_ontology_version.prior_version_id IS '前序版本ID（自引用）';
COMMENT ON COLUMN ont_ontology_version.restore_source_version_id IS '恢复来源版本ID，指向被恢复的历史版本';
COMMENT ON COLUMN ont_ontology_version.compatibility IS '兼容性：PATCH_ONLY/BACKWARD_COMPATIBLE/BREAKING';
COMMENT ON COLUMN ont_ontology_version.release_status IS '发布状态：PREPARED/MIGRATING/PUBLISHED/FAILED/CANCELLED';
COMMENT ON COLUMN ont_ontology_version.release_notes IS '发布说明';
COMMENT ON COLUMN ont_ontology_version.snapshot_format_version IS '快照格式版本，当前为1';
COMMENT ON COLUMN ont_ontology_version.schema_snapshot IS '规范化全量Schema快照JSONB';
COMMENT ON COLUMN ont_ontology_version.snapshot_hash IS '快照SHA-256哈希';
COMMENT ON COLUMN ont_ontology_version.diff_summary IS '与priorVersion的差异摘要JSONB';
COMMENT ON COLUMN ont_ontology_version.migration_plan IS '实例迁移计划JSONB，BREAKING时必填';
COMMENT ON COLUMN ont_ontology_version.validation_report_id IS '关联校验报告ID';
COMMENT ON COLUMN ont_ontology_version.workspace_revision IS 'prepare时记录的工作区修订号，用于激活时乐观锁校验';
COMMENT ON COLUMN ont_ontology_version.published_by IS '发布人';
COMMENT ON COLUMN ont_ontology_version.published_at IS '发布时间';

> `fk_ont_version_validation` 使用 `ON DELETE SET NULL` 而非 `RESTRICT`：校验报告是运维数据，生命周期由模块 09 管理，不应因为版本引用而阻止报告清理。

创建版本表后再增加当前版本外键，避免建表顺序循环：

```sql
ALTER TABLE ont_ontology_project
  ADD CONSTRAINT fk_ont_project_current_version
  FOREIGN KEY (current_version_id)
  REFERENCES ont_ontology_version(id)
  ON DELETE RESTRICT;
```

### 4.4 快照 JSON

快照必须规范排序后再计算 SHA-256。数组顺序不能依赖数据库默认返回顺序。

```json
{
  "snapshotFormatVersion": 1,
  "ontology": {
    "ontologyIri": "http://example.org/standard-ontology",
    "versionIri": "http://example.org/standard-ontology/version/1.2.0"
  },
  "namespaces": [],
  "entityTypes": [],
  "entityTypeHierarchies": [],
  "entityTypeDisjoints": [],
  "entityTypeEquivalents": [],
  "dataProperties": [],
  "dataPropertyEnums": [],
  "objectProperties": [],
  "objectPropertyDomains": [],
  "objectPropertyRanges": [],
  "axiomRules": [],
  "axiomRuleTargets": [],
  "extensionDependencies": [],
  "unitDependencies": []
}
```

元素主键使用 IRI/业务编码，不把数据库自增或雪花 ID 当作跨环境稳定标识。

#### 4.4.1 规范化排序规则

`OntologySnapshotCanonicalizer` 对快照 JSON 执行以下规范化步骤：

1. **移除审计字段**：从所有元素中移除 `id`、`createBy`、`createTime`、`updateBy`、`updateTime`、`delFlag`、`sortOrder`、`remarks`。
2. **ID 替换为 IRI/业务编码**：
   - `entityTypes[].id` → 用 `iri` 作为唯一标识。
   - `entityTypeHierarchies[]`：`parentId`/`childId` → `parentIri`/`childIri`。
   - `entityTypeDisjoints[]`：`typeA`/`typeB` → `iriA`/`iriB`。
   - `entityTypeEquivalents[]`：`entityTypeId`/`equivalentId` → `iriA`/`iriB`。
   - `dataProperties[]`：`id` → `iri`；`domainEntityTypeId` → `domainEntityIri`；`unitId` → `unitIri`。
   - `dataPropertyEnums[]`：`dataPropertyId` → `dataPropertyIri`。
   - `objectProperties[]`：`id` → `iri`；`inverseOfId` → `inverseOfIri`。
   - `objectPropertyDomains[]`/`objectPropertyRanges[]`：`objectPropertyId` → `objectPropertyIri`；`entityTypeId` → `entityTypeIri`。
   - `axiomRules[]`：`id` → `ruleCode`；`axiomRuleTargets[]`：`axiomRuleId` → `ruleCode`。
   - `extensionDependencies[]`：`extensionModuleId` → `moduleCode`；`extensionResourceId` → `resourceIri`。
   - `unitDependencies[]`：`unitId` → `unitIri`。
3. **数组排序**：每个数组按其自然键稳定排序：
   - `entityTypes` 按 `iri` 升序。
   - `entityTypeHierarchies` 按 `parentIri, childIri` 升序。
   - `entityTypeDisjoints` 按 `iriA, iriB` 升序。
   - `entityTypeEquivalents` 按 `iriA, iriB` 升序。
   - `dataProperties` 按 `iri` 升序。
   - `dataPropertyEnums` 按 `dataPropertyIri, value` 升序。
   - `objectProperties` 按 `iri` 升序。
   - `objectPropertyDomains` 按 `objectPropertyIri, entityTypeIri` 升序。
   - `objectPropertyRanges` 按 `objectPropertyIri, entityTypeIri` 升序。
   - `axiomRules` 按 `ruleCode` 升序。
   - `axiomRuleTargets` 按 `ruleCode, targetType, targetIri` 升序。
   - `namespaces` 按 `prefix` 升序。
   - `extensionDependencies` 按 `moduleCode` 升序。
   - `unitDependencies` 按 `unitIri` 升序。
4. **JSON 序列化**：使用 Jackson `ObjectMapper` 配置 `SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS`，确保 JSON 对象字段按字母序输出。空集合输出为 `[]`，空字符串输出为 `""`（不省略）。
5. **哈希计算**：对规范序列化后的 UTF-8 字节流计算 `SHA-256`，十六进制小写输出为 `snapshot_hash`。

## 5. 核心流程

### 5.1 首次基线发布

Flyway V16 **不写入伪基线**。管理员在应用中执行：

1. 配置工程 `ontology_iri` 和 `version_iri_base`。
2. 执行全量校验，必须无 VIOLATION。
3. 输入 `1.0.0` 和发布说明。
4. 系统读取真实工作区构建全量规范快照。
5. 写入 PREPARED 版本。
6. 校验快照 hash 和版本 IRI 唯一性。
7. 激活为 PUBLISHED，并更新 `current_version_id`。

### 5.2 普通发布

```text
锁定 ont_ontology_project 当前工程行
  → 校验版本号严格递增
  → 构建规范化全量 Schema 快照
  → 与 priorVersion 快照按 IRI 比较
  → 系统判定兼容性和建议 SemVer 级别
  → 执行当前工作区全量校验
  → 写入 PREPARED 候选版本
  → 非 BREAKING：同一发布流程内激活
  → BREAKING：等待迁移作业成功和再次校验后激活
  → 更新 project.current_version_id
  → 模块10导出时输出版本声明
  → 发布版本事件（模块26存在时）
```

发布与激活必须校验：

- 候选记录的 `workspace_revision` 与工程当前 revision 一致，并再次核对快照 hash，防止准备后又被修改。
- `prior_version_id` 等于当时的 `current_version_id`。
- 工程行锁/数据库 advisory lock 防止并发发布。使用 PostgreSQL 事务级 advisory lock：
  ```sql
  SELECT pg_advisory_xact_lock(hashtext('ont_version_' || ?::text))
  ```
  参数为本体工程 ID。事务结束后自动释放，无需手动解锁。
- PUBLISHED 版本的快照、版本号、版本 IRI、兼容性不可修改。
- BREAKING 版本激活前必须校验 `migration_plan` 非空，且存在 `status = 'SUCCEEDED'` 的迁移作业记录。
- 首次基线发布（无 priorVersion）的 `diff_summary` 为 `{"firstRelease": true, "added": "<全量元素计数>", "compatibility": "BACKWARD_COMPATIBLE"}`，`compatibility` 记为 `BACKWARD_COMPATIBLE`（首版无破坏性）。

### 5.3 Diff 算法

Diff 比较在规范化后的快照 JSON 上进行（已完成 ID→IRI 替换和审计字段移除，见 §4.4.1）。

- 一级键：资源类型 + IRI（或 ruleCode）。
- 关系型元素键：关系类型 + 两端 IRI，例如 `SUBCLASS(childIri,parentIri)`。
- 标签键：资源 IRI + locale。
- 枚举键：属性 IRI + 规范化枚举值。
- modified 检测：同 IRI 元素逐字段比较，忽略 `sortOrder`、`remarks` 等非语义字段；仅语义字段变化才记入 `changes`。

Diff 输出：

```json
{
  "added": [{"resourceType":"DATA_PROPERTY","iri":"..."}],
  "removed": [],
  "modified": [{
    "resourceType":"ENTITY_TYPE",
    "iri":"...",
    "changes":[{"field":"definition","oldValue":"...","newValue":"..."}]
  }],
  "compatibility":"BACKWARD_COMPATIBLE",
  "breakingReasons": []
}
```

### 5.4 迁移规则

首期支持有限、可审计的声明式规则：

| 规则 | 说明 |
|---|---|
| `SET_DEFAULT_LITERAL` | 为缺少指定属性的实例补默认值 |
| `COPY_LITERAL` | 将旧属性值复制到新属性，可保留或删除旧断言 |
| `MAP_LITERAL` | 按显式映射表转换枚举/文本值；未命中必须失败或进入人工清单 |
| `DROP_ASSERTION` | 删除指定旧属性断言，必须先预览数量 |
| `RETYPE_INSTANCE` | 将指定类型实例迁移到新类型，并校验新类型约束 |
| `COPY_RELATION` | 将旧对象属性关系复制到新属性 |

不支持任意 JavaScript/Groovy/SQL 脚本作为迁移规则，避免不可审计执行。

### 5.5 迁移执行

- 按主键游标分批处理，默认每批 500，不使用一个覆盖全部实例的超大事务。
- 每批事务提交后更新 `cursor_data` 和统计，可从上次游标恢复。
- 规则必须幂等：再次执行不会重复插入相同值/关系。
- 迁移期间锁定受影响 Schema 元素，并阻止相关实例写入或进入维护模式。
- 迁移成功后执行模块 09 全量校验；有 VIOLATION 不得激活候选版本。
- 迁移作业不删除历史版本，也不修改版本快照。

### 5.6 恢复历史版本

API 名称使用“生成恢复计划”，避免误导为数据库瞬时回滚：

```text
选择历史版本
  → 当前工作区快照 vs 历史快照 diff
  → 生成恢复计划与 breaking 风险
  → 管理员确认并进入维护窗口
  → 将恢复计划应用到工作区
  → 执行必要的实例迁移
  → 全量校验
  → 发布新的更高 SemVer 版本
  → 新版本 restore_source_version_id 指向历史版本
```

禁止：

- 直接把 `current_version_id` 改成旧版本。
- 自动删除当前版本新增的实例。
- 在没有反向迁移规则时声称“无损回滚”。
- 修改或覆盖历史 PUBLISHED 快照。

## 6. 序列化模块改造

在模块 10 的 `OntologyModelExporter` 完成 Model 组装后增加本体头声明。实现时应新增专用 `OntologyVersionDeclarationContributor`，不要把版本查询逻辑散落在导出器各方法中。

规则：

- 若工程无已发布版本，只输出 `owl:Ontology`，不伪造 `owl:versionIRI`。
- 若存在当前版本，输出 `owl:versionIRI`。
- 有 priorVersion 时输出 `owl:priorVersion`。
- 仅 `BACKWARD_COMPATIBLE` 输出 `owl:backwardCompatibleWith`。
- `BREAKING` 是否输出 `owl:incompatibleWith` 由兼容性判定结果决定。
- 导出历史版本时，必须从版本快照构建 Model，不能读取当前工作区后只替换版本号。历史版本 Model 构建由 `SnapshotModelBuilder`（§10.3）负责：读取 `ont_ontology_version.schema_snapshot` JSONB，按快照中的 IRI 直接创建 Jena 三元组，不经过数据库关系表查询。

`OntologyModelExporter.buildCompleteModel` 需新增重载方法，接受 `versionId` 参数：当 `versionId` 非空时委托 `SnapshotModelBuilder` 从快照构建，否则走现有工作区读取逻辑。调用方（`SerializationServiceImpl`、`SparqlModelProvider`）在导出/查询时传入当前版本 ID。

## 11. 测试与验收

### 11.1 必测项

- 规范化快照在相同数据、不同查询顺序下 hash 一致。
- 审计字段和数据库 ID 变化不产生语义 diff。
- IRI 删除、datatype 变化、domain/range 收窄、必填增强判为 BREAKING。
- 发布并发只能成功一个；版本号严格递增。
- PUBLISHED 快照不可修改。
- PREPARED 后工作区变化导致 hash 不一致，激活被拒绝。
- 迁移分批恢复、幂等、部分失败和取消。
- 有 VIOLATION 的候选版本不能激活。
- 历史版本导出使用历史快照而不是当前工作区。
- 恢复流程创建新版本，不改变历史版本记录。

### 11.2 验收用例

| 用例 | 预期 |
|---|---|
| 首次基线 | 由应用读取真实工作区发布 1.0.0，`current_version_id` 正确 |
| 仅修改中文定义 | 系统建议 PATCH_ONLY |
| 新增可选扩展属性 | 系统建议 BACKWARD_COMPATIBLE |
| 删除在用属性 | 判为 BREAKING，必须有迁移计划 |
| 迁移未完成 | 候选版本保持 PREPARED/MIGRATING，不能激活 |
| 恢复到历史语义 | 生成恢复计划，执行后发布更高版本，记录 `restore_source_version_id` |
| 导出当前版本 | RDF 包含正确 `owl:versionIRI` 和 `owl:priorVersion` |
| 并发发布 | 只有一个成功，另一个返回版本号冲突或 revision 不一致 |
| 候选版本取消 | PREPARED → CANCELLED，工作区恢复 EDITABLE |
| 迁移作业取消 | 未处理批次取消，cursor_data 保留，工作区恢复 EDITABLE |
| 工程 IRI 配置后发布 | 版本 IRI 正确拼接为 `version_iri_base + version_number` |
| 已有 PUBLISHED 版本后修改 ontology_iri | 被拒绝 |
