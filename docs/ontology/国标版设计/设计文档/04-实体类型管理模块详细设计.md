# 实体类型管理模块详细设计

> 对应 PRD：§4.2 实体类型管理模块、§2.4 实体类型体系、§14.1 附录A.1元数据描述项、§7.1 数据库设计、§3.3 标准化治理策略
> 编写日期：2026-07-09

## 1. 领域定位

实体类型是本体建模的核心 Schema 层。国标第 6 章定义了 18 个核心实体类型（附录 B 详述），每个实体类型含 8 项元数据描述（附录 A.1）。PRD §3.1 将实体类型模块列为五大解耦模块之首，数据属性（定义域绑定实体类型）、对象属性（域/值域绑定实体类型）、实例（rdf:type 绑定实体类型）均依赖它。

本模块职责：

1. **实体类型 CRUD**：创建/查询/修改/删除实体类型，区分核心（内置）与扩展。
2. **继承层次管理**：维护 subClassOf 父子关系，支持多级继承树与多继承。
3. **抽象类标记**：标记抽象类（如相关方、信息单元），不可实例化。
4. **等价类展示与预留**：展示确有相同类扩展的 equivalentClass 关系；首期不预置核心等价类，写入口后续统一归公理模块。
5. **不相交类展示与预置**：预置并展示 disjointWith 关系（如规范性要素与资料性要素互斥），写入口后续统一归公理模块。
6. **核心预置**：开箱即用预置国标附录 B 全部实体类型及继承结构。
7. **校验**：IRI 唯一、名称唯一、继承无环、命名规范。

模块依赖链定位：

```text
namespace（命名空间/IRI）  ← ✅ 已完成
   ↑
entitytype（实体类型）      ← 本模块，被数据属性/对象属性/实例依赖
   ↑
dataproperty / objectproperty
   ↑
axiom → instance → validation / serialization
```

命名空间模块已落地（`ont_namespace` 表 + `OntNamespaceService`），实体类型通过 `namespace_id` 引用命名空间。

## 2. 数据模型

> 字段风格对齐 youming 实际落地规范（ont_ 前缀、char(1) 布尔、ASSIGN_ID 主键、审计字段）。PRD §7.1 使用原生 PG 风格（BIGSERIAL/BOOLEAN），本设计对齐已落地规范。

### 2.1 最小本体工程表 `ont_ontology_project`

为避免实体类型及后续数据属性、对象属性、公理长期处于无工程作用域状态，V6 同步建立最小本体工程表，首期只预置核心工程 `935001/core`。工程管理 UI 和完整生命周期后续开发，但 Schema 数据从首期开始携带 `ontology_id`。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | bigint | 是 | 工程 ID |
| `project_code` | varchar(64) | 是 | 工程编码，未删除数据唯一 |
| `project_name` | varchar(128) | 是 | 工程名称 |
| `is_builtin` | char(1) | 是 | 是否内置核心工程 |
| `description` | varchar(255) | 否 | 描述 |
| 审计/逻辑删除字段 | — | — | 与项目统一规范一致 |

首期所有实体类型默认归属核心工程 `ontology_id=935001`；后续工程模块上线后，API 再开放工程选择与隔离。

### 2.2 实体类型主表 `ont_entity_type`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | bigint | 是 | MyBatis-Plus `ASSIGN_ID` |
| `iri` | varchar(512) | 是 | 全局唯一 IRI，如 `http://example.org/standard-ontology#Standard` |
| `name` | varchar(128) | 是 | 英文名称（IRI 本地标识符），首字母大写，如 `Standard` |
| `definition` | varchar(512) | 否 | 定义（附录 A.1 描述项4） |
| `is_abstract` | char(1) | 是 | 是否抽象类，`1` 是 `0` 否；抽象类不可实例化 |
| `is_builtin` | char(1) | 是 | 是否内置（核心），`1` 核心 `0` 扩展 |
| `ontology_id` | bigint | 是 | 外键，指向 `ont_ontology_project.id`；首期默认 935001 |
| `namespace_id` | bigint | 是 | 外键，指向 `ont_namespace.id`；核心类型引用 std 命名空间 |
| `sort_order` | integer | 是 | 排序值 |
| `remarks` | varchar(255) | 否 | 备注 |
| `create_by` | varchar(64) | 否 | 创建人 |
| `create_time` | timestamp | 是 | 创建时间 |
| `update_by` | varchar(64) | 否 | 修改人 |
| `update_time` | timestamp | 否 | 更新时间 |
| `del_flag` | char(1) | 是 | 逻辑删除标志 |

约束：

1. `iri` 在未删除数据中全局唯一。
2. `name` 在 `(ontology_id, namespace_id)` 范围内唯一，不同命名空间允许相同本地名。
3. `ontology_id`、`namespace_id` 必须引用有效记录。
4. `iri` 必须严格等于 `namespace.uri + name`，由后端作为权威生成方。
5. 内置（核心）实体类型不可删除。
6. 内置实体类型语义字段锁定：`iri`、`name`、`is_abstract`、`is_builtin`、`ontology_id`、`namespace_id` 不允许通过接口改变；允许修改 `definition`、`sort_order`、`remarks`。

### 2.3 多语言标签 `ont_entity_type_label`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `entity_type_id` | bigint | 是 | 外键，指向 `ont_entity_type.id` |
| `locale` | varchar(16) | 是 | 语言区域，如 `zh`、`en` |
| `label` | varchar(128) | 是 | 标签文本（中文标签如 `标准实体`） |

主键：`(entity_type_id, locale)` 复合主键。

> 标签独立成表而非 JSON 列，便于按语言检索和后续国际化扩展。首期预置 `zh` 标签，后续按需补 `en`。

### 2.4 继承关系 `ont_entity_type_hierarchy`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `parent_id` | bigint | 是 | 父类实体类型 ID |
| `child_id` | bigint | 是 | 子类实体类型 ID |

主键：`(parent_id, child_id)` 复合主键。支持多继承（一个 child 可有多个 parent）。

> label/hierarchy/disjoint/equivalent 均通过外键引用实体类型，无 del_flag；实体类型物理清理时由数据库级联清理关系。

### 2.5 不相交类 `ont_entity_type_disjoint`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `type_a` | bigint | 是 | 实体类型 A |
| `type_b` | bigint | 是 | 实体类型 B |

主键：`(type_a, type_b)` 复合主键。存储时保证 `type_a < type_b` 避免重复。

> 首期建表，不相交关系的管理接口随公理规则模块（§4.5）上线后细化。本模块仅提供建表和数据查询能力。

### 2.6 等价类 `ont_entity_type_equivalent`

> PRD §7.1 缺失此表（附录 A.1 描述项8"等价类"引用了 `equivalent_class` 但未建表），本设计补建。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `entity_type_id` | bigint | 是 | 实体类型 ID |
| `equivalent_id` | bigint | 是 | 等价实体类型 ID |

主键：`(entity_type_id, equivalent_id)` 复合主键。等价关系按无向边单行规范化存储，保证 `entity_type_id < equivalent_id`；查询时同时匹配两列。

### 3.3 继承关系预置

通过 `ont_entity_type_hierarchy` 预置上述所有父子关系。每条记录的 parent_id 取"父类"列对应类型的 id。根节点（父类为"—"）不插入 hierarchy 记录。

### 3.4 Clause 多继承预置

Clause（940040）既是 StructuralElement 的子类，又是 InformationUnit 的子类，使用两条直接父类关系表达：

```text
ont_entity_type_hierarchy:
  (parent_id=940038 StructuralElement, child_id=940040 Clause)
  (parent_id=940048 InformationUnit, child_id=940040 Clause)
```

`owl:equivalentClass` 表示两个类具有相同实例集合，不能用于表达“双重父类归属”。首期 `ont_entity_type_equivalent` 无核心种子。

### 3.5 不相交类预置

```text
ont_entity_type_disjoint:
  (type_a=940028 NormativeElement, type_b=940034 InformativeElement)
```

> 规范性要素与资料性要素互斥（国标第 8.2 条实体类型不相交规则）。其余不相交关系随公理规则模块上线后补充。

## 4. 服务规则

### 4.1 新增实体类型

校验流程：

1. `name`、`label`、`namespaceId` 必填，`ontologyId` 缺省为核心工程 935001；`iri` 可省略。
2. `name` 格式：首字母大写驼峰，正则 `^[A-Z][a-zA-Z0-9]*$`。
3. 后端根据 `namespace.uri + name` 生成权威 IRI；若请求携带 iri，必须与生成值完全一致。
4. `iri` 在未删除数据中全局唯一。
5. `name` 在 `(ontology_id, namespace_id)` 范围内唯一。
6. ontologyId/namespaceId 必须引用有效记录；普通扩展接口不得向内置核心命名空间写入类型。
7. 若指定父类，每个父类必须存在、与 child 属于同一工程，并通过继承无环校验；parentIds 去重。
8. 新增数据固定 `is_builtin='0'`，`is_abstract` 缺省为 `'0'`。
9. 主表、zh 标签和父类关系在同一事务中保存。

### 4.2 修改实体类型

1. 若实体类型不存在，返回失败。
2. 若为内置类型，只更新 `definition`、`sort_order`、`remarks`、`labels`（非语义字段）。
3. 若为扩展类型，可更新 `name`、`definition`、`is_abstract`、`namespace_id`、`sort_order`、`remarks`、zh 标签和父类关系；`ontology_id` 首期锁定。
4. 修改 name 或 namespace 时由后端重新生成 IRI，并检查作用域唯一性。
5. 修改父类关系时重新执行**继承无环校验**。

### 4.3 删除实体类型

1. 内置实体类型禁止删除。
2. 删除前检查：
   - 有无子类（`ont_entity_type_hierarchy` 中作为 parent 被引用）。
   - 有无被等价类引用（`ont_entity_type_equivalent`）。
   - 有无被不相交类引用（`ont_entity_type_disjoint`）。
   - 后续数据属性/对象属性/实例模块上线后追加相应引用检查。
3. 存在引用时返回失败，提示引用数量。
4. 有阻断性引用时拒绝删除；无阻断引用时物理清理该类型作为 child 的父类边和标签，再逻辑删除主表。数据库外键负责防止后续物理清理产生孤儿。
5. 通过 MyBatis-Plus 逻辑删除更新主表 `del_flag`。

### 4.4 继承无环校验

基于可达性检测 parent 链无环：

1. 对每个候选 parent 向上遍历直接父类；若可达当前 child，拒绝操作。
2. parentIds 先去重并拒绝自身为父类。
3. 使用显式队列记录 `(node, depth)`，深度超过 100 时 fail-closed，返回“继承层次过深”，不得视为无环。
4. 树查询对已有脏环执行检测，发现后拒绝返回而非静默遗漏。

### 4.5 继承树查询

`GET /admin/ontology/entity-types/tree` 返回完整继承树：

1. 查询全部未删除实体类型。
2. 查询全部 `ont_entity_type_hierarchy` 记录。
3. 以无父类的类型为根节点，递归构建 `OntEntityTypeTreeNode` 树。
4. 多继承场景下，子节点在多个父节点下重复出现（树形展示）。
5. 支持按 `name`/`label` 前端过滤。

## 5. Clause 多继承建模方案

### 5.1 问题背景

Clause 在业务语义上同时属于标准结构层次和信息单元。

### 5.2 落地方案

- **父类一**：Clause `subClassOf` StructuralElement。
- **父类二**：Clause `subClassOf` InformationUnit。
- **禁止错误等价**：Clause 不与 InformationUnit 声明 equivalentClass，否则会把所有信息单元合并为 Clause。
- **直接边存储**：hierarchy 只保存上述两条直接边，不冗余保存祖先闭包。

### 5.3 前端展示

- Clause 在 StructuralElement 和 InformationUnit 两个父节点下各出现一次。
- 两个展示节点使用不同路径 key，但共享同一 `entityTypeId=940040`。
- 点击任一副本均展示同一实体类型详情。

## 7. 前端交互设计

### 7.1 页面结构

采用左树右表布局（splitpanes），与单位字典页面交互范式一致：

```text
实体类型管理页面
├── 左侧继承树面板
│   ├── 搜索框（按名称/标签过滤）
│   ├── 实体类型继承树（el-tree，支持展开/折叠）
│   └── 新增、刷新按钮
└── 右侧详情面板
    ├── 类型标题 + 核心/扩展标签 + 抽象类标签
    ├── 附录A.1 八项元数据展示
    │   ├── IRI
    │   ├── 名称（英文名）
    │   ├── 标签（多语言）
    │   ├── 定义
    │   ├── 属性集（占位，数据属性模块上线后填充）
    │   ├── 父类（列表）
    │   ├── 子类（列表）
    │   └── 等价类（列表）
    ├── 不相交类（列表）
    └── 操作栏：编辑、删除
```

### 7.2 新增/编辑弹窗

弹窗表单字段（label-width 120px）：

| 字段 | 控件 | 备注 |
|------|------|------|
| 命名空间 | el-select | options 来自 `fetchNamespaceList()`；内置编辑时 disabled |
| 英文名称 (name) | el-input | 内置编辑时 disabled；正则 `^[A-Z][a-zA-Z0-9]*$` |
| IRI | el-input | 内置编辑时 disabled；可由命名空间+名称自动拼接 |
| 中文标签 (label) | el-input | 多语言标签的 zh 条目 |
| 定义 (definition) | el-input textarea | maxlength 512 |
| 是否抽象类 | el-switch | active-value='1' inactive-value='0'；内置编辑时 disabled |
| 父类 | el-tree-select | 多选，可多继承；内置编辑时 disabled |
| 排序 | el-input-number | min 0 |
| 备注 | el-input textarea | maxlength 255 |

> `is_builtin`、`is_abstract`（内置类型）不在表单中展示。IRI 可提供"自动生成"按钮（调用 IRI 生成接口）。

### 7.3 内置保护交互

1. 核心实体类型显示蓝色"核心"标签 + 🔒 图标。
2. 抽象类显示橙色"抽象"标签。
3. 删除按钮对核心类型禁用，tooltip 提示"核心实体类型不可删除"。
4. 编辑核心类型时，`name`/`iri`/`is_abstract`/`namespace`/父类 置灰 disabled。

### 7.4 继承树交互

1. 树节点显示中文标签 + 英文名称（如 `标准实体 (Standard)`），多继承副本使用路径唯一 key。
2. 核心类型节点带 🔒 标记，抽象类节点带 `【抽象】`标记。
3. 点击节点加载右侧详情面板。
4. 支持按名称/标签前端过滤，过滤时自动展开匹配节点的父链。
5. 多继承节点在多个父节点下重复出现，业务操作使用 entityTypeId，树状态使用 path key。

## 9. 演进预留

1. **本体工程能力**：V6 已建立最小 `ont_ontology_project` 和 core 工程。后续补充工程 CRUD、选择器、权限和跨工程导入，不再改造实体类型主键作用域。
2. **数据属性引用**：后续数据属性模块通过 `ont_data_property.domain_entity_type_id` 引用 `ont_entity_type.id`。`GET /{id}/properties` 接口届时实现为查询 `domain_entity_type_id = {id}` 的数据属性列表（含继承的父类属性）。
3. **对象属性引用**：后续对象属性模块通过 `ont_object_property.domain_entity_type_id` / `range_entity_type_id` 引用 `ont_entity_type.id`。
4. **不相交类管理接口**：不相交关系的增删改接口随公理规则模块（§4.5）上线后细化，本模块仅提供建表和查询能力。
5. **等价类管理接口**：等价/不相交关系的写入口统一随公理规则模块上线；实体类型模块首期只展示，不预置错误的 Clause↔InformationUnit 等价记录。
6. **实例引用检查**：删除扩展实体类型前，后续实例模块上线后追加 `ont_entity_instance.rdf_type_iri` 引用检查。

## 10. 验收点

1. Flyway V6 能创建 6 张表（ontology_project + entity_type + label + hierarchy + disjoint + equivalent）、预置 1 个核心工程、86 条核心实体类型、72 条直接继承关系、Clause 双父类关系和不相交关系，并注册菜单与按钮权限。
2. 后端 Maven 编译通过。
3. 前端 TypeScript/Vite 构建通过。
4. 登录管理员后可在"本体建模 / 实体类型管理"看到页面，继承树展示完整的 86 个核心类型。
5. 核心类型不可删除、不可改语义字段（name/iri/is_abstract/namespace/父类）。
6. 可新增扩展实体类型（必须绑定扩展命名空间），继承无环校验生效（设 A 的父类为 B、B 的父类为 A 时被拒绝）。
7. Clause 在 StructuralElement 和 InformationUnit 下重复展示，详情中有两个直接父类且不存在错误等价类。
8. `GET /{id}/properties` 首期返回空列表（数据属性模块上线后填充）。
