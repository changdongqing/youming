## 0. 背景与动机

### 0.1 问题陈述

实体之间的关系是否有标准，决定了建模平台能否在关系创建环节从源头阻止错误数据和垃圾关系。结论是：**本平台已有一份国标关系字典（`ont_object_property` 表 35 条预置对象属性 + `ont_axiom_rule` 表 5 条 RELATION 类规则），但它只表达了"谓词的语义声明"，没有表达"推理引擎对这个谓词实际做什么"**。

这导致三类灰色地带：

| 现象 | 根因 | 后果 |
|------|------|------|
| 用户能标 `is_transitive='1'` / `is_symmetric='1'`，但引擎不会据此推出新三元组 | `ReasonerCapability` 有 6 个值，`JenaReasonerAdapter` 只实现 3 个；`inferEntailments()` 直接抛 `UnsupportedOperationException` | 用户以为标记即推理，实际是死标记，数据语义与预期不符 |
| `source_type='EXTENSION'` 的自定义关系可随意新增，无"引擎是否支持"标记 | `ont_object_property` 无推理能力声明列；执行器里 `binding_role`/`subType` 全是硬编码字符串 | 关键业务约束挂在引擎根本不处理的自定义谓词上，校验形同虚设 |
| 关系类型字典（`ont_object_property`）与规则字典（`ont_axiom_rule`）未显式关联 | 两张表只通过 `ont_axiom_rule_target.object_property_id` 间接绑定，前端选择关系时看不到"用了它引擎会做什么" | 建模者无从判断谓词的推理后果，只能凭名称直觉选择 |

### 0.2 设计目标

将现有"数据字典"升级为"能力契约字典"——在**不破坏现有数据模型、不另起炉灶建 `relation_dict` 表**的前提下，补上一层"关系类型 ↔ 推理引擎能力"的显式声明，使：

1. 前端在关系创建/选择环节，能对每个谓词展示"引擎实际支持的能力"与"仅声明但不推理的能力"；
2. 后端在校验与序列化时，能按"能力契约"决定是否真正执行推理/校验，而非盲目信任 Schema 标记；
3. 扩展关系（`source_type='EXTENSION'`）必须在创建时声明推理能力，空声明即标记为"非推理托管"，从源头区分"受推理保护"与"不受推理保护"的关系。

### 0.3 与前置模块的边界

| 能力 | 前置模块（已完成） | 本模块（关系能力契约） |
|------|-------------------|----------------------|
| 关系类型定义（谓词 CRUD、域/值域、OWL 特性标记） | 对象属性模块（06）负责 | 只读引用，新增能力声明列 |
| 公理规则配置（CRUD/启停/目标绑定） | 公理规则模块（07）负责 | 只读引用，补强规则↔能力关联 |
| 实例写入即时校验 | 实体实例模块（08）负责 | 提供能力契约供其复用，不干预写入路径 |
| 校验引擎执行与推理 | 校验引擎模块（09）负责 | 提供能力契约作为执行器路由的权威依据 |
| 推理引擎 SPI 适配 | 校验引擎模块（09）的 `ReasonerAdapter` | 本模块定义能力枚举的权威来源，09 模块引用 |

本模块**不新增独立的推理引擎或校验执行器**，而是在现有 09 模块的 `ReasonerCapability` 枚举与 `ont_object_property` 表之间建立显式契约层。

## 1. 评审结论与设计边界

### 1.1 现状评审

截至本设计时点，对象属性模块（V8）、公理规则模块（V9）、实体实例模块（V10）、校验引擎模块（09 设计文档 + 代码实现）均已落地。但关系类型与推理引擎之间存在以下缺口：

| 缺口 | 现状 | 影响 |
|------|------|------|
| **推理能力与声明能力不对等** | `ReasonerCapability` 枚举 6 个值（DISJOINT_CHECK/FUNCTIONAL_CHECK/TRANSITIVE_INFERENCE/SYMMETRIC_INFERENCE/SUBCLASS_INFERENCE/CUSTOM_RULE_INFERENCE），`JenaReasonerAdapter.getReasonerCapabilities()` 只声明 3 个（DISJOINT_CHECK/FUNCTIONAL_CHECK/SUBCLASS_INFERENCE），`inferEntailments()` 抛异常 | Schema 允许标 `is_transitive/is_symmetric='1'`，但引擎不会据此推理，用户产生错误预期 |
| **关系类型无能力声明列** | `ont_object_property` 只有四个 OWL 特性标记（`is_functional` 等），无"引擎实际支持哪些能力"的声明 | 前端选择关系时无法展示推理后果，扩展关系尤其严重 |
| **规则↔能力关联隐式** | `ont_axiom_rule.category='RELATION'` 的 5 条规则（970008-970012）通过 `executor_code` + `validation_mode` 间接表达能力，但 `binding_role`（RELATION_PROPERTY/STANDARD_CLASS/...）和 `sub_type`（FUNCTIONAL/REFERENCE_DISTINCTION/HIERARCHY_CONTAINMENT/STRUCTURAL_LIMIT/VERSION_REPLACEMENT）全是硬编码字符串，散落在 `ObjectRelationRangeExecutor`、`FunctionalObjectPropertyExecutor` 等执行器中。`binding_role`（V9:104）和 `sub_type`（V9:12）均**无 CHECK 约束**，取值不受数据库约束 | 无集中定义，拼错无人发现，新增规则时易漏校验 |
| **可视化 edgeType 接近枚举但未契约化** | `GraphEdgeVO.edgeType` 注释声明 6 个取值，但代码中实际赋值只有 5 个（`INSTANCE_OF` 无赋值点），是全仓库唯一接近"关系类型枚举"的 Java 侧定义 | 仅用于可视化展示，未与推理能力对齐，不能作为能力契约来源 |

### 1.2 优化结论

| 级别 | 评审发现 | 优化结论 |
|------|----------|----------|
| P0 | 关系类型字典（`ont_object_property`）与推理引擎能力（`ReasonerCapability`）无显式关联，用户无法在选择关系时判断推理后果 | 在 `ont_object_property` 主表新增 `inference_support` 列，声明该谓词被引擎实际支持的能力子集；前端选择关系时展示能力契约 |
| P0 | `ReasonerCapability` 枚举有 6 个值但实现只支持 3 个，差距未在数据层体现 | 能力枚举保持不变（它是引擎 SPI 的能力声明），但在 `inference_support` 列中只允许填写"引擎实际实现"的能力子集，由 Flyway 种子数据固化 |
| P1 | `binding_role`、`sub_type` 在数据库层无 CHECK 约束（V9:104、V9:12），取值不受数据库保护；`object_kind`（V10:144）和 `assertion_origin`（V22:1075）虽有 CHECK 但 Java 侧仍用裸字符串硬编码 | 提取为 Java 枚举/常量类（`BindingRole`、`RelationSubType`、`ObjectKind`、`AssertionOrigin`），执行器和 SQL 种子引用同一常量 |
| P1 | `source_type='EXTENSION'` 的自定义关系无推理能力声明要求 | 扩展关系创建时 `inference_support` 可空，空即标记为"非推理托管"；前端显著提示，避免用户把关键约束挂在不受推理保护的谓词上 |
| P2 | `GraphEdgeVO.edgeType` 注释声明 6 个取值但实际赋值仅 5 个（`INSTANCE_OF` 无赋值点），未契约化 | 收口为 `GraphEdgeType` 常量类（仅含实际使用的 5 个取值），与能力契约分层：edgeType 描述"图上边的种类"，inference_support 描述"引擎对谓词做什么"，二者正交 |

### 1.3 本期范围

**本期包含：**

1. `ont_object_property` 主表新增 `inference_support` 列（`jsonb`），声明谓词被引擎实际支持的能力子集
2. Flyway V27 迁移脚本：`ALTER TABLE` 加列 + 35 条预置关系的 `inference_support` 种子数据 + 完整性断言
3. Java 枚举收口：`BindingRole`、`RelationSubType`、`ObjectKind`、`AssertionOrigin`、`GraphEdgeType` 常量类
4. 对象属性详情 VO 增加 `inferenceSupport` 字段，供前端展示能力契约
5. 对象属性分页/列表查询支持按 `inferenceSupport` 过滤
6. 扩展关系创建时的能力声明引导（DTO 增加可选 `inferenceSupport` 字段，Service 校验取值合法性）
7. 校验引擎执行器路由优化：`ObjectRelationRangeExecutor`、`FunctionalObjectPropertyExecutor` 等执行器从 `inference_support` 读取能力契约，与硬编码 `sub_type`/`binding_role` 双轨校验（过渡期保留硬编码，后续收口）
8. 前端关系选择器增加能力契约展示组件

**本期不包含：**

- 新增推理引擎实现或启用 `inferEntailments()`（大规模图谱推理仍由 09 模块定义为"本期未启用"）
- 新增 RELATION 类公理规则（仍由 07 模块管理）
- 修改现有 35 条预置关系的域/值域/OWL 特性标记（仍由 06 模块管理）
- 引入 Triplestore 或图数据库（仍以关系库为唯一事实源）
- 全量替换执行器中的硬编码字符串（过渡期双轨，后续单独收口）

### 1.4 权威语义口径

1. **能力枚举的权威来源是 `ReasonerCapability`**（09 模块定义的 SPI 枚举），`inference_support` 列的取值受该枚举约束。本模块不新增能力枚举值。
2. **`inference_support` 表示"引擎实际做什么"，不是"Schema 声明了什么"**。例如 `hasPart`（960005）Schema 层未标传递性（`is_transitive='0'`，依据 06 模块 §1.1"不从名称推断"），故 `inference_support` 为空数组；`issuedBy`（960006）标了功能性且引擎真的做功能属性唯一性校验，故 `inference_support` 含 `FUNCTIONAL_CHECK`。
3. **声明 ≠ 推理**。`is_transitive='1'` 是 Schema 层的显式声明，但如果 `inference_support` 不含 `TRANSITIVE_INFERENCE`，则引擎不会做传递闭包推理。二者分开表达，前者是"本体语义声明"，后者是"引擎执行契约"。
4. **能力契约是只读消费者视角的契约**。`inference_support` 由平台治理方（Flyway 种子 + 管理员维护）声明，校验引擎和序列化模块只读引用，不回写。
5. **扩展关系的空声明是合法的**。`source_type='EXTENSION'` 的关系 `inference_support` 可为空数组，表示"非推理托管"，前端显著提示，不阻止创建。

## 2. 领域模型与能力契约语义

### 2.1 三层关系语义模型

平台的关系语义分为三层，本模块补全第三层：

| 层次 | 表达内容 | 载体 | 例子 |
|------|---------|------|------|
| **L1 谓词字典层** | 有哪些关系类型可用 | `ont_object_property`（35 条预置 + 扩展） | `issuedBy`、`hasPart`、`cites` |
| **L2 本体声明层** | 谓词的 OWL 语义特性（声明性） | `ont_object_property.is_functional/is_inverse_functional/is_transitive/is_symmetric/inverse_of_id` | `issuedBy.is_functional='1'` |
| **L3 引擎契约层（本模块）** | 推理引擎对谓词实际执行哪些能力 | `ont_object_property.inference_support`（新增） | `issuedBy.inference_support = ['FUNCTIONAL_CHECK']` |

L2 与 L3 的关系：

- L2 声明是"本体作者声称这个谓词有什么语义特性"；
- L3 契约是"推理引擎实际能对这个谓词做什么"；
- **L3 必须是 L2 的子集**：引擎不能对未声明传递性的谓词做传递推理；但 L2 声明了的能力，L3 可以不实现（如传递性声明了但引擎不推理）。

### 2.3 能力枚举与引擎实现的对照

| `ReasonerCapability` | `JenaReasonerAdapter` 是否实现 | 可填入 `inference_support` | 说明 |
|----------------------|------------------------------|---------------------------|------|
| `DISJOINT_CHECK` | ✓（`checkConsistency` 内） | ✓ | 不相交冲突检测，由 `EntityDisjointExecutor`（970001）调用 |
| `FUNCTIONAL_CHECK` | ✓（声明但走 Java 计数） | ✓ | 功能属性唯一性，由 `FunctionalObjectPropertyExecutor`（970008）调用，实际是 Java 计数非 Jena 推理 |
| `SUBCLASS_INFERENCE` | ✓（声明） | ✓（预留） | 子类层次推理，本期无规则使用，预留 |
| `TRANSITIVE_INFERENCE` | ✗（未实现） | ✗ | 传递闭包推理，`inferEntailments` 抛异常 |
| `SYMMETRIC_INFERENCE` | ✗（未实现） | ✗ | 对称推理，同上 |
| `CUSTOM_RULE_INFERENCE` | ✗（未实现） | ✗ | 自定义规则推理，同上 |

**约束**：`inference_support` 只能填写"引擎已实现"的能力（前 3 个）。后 3 个能力在 `inferEntailments` 启用前不得填入，由 Service 层校验拒绝。

### 2.4 RELATION 类公理规则与能力契约的映射

07 模块预置的 5 条 RELATION 类规则（970008-970012）与能力契约的映射关系：

| 规则 ID | rule_code | sub_type | validation_mode | executor_code | 关联谓词 | 对应能力契约 |
|---------|-----------|----------|-----------------|---------------|---------|-------------|
| 970008 | GB8_ISSUED_BY_FUNCTIONAL | FUNCTIONAL | COMPOSITE | FUNCTIONAL_OBJECT_PROPERTY | issuedBy(960006) | `FUNCTIONAL_CHECK` |
| 970009 | GB8_VERSION_REPLACEMENT | VERSION_REPLACEMENT | SHACL_SPARQL | NULL（BLOCKED） | replaces/isReplacedBy | 无（规则阻塞） |
| 970010 | GB8_HIERARCHY_CONTAINMENT | HIERARCHY_CONTAINMENT | APPLICATION | OBJECT_RELATION_RANGE | hasClause(960015) | 无（APPLICATION 规则，非推理） |
| 970011 | GB8_UNTITLED_NO_SUBCLAUSE | STRUCTURAL_LIMIT | SHACL_CORE | MAX_RELATION_COUNT | hasSubClause(960016) | 无（SHACL 约束，非推理） |
| 970012 | GB8_REFERENCE_DISTINCTION | REFERENCE_DISTINCTION | APPLICATION | OBJECT_RELATION_RANGE | cites/citesStandard | 无（APPLICATION 规则，非推理） |

**结论**：5 条 RELATION 类规则中，只有 970008 对应 `FUNCTIONAL_CHECK` 能力契约；其余 4 条是 APPLICATION/SHACL 校验规则，不属于推理引擎能力范畴。这印证了"能力契约"与"校验规则"是两个正交维度——前者描述推理引擎对谓词做什么，后者描述校验引擎对实例数据做什么。

## 3. 数据模型

> 对齐现有实现：PostgreSQL、`ont_` 前缀、Flyway 增量迁移。已应用的 V1～V26 禁止修改，新增 V27。

### 3.1 主表 `ont_object_property` 扩展

在现有主表基础上增加一列：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `inference_support` | jsonb | 否 | 推理引擎实际支持的能力子集，取值受 `ReasonerCapability` 枚举约束；空数组 `[]` 表示"非推理托管" |

> 存储方案选择 **jsonb** 而非 PostgreSQL 原生 `varchar[]`，理由：
> 1. 与仓库现有 jsonb 列处理方式一致（见 commit `fix(ontology): 系统性补全11个实体的jsonb列StringToJsonbTypeHandler`）；
> 2. 现有 `StringToJsonbTypeHandler` 处理 `String`→jsonb，但**不支持 `List<String>`**，需新增 `StringListToJsonbTypeHandler`（见 §7.2）；
> 3. jsonb 的 `@>` 包含查询和 GIN 索引天然支持"按能力过滤"场景。

**为什么不新建关联表**：

- 一个谓词的能力契约是"扁平标签集合"，不是多实体关联，用数组比关联表更轻量；
- 能力枚举只有 6 个值（且本期只允许填 3 个），数组完全够用；
- 避免引入 `ont_object_property_capability` 关联表带来的 JOIN 开销和治理复杂度。

**为什么不复用 `is_functional` 等 char(1) 列**：

- 那些列是 L2 本体声明层标记，语义是"本体作者声明此谓词有此特性"；
- `inference_support` 是 L3 引擎契约层声明，语义是"引擎实际对此谓词执行此能力"；
- 二者语义不同，必须分开（L3 必须是 L2 的子集，但不能替代 L2）。

### 3.2 约束设计

#### 3.2.1 数据库层约束

`inference_support` 的取值合法性无法用普通 CHECK 约束完整表达（jsonb 数组元素需受枚举约束），由以下三层保证：

1. **Service 层校验**：新增/修改对象属性时，`inference_support` 的每个元素必须属于 `ReasonerCapability` 枚举的"已实现子集"（DISJOINT_CHECK/FUNCTIONAL_CHECK/SUBCLASS_INFERENCE）；
2. **Flyway 种子数据**：35 条预置关系的 `inference_support` 由 V27 脚本固化，完整性断言校验；
3. **数据库 CHECK（jsonb 格式约束）**：

```sql
-- inference_support 必须是数组形式（空数组或字符串数组）
ALTER TABLE ont_object_property
  ADD CONSTRAINT ck_ont_object_property_inference_support
  CHECK (
    inference_support IS NULL
    OR jsonb_typeof(inference_support::jsonb) = 'array'
  );
```

完整的"元素必须属于已实现子集"约束由 Service 层执行（数据库 CHECK 无法表达 jsonb 数组元素属于动态子集）。

> 注意：现有 `ont_object_property` 表已有以下 CHECK 约束（V8 定义，不修改）：
> - `ck_ont_object_property_source_type`（V8:34）：`source_type IN ('GB_TABLE1','GB_TABLE1_DERIVED','EXTENSION')`
> - `ck_ont_object_property_source_builtin`（V8:43-46）：`source_type` 与 `is_builtin` 的组合约束
> - `ck_ont_object_property_transitive_func`（V8:47-49）：传递属性不能同时为功能性或反功能性
>
> 本期新增的 `inference_support` 列和 CHECK 约束不修改上述已有约束。

#### 3.2.2 L3 ⊆ L2 约束

`inference_support` 必须是 L2 声明能力的子集：

| L3 能力 | 前置的 L2 声明 |
|---------|---------------|
| `FUNCTIONAL_CHECK` | `is_functional='1'` |
| `DISJOINT_CHECK` | （无前置，不相交检测针对实体类型而非谓词特性，但谓词可被不相交规则引用） |
| `SUBCLASS_INFERENCE` | （无前置，子类推理针对实体类型层次） |
| `TRANSITIVE_INFERENCE` | `is_transitive='1'`（本期不允许填 L3） |
| `SYMMETRIC_INFERENCE` | `is_symmetric='1'`（本期不允许填 L3） |

Service 层校验：填入 `FUNCTIONAL_CHECK` 时必须 `is_functional='1'`；否则拒绝。

### 3.3 扩展关系的空声明语义

`source_type='EXTENSION'` 的扩展关系：

- `inference_support` 可为空数组 `[]`，表示"非推理托管"——引擎不对此谓词做任何推理/校验；
- 前端在关系选择器中对空声明的关系显著标记"⚠️ 非推理托管"；
- 仍可正常创建实例关系断言，域/值域校验（08 模块即时校验）不受影响；
- 若扩展关系想声明推理能力，必须同时设置对应的 L2 特性标记（如想声明 `FUNCTIONAL_CHECK`，必须先设 `is_functional='1'`）。

## 5. 服务规则

### 5.1 新增扩展对象属性的能力声明

1. `inferenceSupport` 为可选字段，缺省为空数组 `[]`；
2. 若提供，每个元素必须属于 `ReasonerCapability` 的"已实现子集"（DISJOINT_CHECK/FUNCTIONAL_CHECK/SUBCLASS_INFERENCE），否则拒绝并返回"本期未启用的推理能力：{value}"；
3. 填入 `FUNCTIONAL_CHECK` 时，必须同时设 `isFunctional='1'`（L3 ⊆ L2 约束），否则拒绝；
4. 填入 `DISJOINT_CHECK`/`SUBCLASS_INFERENCE` 时无 L2 前置要求（这两种能力针对实体类型层次，不要求谓词特性标记）；
5. 内置属性（`is_builtin='1'`）的 `inferenceSupport` 由 Flyway 管理，普通接口不允许修改。

### 5.2 修改扩展对象属性

1. 扩展属性可修改 `inferenceSupport`，按 §5.1 校验；
2. 修改 `isFunctional` 从 `'1'` 改为 `'0'` 时，若 `inferenceSupport` 含 `FUNCTIONAL_CHECK`，必须同时移除该能力，否则拒绝（L3 ⊆ L2 约束）；
3. 内置属性仅允许修改 `sortOrder/remarks`（与 06 模块一致），`inferenceSupport` 不可修改。

### 5.3 查询

1. 对象属性详情 VO（`OntObjectPropertyDetailVO`）增加 `inferenceSupport: List<String>` 字段；
2. 对象属性摘要 VO（`OntObjectPropertySummaryVO`）增加 `inferenceSupport: List<String>` 字段，供列表展示能力契约标签；
3. 分页查询支持按 `inferenceSupport` 过滤（如"只看有推理能力的关系"或"只看非推理托管的关系"），使用 PostgreSQL jsonb 包含查询 `@>`；
4. 新增"能力契约查询"接口：`GET /ontology/object-properties/by-capability/{capability}`，返回声明了指定能力的关系列表，供校验引擎和前端选择器调用。

### 5.4 校验引擎路由优化（过渡期双轨）

1. 过渡期保留执行器中的硬编码 `sub_type`/`binding_role`，确保现有校验逻辑不回归；
2. `ObjectRelationRangeExecutor`、`FunctionalObjectPropertyExecutor` 等执行器在执行前，先读取谓词的 `inference_support`：
   - 若谓词未声明对应能力（如功能属性校验但 `inference_support` 不含 `FUNCTIONAL_CHECK`），记录 WARNING 级提示"谓词 {name} 未声明能力契约 {capability}，校验结果仅供参考"；
   - 若声明了，正常执行；
3. 后续单独收口（本期不做）：将硬编码 `sub_type`/`binding_role` 全部替换为引用 `BindingRole`/`RelationSubType` 枚举常量。

### 5.5 即时校验联动

08 模块的 `OntEntityInstanceServiceImpl.validateRelation()` 保持不变，但可复用能力契约：

1. 功能性校验（`is_functional='1'` 时至多一条断言）逻辑不变，但若 `inference_support` 含 `FUNCTIONAL_CHECK`，在违规提示中增加"该谓词受推理引擎功能属性契约保护"的说明；
2. 域/值域校验逻辑不变，能力契约不影响即时校验；
3. 本模块不修改 `validateRelation()` 的签名和返回值，只在提示文案层增强。

### 7.5 Service 层校验

`OntObjectPropertyServiceImpl` 新增私有方法：

```java
/**
 * 校验推理能力契约的合法性。
 * - 每个元素必须属于 ReasonerCapability 的已实现子集
 * - L3 必须是 L2 的子集（如 FUNCTIONAL_CHECK 要求 is_functional='1'）
 */
private String validateInferenceSupport(List<String> inferenceSupport,
        String isFunctional, String isTransitive, String isSymmetric) {
    if (CollectionUtils.isEmpty(inferenceSupport)) {
        return null;  // 空声明合法
    }
    Set<String> implemented = Set.of(
        "DISJOINT_CHECK", "FUNCTIONAL_CHECK", "SUBCLASS_INFERENCE"
    );
    for (String cap : inferenceSupport) {
        if (!implemented.contains(cap)) {
            return "本期未启用的推理能力：" + cap;
        }
    }
    // L3 ⊆ L2 约束
    if (inferenceSupport.contains("FUNCTIONAL_CHECK") && !"1".equals(isFunctional)) {
        return "声明 FUNCTIONAL_CHECK 需先设置 isFunctional='1'";
    }
    return null;
}
```

## 13. 迁移路线（本期之后）

本模块是"关系能力契约"的第一期，后续演进路线：

| 阶段 | 内容 | 前置条件 |
|------|------|---------|
| 第二期 | 启用 `inferEntailments()` 传递/对称推理 | `jena-core`/`jena-shacl` 性能压测通过 |

| 第四期 | 扩展关系能力声明审批流程 | 扩展管理模块（11）落地 |
| 第五期 | 自定义规则推理（`CUSTOM_RULE_INFERENCE`） | SPARQL 规则编辑器落地 |

每期演进都通过新 Flyway 脚本填充对应谓词的 `inference_support`，不修改已应用脚本（checksum 校验）。
