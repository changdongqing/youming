# 组织账号扩展本体与UPMS映射详细设计

> 模块：18 数据源映射  
> 功能编号：18-09  
> 首个自举场景：youming UPMS用户、部门、岗位  
> 设计日期：2026-07-14

## 1. 目标

用当前系统真实的`sys_user/sys_dept/sys_post/sys_user_dept/sys_user_post`验证模块18的实体、字段、关系、增量、删除、安全、SPARQL和可视化能力，同时建立与物理表解耦的组织账号扩展本体。

## 2. 建模结论

### 2.1 UserAccount不等于Person

`sys_user`表示平台账号，包含登录名、认证状态和部分联系人信息，不足以证明其等同于现实世界自然人。因此：

- V1建模为`UserAccount`；
- 不创建`Person owl:sameAs UserAccount`；
- 后续接入HR主数据时增加`Person --hasAccount--> UserAccount`；
- 不从账号姓名推断自然人唯一身份。

### 2.2 Position不等于RBAC Role

`sys_post`是岗位，`sys_role`是系统授权角色，两者语义不同：

- `Position`用于组织职责和任职；
- RBAC Role暂不进入本场景；
- 不建立`Position equivalentClass Role`；
- 用户岗位关系来自`sys_user_post`。

### 2.3 不推断岗位属于部门

当前源模型没有`post_id/dept_id`直接关系。不能因为某部门用户拥有某岗位就推断岗位属于该部门。若后续需要，应引入权威岗位编制数据源。

## 4. 实体类型

| ID | IRI本地名 | 抽象 | 父类 | 定义 |
|---|---|---|---|---|
| 942001 | OrganizationDomainEntity | 是 | Object(940063) | 组织账号领域抽象对象 |
| 942002 | UserAccount | 否 | 942001 | 可用于登录或被系统识别的平台账号 |
| 942003 | OrganizationalUnit | 否 | 942001 | 部门、机构等组织单元 |
| 942004 | Position | 否 | 942001 | 可分配给账号/人员的岗位 |

不直接继承核心`Stakeholder`，因为账号不等于相关方。后续若定义Organization/Person，可通过更精确子类或对象关系扩展。

中文标签：

```text
OrganizationDomainEntity → 组织账号领域对象
UserAccount → 用户账号
OrganizationalUnit → 组织单元
Position → 岗位
```

实体类型及层次需加入`ont_extension_resource`，归属扩展模块939002。

### 5.1 枚举

`externalSystem`：

```text
YOU_MING_UPMS
```

`accountStatus`：

```text
ACTIVE
LOCKED
```

`lifecycleStatus`：

```text
ACTIVE
INACTIVE
```

源`del_flag`不映射为账号锁定状态，而用于`lifecycleStatus`失活检测。`password_expire_flag`首期不映射。

### 5.2 唯一性

- `username.is_unique=1`；
- `positionCode.is_unique=1`；
- `externalId.is_unique=0`，因为用户ID、部门ID和岗位ID可能重复；
- 来源绑定提供`映射工程+实体映射码+源主键`唯一身份。

### 5.3 DATETIME前置

V22必须按18-04扩展：

- 实例字面量类型；
- Java枚举/DTO；
- 校验器；
- RDF序列化`xsd:dateTime`；
- 前端日期时间展示。

该改造是V23前置，不设置降级为字符串的实现分支。

## 6. 对象属性

| ID | name | domain | range | 功能性 | 来源 |
|---|---|---|---|---|---|
| 962001 | parentOrganizationUnit | OrganizationalUnit | OrganizationalUnit | 是 | `sys_dept.parent_id` |
| 962002 | primaryDepartment | UserAccount | OrganizationalUnit | 是 | `sys_user.dept_id` |
| 962003 | memberOfDepartment | UserAccount | OrganizationalUnit | 否 | `sys_user_dept` |
| 962004 | assignedPosition | UserAccount | Position | 否 | `sys_user_post` |

说明：

- `primaryDepartment`可同时视为`memberOfDepartment`的更具体语义，但V1不自动推理或物化超属性关系；
- 如果希望主部门也出现在memberOf查询，可在SPARQL模板使用UNION，或后续增加subPropertyOf能力；
- 不配置inverseOf自动落库；
- 根部门`parent_id=0/NULL`不创建父关系。

## 7. UPMS源表映射

### 7.1 部门实体映射

```yaml
mappingCode: DEPARTMENT
source: public.sys_dept
keyColumns: [dept_id]
targetEntityType: OrganizationalUnit
iriTemplate: organization/{dept_id|url}
labelTemplate: "{name}"
filter: null  # 删除行必须可见，由sourceDeleteFlagColumn处理
incrementalColumn: update_time
sourceDeleteFlagColumn: del_flag
sourceDeleteValues: ['1']
deleteStrategy: MARK_INACTIVE
syncOrder: 10
```

字段：

| 源列 | 目标属性 | 转换 |
|---|---|---|
| 常量YOU_MING_UPMS | externalSystem | `source_kind=CONSTANT` |
| dept_id | externalId | TO_STRING |
| name | organizationName | TRIM |
| sort_order | organizationSortOrder | TO_INTEGER |
| create_time | createdAt | DATETIME |
| update_time | updatedAt | DATETIME，NULL→SKIP |
| 常量ACTIVE | lifecycleStatus | `source_kind=CONSTANT` |

> 18-04已将字段来源定义为`COLUMN/CONSTANT`。常量仍不得保存凭证、Token或环境密钥。

### 7.2 岗位实体映射

```text

```

```text

```

## 8. 关系映射

### 8.1 部门父子

```yaml
mappingCode: DEPARTMENT_PARENT
mode: SELF_REFERENCE
source: public.sys_dept
subject: DEPARTMENT.dept_id <- source.dept_id
object: DEPARTMENT.dept_id <- source.parent_id
property: parentOrganizationUnit
filter: del_flag='0' AND parent_id IS NOT NULL AND parent_id>0
missingTargetPolicy: PENDING
syncOrder: 100
```

### 8.2 主部门

```yaml
mappingCode: USER_PRIMARY_DEPARTMENT
mode: FOREIGN_KEY
source: public.sys_user
subject: USER_ACCOUNT.user_id <- source.user_id
object: DEPARTMENT.dept_id <- source.dept_id
property: primaryDepartment
filter: del_flag='0' AND dept_id IS NOT NULL AND dept_id>0
missingTargetPolicy: PENDING
syncOrder: 110
```

### 8.3 多部门

```yaml
mappingCode: USER_DEPARTMENT
mode: JOIN_TABLE
source: public.sys_user_dept
relationKeyColumns: [user_id, dept_id]
subject: USER_ACCOUNT.user_id <- source.user_id
object: DEPARTMENT.dept_id <- source.dept_id
property: memberOfDepartment
missingTargetPolicy: PENDING
deleteStrategy: REMOVE_ASSERTION
syncOrder: 120
```

### 8.4 用户岗位

```yaml
mappingCode: USER_POSITION
mode: JOIN_TABLE
source: public.sys_user_post
relationKeyColumns: [user_id, post_id]
subject: USER_ACCOUNT.user_id <- source.user_id
object: POSITION.post_id <- source.post_id
property: assignedPosition
missingTargetPolicy: PENDING
deleteStrategy: REMOVE_ASSERTION
syncOrder: 130
```

中间表没有`update_time/del_flag`，INCREMENTAL无法发现物理删除，因此：

- 首期计划任务可对两个小关联表执行周期FULL关系扫描；
- 或每次实体增量后执行关系FULL；
- 发布校验必须提示删除检测限制；
- 不得声称纯INCREMENTAL可以可靠移除关联。

## 9. 失活策略

每个实体映射使用954017 `lifecycleStatus`：

```text
inactivePropertyId=954017
inactiveLiteralValue=INACTIVE
```

正常摄入时通过常量字段映射写`ACTIVE`；源删除或连续FULL未见时由删除策略改写为`INACTIVE`，不立即删除实例。

`accountStatus`只表达账号锁定状态，不承担源记录删除语义。

## 10. 映射模板交付

V23不插入环境相关`ont_data_source`或映射版本记录，不保存本机数据库密码。交付类路径模板：

```text
server/pig-ontology/pig-ontology-biz/src/main/resources/mapping-templates/upms-organization-v1.json
```

前端“从模板创建”流程：

1. 用户选择已配置数据源；
2. 系统校验存在所需5张表和列；
3. 创建DRAFT映射工程；
4. 将模板中的逻辑目标ID/代码解析为V23种子资源；
5. 用户预览、校验并发布；
6. 不自动执行FULL，需用户确认。

## 11. SPARQL验收查询

### 11.1 用户主部门

```sparql
SELECT ?account ?accountLabel ?department ?departmentLabel
WHERE {
  ?account a ymorg:UserAccount ;
           rdfs:label ?accountLabel ;
           ymorg:primaryDepartment ?department .
  OPTIONAL { ?department rdfs:label ?departmentLabel }
}
```

实际导出模型是否将UI label输出为`rdfs:label`按模块10策略；若不输出，查询改用`ymorg:displayName/organizationName`。

### 11.2 部门层级

```sparql
SELECT ?child ?parent
WHERE {
  ?child a ymorg:OrganizationalUnit ;
         ymorg:parentOrganizationUnit ?parent .
}
```

### 11.3 用户岗位

```sparql
SELECT ?account ?position
WHERE {
  ?account a ymorg:UserAccount ;
           ymorg:assignedPosition ?position .
}
```

## 12. 可视化验收

图谱中应呈现：

```text
OrganizationalUnit层级树
UserAccount → primaryDepartment
UserAccount → memberOfDepartment
UserAccount → assignedPosition
```

手机号、邮箱默认不在图谱节点详情显示明文；无权限时MASK/DENY。

## 13. V23迁移内容

- 命名空间930200；
- 扩展模块939002；
- 实体类型942001～942004及标签/层次；
- 数据属性954001～954017及标签/枚举；
- 对象属性962001～962004及domain/range；
- `ont_extension_resource`资源关联；
- 不插入业务实例；
- 不插入数据源密码；
- 不自动创建/发布映射版本。

若V22后因实现修正已占用V23，组织种子顺延到下一个Flyway版本，禁止回改已应用V22。

## 14. 测试与验收

1. V23幂等迁移且所有IRI唯一；
2. 实体层次和对象属性domain/range正确；
3. email/phone安全级别CONFIDENTIAL；
4. 模板不包含password/salt/OpenID映射；
5. 全量同步实例数与源有效记录数一致；
6. 重跑不重复；
7. 用户名称修改更新原IRI实例；
8. 部门父子、主部门、多部门、岗位关系正确；
9. 关联表删除在FULL关系扫描后移除来源断言；
10. 源逻辑删除映射为lifecycleStatus=INACTIVE；
11. SPARQL查询能返回预期关系；
12. 图谱和导出不泄漏敏感明文；
13. `sys_user`不能被错误声明为Person；
14. 不生成无来源依据的岗位—部门关系。
