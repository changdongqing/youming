## 1. 评审结论

### 1.1 结论

安全与合规必须在 IoT 接入和下行控制前落地，但本模块的目标应表述为“提供可验证的技术控制”，不能声称仅靠若干表和 AOP 即“满足等保、数据安全法或个人信息保护法”。最终合规仍依赖组织制度、数据清单、合法性基础、留存期限、应急响应、测评和运维控制。

本期安全基线包含：

1. 本体工程级 ACL。
2. 实体类型、实例、数据属性、属性值四层数据分级继承。
3. 集中的数据访问决策服务，统一覆盖实例 API、可视化、SPARQL、序列化导出和版本快照。
4. 动态脱敏与受限数据阻断。
5. 敏感实例值的可选认证加密（AES-GCM + 可插拔密钥提供者），密钥缺失时失败关闭。
6. 数据访问审计和可验证哈希链。
7. IoT 设备凭证元数据与 Token 哈希治理；协议层认证由模块 19/网关/MQTT Broker 执行。
8. 高风险操作审批请求，支持双人审批、请求绑定、一次执行和过期。

### 1.2 对原设计的关键修正

| 原设计问题 | 修正 |
|---|---|
| 只描述“无数据级权限”，却只设计字段权限 | 新增本体工程 ACL 和主体安全许可（clearance） |
| 用 MyBatis 拦截器动态改写任意 SELECT 字段 | 删除该方案。实例数据属性是“行”而非固定 SQL 列，SQL 重写既脆弱又无法覆盖 SPARQL/导出；改为统一策略服务和授权 RDF/VO 投影 |
| Jackson 序列化器取第一个角色，且无用户时明文放行 | 采用所有主体规则的 deny-overrides；缺失安全上下文默认拒绝敏感数据，不允许 fail-open |
| 只在响应阶段脱敏 SPARQL | 在查询前构建授权 RDF 投影；否则 ASK/COUNT/FILTER 已泄漏受限数据 |
| AOP 按 `get*/list*/page*` 方法名审计 | 改为显式 `@DataAccessAudit`/统一服务调用，记录成功和失败，避免遗漏或误拦截 |
| “链式哈希=不可篡改” | 修正为“篡改可检测”；按链作用域加锁生成序号，日终根哈希需外部锚定才有更强证据力 |
| 设备 Token 用 AES 解密后比较 | 高熵 Token 只展示一次，数据库仅存 HMAC-SHA-256/哈希摘要和密钥版本；mTLS 只存证书指纹/公钥信息，不存设备私钥 |
| AES-CBC、静态环境变量、密钥缺失返回明文 | 改为 AES-256-GCM + 随机 IV + `KeyProvider` + key version；密钥不可用时拒绝读写 |
| “确认 Token”不绑定操作、目标、参数，dualConfirm 未实现 | 改为审批请求 + 审批明细，绑定 operation/target/payload digest；执行时原子消费，双人审批排除发起人 |
| 迁移脚本假定角色 3/4 存在 | 当前实际只预置管理员 1、普通用户 2；V20 仅给管理员 1 授权，其他角色由部署方配置 |
| 迁移脚本版本号 V17 与已占用冲突 | V17 已被 SPARQL 端点占用，V18–V19 也已被版本管理和 EDA 骨干占用；改为 **V20** |
| 菜单 ID 901400 段与 V19 事件模块冲突 | 901400–901402 已被 V19 事件中心占用；改为 **901500–901506** 段 |
| 缺少与已有 EDA 基础设施对接 | 已有 `ONTOLOGY_SECURITY_EVENT` 事件类型和 `SecurityAuditEventHandler` 消费者（一期空实现）；补充同步审计 + 异步事件双写策略 |
| 缺少现有 SPARQL 接入点替换说明 | 已有 `OntologyQueryAccessGuard`（一期仅校验工程存在）和 `DefaultSparqlModelProjectionPolicy`（一期空实现）；明确替换为安全策略实现 |
| 缺少实例 REST 侧改造方法级细节 | `OntEntityInstanceServiceImpl` 的 `buildDetailVO`/`getDataValues`/`buildRelationVOs`/`buildSummaryList`/`pageOptions` 完全无过滤；补充各方法改造点和接入策略 |
| `ont_security_level.level_rank` UNIQUE 约束不合理 | 去掉 `UNIQUE(level_rank)`，改为普通索引；部署方可自由插入自定义中间级别 |
| `ont_data_access_log` 外键 `ON DELETE RESTRICT` 不当 | 审计日志不应因工程删除而阻塞；改为 `ON DELETE SET NULL`（`ontology_id` 允许 NULL 已支持） |

## 2. 安全边界与原则

### 2.1 与 pig 基础能力的分工

| 能力 | pig 已有 | 本模块补充 |
|---|---|---|
| 用户认证 | OAuth2/Spring Security | 不重复实现 |
| 菜单/按钮 RBAC | `@HasPermission`、`sys_role_menu` | 继续作为功能入口权限 |
| 操作日志 | `@SysLog`、`sys_log` | 数据访问审计、策略决策和敏感级别 |
| 用户上下文 | `PigUser.id/roleIds/deptIds` | 用作 ACL 和策略主体 |
| Redis | 登录态/缓存基础设施 | 审批短期状态可用，但数据库是审批事实源 |
| 本体数据 | PostgreSQL 各 `ont_*` 表 | 分级、授权、加密和输出策略 |

### 2.2 核心原则

- **功能权限和数据权限分离**：有 `ontology_instance_view` 不代表能看所有工程和全部属性。
- **默认拒绝**：敏感数据无法判定用户、主体许可或密钥状态时，不返回明文。
- **Deny overrides**：任一适用规则明确 DENY 时，不因另一个角色 ALLOW 而放行。
- **最小数据返回**：先过滤不可见资源，再脱敏可见资源。
- **策略统一**：Controller、SPARQL、导出、可视化不得各自实现一套判断。
- **秘密不进日志**：Token、证书私钥、明文字段、完整受限查询结果不得进入 `sys_log`/审计日志。
- **审批与执行绑定**：审批不是一个可复用万能 Token。
- **合规可配置**：留存期、脱敏规则、级别映射由部署策略决定，不把法律结论硬编码到代码。

### 2.3 不在本期范围

- 替代专业 IAM/PAM、KMS/HSM、WAF、SIEM、DLP。
- 自动完成等保测评或法律合规认证。
- IoT MQTT/TLS 握手和 Broker ACL 的具体实现。
- 患者知情同意、数据主体请求、跨境评估等行业流程。
- 对全部历史明文数据自动在线加密；需独立迁移作业。
- 前端加密后端解密之类“自定义协议替代 TLS”。

## 3. 授权模型

### 3.1 两阶段决策

```text
阶段1：功能权限
  @HasPermission("ontology_xxx")
        ↓
阶段2：数据权限
  OntologyDataPolicyService.decide(subject, ontologyId, resource, action)
        ↓
  DENY  → 不查询/不投影/不导出
  MASK  → 返回结构和脱敏值
  ALLOW → 返回授权明文（仍需审计）
```

### 3.2 主体

策略主体支持：

- `USER`：`PigUser.id`。
- `ROLE`：`PigUser.roleIds`。
- `DEPT`：`PigUser.deptIds`。

不得只取第一个角色或第一个部门。

### 3.3 工程 ACL

访问级别：

| 级别 | 权限 |
|---|---|
| `VIEW` | 查看工程元数据和授权数据 |
| `EDIT` | VIEW + 修改 Schema/实例 |
| `PUBLISH` | EDIT + 发布版本/导出受控快照 |
| `ADMIN` | 本工程安全策略和成员管理 |

系统管理员是否旁路工程 ACL 应由配置控制。默认 `ROLE_ADMIN` 可管理，但敏感数据明文访问仍记录审计。

### 3.4 数据分级继承

安全等级：

| code | rank | 示例 | 默认输出 |
|---|---:|---|---|
| `PUBLIC` | 10 | 可公开标准编号 | ALLOW |
| `INTERNAL` | 20 | 内部 Schema、一般设备元数据 | 需工程 VIEW |
| `CONFIDENTIAL` | 30 | 联系方式、商业敏感参数 | 默认 MASK |
| `RESTRICTED` | 40 | 身份证件、医疗信息、控制凭证 | 默认 DENY，显式授权才可明文 |

有效等级取以下最大 rank：

```text
entity type level
instance override level
property level
instance value override level
```

对象关系的敏感级别至少取“主语实例、对象属性、宾语实例”三者最大值。

### 3.5 策略优先级

1. 工程 ACL 不满足 → DENY。
2. 匹配到任何显式 DENY → DENY。
3. 资源级 USER 规则。
4. 资源级 ROLE/DEPT 规则。
5. 主体 clearance 与数据 rank 比较。
6. 等级默认策略。

多个 ALLOW/MASK 冲突时取更严格结果：`DENY > MASK > ALLOW`。

## 4. 数据模型

### 4.1 安全级别 `ont_security_level`

```sql
CREATE TABLE ont_security_level (
  id bigint NOT NULL,
  level_code varchar(32) NOT NULL,
  level_name varchar(64) NOT NULL,
  level_rank integer NOT NULL,
  default_view_effect varchar(16) NOT NULL,
  default_export_effect varchar(16) NOT NULL,
  description text DEFAULT NULL,
  is_builtin char(1) NOT NULL DEFAULT '1',
  sort_order integer NOT NULL DEFAULT 0,
  create_by varchar(64) DEFAULT ' ',
  create_time timestamp NOT NULL DEFAULT now(),
  update_by varchar(64) DEFAULT ' ',
  update_time timestamp DEFAULT NULL,
  del_flag char(1) NOT NULL DEFAULT '0',
  PRIMARY KEY (id),
  CONSTRAINT uk_ont_security_level_code UNIQUE (level_code),
  CONSTRAINT ck_ont_security_view_effect
    CHECK (default_view_effect IN ('ALLOW', 'MASK', 'DENY')),
  CONSTRAINT ck_ont_security_export_effect
    CHECK (default_export_effect IN ('ALLOW', 'MASK', 'DENY')),
  CONSTRAINT ck_ont_security_builtin CHECK (is_builtin IN ('0', '1')),
  CONSTRAINT ck_ont_security_level_del CHECK (del_flag IN ('0', '1'))
);

CREATE INDEX idx_ont_security_level_rank ON ont_security_level (level_rank);
```

安全级别使用固定种子 ID，避免依赖数据库自增：

`level_rank` 仅建普通索引不设 UNIQUE 约束，允许部署方在两个预置级别之间插入自定义级别（如在 `INTERNAL` rank 20 和 `CONFIDENTIAL` rank 30 之间插入 rank 25 的级别），无需调整预置值。

```sql

```

### 4.6 加密值字段

```sql
ALTER TABLE ont_instance_data_value
  ALTER COLUMN literal_value DROP NOT NULL,
  ADD COLUMN IF NOT EXISTS is_encrypted char(1) NOT NULL DEFAULT '0',
  ADD COLUMN IF NOT EXISTS encrypted_value bytea DEFAULT NULL,
  ADD COLUMN IF NOT EXISTS crypto_key_id varchar(64) DEFAULT NULL,
  ADD COLUMN IF NOT EXISTS crypto_iv bytea DEFAULT NULL;

ALTER TABLE ont_instance_data_value
  ADD CONSTRAINT ck_ont_instance_value_encryption CHECK (
    (is_encrypted = '0' AND literal_value IS NOT NULL
      AND encrypted_value IS NULL AND crypto_key_id IS NULL AND crypto_iv IS NULL)
    OR
    (is_encrypted = '1' AND literal_value IS NULL
      AND encrypted_value IS NOT NULL AND crypto_key_id IS NOT NULL AND crypto_iv IS NOT NULL)
  );
```

约束要求：

- `is_encrypted='1'` 时 `literal_value` 不保存明文，`encrypted_value/crypto_key_id/crypto_iv` 必填。
- 使用 AES-256-GCM，认证标签与密文一并保存。
- AAD 至少绑定 `ontology_id + instance_id + data_property_id`，防止密文换位。
- `KeyProvider` 从部署侧 KMS/密钥服务获取版本化数据密钥；不得把根密钥写入源码、数据库或前端。
- 密钥不可用时读写失败并告警，禁止回退明文。

### 4.7 数据访问审计 `ont_data_access_log`

```sql
CREATE TABLE ont_data_access_log (
  id bigint NOT NULL,
  audit_event_id varchar(36) NOT NULL,
  chain_scope varchar(64) NOT NULL,
  chain_seq bigint NOT NULL,

  max_security_level varchar(32) DEFAULT NULL,
  decision varchar(16) NOT NULL,
  outcome varchar(16) NOT NULL,
  error_code varchar(64) DEFAULT NULL,
  trace_id varchar(128) DEFAULT NULL,
  remote_addr varchar(255) DEFAULT NULL,
  user_agent_hash varchar(64) DEFAULT NULL,
  occurred_at timestamp NOT NULL DEFAULT now(),
  prev_hash varchar(64) DEFAULT NULL,
  current_hash varchar(64) NOT NULL,
  create_by varchar(64) DEFAULT 'system',
  create_time timestamp NOT NULL DEFAULT now(),
  PRIMARY KEY (id),
  CONSTRAINT uk_ont_audit_event UNIQUE (audit_event_id),
  CONSTRAINT fk_ont_audit_project
    FOREIGN KEY (ontology_id) REFERENCES ont_ontology_project(id) ON DELETE SET NULL,
  CONSTRAINT uk_ont_audit_chain_seq UNIQUE (chain_scope, chain_seq),
  CONSTRAINT ck_ont_audit_decision CHECK (decision IN ('ALLOW', 'MASK', 'DENY')),
  CONSTRAINT ck_ont_audit_outcome CHECK (outcome IN ('SUCCESS', 'FAILED'))
);

CREATE INDEX idx_ont_audit_project_time
  ON ont_data_access_log (ontology_id, occurred_at DESC);
CREATE INDEX idx_ont_audit_user_time
  ON ont_data_access_log (user_id, occurred_at DESC);
```

审计表不提供普通删除接口，不使用逻辑删除。生产环境应按月分区并配置留存与归档策略。

审计表的外键 `ontology_id` 使用 `ON DELETE SET NULL` 而非 `RESTRICT`：审计记录的留存要求不应因工程被删除而阻塞，工程删除后审计记录保留，`ontology_id` 置空表示原工程已不存在。

### 4.8 设备凭证 `ont_device_credential`

```sql
CREATE TABLE ont_device_credential (
  id bigint NOT NULL,
  device_code varchar(128) NOT NULL,
  auth_type varchar(16) NOT NULL,
  token_digest varchar(128) DEFAULT NULL,
  digest_key_version varchar(32) DEFAULT NULL,
  certificate_fingerprint varchar(128) DEFAULT NULL,
  certificate_subject varchar(512) DEFAULT NULL,
  status varchar(16) NOT NULL DEFAULT 'ACTIVE',
  expires_at timestamp DEFAULT NULL,
  last_authenticated_at timestamp DEFAULT NULL,
  last_authenticated_ip varchar(255) DEFAULT NULL,
  failed_count integer NOT NULL DEFAULT 0,
  locked_until timestamp DEFAULT NULL,
  create_by varchar(64) DEFAULT ' ',
  create_time timestamp NOT NULL DEFAULT now(),
  update_by varchar(64) DEFAULT ' ',
  update_time timestamp DEFAULT NULL,
  del_flag char(1) NOT NULL DEFAULT '0',
  PRIMARY KEY (id),
  CONSTRAINT ck_ont_device_auth_type CHECK (auth_type IN ('TOKEN_HASH', 'MTLS')),
  CONSTRAINT ck_ont_device_status CHECK (status IN ('ACTIVE', 'LOCKED', 'REVOKED', 'EXPIRED')),
  CONSTRAINT ck_ont_device_material CHECK (
    (auth_type = 'TOKEN_HASH' AND token_digest IS NOT NULL AND digest_key_version IS NOT NULL)
    OR (auth_type = 'MTLS' AND certificate_fingerprint IS NOT NULL)
  ),
  CONSTRAINT ck_ont_device_del CHECK (del_flag IN ('0', '1'))
);

CREATE UNIQUE INDEX uk_ont_device_code
  ON ont_device_credential (device_code)
  WHERE del_flag = '0';
```

Token 为至少 256 bit 随机值，只在创建/轮换时返回一次；数据库存 HMAC-SHA-256 摘要，不存可逆 Token。设备私钥永不上传平台。

## 5. 核心服务设计

### 5.1 `OntologyDataPolicyService`

唯一策略入口：

```java
PolicyDecision decide(SecuritySubject subject,
                      Long ontologyId,
                      SecuredResource resource,
                      DataAction action);

List<PolicyDecision> batchDecide(SecuritySubject subject,
                                  Long ontologyId,
                                  List<SecuredResource> resources,
                                  DataAction action);
```

返回：

```java
class PolicyDecision {
    DecisionEffect effect; // ALLOW / MASK / DENY
    String effectiveLevelCode;
    String maskType;
    Map<String, Object> maskParameter;
    List<Long> matchedRuleIds;
    String reasonCode;
}
```

`SecuritySubject` 通过 `SecuritySubjectResolver` 从 pig 安全上下文解析：

```java
class SecuritySubjectResolver {
    // 优先从 SecurityUtils.getUser() 获取 PigUser
    // 降级时从 UserContextHolder.get() 获取 UserContext（data 模块通用接口）
    // 无安全上下文时返回 SYSTEM 主体，策略服务对 SYSTEM 主体按失败关闭处理
    SecuritySubject resolve();
}
```

`SecuritySubject` 包含 `userId`、`roleIds`（全部角色）、`deptIds`（全部部门），不得只取第一个角色或第一个部门。

缓存与修订号设计：

```text
缓存 key: ont:policy:{ontologyId}:{subjectHash}:{resourceType}:{resourceId}:{action}
缓存 value: PolicyDecision
缓存 TTL: 5 分钟
修订号: ont:policy:revision:{ontologyId}（Redis 自增）
```

要求：

- 决策结果可在请求内缓存，键包含 user/roles/depts、ontologyId、resource、action 和策略修订号。
- 策略规则、ACL、clearance 变更后递增对应 `ontologyId` 的 `policyRevision`，使旧缓存自然过期。
- 服务内部不能依赖 Controller 参数拼装安全上下文。
- 批量查询必须使用 `batchDecide` 接口，避免 N+1 查询。`batchDecide` 内部按 `resourceType + resourceLevelCode` 分组，先查规则再逐条匹配。

### 5.3 脱敏

内置脱敏类型：

- `PHONE`：保留前三后四。
- `ID_CARD`：按证件类型配置保留位，不假定所有证件均为 18 位身份证。
- `EMAIL`：保留首字符和域名。
- `IP`：IPv4/IPv6 分别处理。
- `NAME`：按 Unicode code point 处理，避免截断代理对。
- `FIXED`：固定返回 `***`。
- `PARTIAL`：由受控 JSON 参数指定前后保留长度。

不允许用户提交任意正则替换或脚本作为脱敏规则，避免 ReDoS 和代码执行风险。

脱敏后的值只用于展示，不回写数据库，不进入版本快照。

### 5.4 敏感值加解密

`KeyProvider` SPI 接口：

```java
public interface KeyProvider {
    // 获取当前活跃数据密钥（版本 + 密钥字节）
    DataKey getActiveKey();

    // 按 key version 获取历史密钥（轮换后旧密钥仍在保留期内可解密）
    Optional<DataKey> getKey(String keyId);

    // 当前活跃 keyId，用于判断是否需要重加密
    String getActiveKeyId();
}

@Data
public class DataKey {
    private String keyId;        // 密钥版本标识
    private byte[] keyBytes;     // AES-256 密钥字节（32 字节）
    private String algorithm;    // 固定 “AES/GCM/NoPadding”
}
```

默认实现 `EnvironmentKeyProvider`：从 Spring 配置 `ontology.security.crypto.keys.{keyId}` 读取 Base64 编码密钥，`ontology.security.crypto.active-key-id` 指定当前活跃版本。生产环境应替换为 KMS/HSM 实现（如 Vault Transit、AWS KMS），不得把根密钥写入源码、数据库或前端。

`SystemSecurityContext`：

```java
// 显式系统内部调用上下文，不允许通过”user==null”自动获得
public class SystemSecurityContext {
    // 由内部定时任务、迁移作业等受信入口显式创建
    // 携带调用来源标记（如 “key-rotation-job”），用于审计追踪
    // 不等同于管理员权限：系统上下文只能执行指定操作，仍受策略审计
    static SystemSecurityContext forInternalOperation(String source);
}
```

`SensitiveValueCryptoService`：

- 写入：策略判断需加密 → 获取 active key → 随机 96-bit IV → AES-GCM → 清空 `literal_value` → 写密文与 key id。
- 读取：先做策略决策；DENY 不解密，MASK 可按业务需要解密后在内存脱敏，ALLOW 解密后返回。
- 校验引擎属于受信内部调用，但必须使用显式 `SystemSecurityContext`，不能通过”user==null”自动获得明文。
- 密钥轮换通过后台迁移作业逐批重加密；旧 key 在轮换完成和备份保留期内可解密。
- 解密失败不得返回密文或空字符串冒充有效值。

### 5.5 数据访问审计

仅通过显式注解或服务门面记录：

```java
@DataAccessAudit(accessType = SPARQL, resourceType = ONTOLOGY)
```

审计内容：

- 谁、何时、从何处、访问哪个工程/资源。
- 动作类型、结果数量、最高安全级别、策略决策、成功/失败、稳定错误码。
- SPARQL 仅记录 query hash 和受控摘要，不记录敏感字面量全文。
- 导出记录格式、范围、行数和策略结果，不记录文件正文。

哈希链：

1. `chain_scope` 建议为 `yyyyMMdd:ontologyId`。
2. 插入前用 PostgreSQL transaction advisory lock 锁定该 scope。
3. 读取上一条 `chain_seq/current_hash`。
4. 规范化字段并计算 SHA-256。
5. 插入下一序号。
6. 每日根哈希由模块 37 导出到独立只写存储/外部时间戳服务。

链式哈希只能检测普通篡改；拥有数据库和应用密钥完全权限的攻击者仍可能重算整链，因此不得宣传为绝对不可篡改。

与已有 EDA 基础设施对接：

本模块采用**同步审计写入 + 异步事件通知**双写模式：

1. **同步落库**：`DataAccessAuditService` 在业务事务内同步写入 `ont_data_access_log`，确保 Redis 不可用时不丢失合规记录（已有 `SecurityAuditEventHandler` 注释明确警示此点）。
2. **异步事件**：审计写入成功后，通过 `OntDomainEventPublisher.append()` 发布 `ONTOLOGY_SECURITY_EVENT` 事件（payload 只含资源 ID/IRI、决策结果、非敏感摘要），供已存在的 `SecurityAuditEventHandler`（Consumer Group `ontology-security-audit-v1`）消费，用于下游告警、指标聚合和跨模块通知。
3. **降级策略**：异步事件发布失败（如 Outbox 写入异常）不影响同步审计结果；事件由 EDA 模块的 Inbox 幂等和死信机制保障最终一致性。
4. **事件 payload 约束**：`ONTOLOGY_SECURITY_EVENT` 的 payload 不得包含 Token、明文受限值、完整查询结果；只放 `auditEventId`、`ontologyId`、`decision`、`outcome`、`maxSecurityLevel` 和 `resourceRef`。

### 5.6 设备凭证

`DeviceCredentialService` 只负责：注册、轮换、吊销、摘要校验、锁定策略和审计。

- Token 比较使用常量时间比较。
- 失败计数和锁定更新采用原子 SQL，避免并发绕过。
- 认证接口不使用 `/devices/{id}/authenticate`；协议层按 `deviceCode + credential` 认证。
- HTTP/MQTT 接入、mTLS 握手、证书链验证和主题 ACL 由模块 19/网关/Broker 实现。
- 设备认证失败只记录设备 code 的 hash/安全摘要，不记录原 Token。

### 5.7 高风险审批

适用场景：版本恢复执行、批量删除、死信强制重放、下行控制、设备凭证吊销等。

流程：

```text
发起人提交操作预览
  → 服务计算 targetDigest + payloadDigest
  → 创建审批请求（1人或2人，5分钟/配置化过期）
  → 审批人审批；双人场景发起人不得作为审批人
  → 达到审批数后状态 APPROVED
  → 执行接口提交 approvalRequestNo + 原始操作参数
  → 服务重新计算两个 digest 并比对
  → 数据库行锁下将 APPROVED 原子更新为 CONSUMED
  → 执行业务操作并记录审计
```

审批请求只能消费一次，不能作为通用 Token，也不能通过 URL query 参数传递。

若业务操作和审批消费必须原子，二者应在同一 PostgreSQL 事务中；跨外部设备命令时采用“已批准待执行”状态机和幂等命令 ID。

## 10. 测试与验收

### 10.1 必测项

- USER/ROLE/DEPT 多主体合并，DENY 覆盖 ALLOW。
- 工程 ACL 在所有入口生效。
- 四层级别继承取最大 rank。
- 实例 API、可视化、SPARQL、导出对同一用户作出一致决策。
- ASK/COUNT/FILTER 无法从被 DENY 属性推断信息。
- 无安全上下文、策略异常、密钥不可用均失败关闭。
- AES-GCM 篡改检测、AAD 换位检测、key version 轮换。
- Token 只返回一次、数据库无明文、常量时间校验、失败锁定。
- 审计同时记录成功/失败，日志中无 Token 和明文受限值。
- 并发审计 hash 链序号不重复，验证可发现删改/断链。
- 单人审批、双人审批、发起人禁止自批、过期、参数变化、重复消费。

### 10.2 验收用例

| 用例 | 预期 |
|---|---|
| 无工程 ACL 的普通用户访问实例 | 403，且记录 DENY 审计 |
| CONFIDENTIAL 手机属性 | 有 MASK 权限返回脱敏值；无权限不返回该属性 |
| SPARQL COUNT 受限属性 | 授权 RDF 投影不含该三元组，无法统计 |
| 导出含 RESTRICTED 值 | 默认阻断或按显式策略脱敏，不生成明文文件 |
| 密钥服务不可用 | 敏感值读取失败，不返回明文/密文占位 |
| 创建设备 Token | 响应显示一次；数据库只有摘要 |
| 双人审批下行命令 | 两名不同审批人通过且参数 digest 一致后仅执行一次 |
| 审计链被删除一条 | 校验返回断链位置；外部根 hash 不一致 |
