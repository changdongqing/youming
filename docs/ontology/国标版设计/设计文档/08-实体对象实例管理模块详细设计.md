>
> 前置模块：01-模块化架构、02-单位字典、03-命名空间与IRI、04-实体类型、05-数据属性、06-对象属性、07-公理与规则（均已实现）

## 1. 评审结论

原设计采用“实例主表 + 数据属性值表 + 对象属性断言表”、Schema驱动动态表单和附录D种子数据的总体方向正确，但对国标附录D中的异常文本、OWL 2类/个体复用语义、对象属性断言物化策略、枚举兼容、并发生成和大数据量查询处理仍存在阻断性问题。本次评审已直接修订，结论如下。

| 级别 | 评审发现 | 优化结论 |
|------|----------|----------|
| P0 | PRD提出关系库+Triplestore双存储，但当前工程尚未引入Jena TDB/GraphDB；实例模块若强依赖双写，将无法独立交付且存在一致性风险 | V10采用**PostgreSQL单一事实源**：实例、字面量值和对象断言均存关系库；后续校验/序列化模块只读组装RDF模型。不得在本模块引入半成品双写 |
| P0 | 附录D步骤4引用 `Capacity_Constraint_3`，步骤5却只显式定义 `_1/_2`；PRD同时出现“7个约束”和仅6行定义的矛盾 | 保留第三个约束资源：预置 `Capacity_Constraint_3` 为无数据属性的内置 Constraint 实例，并标记来源异常；不得静默删除附录D中的引用 |
| P0 | 附录D将核心类IRI `:TextualParagraph` 直接作为 `hasRepresentationForm` 客体；原设计误造扩展实例 `std:TextualParagraph`，并会改变导出语义 | 对象断言支持受控的 `ENTITY_TYPE` 客体；4条 `hasRepresentationForm` 直接引用实体类型 940056。普通用户接口首期仅允许 `INSTANCE` 客体，类资源客体仅用于受保护种子数据/后续导入兼容 |
| P0 | 原设计新增 `constrainsObject`、`constrainsCharacteristic`、`referencesExternalResource` 共8条“补充关系”，但PRD附录D配置和国标示例未声明这些三元组 | 种子数据只保存权威来源明确要求的断言；补充推断不得伪装成源数据。V10对象断言总数修正为39条 |
| P0 | `fileType(950042)` 为 CLOSED_ENUM，V7仅预置法规/专利/文献/公共数据库，而附录D使用“产品技术条件” | V10向 `ont_data_property_enum` 增补非国标附录C、但由附录D直接要求的“产品技术条件”，来源记为 `D-Step8`；校验器只读枚举表，不硬编码 |
| P0 | 原设计对存在 `inverse_of_id` 的对象属性自动双向落库，会把推理结果当作显式断言，导致重复导出和删除联动复杂化 | 只保存用户/种子**显式断言**；逆属性由后续推理/序列化按需计算，不自动物化。若未来需要物化，必须增加 asserted/derived 来源和独立重建机制 |
| P0 | 原设计一律禁止主体=客体，但RDF/OWL并不普遍禁止自反关系，当前对象属性模型也没有 irreflexive 特性 | 取消全局自引用禁令；仅做三元组去重、定义域/值域和功能性校验。未来引入 irreflexive 公理后再按规则禁止 |
| P0 | 自动IRI使用 `MAX + 1` 并声称 `SELECT MAX(...) FOR UPDATE`，PostgreSQL聚合结果不能按该方式可靠加行锁，并发下仍会冲突 | 先生成 MyBatis-Plus ASSIGN_ID，再以 `类型本地名_ID` 生成本地名；无需业务序列表、无需查询最大值，并由唯一索引最终兜底 |
| P1 | 步骤2把带 `clauseTitle` 的条实例建为Clause，但V7将该属性定义域限定为TitledClause；原设计转存label会丢失附录D谓词 | 4个有标题条使用最具体类型TitledClause(940041)，同时保存clauseNumber和clauseTitle；通过继承仍满足Clause值域 |
| P1 | 步骤4漏存附录D已落地到V7的 `propertyDescription(952001)`，条款正文又使用省略号，无法作为可执行种子清单 | 补齐5项特性描述和4段完整条款正文；种子设计不得使用“...”作为值 |
| P1 | 内置实例“可改label/排序/备注”与“全部只读”表述冲突 | 统一为：IRI、类型、语义值和断言只读；治理字段 `label/sortOrder/remarks` 可由编辑权限用户修改 |
| P1 | `by-type` 无分页返回可能一次加载10万实例，不符合PRD性能目标 | 主列表统一分页；关系选择器提供分页远程搜索接口，默认20条、最大100条 |
| P1 | 原设计称实例可能被 `ont_axiom_rule_target` 引用，但V9目标类型仅支持Schema资源和单位分类 | 删除不存在的实例规则绑定检查；删除保护仅覆盖真实外键/后续已落地引用表 |
| P1 | 前端把所有枚举都做成不可自由录入下拉，错误处理了 OPEN_ENUM | CLOSED_ENUM只能选择；OPEN_ENUM使用“可搜索选择 + 允许新增值”；FREE按基础类型输入 |

### 1.1 权威语义口径

1. 实体对象实例按 `owl:NamedIndividual` 管理，每个普通实例有一个平台显式 `rdf:type`；首期不支持多类型和匿名个体。
2. `is_abstract='1'` 是平台治理约束，不是OWL内建语义；普通创建接口不得实例化抽象实体类型。
3. 数据属性值是RDF Literal；关系库保存规范化词法值和字面量类型，序列化模块负责输出XSD类型。
4. 对象属性断言是 `<subject IRI, predicate IRI, object IRI>`。通常客体为实例；为精确兼容附录D的OWL 2 punning写法，受控支持实体类型IRI作为客体。
5. 数据库只保存显式断言，不把逆属性、传递闭包、range/domain推断结果写回显式数据表。
6. 附录D既是验收场景，也包含源文本不一致。平台必须记录异常并保持可追溯，不得用无依据的业务补全掩盖标准原文。
7. 本模块不执行SHACL、OWL一致性推理或Turtle序列化；本模块负责提交前可确定的结构和值域校验，并提供稳定读取契约。

## 2. 领域模型与本体语义

### 2.1 核心RDF映射

```turtle
# 普通实例声明
std:GB-T_31486-2024 a :Standard .

# 数据属性赋值
std:GB-T_31486-2024 :standardNumber "GB/T 31486—2024" ;
    :issuedDate "2024-09-29"^^xsd:date .

# 实例到实例的对象属性断言
std:BatteryCell :hasCharacteristic std:Appearance_Prop .

# 附录D类IRI作为对象资源（OWL 2 punning兼容）
std:Appearance_Requirement :hasRepresentationForm :TextualParagraph .
```

关系库映射：

- 第一类三元组由 `ont_entity_instance.rdf_type_id` 表达；
- 第二类由 `ont_instance_data_value` 表达；
- 第三、四类由 `ont_instance_object_relation` 表达，客体类型分别为 `INSTANCE`、`ENTITY_TYPE`。

### 2.2 实例IRI生成

实例IRI必须由后端生成：

```text
iri = namespace.uri + iriLocalName
```

| 模式 | 本地名规则 | 说明 |
|------|------------|------|
| 用户指定 | `^[A-Za-z][A-Za-z0-9_-]{0,127}$` | 适用于标准号、既有业务标识等 |
| 自动生成 | `<rdfType.iriLocalName>_<ASSIGN_ID>` | 先分配实例ID，再生成，如 `Clause_203889...`，并发安全 |

规则：

1. `ontologyId`、`namespaceId`、`rdfTypeId`必填；当前只有核心工程时前端可默认935001，但API不依赖隐式默认。
2. 命名空间、实体类型必须有效；实体类型和实例必须属于同一 `ontology_id`。
3. `iri`不作为写入DTO字段，避免客户端提交与命名空间不一致的完整IRI；DTO只接收 `iriLocalName`。
4. 完整IRI由 `OntIriUniquenessService` 检查命名空间URI、实体类型、数据属性、对象属性和实例表冲突，数据库部分唯一索引最终兜底。
5. 扩展实例修改本地名或命名空间时，关系表使用ID引用，无需因已有关系而拒绝；事务内重算IRI并重新做唯一性校验即可。
6. 命名空间 `prefix` 只影响展示和序列化前缀，不进入实例IRI；URI迁移由03模块预留的 relocate 流程统一重算，不允许普通编辑绕过。

### 2.3 字面量类型

| `literal_type` | 兼容 `base_type` | 规范化词法值 | RDF输出 |
|----------------|------------------|--------------|---------|
| `STRING` | TEXT、UNIT_REF、TEXT_OR_NUMERIC | 原文本 | `xsd:string` |
| `URI` | URI | 规范化后的绝对IRI词法值 | `xsd:anyURI` |
| `DATE` | DATE | `YYYY-MM-DD` | `xsd:date` |
| `INTEGER` | NUMERIC、TEXT_OR_NUMERIC | 无前导加号的十进制整数 | `xsd:integer` |
| `DECIMAL` | NUMERIC、TEXT_OR_NUMERIC | `BigDecimal.toPlainString()` | `xsd:decimal` |
| `BOOLEAN` | BOOLEAN | `true` / `false` | `xsd:boolean` |

补充规则：

- API日期可接受 `YYYYMMDD` 或 `YYYY-MM-DD`，落库统一为后者；
- `TEXT_OR_NUMERIC` 必须显式提交实际 `literalType`；
- UNIT_REF 的 `literalValue`、`literalSymbol` 均保存当次选择的单位符号，且 `unitId` 必填；写入时三者必须一致；
- CLOSED_ENUM必须命中有效 `enum_value`；若该行 `canonical_value` 非空则落库标准值，否则落库 `enum_value`。OPEN_ENUM对已知值执行同样归一，未命中时允许非空自定义值；FREE不做枚举限制。

### 2.4 对象属性断言

断言校验顺序：

1. 主体、对象属性和客体资源存在且有效；
2. 主体、对象属性、客体资源归属同一本体工程；
3. 主体类型满足对象属性任一声明定义域或其子类；
4. `INSTANCE` 客体的实例类型满足任一声明值域或其子类；
5. `ENTITY_TYPE` 客体仅允许受保护种子/导入兼容流程，目标实体类型本身须等于声明值域或其子类；
6. 显式三元组不得重复；
7. `is_functional='1'` 时，同一主体+谓词在两种客体类型合计至多一条有效显式断言；
8. 不做全局主体≠客体限制；
9. 不自动创建逆属性断言。

### 2.5 附录D异常与平台处理

| 异常 | 权威文本现象 | 平台处理 |
|------|--------------|----------|
| 第三个容量约束 | 步骤4引用 `_1/_2/_3`，步骤5只定义 `_1/_2` | 创建 `_3` 内置实例，保留引用，不虚构数据属性；remarks记录“仅被引用，原文未定义” |
| TextualParagraph | 使用核心类IRI作为对象值 | 断言客体类型=`ENTITY_TYPE`、ID=940056，不创建同名扩展实例 |
| 有标题条类型 | 原文显式写Clause但同时赋clauseTitle；V7规定clauseTitle定义域为TitledClause | 单类型平台保存最具体类型TitledClause；其继承Clause，且RDFS domain语义也可推出该类型 |
| 条款层次谓词 | 国标示例、PRD早期文字与PRD §0.4统一口径不一致 | 依PRD统一口径：Standard→Section用hasStructuralElement，Section→Clause用hasClause，Clause→要求条款用hasSubClause |
| `unit`/`measurementUnit` | 附录C为unit，附录D为measurementUnit | 存权威数据属性950041；UI显示preferredAlias，导出策略决定谓词IRI |
| fileType枚举 | 附录C闭枚举未含“产品技术条件”，附录D实际使用 | V10将其作为D-Step8兼容枚举值增补 |
| 外部引用关系 | 示例只定义资源，未声明条款到资源的对象属性 | 不擅自增加 `referencesExternalResource` 断言 |
| 约束对象关系 | 示例只通过Property→Constraint关联 | 不擅自增加 `constrainsObject/constrainsCharacteristic` 断言 |

## 3. 数据模型

> 对齐现有实现：PostgreSQL、`ont_`前缀、MyBatis-Plus ASSIGN_ID、`char(1)`布尔、审计字段、逻辑删除、Flyway增量迁移。

### 3.1 实例主表 `ont_entity_instance`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | bigint | 是 | ASSIGN_ID；内置种子使用固定ID |
| `iri` | varchar(512) | 是 | 完整IRI |
| `iri_local_name` | varchar(128) | 是 | 本地标识符 |
| `rdf_type_id` | bigint | 是 | FK→`ont_entity_type.id`，RESTRICT |
| `label` | varchar(255) | 否 | UI显示标签，不替代本体数据属性 |
| `namespace_id` | bigint | 是 | FK→`ont_namespace.id`，RESTRICT |
| `ontology_id` | bigint | 是 | FK→`ont_ontology_project.id`，RESTRICT |
| `source_type` | varchar(32) | 是 | `APPENDIX_D/EXTENSION` |
| `source_reference` | varchar(128) | 否 | 如 `D-Step5`、`D-Step4 dangling reference` |
| `declaration_mode` | varchar(16) | 是 | `EXPLICIT/REFERENCE_ONLY`；普通实例显式声明，源文本仅引用资源时使用后者 |
| `is_builtin` | char(1) | 是 | 1内置，0扩展 |
| `sort_order` | integer | 是 | 默认0 |
| `remarks` | varchar(255) | 否 | 治理说明/源异常说明 |
| 审计字段 | — | — | `create_by/create_time/update_by/update_time` |
| `del_flag` | char(1) | 是 | 0有效，1删除 |

约束：

1. `iri`有效数据全局唯一；
2. `(ontology_id, namespace_id, iri_local_name)`有效数据唯一；
3. `source_type=APPENDIX_D ↔ is_builtin='1'`，`EXTENSION ↔ '0'`；
4. `declaration_mode` 仅允许 `EXPLICIT/REFERENCE_ONLY`，且普通扩展接口只能创建 `EXPLICIT`；
5. `sort_order>=0`；
6. Service保证 `iri=namespace.uri+iri_local_name`、同工程、非抽象类型。

### 3.2 数据属性值表 `ont_instance_data_value`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | bigint | 是 | ASSIGN_ID |
| `instance_id` | bigint | 是 | FK→实例，CASCADE（物理清理兜底） |
| `data_property_id` | bigint | 是 | FK→数据属性，RESTRICT |
| `literal_value` | text | 是 | 规范化词法值 |
| `literal_type` | varchar(16) | 是 | STRING/URI/DATE/INTEGER/DECIMAL/BOOLEAN |
| `unit_id` | bigint | 否 | FK→`ont_unit.id`，UNIT_REF必填 |
| `literal_symbol` | varchar(32) | 否 | UNIT_REF词法快照 |
| `sort_order` | integer | 是 | 同属性多值排序 |
| 审计字段、`del_flag` | — | — | 与领域主表一致 |

数据库CHECK：

- `literal_type`枚举（STRING/URI/DATE/INTEGER/DECIMAL/BOOLEAN）；
- `sort_order>=0`；
- `unit_id IS NULL`时 `literal_symbol`必须为空，`unit_id IS NOT NULL`时 `literal_symbol`非空；
- 不能仅凭本表CHECK判断UNIT_REF、定义域和枚举，均由Service读取Schema校验。

唯一性：同一实例同一属性允许多值；Service在锁定实例行后拒绝完全相同的有效字面量重复。`literal_value`为text，不为避免大字段B-tree限制而建立全值唯一索引。

`ont_data_property.is_unique='1'` 的工程级唯一性由Service按 `(ontology_id, data_property_id, normalizedValue)` 检查，并通过锁定数据属性行串行化并发写入。

### 3.3 对象属性断言表 `ont_instance_object_relation`

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | bigint | 是 | ASSIGN_ID |
| `subject_instance_id` | bigint | 是 | FK→实例，CASCADE |
| `object_property_id` | bigint | 是 | FK→对象属性，RESTRICT |
| `object_kind` | varchar(16) | 是 | `INSTANCE/ENTITY_TYPE` |
| `object_instance_id` | bigint | 条件必填 | `INSTANCE`时FK→实例，RESTRICT |
| `object_entity_type_id` | bigint | 条件必填 | `ENTITY_TYPE`时FK→实体类型，RESTRICT |
| `sort_order` | integer | 是 | 多值顺序 |
| 审计字段、`del_flag` | — | — | 与领域主表一致 |

CHECK保证两种目标恰有一个：

```sql
CHECK (
  (object_kind = 'INSTANCE' AND object_instance_id IS NOT NULL AND object_entity_type_id IS NULL)
  OR
  (object_kind = 'ENTITY_TYPE' AND object_instance_id IS NULL AND object_entity_type_id IS NOT NULL)
)
```

分别建立部分唯一索引：

- INSTANCE：`(subject_instance_id, object_property_id, object_instance_id)`；
- ENTITY_TYPE：`(subject_instance_id, object_property_id, object_entity_type_id)`。

### 3.4 跨表完整性和删除语义

1. 主表逻辑删除前，Service物理删除该实例的数据值和以其为主体的显式断言；数据库CASCADE仅作为物理删除兜底，不作为正常业务流程。
2. 实例作为 `INSTANCE` 客体被引用时拒绝删除，返回引用数量和前若干主体摘要。
3. 实体类型删除前新增两类检查：实例 `rdf_type_id` 引用、断言 `object_entity_type_id` 引用；存在任一引用均拒绝。
4. 数据属性、对象属性删除前分别检查有效值/断言引用。
5. 将实体类型改为抽象类前检查现有实例引用；存在实例则拒绝。
6. 扩展命名空间被实例引用后，普通编辑不得修改URI；必须走03模块预留的relocate事务，批量重算并校验实例IRI。
7. 单位删除或修改符号前检查实例UNIT_REF引用；已有引用时拒绝删除/改符号，避免词法快照漂移。
8. `ont_axiom_rule_target` 不引用实例，本模块不添加虚假检查。

- `ont_entity_type`及hierarchy/label；
- `ont_data_property`及enum/label；

## 5. 服务规则

### 5.1 创建实例

事务步骤：

1. 校验ontology、namespace、rdfType有效且同工程，类型非抽象；
2. 使用IdentifierGenerator取得ASSIGN_ID；
3. 规范化用户本地名，未提交则按 `<typeLocalName>_<id>` 生成；
4. 后端拼接完整IRI并调用全局唯一性组件；
5. 校验全部dataValues；
6. 插入实例主表和数据值；
7. 校验并插入仅指向**已存在资源**的对象断言；创建请求不支持用临时客户端ID互相引用；
8. 捕获唯一索引冲突并转换为可理解业务错误。

普通API固定写入 `sourceType=EXTENSION/declarationMode=EXPLICIT/isBuiltin='0'`；不得信任客户端提交来源、声明模式和内置标记。

### 5.2 数据属性值写入

1. 按数据属性定义域向上展开实例类型祖先，验证适用性；
2. 按 `base_type + value_mode` 校验和规范化；
3. CLOSED_ENUM必须命中有效枚举；OPEN_ENUM允许自定义；已知兼容值按 `canonical_value` 归一，比较前后去空白但不擅自改写大小写；
4. DATE、NUMERIC、BOOLEAN按§2.3规范化；
5. URI基础类型必须为绝对IRI；
6. UNIT_REF校验单位有效、符号一致；若数据属性限定unit_category_id，单位必须属于该分类；
7. 同一请求内先做重复值检查；
8. `is_unique='1'` 时锁定数据属性行，再检查工程内规范化值唯一，避免并发穿透；
9. 内置实例的语义值不可通过普通接口修改或删除；
10. 批量设置采用“完整校验→物理删除旧有效值→批量插入”的单事务整体替换。

### 5.3 对象属性断言写入

1. 普通API只接受 `objectKind=INSTANCE`；`ENTITY_TYPE` 由迁移种子或受控导入服务调用内部方法；
2. 定义域/值域按DAG祖先集合校验；多定义域/多值域按并集处理；
3. 锁定对象属性行和主体实例行；功能性属性在锁内统计两种客体断言总数；
4. 同一显式三元组重复时返回冲突，不静默成功；
5. 允许自引用，除非后续公理模型明确提供irreflexive规则；
6. 不自动写入inverse_of对应断言；
7. 内置实例的断言不可通过普通接口增删；
8. 删除断言只删除指定显式断言，不级联删除可能存在的逆向显式断言。

### 5.4 修改实例

- 内置实例：仅可修改 `label/sortOrder/remarks`；
- 扩展实例：可修改本地名、命名空间、类型、label、排序、备注；
- 修改类型前必须以新类型重新校验全部数据值、出向断言定义域和入向断言值域；任一不兼容则整体拒绝；
- 修改IRI不因关系引用而拒绝，因为关系使用ID；只需重算IRI并检查全局唯一；
- `ontologyId/sourceType/isBuiltin` 不允许修改。

### 5.5 删除实例

1. 内置实例禁止删除；
2. 查询作为INSTANCE客体的有效入向断言；有引用则拒绝，并返回引用总数和最多10条主体/谓词摘要；
3. 无入向引用时，物理删除数据值和出向断言，逻辑删除主表；
4. 删除事务锁定实例行，防止检查后又新增入向断言；关系创建按主体和客体ID升序锁定实例行，避免死锁；
5. 后续模块若新增真实外键引用，应在其迁移中同步扩展删除保护。

### 5.6 查询与装配

- 主列表统一分页，条件：keyword、rdfTypeId、includeSubtypes、ontologyId、namespaceId、sourceType、isBuiltin；
- 先分页主表，再按ID集合批量读取类型标签、值数量、出向/入向断言数量，禁止N+1；
- 详情返回基本信息、数据值、出向断言和入向引用；实体类型客体返回Schema摘要而非伪实例摘要；
- 关系选择器使用远程分页搜索，按对象属性值域或显式rangeEntityTypeId过滤，支持子类，size默认20、最大100；
- 读取API不得触发逆属性或传递闭包推理，返回内容标记为 `asserted=true`。

```text
sourceType、isBuiltin、sortOrder、dataValueCount、outgoingRelationCount、incomingRelationCount
```

关系VO统一返回：

```text
id、objectPropertyId/name/label、objectKind、objectResourceId、objectIri、objectLabel
objectRdfTypeId?、asserted=true、sortOrder
```

所有Java ID使用Long；所有TypeScript ID使用string，axios响应层不得数值化。

### 7.4 事务、锁和性能

1. 写方法 `@Transactional(rollbackFor=Exception.class)`；
2. IRI自动生成只依赖已分配ID，不执行MAX扫描；
3. 功能性断言：锁对象属性行+主体实例行后检查；
4. 唯一数据属性：锁数据属性行后检查工程内值；
5. 关系创建同时涉及两个实例时，按ID升序 `SELECT ... FOR UPDATE`；
6. 批量装配使用Mapper批量SQL，列表查询不得循环调用Service；
7. `options`强制分页并限制size≤100；
8. 详情的值和关系可分3次批量查询，不追求单条巨型笛卡尔JOIN。
