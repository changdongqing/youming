# 同步作业、增量、幂等与错误恢复功能详细设计

> 模块：18 数据源映射  
> 功能编号：18-07  
> 前置：18-01～18-06、26 EDA  
> 设计日期：2026-07-14

## 1. 目标

执行PUBLISHED映射版本的预览、全量、增量和失败记录重试，提供可恢复游标、租约、取消、记录级错误、删除检测和作业生命周期管理。

## 2. 执行类型

| run_type | 是否写实例 | 用途 |
|---|---|---|
| `PREVIEW` | 否 | 抽样预览，主体由18-06管理 |
| `FULL` | 是 | 全量扫描、建立seen集合和物理删除检测 |
| `INCREMENTAL` | 是 | 按持久化游标增量读取 |
| `RETRY` | 是 | 重试指定失败记录键，继承原映射版本 |
| `RELATION_RETRY` | 是 | 重试待解析关系 |

PREVIEW可以复用作业表，但不会更新项目生产游标和last successful job。

## 3. 作业主表

CREATE INDEX idx_ont_job_queue
  ON ont_mapping_job(job_status, create_time)
  WHERE del_flag = '0' AND job_status IN ('QUEUED','RECOVERING');
CREATE INDEX idx_ont_job_lease
  ON ont_mapping_job(job_status, lease_until)
  WHERE del_flag = '0' AND job_status IN ('STARTING','RUNNING','CANCELLING');

  ON ont_mapping_job(mapping_project_id, create_time DESC)
  WHERE del_flag = '0';

同一映射工程V1只允许一个生产作业运行；PREVIEW不占用生产作业唯一槽位。

## 5. 作业领取与租约

Mapper使用PostgreSQL：

```sql
SELECT id
FROM ont_mapping_job
WHERE job_status IN ('QUEUED','RECOVERING')
  AND del_flag='0'
ORDER BY create_time
FOR UPDATE SKIP LOCKED
LIMIT :limit;
```

领取后CAS更新：

```text
job_status=STARTING
lease_owner={applicationName}:{instanceId}:{thread}
lease_until=now()+60s
heartbeat_at=now()
```

Worker每15秒续租。续租更新0行表示租约丢失，当前Worker必须停止，不得继续写。

Reclaimer扫描超时租约：

- 最后游标存在且映射/本体依赖仍有效 → RECOVERING；
- 依赖漂移、取消请求或超过最大恢复次数 → FAILED；
- 作业恢复不是重新从第一页开始，而是从已提交`cursor_after`继续。

## 6. 游标模型

按每个实体/关系映射分别保存：

```json
{
  "entityMappings": {
    "USER_ACCOUNT": {
      "incrementalValue":"2026-07-14T10:00:00Z",
      "lastKey":{"user_id":"100"}
    }
  },
  "relationMappings": {}
}
```

### 6.1 Keyset分页

全量：

```sql
WHERE (pk1, pk2) > (?, ?)
ORDER BY pk1, pk2
LIMIT ?
```

增量：

```sql
WHERE (updated_at > ?)
   OR (updated_at = ? AND (pk1,pk2) > (?,?))
ORDER BY updated_at, pk1, pk2
LIMIT ?
```

不使用OFFSET，防止大表性能退化和并发变化导致跳记录。

### 6.2 时间边界和迟到数据

- 将源时间统一转换为Instant；
- 记录源数据库时区配置；
- 增量扫描使用固定`scanUpperBound`，作业启动时查询源库当前时间；
- 条件为`lastCursor < updated_at <= scanUpperBound`；
- 下一作业从已提交游标继续；
- 对可能乱序更新的数据源可配置`lookbackSeconds`，默认0，最大3600；回看依赖幂等去重。

## 7. 事务粒度

- 源读取页：默认500；
- 目标事务批：默认50条；
- V1采用每条记录`TransactionTemplate + REQUIRES_NEW`事务，保证单条失败不回滚同页已成功记录；
- 页大小默认500，但目标写事务仍按记录隔离；后续只有在压测证明事务开销成为瓶颈后，才允许引入批内保存点优化；
- 游标仅在对应源读取页全部处理并持久化计数后更新；
- 进程在游标提交前崩溃会重放该批，来源绑定保证幂等。

## 8. 执行流程

```text
创建作业并固化版本/hash/授权/本体版本
 → Worker领取租约
 → 再校验数据源、映射版本、本体版本、工作区
 → 编译或加载执行计划
 → ENTITY阶段按syncOrder扫描
    → 每页读取
    → 每记录转换和摄入
    → 写失败明细/计数
    → 提交游标和心跳
 → RELATION阶段
 → PENDING立即重试
 → FULL作业执行删除检测
 → 可选触发范围SHACL校验
 → 汇总SUCCEEDED/PARTIAL_SUCCESS/FAILED
 → 更新project.last_job_id和生产游标
 → 发布完成事件
```

### 8.1 结果状态

- `SUCCEEDED`：无FAILED，允许SKIPPED和PENDING=0；
- `PARTIAL_SUCCESS`：存在记录失败或仍有PENDING，但成功记录已提交；
- `FAILED`：作业级前置失败、源连接中断超过重试、错误率超过阈值或无任何可完成阶段；
- 可配置`maxErrorRate`默认10%，超过后快速失败；至少读取100条后才使用比例，前100条可配置绝对上限20。

## 9. 重试

### 9.1 源读取重试

仅以下可重试：

- 临时网络中断；
- 连接池获取超时；
- 数据库短暂不可用。

认证失败、白名单拒绝、元数据漂移不可重试。退避1s/5s/30s，最多3次。

### 9.2 记录重试

`RETRY`作业引用原FAILED记录：

- 必须使用原`mapping_version_id`解释错误；
- 原版本RETIRED仍可重试，但当前Ontology版本必须兼容；
- 源记录已不存在时按删除策略处理；
- 用户可选择指定错误码/映射码/记录ID集合，最多1000条；
- 成功后不修改原记录，新增重试记录并通过`retry_of_record_id`建立重试链。

## 10. 取消

- Controller只设置`cancel_requested=1`和状态CANCELLING；
- Worker在每页读取前、每目标批提交后检查；
- 不中断正在提交的单记录事务；
- 已提交数据不回滚；
- 停止后状态CANCELLED，保存最后游标；
- 用户可新建INCREMENTAL/FULL作业继续，不能把CANCELLED原作业改回RUNNING；
- 数据源停用等价于请求安全停止，最终FAILED或CANCELLED由触发原因决定。

## 11. FULL删除检测

避免将所有seen key保存在JVM内：

1. FULL作业开始时不全量重置绑定；
2. 每读取记录更新绑定`last_seen_job_id=currentJobId`；
3. 实体映射完成后查询：

```sql
WHERE mapping_project_id=?
  AND entity_mapping_code=?
  AND binding_status='ACTIVE'
  AND (last_seen_job_id IS NULL OR last_seen_job_id<>currentJobId)
```

4. 对未见绑定增加missCount；
5. 默认连续2次FULL未见才执行删除策略，减少源瞬时过滤/权限异常误删；
6. 显式软删除列命中时可立即执行策略；
7. FULL作业若中途失败，不执行未见删除检测。

## 12. 调度

- 复用项目已有Quartz基础，不新增第二套调度框架；
- 每个mappingProject一个逻辑Job，cron变更时重建Trigger；
- 调度只创建`ont_mapping_job`，不在Quartz线程内执行扫描；
- 上次作业仍运行时跳过本次并记录指标，不排无限队列；
- 调度主体按18-03配置并在每次创建作业时重新校验；
- 应用多实例通过数据库唯一运行索引和租约保证单执行。

## 14. 事件

| 事件 | 时机 |
|---|---|
| `MAPPING_JOB_STARTED` | 作业通过前置并开始扫描 |
| `MAPPING_JOB_PROGRESS` | 默认不每页发布，避免事件风暴；可每10%或每分钟 |
| `MAPPING_JOB_COMPLETED` | SUCCEEDED/PARTIAL_SUCCESS |
| `MAPPING_JOB_FAILED` | 作业级失败 |
| `MAPPING_JOB_CANCELLED` | 安全停止 |
| `MAPPING_RECORD_REJECTED` | 默认聚合，不逐条发布；高价值错误可采样 |

事件payload只含计数、状态、ID和错误码摘要。

## 15. 保留与清理

- 作业主记录长期保留或按审计要求归档；
- 成功记录明细默认不落库；
- FAILED/PENDING明细默认保留30天；
- 清理前保留错误计数和按错误码聚合摘要；
- 来源绑定和provenance不随作业明细清理；
- 清理任务使用小批次并记录审计；
- 被重试链引用的记录在链条保留期内不删除。

## 17. 测试与验收

1. 多节点并发只领取一次作业；
2. 租约丢失后旧Worker停止写入；
3. 页提交后崩溃从持久化游标恢复；
4. 重放最后一批不产生重复实例；
5. Keyset分页不因插入新记录跳过已存在记录；
6. 同一更新时间通过PK次序不漏记录；
7. FULL失败不执行删除检测；
8. 连续两次未见才失活；
9. 取消不回滚已提交记录且保留游标；
10. 错误率超过阈值快速失败；
11. 调度重叠时跳过而非无限排队；
12. RETRY使用原映射版本并建立重试链；
13. 日志和record表不保存源整行；
14. 10000条UPMS数据可稳定同步并输出吞吐、失败率和耗时。
