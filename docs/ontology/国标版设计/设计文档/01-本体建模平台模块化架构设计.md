# 本体建模平台模块化架构设计

> 对应 PRD：《标准本体建模平台PRD.md》  
> 本文范围：后端/前端模块化落地方案，以及本次“单位字典管理模块”的接入边界。  
> 编写日期：2026-07-09

## 1. 目标与约束

### 1.1 目标

1. 在 pig / pig-ui 现有工程内，以模块化方式承载后续所有 ontology 建模能力。
2. 本次只实现 PRD §4.11“单位字典管理模块”，但目录、依赖、菜单、权限命名要为后续实体类型、数据属性、对象属性、公理规则、实体对象等模块预留清晰边界。
3. 复用 pig 既有能力：Spring Boot 4、MyBatis-Plus、统一响应 `R`、`@HasPermission`、`@SysLog`、Element Plus、后端菜单驱动路由、Flyway 迁移。
4. 遵守 youming PostgreSQL + Flyway 规范：新增版本脚本，不修改已应用的 V1/V2/V3。

### 1.2 明确不做

1. 本次不实现实体类型、数据属性、对象属性、公理规则、实体对象实例等模块。
2. 本次不引入 RDF 三元组库、Jena、SHACL 校验引擎。
3. 本次不读取、不依赖 `yuanxing/index.html`。
4. 本次不把单位字典塞进系统字典 `sys_dict`，因为单位字典需要内置保护、单位分类、符号解析、换算参数、后续引用校验等领域语义。

## 2. 后端模块化设计

### 2.1 模块选择

新增后端 Maven 聚合模块：

```text
server/pig-ontology/
├── pom.xml                         # ontology 聚合模块
└── pig-ontology-biz/
    ├── pom.xml                     # ontology 业务 jar
    └── src/main/java/com/pig4cloud/pig/ontology/
        ├── controller/
        ├── entity/
        ├── mapper/
        ├── service/
        ├── service/impl/
        └── vo/
```

设计理由：

| 方案 | 结论 | 原因 |
|------|------|------|
| 直接放入 `pig-upms-biz` | 不采用 | 会把领域建模能力混入用户权限模块，后续实体/实例/公理代码膨胀后边界不清 |
| 新建 `pig-ontology-biz` | 采用 | 与 upms、visual 同级，后续 ontology 功能可集中演进 |
| 本次即拆 `pig-ontology-api` | 暂不采用 | 当前没有跨服务 Feign DTO 复用需求，先保持简单；后续出现远程调用再拆 API 包 |

### 2.2 与单体版 `pig-boot` 的关系

`pig-boot` 增加对 `pig-ontology-biz` 的依赖。单体版启动后，ontology Controller 与现有 admin Controller 一样被 Spring Boot 扫描。

由于 `pig-boot` 的 context-path 为 `/admin`，后端接口实际路径形如：

```text
/admin/ontology/unit-categories
/admin/ontology/units
```

前端请求仍使用 pig-ui 的既有适配机制。为了避免 `VITE_IS_MICRO=false` 时被 `adaptationUrl()` 截断，前端 API 使用 `/admin/ontology/...` 作为原始 URL，单体模式下仍会落到 `/admin/ontology/...`。

### 2.3 与微服务版的关系

本次 `pig-ontology-biz` 先作为可被 `pig-boot` 装配的业务 jar，并纳入根 Maven modules 编译。后续若要作为独立微服务运行，可在同一模块补充 `PigOntologyApplication`、Nacos 配置和 Gateway 路由；这不影响当前代码包结构和接口路径。

### 2.4 后端包与命名规范

```text
com.pig4cloud.pig.ontology
├── controller     # REST API
├── entity         # MyBatis-Plus 实体
├── mapper         # Mapper 接口，使用 @Mapper
├── service        # Service 接口
├── service.impl   # ServiceImpl
└── vo             # 页面/接口视图对象，如树节点
```

权限标识统一使用：

```text
ontology_unit_view
ontology_unit_add
ontology_unit_edit
ontology_unit_del
```

说明：单位分类和单位条目同属一个页面模块，首期共用这组权限，避免权限颗粒度过细。

## 3. 数据库与 Flyway 设计

### 3.1 迁移策略

新增迁移脚本：

```text
server/pig-common/pig-common-data/src/main/resources/db/migration/V4__ontology_unit_dictionary.sql
```

脚本内容包含：

1. 单位分类表 `ont_unit_category`。
2. 单位条目表 `ont_unit`。
3. 唯一索引与常用查询索引。
4. 本体建模菜单分组与“单位字典”菜单及按钮权限。
5. 管理员角色 `role_id=1` 的菜单授权。
6. 国标口径最小可用预置分类与单位。

### 3.2 表前缀

Ontology 领域表统一使用 `ont_` 前缀：

| 表 | 用途 |
|----|------|
| `ont_unit_category` | 单位物理量分类 |
| `ont_unit` | 单位条目 |

后续建议继续使用：

```text
ont_entity_type
ont_data_property
ont_object_property
ont_axiom_rule
ont_entity_instance
```

## 4. 前端模块化设计

### 4.1 目录结构

新增前端目录：

```text
web/src/api/ontology/unit.ts
web/src/views/ontology/unit/index.vue
```

说明：

1. `src/api/ontology/` 承载 ontology 领域接口。
2. `src/views/ontology/` 承载 ontology 菜单页面。
3. 菜单路由路径使用 `/ontology/unit/index`，与文件 `views/ontology/unit/index.vue` 对齐，兼容后端动态路由加载。

### 4.2 菜单组织

新增一级菜单分组：

```text
本体建模
└── 单位字典
```

菜单种子数据通过 Flyway V4 写入 `sys_menu`，不手工操作数据库。

### 4.3 页面布局原则

单位字典页面参考现有 `http://localhost:8888/#/admin/dict/index` 的交互范式，但不照搬系统字典领域模型：

1. 左侧：单位分类树/列表，支持新增、编辑、删除、刷新。
2. 右侧：当前分类下单位条目表格，支持查询、新增、编辑、删除。
3. 顶部：按单位代码、符号、名称筛选。
4. 内置数据：禁删；语义字段锁定，只允许修改名称、排序、备注等非语义字段。
5. 扩展数据：可完整编辑和删除。

## 5. API 总体设计

### 5.1 单位分类 API

| 方法 | 单体实际路径 | 说明 | 权限 |
|------|--------------|------|------|
| GET | `/admin/ontology/unit-categories` | 分类列表 | `ontology_unit_view` |
| GET | `/admin/ontology/unit-categories/{id}` | 分类详情 | `ontology_unit_view` |
| POST | `/admin/ontology/unit-categories` | 新增分类 | `ontology_unit_add` |
| PUT | `/admin/ontology/unit-categories` | 修改分类 | `ontology_unit_edit` |
| DELETE | `/admin/ontology/unit-categories/{id}` | 删除分类 | `ontology_unit_del` |

### 5.2 单位条目 API

| 方法 | 单体实际路径 | 说明 | 权限 |
|------|--------------|------|------|
| GET | `/admin/ontology/units` | 单位分页/列表 | `ontology_unit_view` |
| GET | `/admin/ontology/units/{id}` | 单位详情 | `ontology_unit_view` |
| GET | `/admin/ontology/units/tree` | 分类+单位两级树 | `ontology_unit_view` |
| GET | `/admin/ontology/units/by-symbol/{symbol}` | 按符号解析 | `ontology_unit_view` |
| POST | `/admin/ontology/units` | 新增单位 | `ontology_unit_add` |
| PUT | `/admin/ontology/units` | 修改单位 | `ontology_unit_edit` |
| DELETE | `/admin/ontology/units/{id}` | 删除单位 | `ontology_unit_del` |
| GET | `/admin/ontology/units/convert` | 可选换算 | `ontology_unit_view` |

## 6. 演进预留

1. 后续“数据属性模块”可通过 `unitCategoryId` 引用 `ont_unit_category.id`。
2. 后续“实例建模模块”的 `measurementUnit` 可通过 `unitId` 引用 `ont_unit.id`，导出时取 `unit_symbol`。
3. 后续“公理规则模块”可做单位一致性校验：数值约束所绑定单位分类与 `measurementUnit` 所属分类一致。
4. 后续“命名空间模块”上线后，扩展单位可将 `namespace` 字段替换或补强为 `namespace_id` 外键/逻辑引用；首期为避免阻塞单位模块，先使用字符串命名空间。
