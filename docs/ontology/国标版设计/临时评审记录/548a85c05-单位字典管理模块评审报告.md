**问题 P2（中）— 外键约束与逻辑删除冲突**：
`ont_unit` 声明了物理外键 `CONSTRAINT fk_ont_unit_category FOREIGN KEY (category_id) REFERENCES ont_unit_category(id)`。但 `ont_unit_category` 使用逻辑删除（`del_flag`），分类被逻辑删除后记录仍在表中，外键不会阻止删除分类。然而真正的风险在反向场景：**若未来需要物理清理逻辑删除的分类记录，而 `ont_unit` 仍有引用该 `category_id` 的记录（哪怕也是逻辑删除态），物理删除将被外键阻止**。pig 上游 `sys_*` 表普遍不使用物理外键（仅靠应用层校验），youming 迁移设计文档也强调逻辑删除。建议移除物理外键，改为应用层校验（当前 Service 层 `removeCategory` 已校验"分类下存在单位不能删除"，足够），或在设计文档中明确外键保留的取舍理由。

**问题 P3（低）— `ont_unit_category` 缺少 `update_time` 默认值**：
`ont_unit` 与 `ont_unit_category` 的 `update_time` 均为 `DEFAULT NULL`（无默认值），而 `create_time` 有 `DEFAULT now()`。这是 pig 上游一贯写法（`create_time` 默认 now，`update_time` 由 MyBatis-Plus `FieldFill.UPDATE` 填充），属可接受惯例，仅作记录。

**问题 P5（低）— PRD §4.11.3 与实现的基准单位口径差异**：

**问题 P10（已知局限，不改代码）— 基准单位唯一性在并发场景存在竞态**：
`validateUnit` 中"同分类只能一个基准单位"通过应用层 `count` 查询实现。虽然 V4 脚本已建数据库部分唯一索引 `uk_ont_unit_category_base`（`WHERE del_flag='0' AND is_base_unit='1'`）作为兜底，但 Service 层的 `count` 检查与 `save` 之间非原子。并发新增两个基准单位时，应用层 count 都为 0，随后 DB 唯一索引会拒绝其中一条并抛 `DuplicateKeyException`。

**结论：保留不改。** 经探索发现：(1) pig-boot 运行时上下文未引入 pig-common-sentinel 的全局异常处理器，全项目无 `DuplicateKeyException` 处理先例；(2) `@Transactional` 下捕获该异常后事务仍会标记 rollback-only，处理有事务传播的坑。当前应用层 count 预检 + DB 唯一索引兜底已足以防止脏数据，并发场景下异常提示不友好是已知局限，后续在统一异常处理方案中一并解决。

**问题 P11（中）— `updateUnit` 扩展单位全量更新可能覆盖语义字段**：
`updateUnit` 对扩展单位（isBuiltin=0）直接 `updateById(unit)`，即用户提交什么就更新什么。若扩展单位已被其他模块引用（后续数据属性/实例），修改 `unit_code`/`unit_symbol`/`category_id`/`is_base_unit` 会破坏引用一致性。设计文档 §4.5 允许扩展单位改这些字段并"重新执行校验"，但未要求引用检查。

当前首期无引用模块，可接受。但**建议在设计文档演进预留中明确：扩展单位一旦被引用，其语义字段修改也需追加引用检查**（设计文档 §6 已预留第2/3点，但未强调"扩展单位被引用后也应锁定语义字段"）。

**问题 P12（中）— `getBySymbol` 返回 null 未统一处理**：
Controller `getBySymbol` 直接 `R.ok(ontUnitService.getBySymbol(symbol))`，若未匹配返回 `R.ok(null)`，前端 `res.data` 为 null。无明确"未找到"业务提示。PRD §4.11.4 该接口用于"导入与附录D兼容"，附录D导入 `%` 时若解析失败应明确报错而非静默 null。

**问题 P13（低）— `convert` 精度与 stripTrailingZeros**：
`divide(factor_to, 12, HALF_UP).stripTrailingZeros()`。`stripTrailingZeros` 在某些 JDK 版本对 `1E+3` 这类科学计数法输出可能导致前端展示异常（如 `1E3`）。pig 体系返回 BigDecimal 给前端 JSON 序列化通常没问题，但**建议**在 Controller 层或前端明确数值格式化策略，避免科学计数法展示。风险低。

**问题 P14（低）— `convert` 未校验 value 合理性**：
未校验 value 是否为 null（已校验）但未校验数值范围/负数。换算本身无业务范围约束，可接受。

**问题 P24（高）— 左侧分类树节点布局错位，分类名/编码/符号未同行显示**

**现象**：左侧单位分类列表中，以"电压"为例，`电压`、`内置`标签、`voltage / V` 三者应显示在同一行，实际渲染时 `voltage / V` 换行到了下一行，且与"电压"标签产生视觉错位。每条分类数据内部排版混乱。

**根因定位**（`web/src/views/ontology/unit/index.vue`）：

模板结构（第22-27行）：
```html
<span class="custom-tree-node">        <!-- 外层：display:flex; justify-content:space-between -->
  <span>                                  <!-- ❌ 内层包裹 span 无 flex 布局，为默认 inline -->
    <span class="label">电压</span>
    <el-tag ...>内置</el-tag>
    <span class="code">voltage / V</span>  <!-- ❌ .code 设 display:block，强制换行 -->
  </span>
  <span class="do">...</span>
</span>
```

样式（第480-485行）：
```css
.custom-tree-node .code {
    display: block;       /* ← 罪魁祸首：block 导致 code 换到下一行 */
    font-size: 12px;
    color: #999;
    margin-top: 2px;      /* ← 叠加 margin-top 使换行后视觉错位更明显 */
}
```

两个缺陷叠加：
1. **`.code` 设为 `display: block`**：`block` 元素独占一行，导致 `categoryCode / baseUnitSymbol`（如 `voltage / V`）被强制换到下一行显示，无法与"电压""内置"同行。
2. **内层包裹 `<span>`（第23行）无 `display: flex`**：即使去掉 `.code` 的 block，内层 span 是默认 inline 流，子元素（label、tag、code）在宽度不足时仍可能折行。缺少 `display: flex; align-items: center; flex-wrap: nowrap` 的横向排列约束。

**影响**：左侧分类树是用户操作单位字典的主入口，布局错位直接影响可用性和专业感，属于必须修复的视觉缺陷。设计文档 §6 验收点 4"登录管理员后可在'本体建模 / 单位字典'看到页面"隐含页面展示正常，当前样式缺陷使该验收点无法真正通过。

**修复建议**（仅建议，本次不改代码）：
```css
/* 内层包裹 span 改为 flex 横向排列 */
.custom-tree-node > span:first-child {
    display: flex;
    align-items: center;
    flex-wrap: nowrap;
    gap: 6px;
    min-width: 0;
}
/* .code 改为 inline，不强制换行 */
.custom-tree-node .code {
    display: inline;        /* 或 inline-block */
    font-size: 12px;
    color: #999;
    margin-top: 0;          /* 去掉错位 margin */
    margin-left: 6px;
    white-space: nowrap;
    overflow: hidden;
    text-overflow: ellipsis;
}
```
同时考虑分类节点宽度有限时 `voltage / V` 过长截断的处理（`text-overflow: ellipsis`）。

- 换算工具：PRD 标注"可选增强"，后端已实现 `convert`，前端 unit.ts 已封装 `convertUnit`，但页面无入口。**建议**补一个简单的换算弹窗或入口按钮，否则已实现的后端能力无前端出口，属于半成品。或明确声明首期不提供换算 UI。

**问题 P20（低）— 前端未使用 `fetchUnitTree`**：
unit.ts 声明了 `fetchUnitTree`（对应后端 `/units/tree`），但 `index.vue` 未调用——分类用 `fetchCategoryList`，单位用 `fetchUnitPage`。`tree` 接口在首屏加载场景（一次取全树）更高效，当前实现分类+分页两次请求。首期数据量小无影响，但 `tree` 接口成未使用代码。**建议**：要么首屏改用 `fetchUnitTree` 一次性渲染分类+展开首个分类单位，要么在设计文档注明 `tree` 为后续"单位选择器/级联"预留。

**问题 P21（低）— `el-tree` 用 `data`（扁平分类数组）而非树形结构**：

**问题 P22（低）— 前端 `unitForm` 初始化 `offsetValue: 0` 但 `factor: undefined`**：
`resetUnitForm` 新增时 `factor: undefined, offsetValue: 0`。新增单位若不填 factor，提交 `factor=null, offsetValue=0`。后端接收后 factor 为 null（换算时提示未配置），offsetValue=0。这与"首期不预置换算"一致，但 offsetValue 默认 0 可能误导用户以为已配置偏移。**建议**新增时 offsetValue 也默认 undefined/null，与 factor 一致。
