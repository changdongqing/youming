> - **M-4（版本声明）**：注明根 pom `spring-boot.version` 重复声明、以生效值 4.0.7 为准。

## 一、文档说明

### 1.1 本文档定位

《本体模板化治理整体设计文档.md》是**设计沟通稿**，回答"治理方案是什么、为什么这么设计、机制如何"。本 PRD 回答"**在本程序里做成什么功能、做到什么程度算交付**"：

- 设计稿给机制与论证 → PRD 给**贴合 youming 技术栈的可验收需求条目**（FR/NFR）。
- 设计稿给里程碑 M1–M5 → PRD 给**带数据库表、接口、菜单、验收标准的交付计划**。
- 设计稿聚焦治理机制 → PRD 明确**本功能是建模功能的前置依赖**，界定边界（治理 vs 建模）。

### 1.3 术语速读

- **六者**：类（Class）、对象属性（ObjectProperty）、数据属性（DatatypeProperty）、注释属性（AnnotationProperty）、数据类型（Datatype）、数值单位（Unit）。
- **治理资产**：本功能维护的可复用资产——属性模板库、**分类模板体系**（含外观/结构骨架/父子继承/编码）、单位注册表、注释属性注册表。
- **建模侧**：未来的本体建模功能（ontology modeling），是治理资产的消费方；本功能为它供给模板/单位/注册表。
- **方案 A / 方案 B**：属性序列化的"共享单一属性 + 多 domain"与"带前缀独立副本"两种策略（序列化属建模侧能力，本功能仅提供判据来源 `templateRef`）。
- **templateRef / unitRef / quantityKindRef**：溯源与单位引用字段，由治理资产产出、被建模侧消费。
- **分类模板体系**：类模板的升级形态，参照 GB/T 51269——模板可父子继承（子模板继承父模板字段+外观）、带分类编码（`classificationCode`，段位/位数规则）。例：`泵`模板 → 子模板`喷淋泵`/`给水泵`/`污水泵`，各继承泵的"额定流量/扬程/功率"并追加专属字段。
- **模板继承（template↔template）vs 类层级（class↔class）**：两套并行关系。模板继承是治理资产侧的原型复用（子模板继承父模板定义）；类层级是本体类的 `rdfs:subClassOf`（如"XX品牌喷淋泵 subClassOf 喷淋泵"），由建模侧消费治理资产产出，本功能提供分类树供给与维护能力（FR-9）。
- **个体实例对象（Individual）**：`owl:NamedIndividual`，是某个本体类的具体实例（如消防水泵房 1# 泵），属建模侧，本功能不维护个体。

## 二、产品背景与目标

### 2.1 背景

youming 将在本体建模功能中支持类的可视化建模、属性/关系编辑、RDF（OWL/XML 或 Turtle）序列化与解析。设计沟通稿指出，若不预先治理，建模侧会自然产生三类冗余与杂乱（依据设计稿第一节，结论作为方法依据吸收）：

| 问题类型 | 表现 | 后果 |
|---|---|---|
| 数据属性同名重复 | `name` 在多个类各自独立 IRI、定义重复 N 份 | RDF 膨胀、语义割裂、维护成本高 |
| 对象属性语义重复 | 跨本体反复出现 `contains`/`has`，各为独立 ObjectProperty | 同一关系语义无法复用 |
| 外观元数据散落 | 每个类硬编码 icon/color；注释属性散落硬编码 | 风格难统一、新增展示属性要改多处代码 |
| 数值单位裸字符串 | `unit` 为无结构字符串（`"USD"`/`"kg"`），无 IRI、无换算、无量纲归属 | 单位无身份、无法换算、无法量纲校验 |
| **类无分类层级/编码** | 类平铺、互相独立，无父子继承、无统一分类编码（如设备类"泵→喷淋泵→给水泵"无法表达层级与归属） | 无法表达"XX品牌喷淋泵是一种喷淋泵、喷淋泵是一种泵"的层级语义；分类无规范编码，检索/统计/对接国标困难 |

**前置治理的必要性**：建模功能一旦上线，用户会快速产生大量本体；若治理资产（模板/单位/注册表/**分类体系**）未就绪，冗余与杂乱会直接固化进 RDF，事后治理成本远高于事前。尤其分类层级与编码规范——一旦类被大量创建后再补层级和编码，IRI 迁移与数据回填成本极高，**必须在建模前先定**。因此本功能**先于建模功能建设**，作为建模侧的可复用资产底座与分类规范底座。

### 2.2 目标（SMART）

| 编号 | 目标 | 度量（→ 第十七节） |
|---|---|---|
| G1 | 提供可复用属性模板，覆盖数据属性 + 对象属性（同构共用一套机制） | 内置模板 ≥12 项，8 量纲覆盖 |
| G2 | 提供分类模板体系（外观+结构骨架+**父子继承**），组合属性模板 | 内置分类树 ≥1 棵（设备类，含 ≥2 级、≥3 子类），外观 ≥3 套 |
| G3 | 提供规范单位注册表（引用 QUDT），具备换算与量纲校验 | 量纲 ≥8 类，换算正确率 100% |
| G4 | 注释属性集中注册表化，驱动序列化/解析（建模侧消费） | 注册表 ≥10 项，0 硬编码 |
| G5 | 治理资产可持久化、可治理（CRUD + 弃用 + 提升）、对建模侧稳定供给 | 供给接口可用率 100%，回归 0 失败 |
| G6 | 提供国标式分类编码规范与类分类树（subClassOf）治理能力 | 编码规则可配置、分类树可维护、类层级可供给建模侧 |

### 2.3 业务价值

- **对建模侧（未来）**：建模时从模板挑选 + 微调，而非从零建模，效率提升、风格统一、语义一致。
- **对治理员**：沉淀组织级可复用资产，控制模板库质量与一致性。
- **对下游消费**：治理资产产出的 `templateRef`/`unitRef` 使未来 RDF 可去重、可换算、可被 SPARQL 查询。

## 三、本程序现状与基线

### 3.1 后端现状

| 项 | 现状 | 对本功能的影响 |
|---|---|---|

| 模块拆分惯例 | pig 惯例为 `xxx-api`（Feign/DTO/常量）+ `xxx-biz`（Controller/Service/Entity）拆分 | 本期 **仅建 `pig-ontology-biz` 单模块**，供给接口走 HTTP；未来建模侧微服务化需 Feign 时再抽 `pig-ontology-api` |
| 运行形态 | 微服务版（Nacos）+ 单体版 pig-boot（9999，context-path `/admin`，直连 PG/Redis） | 治理功能需在两种形态下均可用 |

### 3.2 数据库现状

| 项 | 现状 | 对本功能的影响 |
|---|---|---|
| 数据库 | PostgreSQL 18，业务库 `mingwanwudb` | 治理表建于此库 |
| 库结构管理 | Flyway，脚本位于 `server/pig-common/pig-common-data/src/main/resources/db/migration/`，现有 V1（结构）/V2（种子）/V3（Quartz），**最大版本号 V3** | **治理表用 V4+ 脚本**；内置模板/注册表项作为种子数据写入；禁止改已应用脚本 |
| 表命名 | `sys_xxx`（系统表，约 28 张）、`gen_xxx`（代码生成）、`qrtz_xxx`（定时任务），**无无前缀业务表**，按模块前缀分类 | 治理表用前缀 `ont_`（如 `ont_property_template`），与现有规范一致、无冲突 |
| 审计字段范式 | pig 全表统一：`create_by varchar(64)`、`create_time timestamp DEFAULT now()`、`update_by varchar(64)`、`update_time timestamp`、`del_flag char(1) DEFAULT '0'`（值域 `'0'/'1'` 字符串） | 治理表沿用同一范式；**布尔语义字段统一用 `char(1) '0'/'1'`**（与 del_flag 一致），不用 smallint |
| 菜单与权限 | `sys_menu` 表 + 权限标识驱动前端路由与按钮；现有 menu_id 占用段：1000-2999、4000-4014、**9000-9910**（codegen 模块），最大值 9910 | 治理功能菜单与权限点通过 Flyway 种子 INSERT 进 `sys_menu`，menu_id 用 **10000+** 段，权限标识用 `ont_*` |
| SQL 方言 | PG 方言但偏保守：用 `COMMENT ON TABLE/COLUMN`、`DEFAULT now()`；**未用** serial/bigserial/timestamptz/boolean/text 类型，主键统一 `bigint NOT NULL` + 显式值，时间用 `timestamp`，布尔用 `char(1)` | 新增脚本沿用同一保守风格，便于维护一致性 |

### 3.3 前端现状

| 项 | 现状 | 对本功能的影响 |
|---|---|---|
| 前端框架 | Vue 3.5 + Element Plus 2.13 + Vite 8 + TypeScript（pig-ui），含 Pinia/vue-router 4/vue-i18n 9/axios | 治理页面用同栈 |

## 五、名词与约定

### 5.1 六者治理形态（吸收设计稿第二节结论，本版升级"类"）

| 概念 | 模板化适用性 | 治理形态 | 进入 RDF? | 本功能是否建设 |
|---|---|---|---|---|
| 数据属性 | ⭐⭐⭐ 高 | 属性模板 + 复用副本 | 方案A/B（建模侧） | ✅ FR-1 |
| 对象属性 | ⭐⭐⭐ 高 | 属性模板 + 复用副本（同构） | 同上 | ✅ FR-1 |
| 类 | ⭐⭐⭐ 高 | **分类模板体系**（外观+结构骨架+父子继承+分类编码） | 不进入（治理资产侧） | ✅ FR-2/FR-8/FR-9 |
| 数值单位 | ⭐⭐⭐ 高 | 引用 QUDT + 量纲/前缀分层注册表 | 以 IRI 引用 | ✅ FR-3 |
| 注释属性 | ⭐⭐ 中 | 元属性注册表（非副本） | 本身即全局 | ✅ FR-4 |
| 数据类型 | ⭐ 不适合 | —（XSD 标准枚举） | — | ❌ 不做 |

### 5.2 关键约定

- **模板不含 IRI**：`templateCode`/`classificationCode` 仅治理期标识，不进 `rdf:about`；IRI 由建模侧序列化时赋予。
- **复制字段值，不是 IRI**：建模侧从模板实例化时复制字段并挂 `templateRef` 溯源（由建模侧负责，本功能只产出模板与 `templateCode`）。
- **属性同构**：数据属性与对象属性共用一套 `ont_property_template` 表，以 `kind` 字段区分。
- **单位引用而非自建**：不在本程序重定义 `qudt:Unit` 等类，只引用 QUDT 单位 IRI 作为取值。
- **分类模板不进 RDF**：分类模板是治理资产侧的原型，不直接序列化；RDF 层的类是独立资源，类层级走 `rdfs:subClassOf`（由建模侧消费治理资产产出，本功能供给分类树）。
- **两套并行关系（核心边界）**：
  - **模板继承**（template↔template）：治理资产侧，子分类模板继承父分类模板的字段+外观（FR-2）。
  - **类层级**（class↔class）：本体类间的 `rdfs:subClassOf`，由建模侧消费治理资产产出（FR-9 供给建议与只读镜像）。
  - 二者不混淆：模板继承是"原型复用"，类层级是"本体语义"。子模板继承父模板 ≠ 子类 subClassOf 父类，但建模侧从子模板派生类时，可同时建议该类 `subClassOf` 从父模板派生的类。
- **类层级权威源**：建模侧是 `owl:Class` 实体与类层级关系的**唯一权威源**。本功能对类层级**只做两件事**：(1) 基于 `templateRef` + 分类模板父链**供给建议**（suggest）；(2) 从建模侧**只读同步镜像**类层级到 `ont_class_hierarchy` 供治理侧展示与统计，**不主动创建/登记类层级**（FR-9 边界，呼应 R-15）。
- **边界**：本功能**只产治理资产 + 供给接口 + 治理 UI**；序列化/解析/建模画布/个体实例属建模侧（未来功能），本功能仅为其提供 `templateRef` 判据、单位 IRI、分类树与编码规范。

### 5.3 三层模型与国标对照（GB/T 51269 思路）

参照 GB/T 51269《信息模型分类和编码标准》的"分类体系 → 具体类目 → 实际对象"三层，本功能的三层对应：

```
分类模板层（治理资产，本功能维护）
  分类模板：泵 ——继承——> 喷淋泵模板 ——继承——> 某品牌喷淋泵模板
  （带分类编码：泵=30 / 喷淋泵=30-01 / 给水泵=30-02 / 污水泵=30-03）
        │ applyClassTemplate（建模侧实例化，挂 templateRef）
        ▼
本体类层（建模侧，有 IRI）
  泵(owl:Class) ——subClassOf——> 喷淋泵(owl:Class) ——subClassOf——> XX品牌喷淋泵(owl:Class)
        │ rdf:type（建模侧）
        ▼
个体实例层（建模侧）
  消防水泵房 1#泵（owl:NamedIndividual，rdf:type XX品牌喷淋泵）
```

| 层 | GB/T 51269 对应 | 本功能职责 |
|---|---|---|
| 分类模板 | 国标分类编码体系的"分类节点 + 编码" | ✅ 维护（FR-2/FR-8） |
| 本体类 | 国标"具体类目"（有编码的细类） | △ 供给分类树供建模侧建类（FR-9） |
| 个体实例 | 国标"实际对象" | ❌ 建模侧，本功能不维护 |

> GB/T 51269 是方法参照（提供"层级分类 + 编码规范"的思路），非逐条遵从——本功能的编码规则可配置，不硬绑国标段位。

## 七、功能需求详述

> 每条需求标注：**优先级**、**里程碑**、**用户故事**、**功能描述**、**验收标准（AC）**、**数据契约**（指向第九节）、**接口**（指向第十节）。

### FR-1 属性模板库（数据属性 + 对象属性）

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 里程碑 | M1 |
| 依赖 | 无（前置：搭建 pig-ontology 模块骨架 + V4 建表） |
| 用户故事 | 作为本体治理员，我希望维护一个属性模板库（数据属性 + 对象属性同构），内置常用模板并支持自定义，从而让建模侧能从模板派生属性而非从零建模。 |

**功能描述：**

1. 单表 `ont_property_template` 承载属性模板，`kind` 字段区分 `datatype`/`object`，二者同构共用一套 CRUD。
2. 内置模板（`source='builtin'`）随 Flyway 种子数据分发，覆盖：
   - 数据属性：`name/description/email/phone/price/amount/createdDate/isActive`（基础/联系/货币/时间/状态分组）。
   - 对象属性：`contains/belongsTo/hasPart/references`（containment/attribution 分组）。
3. 自定义模板（`source='custom'`）由治理员 CRUD 维护，含弃用标记（`deprecated`）。
4. 模板字段：`templateCode`（唯一标识）、`kind`、`label`、`description`、`category`、`type`（datatype 专属）、`isIdentifier`、`unitRef`（预设单位，FR-3 交汇）、`values`（枚举值）、`defaultCardinality`（object 专属）。
5. 治理 UI：列表（按 kind/category 过滤 + 关键字搜索）、新增/编辑/弃用/删除、字段预览。
6. 供给接口（FR-5）：供建模侧按 kind/category 拉取模板列表与详情。

**验收标准（AC）：**

- AC-1.1：Flyway 种子写入 ≥12 个内置模板（8 数据属性 + 4 对象属性），`source='builtin'`、`category` 分组正确。
- AC-1.2：治理员新增 custom 模板 `weight`（kind=datatype, type=decimal, unitRef=KiloGM），持久化到 `ont_property_template`，`source='custom'`。
- AC-1.3：`templateCode` 唯一约束生效，重复新增返回业务错误（非 500）。
- AC-1.4：按 `kind=object` 过滤时，数据属性模板不出现在结果中。
- AC-1.5：弃用模板（`deprecated=1`）默认不在供给接口默认列表返回，但详情可查。
- AC-1.6：内置模板不可编辑/删除（`source='builtin'` 校验），仅可弃用查看。
- AC-1.7：删除 custom 模板时，若已被建模侧引用（后续由建模侧反馈计数，本期接口预留），给出引用提示；本期无引用计数时直接软删除。
- AC-1.8：供给接口返回的模板字段完整（含 `templateCode`/`kind`/`label`/`type`/`unitRef`/`defaultCardinality` 等）。

**数据契约：** `ont_property_template` 表（见 9.1）。**接口：** `/admin/ont/property-template/**`（见 10.1）。

### FR-2 分类模板体系（外观 + 结构骨架 + 父子继承 + 编码）

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 里程碑 | M2 |
| 依赖 | FR-1（结构骨架引用属性模板）、FR-8（分类编码） |
| 用户故事 | 作为本体治理员，我希望维护一棵**可继承的分类模板树**（如"泵→喷淋泵/给水泵/污水泵"），子模板继承父模板的字段与外观，并带分类编码，让建模侧套用即可得到带层级的规范本体类，而非平铺独立的类。 |

**功能描述：**

1. **分类模板**（升级原"类模板"）：单表 `ont_class_template` 承载，融合外观（icon/color）+ 结构骨架（propertyRefs）+ **父子继承**（`parent_id`）+ **分类编码**（`classification_code`，见 FR-8）。
2. **父子继承机制（核心新增）**：
   - `parent_id` 指向父分类模板，形成分类树（参照 GB/T 51269 分类层级、Brick 设备 `rdfs:subClassOf` 树）。
   - 子模板**继承**父模板的结构骨架（propertyRefs）与外观（icon/color），可在继承基础上**追加**专属字段、**覆盖**外观。
   - 继承为"计算视图"：供给接口返回子模板时，合并父链上的全部 propertyRefs（去重，子模板同名 propertyTemplateCode 覆盖父）。
   - 例：`泵`模板带 `额定流量/扬程/功率/介质`；`喷淋泵`继承之并追加 `喷淋系统编号`；`给水泵`继承之并追加 `供水压力等级`。
3. **结构骨架**：子表 `ont_class_template_ref`（`class_template_id` + `property_template_code` + `ref_type=property/relationship` + `sort_order` + `inherit_flag`），可指向 FR-1 属性模板，形成"分类模板→属性模板"嵌套复用。
4. **内置分类树（设备类，参照 Brick）**：≥1 棵、≥2 级、≥3 子类。示例：
   ```
   设备(30) ── 泵(30-01) ── 喷淋泵(30-01-01)
                       └─ 给水泵(30-01-02)
                       └─ 污水泵(30-01-03)
   ```
   外观内置 ≥3 套（business-blue/retail-warm/nature-green）。
5. 分类模板**不进 RDF**（由建模侧保证）；本功能只维护模板树与供给。类层级（`subClassOf`）见 FR-9。
6. 治理 UI：**分类树视图**（左树右表/详情），节点显示编码+label+继承来源；新增子节点时可选父节点、自动继承字段预览；外观卡片预览；结构骨架属性清单（区分"继承自父/本节点新增"）。

**验收标准（AC）：**

- AC-2.1：内置设备分类树 ≥1 棵、≥2 级、≥3 子类（如泵下喷淋泵/给水泵/污水泵），编码按 FR-8 规则生成（如 30-01-01）。
- AC-2.2：套用外观模板 `business-blue`，子模板未覆盖外观时继承父外观；子模板覆盖时用子模板值。
- AC-2.3：结构骨架继承：`喷淋泵`模板供给接口返回的属性清单 = 父`泵`的 4 属性 + 本节点追加的 `喷淋系统编号`（共 5 个，去重）。
- AC-2.4：`propertyRefs` 指向不存在的 `templateCode` 时，保存校验失败并提示（不静默）。
- AC-2.5：子模板与父模板同名 `propertyTemplateCode` 时，子模板覆盖父（同名属性以子为准），并在 UI 标注"已覆盖父"。
- AC-2.6：分类树禁止成环：设 `喷淋泵`的 parent 为其后代会保存失败并提示。
- AC-2.7：删除有子节点的分类模板时，提示"存在子节点，不可直接删除"（需先处理子节点）。
- AC-2.8：分类模板相关表无任何 RDF 序列化字段（边界正确）。

**数据契约：** `ont_class_template`、`ont_class_template_ref`（见 9.2/9.3）。**接口：** `/admin/ont/class-template/**`（见 10.2）。

### FR-3 单位注册表（引用 QUDT）

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 里程碑 | M3 |
| 依赖 | 无（可与 M1 并行；"模板预设单位"处与 FR-1 交汇） |
| 用户故事 | 作为本体治理员，我希望维护一个引用 QUDT 的单位注册表（按量纲分组、带换算系数），让建模侧选规范单位、做同量纲换算与跨量纲校验。 |

**功能描述：**

1. 两表承载：`ont_quantity_kind`（量纲，含 `dimensionVector`）+ `ont_unit`（单位，含 `qudtIri/symbol/label/quantityKindId/conversionMultiplier/conversionOffset/scalingOf/ucumCode`）。
2. 内置常用子集（非全量 2927 个），按量纲分组：长度/质量/时间/温度/面积/体积/货币/数据量，每个量纲至少含基准单位 + ≥2 派生单位，均带 `conversionMultiplier`。
3. QUDT 单位 `qudtIri` 为规范身份；`symbol` 冗余存储保降级。注册表锁定 QUDT 具体版本快照（AC-3.7）。
4. 治理 UI：按量纲分组浏览单位、新增/编辑/弃用 custom 单位、展示换算系数与派生关系（scalingOf）。
5. 供给接口（FR-5）：供建模侧按量纲查单位、回填单位、执行换算。
6. 换算能力 `convertValue(value, fromIri, toIri)`：同量纲返回换算值，不同量纲返回 null（不报错）。温度等有偏移单位用 conversionOffset。
7. 属性模板（FR-1）可预设 `unitRef`（如 length 模板预设 `unit:M`），建模侧派生时继承。

**验收标准（AC）：**

- AC-3.1：内置注册表覆盖 ≥8 量纲，每类含基准 + ≥2 派生单位。
- AC-3.2：单位 `KiloGM` 的 `qudtIri='http://qudt.org/vocab/unit/KiloGM'`、`symbol='kg'`、`quantityKindLabel='Mass'`、`conversionMultiplier` 齐备。
- AC-3.3：`convertValue(1, KiloM, M)===1000`；`convertValue(100, CentiM, M)===1`；`convertValue(1, KiloGM, USD)===null`（量纲不同）。
- AC-3.4：温度等有偏移单位（如华氏度相对摄氏度）换算正确使用 conversionOffset。
- AC-3.5：`qudtIri` 唯一约束生效；重复新增返回业务错误。
- AC-3.6：属性模板 `length` 预设 `unitRef=.../unit/M`，供给接口返回该模板时携带预设单位，建模侧可继承。
- AC-3.7：注册表记录所用 QUDT 版本快照（如 `ont_unit` 表或元数据表存版本标识），`symbol` 冗余存储以支持 QUDT IRI 漂移时降级。
- AC-3.8：换算浮点精度风险：关键场景优先使用 QUDT 的科学计数系数（conversionMultiplierSN），或换算结果保留合理有效位（见风险 R-7）。

**数据契约：** `ont_quantity_kind`、`ont_unit`（见 9.4/9.5）。**接口：** `/admin/ont/unit/**` + `/admin/ont/unit/convert`（见 10.3）。

### FR-8 分类编码规范（GB/T 51269 式）

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 里程碑 | M2 |
| 依赖 | FR-2（编码挂在分类模板上） |
| 用户故事 | 作为本体治理员，我希望分类模板带国标式分类编码（如"泵=30-01、喷淋泵=30-01-01"），编码规则可配置、编码随层级自动生成，从而检索/统计/对接国标有统一标识，看编码即知在分类树的位置。 |

**功能描述：**

1. **编码规则可配置**：`ont_classification_rule` 表（或元数据表）定义编码规则——分隔符（默认 `-`）、每级位数（默认 2 位）、编码基数（如大类从 30 起）、是否零填充。参照 GB/T 51269 思路但**不硬绑国标段位**，规则可改。
2. **编码随层级自动生成**：新增子分类模板时，按父编码 + 同级序号 + 规则自动生成 `classification_code`；治理员可手动覆盖（受规则校验）。
3. **编码承载层级**：编码前缀即父链（如 `30-01-01` 的父是 `30-01`，祖父是 `30`），支持"按编码前缀查子树"。
4. **唯一性校验**：`classification_code` 在分类树内唯一；重复返回业务错误。
5. **编码与 templateCode 区分**：`classification_code` 是规范分类编码（受规则约束、承载层级）；`templateCode` 是人类可读标识（自由）。二者并存，`classification_code` 供建模侧/下游检索统计，`templateCode` 供溯源。
6. 治理 UI：编码规则配置页；分类树节点展示编码；新增子节点自动预览编码；编码违规红色提示。
7. 内置设备分类树种子带规范编码（如设备=30/泵=30-01/喷淋泵=30-01-01…）。

**验收标准（AC）：**

- AC-8.1：编码规则可配置（分隔符/位数/基数/零填充），改规则后新节点按新规则生成（旧编码不变）。
- AC-8.2：在 `泵(30-01)` 下新增第 1 个子节点，自动生成 `30-01-01`；第 2 个生成 `30-01-02`。
- AC-8.3：`classification_code` 唯一约束生效，重复新增返回业务错误。
- AC-8.4：按编码前缀 `30-01` 查询能返回其下全部子节点（30-01-01/02/03）。
- AC-8.5：手动覆盖编码时，校验其与父编码前缀一致 + 符合规则，否则拒绝。
- AC-8.6：内置设备分类树种子编码符合规则（30/30-01/30-01-01…）。
- AC-8.7：`classification_code` 与 `templateCode` 并存且均可查询，不互相覆盖。

**数据契约：** `ont_class_template.classification_code`、`ont_classification_rule`（见 9.2/9.7）。**接口：** `/admin/ont/classification-rule/**` + 编码生成内嵌于 FR-2 接口（见 10.2）。

### FR-9 类分类树（subClassOf）治理

| 项 | 内容 |
|---|---|
| 优先级 | P1 |
| 里程碑 | M2 |
| 依赖 | FR-2（分类模板树作为类层级的来源建议） |
| 用户故事 | 作为本体治理员/建模侧，我希望治理资产侧能**供给"本体类分类树"（`rdfs:subClassOf` 层级）的建议与只读镜像视图**，让建模侧从子分类模板派生类时，获得建议父类（来自父分类模板派生的类），从而本体类有规范的层级语义（"XX品牌喷淋泵是一种喷淋泵"）。建模侧是类层级权威源，治理侧只做供给建议与只读展示。 |

**功能描述：**

1. **边界**：本功能**不创建本体类、不主动登记类层级**（类与类层级属建模侧权威，见 5.2 + R-15）。本功能对类层级只做两件事：
   - (a) **供给建议**：建模侧创建类时，治理侧据其 `templateRef` 推荐父类（来自父分类模板派生类），供建模侧确认后由建模侧写入 `subClassOf`。
   - (b) **只读镜像视图**：从建模侧同步类层级到 `ont_class_hierarchy`（镜像源是建模侧），供治理侧展示与统计；镜像**只读，治理侧不写**。
2. **类层级镜像表** `ont_class_hierarchy`：**只读镜像**建模侧类间的 `subClassOf` 关系（`child_class_iri` + `parent_class_iri` + `source_template_ref` 溯源 + `sync_status` 同步状态）。这是治理侧维护的"类层级视图"，**数据来源是建模侧推送/同步**，治理侧不提供写入接口。
3. **从分类模板推荐类层级**：供给接口 `GET /supply/v1/class-hierarchy/suggest?templateCode=` 返回"若从此模板派生类，建议的父类 IRI（来自父分类模板）"。
4. **分类树视图（类层，只读）**：治理 UI 展示已镜像的本体类分类树（subClassOf），与分类模板树（FR-2）对照--模板树是原型，类树是建模侧实例化结果的镜像。
5. **环路校验**：环路校验在**建模侧**执行（它写入 subClassOf）；治理侧镜像入库时仅做基本格式校验，不做环路校验（避免与建模侧权威源冲突）。
6. **与 Brick 对齐**：类层级语义与 Brick 的 `rdfs:subClassOf` 一致；FR-7 导入 Brick 类为**分类模板**（治理侧），其 subClassOf 关系映射到分类模板树（FR-2 parent_id），**不直接写入 `ont_class_hierarchy`**（后者只镜像建模侧类层级）。

**验收标准（AC）：**

- AC-9.1：供给接口 `suggest` 对子分类模板 `喷淋泵` 返回建议父类（来自父模板`泵`派生的类，若建模侧已镜像）。
- AC-9.2：建模侧推送一条 `XX品牌喷淋泵 subClassOf 喷淋泵`，治理侧 `ont_class_hierarchy` **只读镜像入库**，带 `source_template_ref` 溯源与 `sync_status`。
- AC-9.3：治理侧**不提供** `POST /admin/ont/class-hierarchy` 主动登记接口（边界正确，类层级权威在建模侧）；只有只读查询与建模侧同步接口。
- AC-9.4：类层级视图能展示已镜像类树，并与分类模板树对照（模板->类的映射可见）。
- AC-9.5：FR-7 导入 Brick 类时，映射为分类模板树（parent_id），**不写入 ont_class_hierarchy**（后者只镜像建模侧）。
- AC-9.6：边界正确：本功能不创建 `owl:Class` 实体（类实体属建模侧），类层级关系由建模侧权威写入、治理侧只读镜像。

**数据契约：** `ont_class_hierarchy`（见 9.8，只读镜像表）。**接口：** `/admin/ont/class-hierarchy/**`（只读）+ `/supply/v1/class-hierarchy/suggest`（见 10.2/10.5）+ 建模侧同步接口（见 10.7）。

| NFR-11 | 模块隔离 | `pig-ontology` 模块独立编译，依赖 `pig-common-data`（Flyway/MyBatis-Plus）、`pig-common-core`（R/权限）、`pig-common-security`；不反向依赖 upms/visual。本期仅建 `pig-ontology-biz` 单模块（不拆 api/biz），供给接口走 HTTP+用户 token 鉴权（`@HasPermission ont_supply_view`）。 |
| NFR-12 | 继承视图性能（S-1） | 分类模板继承视图（AC-2.3）合并父链 propertyRefs，树深 ≤5 时 P95 <300ms；对深树或高频访问做 Caffeine 本地缓存（key=templateCode，TTL 5min，模板变更时失效）。 |
| NFR-13 | 环路检测（S-2） | 分类模板父子继承的环路检测（AC-2.6）在 Service 层 DFS 遍历父链（自底向上查 parent_id 至根），时间复杂度 O(树深)；建议树深上限 5 级（R-13）。 |
| NFR-14 | 供给三态标记（S-7） | 继承视图供给接口返回的每条属性带 `source` 三态标记：`node`(本节点新增)/`inherited`(继承自父)/`overridden`(覆盖父同名)，供前端区分展示。 |
| NFR-15 | 前端试算防抖（S-8） | 单位换算试算区（12.4）前端本地拉系数后计算，避免每次按键调 /convert 接口；若必须调接口则 debounce 300ms。 |

## 十一、用户故事与场景

### 11.1 场景一：治理员维护属性模板（FR-1/FR-6）

1. 治理员登录 pig-ui，进入"本体治理 → 属性模板"。
2. 查看内置 12 个模板（name/contains 等），按 category 分组。
3. 新增 custom 模板 `weight`（datatype, decimal, 预设 unitRef=`.../unit/KiloGM`）。
4. 把已有属性快照（来自设计稿）提升为模板：调 `/promote`。
5. **结果**：模板库就绪，建模侧可拉取。

### 11.2 场景二：建模侧拉取模板（FR-5，未来对接）

1. 建模侧（未来功能）调 `/supply/v1/property-templates?kind=datatype`。
2. 获得模板列表，用户选 `name` 派生到 Customer/Product/Store。
3. 建模侧据 `templateCode='name'` 挂 `templateRef`，为后续序列化方案 A 提供判据。
4. **结果**：治理资产稳定供给建模侧。

### 11.3 场景三：单位注册表与换算（FR-3）

1. 治理员进入"本体治理 → 单位注册表"，按量纲浏览。
2. 长度量纲下有 M/CentiM/MilliM/KiloM，均带 conversionMultiplier。
3. 建模侧调 `/supply/v1/units/convert?value=1&fromIri=.../KiloM&toIri=.../M` 得 1000。
4. 误把质量单位换算为货币：返回 `{result:null, reason:'quantity kind mismatch'}`。
5. **结果**：单位有身份、可换算、可量纲校验。

### 11.4 场景四：设备分类模板树与继承（FR-2/FR-8，核心新场景）

1. 治理员进入"本体治理 → 分类模板"，新建分类树 `equipment`，配置编码规则（分隔符 `-`、每级 2 位、基数 30）。
2. 建根节点 `设备(30)`；建子节点 `泵(30-01)`，带属性 `额定流量/扬程/功率/介质` + 外观 business-blue。
3. 在 `泵` 下建三个子节点：`喷淋泵(30-01-01)`、`给水泵(30-01-02)`、`污水泵(30-01-03)`，编码自动生成。
   - `喷淋泵` 追加 `喷淋系统编号`；`给水泵` 追加 `供水压力等级`；`污水泵` 追加 `排污方式`。
4. 建模侧（未来）调 `/supply/v1/class-template/spray-pump/inherited`，获得合并视图：父`泵`的 4 属性 + 本节点 1 属性 = 5 属性 + 外观（继承自泵）。
5. 建模侧据返回的 `templateCode='spray-pump'` 派生本体类 `XX品牌喷淋泵`，挂 `templateRef`。
6. 建模侧调 `/supply/v1/class-hierarchy/suggest?templateCode=spray-pump`，获建议父类（来自父模板`泵`派生的类），确认后登记 `XX品牌喷淋泵 subClassOf 泵`。
7. **结果**：建模得到带层级语义、带编码、字段继承的规范本体类，而非平铺独立类；分类树可检索统计。

### 11.5 场景五：结构骨架复用（FR-2，审计类，非分类树用法）

1. 治理员建 `audit-mixin` 分类模板（无父节点，平铺用法），propertyRefs 指向 4 个审计属性模板。
2. 建模侧调 `/supply/v1/class-template/audit-mixin/inherited`，获得展开的 4 属性清单。
3. 建模侧套用到 Order/Invoice/Payment 三类，各注入 4 属性。
4. **结果**：避免 12 次手填，风格统一。

### 11.6 场景六：注释属性注册表驱动（FR-4）

1. 治理员新增注释属性 `ont:displayName`（localName/rangeXsd/appliesTo）。
2. 建模侧序列化器调 `/supply/v1/annotation-properties` 获全量注册表。
3. 建模侧遍历注册表驱动序列化/解析，无需硬编码 `ont:` 字面量。
4. **结果**：新增展示属性只改注册表一处。

### 11.7 场景七：参考本体复用（FR-7，含 Brick 类导入）

1. 治理员进入"本体治理 → 参考本体库"，打开 QUDT。
2. 按量纲浏览，选中 `unit:KiloGM`，点"导入到单位注册表"。
3. `ont_unit` 新增 custom 单位（含 qudtIri/symbol/换算系数），`source_ref='qudt'`。
4. 打开 Brick，浏览设备类层次（`rdfs:subClassOf`），选中 `brick:Pump` 及其子类，点"导入为分类模板"。
5. Brick 的 subClassOf 关系映射为 `ont_class_template.parent_id`，形成分类树；同时登记到 `ont_class_hierarchy`。
6. **结果**：复用 Brick 现成分类树（国标式层级），不自造；与 FR-2/FR-9 打通。

## 十八、不做事项（Out of Scope）

> 与设计稿第六/七节"范围与不做什么"一致，并明确本功能与建模功能的边界。

| 不做项 | 理由 |
|---|---|
| **数据类型模板化** | XSD 标准枚举是既定有限集合，原子值域无结构可复用；枚举值集合归到类模板或独立字典 |
| **全量内置 2927 个 QUDT 单位** | 本地注册表只抽常用子集（8 类量纲），按需扩展（FR-7 导入） |
| **内置 QUDT schema** | 不在本程序重定义 `qudt:Unit` 等类，只引用 QUDT 单位 IRI 作为取值 |
| **OWL 推理实现** | 换算由本程序 Java 代码执行，不依赖 OWL 推理机——工具行为非本体语义 |
| **序列化/解析（方案 A/B）** | 属未来建模功能；本功能只产 templateCode/classificationCode 作为判据来源 |
| **建模画布/可视化编辑** | 属未来建模功能；本功能是前置治理底座 |
| **个体实例对象（owl:NamedIndividual）** | 实际对象（如消防水泵房那台泵）属建模侧；本功能只到"类"层，不维护个体 |
| **本体类实体创建** | owl:Class 实体属建模侧；本功能只维护分类模板与类层级登记（FR-9 边界） |
| **多继承分类模板** | 分类模板 parent_id 为单父（单继承）；多继承留待后续（Brick 多继承导入时取主父类，见 R-16） |
| **实时货币汇率** | 货币换算标注"参考汇率"或走外部源，不在治理范围（R-7） |
| **Builtin 模板可编辑** | builtin 随 Flyway 分发只读；复用沉淀走 custom（AC-1.6） |
| **强制迁移** | 本功能为新建功能，无旧治理资产需迁移 |

| 数据属性 | ✅ | 属性模板 + 副本 | 方案A/B（建模侧） | 全局属性+多domain | 同名重复 | FR-1 |
| 对象属性 | ✅ | 属性模板 + 副本（同构） | 同上 | 全局属性+多domain | 跨本体语义重复 | FR-1 |
| 类（分类模板） | ✅ | 分类模板体系（外观+骨架+父子继承+分类编码） | 不进入（治理资产侧） | GB/T 51269 分类层级 + OWL subClassOf | 类无层级/编码、icon/color+结构重复 | FR-2/FR-8/FR-9 |
| 数值单位 | ✅ | 引用 QUDT + 量纲/前缀分层注册表 | 以 IRI 引用 | QUDT 全局单位本体 | 裸字符串无身份/换算 | FR-3 |
| 注释属性 | ✅(中度) | 注册表（非副本） | 本身即全局 | 注释属性全局唯一 | 声明散落硬编码 | FR-4 |
| 数据类型 | ❌ | — | — | XSD标准枚举 | 无复用空间（叶子） | 不做（OoS） |
| 个体实例 | ❌ | — | 建模侧 | owl:NamedIndividual | 实际对象 | 不做（OoS，属建模侧） |

**核心洞察：**
- 数据属性与对象属性**同构**，共用一套属性模板机制（FR-1，M1 首落地）。
- **类模板升级为分类模板体系**（v1.1）：模板间父子继承 + GB/T 51269 式分类编码（FR-2/FR-8）；类层级（subClassOf）由建模侧消费治理资产产出，本功能供给与维护（FR-9）。模板继承与类层级是两套并行关系。
- 分类模板组合属性模板，与未来建模侧的整本体模板形成三层（整本体模板 > 分类模板 > 属性模板）。
- 单位治理**引用而非自建** QUDT 本体，量纲/前缀分层天然模板化（FR-3，M3）。
- 注释属性做注册表，不做副本（FR-4，M4）。
- 数据类型不模板化；枚举值集合治理归到分类模板或独立字典。
- 个体实例（owl:NamedIndividual）属建模侧，本功能不维护。
- **本功能是建模功能的前置底座**，只产治理资产 + 供给接口 + 治理 UI，不侵入序列化/建模/个体。

## 附录 B：QUDT 引用契约

### B.1 命名空间（供未来建模侧序列化时声明）

```
xmlns:qudt="http://qudt.org/schema/qudt#"
xmlns:unit="http://qudt.org/vocab/unit/"
xmlns:quantitykind="http://quvocab/quantitykind/"
```

> 注：本功能不生成 RDF；本附录为建模侧（未来）提供引用契约，确保治理资产产出的 unitRef 与建模侧序列化一致。

### B.2 QUDT 核心谓词速查

| 谓词 | 含义 | 示例 |
|---|---|---|
| `qudt:hasQuantityKind` / `qudt:unitForQuantityKind` | 单位→量纲归属 | `unit:M → quantitykind:Length` |
| `qudt:conversionMultiplier` | 相对基准换算系数 | `unit:CentiM = 0.01` |
| `qudt:conversionOffset` | 换算偏移（温度等） | 华氏度相对摄氏度 |
| `qudt:scalingOf` | 派生单位→基准单位 | `unit:KiloM → unit:M` |
| `qudt:hasDimensionVector` | 量纲向量 | `A0E0L1I0M0H0T0D0`（长度 L=1） |
| `qudt:prefixMultiplier` | SI 前缀缩放系数 | `prefix:Centi = 0.01` |
| `qudt:symbol` / `qudt:ucumCode` | 单位符号 / UCUM 编码 | `m` / `m` |

### B.3 长度单位换算表（来自 QUDT，FR-3 内置子集）

| 单位 | 符号 | conversionMultiplier | = 多少米 |
|---|---|---|---|
| `unit:M` | m | 1.0 | 1（基准） |
| `unit:CentiM` | cm | 0.01 | 0.01 |
| `unit:MilliM` | mm | 0.001 | 0.001 |
| `unit:KiloM` | km | 1000.0 | 1000 |

### B.4 QUDT 三层模板结构（与属性模板同构）

```
QuantityKind（量纲）        ≈  分类模板的结构原型
   │ hasQuantityKind / unitForQuantityKind
   ▼
Unit（基准单位，multiplier=1） ≈  属性模板的"原型实例"
   │ scalingOf / conversionMultiplier
   ▼
DerivedUnit（cm/mm/km）      ≈  从模板派生的带换算副本
```

### D.1 GB/T 51269 编码规则示例（设备分类树）

按 FR-8 默认规则（分隔符 `-`、每级 2 位、基数 30、零填充）：

| classification_code | template_code | label | parent_id 指向 |
|---|---|---|---|
| 30 | equipment | 设备 | NULL（根） |

| 30-01-01 | spray-pump | 喷淋泵 | 30-01 |

### D.2 模板继承字段合并示例

```
泵(30-01) 模板：
  结构骨架（本节点）：额定流量 / 扬程 / 功率 / 介质   （4 个）
  外观：business-blue

喷淋泵(30-01-01) 模板（parent=泵）：
  结构骨架（本节点追加）：喷淋系统编号              （1 个）
```

### D.3 Brick 类导入映射（FR-7 → FR-2/FR-9）

| Brick 资源 | 映射到本功能 | 说明 |
|---|---|---|
| `brick:Equipment` 等 `owl:Class` | `ont_class_template`（一条记录） | 导入为分类模板节点 |
| `rdfs:subClassOf`（主父类） | `ont_class_template.parent_id` | 取主父类（R-16，多继承取 primary） |
| `rdfs:subClassOf`（多继承） | 仅记 `source_ref='brick'` 溯源，不映射 | 多继承不进 ont_class_hierarchy（后者只镜像建模侧类层级）；多继承信息保留在 source_ref 供回溯 |
| `rdfs:label` | `ont_class_template.label` | |
| Brick IRI | `ont_class_template.source_ref='brick'` | 溯源 |

> Brick 本身就是一棵 `rdfs:subClassOf` 设备分类树（已核实 `Brick.ttl`），可直接作为内置设备分类树的来源，免去自建。

### D.4 两套并行关系对照（防混淆）

| 维度 | 模板继承（template↔template） | 类层级（class↔class） |
|---|---|---|
| 关系 | `ont_class_template.parent_id` | `ont_class_hierarchy`（subClassOf） |
| 层 | 治理资产侧（原型） | 本体类侧（语义，建模侧权威） |
| 语义 | 子模板继承父模板字段+外观 | 子类 is-a 父类 |
| 产出方 | 本功能维护 | 建模侧权威写入；本功能只读镜像与供给建议 |
| 例子 | 喷淋泵模板继承泵模板 | XX品牌喷淋泵 subClassOf 喷淋泵 |
