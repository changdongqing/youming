## 一、背景与问题

### 1.1 现状

Ontology-Playground 当前的本体建模存在三类冗余与杂乱：

| 类型 | 表现 | 根源位置 |
|---|---|---|
| **数据属性同名重复** | `customer_name`/`product_name`/`store_name` 各自独立 IRI，定义重复 3 份 | `serializer.ts:101-125`，IRI 由 `{entityId}_{propName}` 拼接 |
| **对象属性语义重复** | 跨本体反复出现 `contains`/`has`/`in-region` 等同义关系，各为独立 `ObjectProperty` | `catalogue/official/*`，扫描发现 `contains` 重复 6+ 次 |
| **外观元数据散落** | 每个类硬编码 `ont:icon`/`ont:color`；序列化器硬编码十多个 `ont:xxx` 注释属性 | `serializer.ts` 各处 `ont:` 字面量；`designerStore.ts` 的 `ENTITY_ICONS/COLORS` 轮转 |
| **数值单位裸字符串** | `unit` 字段是无结构的字符串（`"USD"`/`"kg"`/`"minutes"`/`"%"`），无 IRI、无换算、无量纲归属 | `ontology.ts` 的 `Property.unit`；`serializer.ts:116` 的 `<ont:unit>` |

### 1.2 目标

- **治理冗余**：同一语义在 RDF 层尽量合并为单一资源。
- **治理杂乱**：设计期提供可沉淀、可复用的原型，避免每次从零建模。
- **贴合 OWL 规范**：复用走 OWL 原生的"全局属性 + 多 domain"机制，不偏离语义。
- **向后兼容**：现有 RDF 文件零破坏，渐进迁移。

## 二、模板化适用性评估（六者）

### 2.1 评估结论速览

| 概念 | 模板化适用性 | 治理形态 | 进入 RDF? |
|---|---|---|---|
| **数据属性** | ⭐⭐⭐ 高度适合 | 属性模板 + 复用副本 | 方案A共享/方案B副本 |
| **对象属性** | ⭐⭐⭐ 高度适合 | 属性模板 + 复用副本（与数据属性同构） | 同上 |
| **类** | ⭐⭐⭐ 高度适合 | 外观模板 + 结构骨架模板 | 不进入，各自独立 |
| **数值单位** | ⭐⭐⭐ 高度适合 | 引用 QUDT 单位本体 + 量纲/前缀分层模板 | 以 IRI 引用 |
| **注释属性** | ⭐⭐ 中度适合 | 元属性注册表（非副本复用） | 本身即全局 |
| **数据类型** | ⭐ 不适合 | —（XSD 标准枚举，无复用空间） | — |

### 2.2 评估依据

#### 数据属性、对象属性 —— 同构，共享一套机制

二者在 OWL 中都是**全局资源**（由 IRI 标识），都有 `rdfs:label`/`rdfs:domain`/`rdfs:range`/`rdfs:comment`，差别仅在 range 指向类还是数据类型。**一个属性天然可带多个 domain**——这是 OWL 原生支持的"多类共享"机制，无需"复制"。

- 数据属性冗余：`name` 在 3 个类里重复定义 3 份。
- 对象属性冗余：`contains` 在 6+ 个本体里语义雷同却各自独立 IRI。

→ 二者应共用一套**属性模板**机制，几乎零额外设计成本。

#### 类 —— 模板化收益次于属性，但方向已存在

类不像属性那样"同名重复"，但冗余体现在**外观元数据与结构骨架**：

```xml
<owl:Class rdf:about=".../Customer">
  <ont:icon>👤</ont:icon>        <!-- 每个类都要填 -->
  <ont:color>#0078D4</ont:color>  <!-- 每个类都要填 -->
</owl:Class>
```

项目已有"起始模板"雏形（`designerTemplates.ts` 的 Retail/Healthcare 模板、`ENTITY_ICONS/COLORS` 轮转），说明类模板化是既有方向的延伸，不是凭空引入。

#### 注释属性 —— 做注册表，不做副本

本项目自定义注释属性（`ont:icon`/`ont:color`/`ont:unit`/`ont:propertyType`/`ont:cardinality`/`ont:isIdentifier`/`ont:enumValues`/`ont:fromEntityId`/`ont:toEntityId`...）**散落在序列化代码里硬编码**，没有集中声明。注释属性本就全局唯一，谈不上"复用副本"，治理形态是**集中注册表**，驱动 serializer/parser 而非硬编码。

#### 数据类型 —— 不适合，理由有三

1. 本项目数据类型**全部复用 XSD 标准枚举**（扫描 catalogue 无任何 `rdfs:Datatype` 自定义），是既定的有限集合，不是用户定义对象。
2. 自定义 Datatype 用途窄（仅"约束字面量取值空间"），本项目用 `ont:enumValues` 字符串已覆盖枚举需求。
3. 数据类型是**原子值域定义**，没有"结构"可供复用——它本身就是叶子。

> 枚举值集合的治理（如订单状态 `pending/paid/shipped`）归到"类模板"或独立"枚举值字典"，不套在数据类型上。

## 三、核心设计：统一属性模板机制

数据属性与对象属性同构，**合并为一套属性模板**，是整体方案的核心与最高 ROI 单元。

### 3.1 属性模板（不含 IRI）

```ts
// src/data/ontology.ts（新增）

/**
 * 属性模板：可被多个类/多对类复用的属性"原型"。
 * 不含 IRI、不含 domain——这些在实例化时赋予。
 * kind 区分数据属性与对象属性，共用一套机制。
 */
export interface PropertyTemplate {
  /** 模板唯一标识（人类可读，如 'name'、'contains'、'price'） */
  templateId: string;
  /** 数据属性 or 对象属性 */
  kind: 'datatype' | 'object';
  /** 显示名 */
  label: string;
  /** 业务说明 */
  description?: string;
  /** 分类标签，便于模板选择器分组 */
  category?: string;

  // —— 数据属性专属（kind='datatype' 时）——
  type?: Property['type'];            // 'string' | 'integer' | ...
  isIdentifier?: boolean;
  unit?: string;
  values?: string[];

  // —— 对象属性专属（kind='object' 时）——
  /** 关系倾向的基数（实例化时可被覆盖） */
  defaultCardinality?: Relationship['cardinality'];
}
```

**为什么不带 IRI：** IRI 是资源身份，模板是设计原型。`templateId` 只在设计期起标识作用，不进 `rdf:about`。这正符合"模板字典中没有 IRI"的设想。

### 3.2 内置模板库

```ts
export interface PropertyTemplateLibrary {

}

export const builtinPropertyTemplates: PropertyTemplate[] = [

  { templateId: 'description', kind: 'datatype', label: 'Description', type: 'string',  category: 'basic' },
  { templateId: 'email',       kind: 'datatype', label: 'Email',       type: 'string',  category: 'contact' },
  { templateId: 'phone',       kind: 'datatype', label: 'Phone',       type: 'string',  category: 'contact' },
  { templateId: 'price',       kind: 'datatype', label: 'Price',       type: 'decimal', unit: 'USD', category: 'monetary' },
  { templateId: 'amount',      kind: 'datatype', label: 'Amount',      type: 'decimal', unit: 'USD', category: 'monetary' },
  { templateId: 'createdDate', kind: 'datatype', label: 'Created Date', type: 'datetime',category: 'temporal' },
  { templateId: 'isActive',    kind: 'datatype', label: 'Is Active',   type: 'boolean', category: 'status' },

  // —— 对象属性（跨本体高频关系语义）——
  { templateId: 'contains',    kind: 'object', label: 'contains',    defaultCardinality: 'one-to-many',  category: 'containment' },

```

### 3.3 扩展 Property / Relationship：溯源到模板

```ts
export interface Property {
  name: string;
  type: Property['type'];
  isIdentifier?: boolean;
  unit?: string;
  values?: string[];
  description?: string;
  /** 新增：溯源到属性模板。有值表示此属性由模板派生。 */
  templateRef?: string;
}

export interface Relationship {
  id: string;
  name: string;
  from: string;
  to: string;
  cardinality: Relationship['cardinality'];
  description?: string;
  attributes?: RelationshipAttribute[];
  /** 新增：溯源到属性模板。 */
  templateRef?: string;
}
```

**`templateRef` 的作用：**
- 设计期：标记"来自哪个模板"，便于后续模板改动时批量同步。
- 序列化期：作为"是否共享"的判据——同一 `templateRef` 被多处引用时序列化为共享单一属性。
- 解析期：反向重建 `templateRef`，恢复模板关联。

### 3.4 实例化语义（"复制一个关联"）

对应"建类时从模板复制一份关联，并关联 IRI"的设想。注意复制的是**字段值**，不是 IRI——IRI 在序列化时才赋予。

**数据属性实例化：**
```ts
applyPropertyTemplate(entityId, templateId) {
  const tpl = findTemplate(templateId, kind='datatype');
  const prop: Property = {
    name: tpl.label, type: tpl.type!,
    isIdentifier: tpl.isIdentifier, unit: tpl.unit,
    values: tpl.values, description: tpl.description,
    templateRef: tpl.templateId,   // 溯源
  };
  appendProperty(entityId, prop);    // 挂到类的 properties
}
```

**对象属性实例化：**
```ts
applyRelationshipTemplate(fromId, toId, templateId) {
  const tpl = findTemplate(templateId, kind='object');
  const rel: Relationship = {
    id: '',  // 序列化时由 from/to + templateRef 派生
    name: tpl.label, from: fromId, to: toId,
    cardinality: tpl.defaultCardinality ?? 'one-to-many',
    description: tpl.description,
    templateRef: tpl.templateId,
  };
  appendRelationship(rel);
}
```

## 四、类模板：外观 + 结构骨架

类模板不进入 RDF（类是独立资源，IRI 各不同），与数据属性的"方案 B"同理——治理设计期冗余，RDF 层保持类独立身份，**规范完全合规**。

### 4.1 外观模板（治理 icon/color 杂乱）

现状：`ENTITY_ICONS`/`ENTITY_COLORS` 按序轮转，7 个类各自硬编码，想统一风格要逐个改。

```ts
export interface ClassAppearanceTemplate {
  templateId: string;          // 'business-blue' | 'retail-warm'
  label: string;
  icon: string;
  color: string;
}
```

实例化：`applyAppearanceTemplate(entityId, templateId)` → 给类设置 icon/color。

### 4.2 结构骨架模板（治理"重复建模"）

典型场景：多个领域都有"审计实体"——都带 `createdDate`/`createdBy`/`lastModified`/`isActive`。每次新建都要手动加这 4 个属性。

```ts
export interface ClassStructureTemplate {
  templateId: string;          // 'audit-mixin' | 'contactable'
  label: string;
  description?: string;
  /** 一组属性引用（可指向属性模板，形成嵌套复用） */
  propertyRefs: string[];      // ['createdDate', 'createdBy', ...] → 对应 PropertyTemplate.templateId
  /** 可选：预设关系引用 */
  relationshipRefs?: Array<{ templateId: string; toEntityHint?: string }>;
}
```

实例化：`applyClassStructureTemplate(entityId, templateId)` → 批量注入一组属性（每个内部走 `applyPropertyTemplate`）。

### 4.3 类模板与属性模板的嵌套关系

```
ClassStructureTemplate（类结构骨架）
       │ propertyRefs
       ▼
PropertyTemplate（属性模板，kind=datatype/object）
       │ applyPropertyTemplate
       ▼
Property / Relationship（实例，带 templateRef 溯源）
```

> 类模板是更高层抽象，组合了属性模板。这与项目已有的 `designerTemplates`（整本体起始模板）形成三层：**整本体模板 > 类结构骨架 > 属性模板**。


### 5.2 收益

- 把散落的 `ont:xxx` 集中声明，serializer/parser 从注册表驱动而非硬编码。
- 新增展示元属性只改注册表一处，自动同步到序列化/解析。
- 可生成"本项目注释属性"文档/校验。

### 5.3 为什么只评 ⭐⭐

量小（十来个）、稳定后改动频率低，ROI 低于属性模板。价值在工程整洁而非语义治理，适合作为属性模板落地后的收尾工作。

## 六、数据类型：不模板化的理由与替代治理

### 6.1 不模板化的三条理由

1. 本项目数据类型**全部复用 XSD 标准枚举**（`xsd:string` 17 次、`xsd:decimal` 5 次、`xsd:dateTime`/`xsd:integer`/`xsd:boolean` 各若干），扫描 catalogue 无任何 `rdfs:Datatype` 自定义。
2. 数据类型是**原子值域定义**，没有"结构"可供复用——它本身就是叶子。
3. 自定义 Datatype 用途窄，本项目用 `ont:enumValues` 已覆盖枚举需求。

### 6.2 枚举值集合的替代治理

若领域有大量"固定取值集合"（订单状态 `pending/paid/shipped/delivered`），规范做法是：
- 用 `owl:Class` + `owl:oneOf` 建枚举类，或
- 用 `skos:ConceptScheme` 建概念体系。

→ 归到"类模板"或独立"枚举值字典"，**不套在数据类型上**。

## 七、数值单位治理：引用 QUDT + 模板化

### 7.1 现状与问题

本项目数值单位当前只是**裸字符串**：

```ts
// ontology.ts
export interface Property {
  unit?: string;   // ← 无结构、无 IRI、无换算、无量纲归属
}
```

实际取值散乱：`"USD"`（货币）、`"kg"`（质量）、`"minutes"`（时间）、`"%"`（无量纲比）。问题：
- **无身份**：`"kg"` 与 `"KG"`、`"千克"` 无法被识别为同一单位。
- **无换算**：`mm`/`cm`/`m`/`km` 之间的换算关系无处表达，无法做单位换算查询。
- **无量纲归属**：无法知道 `mm` 与 `cm` 同属"长度"量纲，也无法知道 `kg` 与 `g` 可换算而 `kg` 与 `USD` 不可换算。
- **治理杂乱**：每个属性各自手填单位字符串，易不一致（如 `USD` vs `usd` vs `$`）。

### 7.2 QUDT 调研结论：现成的、规范化的单位本体

经实地调研 `/home/chdq/chdq/src/gitee/ttshang/qudt-public-repo`，QUDT（Quantities, Units, Dimensions and Types）是一个成熟的单位本体，可直接引用而无需自建：

| QUDT 资源 | 规模 | 路径 |
|---|---|---|
| 单位（`qudt:Unit`） | **2927 个** | `src/main/rdf/vocab/unit/VOCAB_QUDT-UNITS-ALL.ttl` |
| 量纲（`qudt:QuantityKind`） | **1221 个** | `src/main/rdf/vocab/quantitykinds/` |
| 前缀（`qudt:Prefix`） | **33 个**（含 Centi/Milli/Kilo 等 SI 前缀） | `src/main/rdf/vocab/prefixes/` |
| Schema（类/属性定义） | — | `src/main/rdf/schema/SCHEMA_QUDT.ttl` |

**QUDT 用四组核心谓词刻画单位：**

#### （1）量纲归属——`qudt:hasQuantityKind` / `qudt:unitForQuantityKind`
单位通过此谓词归属到一个量纲（QuantityKind），同量纲的单位才可换算。

```turtle
# 量纲：长度
quantitykind:Length
  a qudt:QuantityKind ;
  qudt:hasDimensionVector qkdv:A0E0L1I0M0H0T0D0 .   # 量纲向量：长度维 L=1

# 单位：米
unit:M
  a qudt:Unit ;
  qudt:hasQuantityKind quantitykind:Length ;        # ← 米属于长度量纲
  qudt:conversionMultiplier 1.0 ;                    # ← 基准单位（系数=1）
  qudt:symbol "m" .
```

#### （2）换算系数——`qudt:conversionMultiplier` + `qudt:conversionOffset`
每个单位相对其量纲基准单位的线性换算：`基准值 = 单位值 × multiplier + offset`。

```turtle
unit:CentiM                                        # 厘米
  qudt:hasQuantityKind quantitykind:Length ;
  qudt:conversionMultiplier 0.01 .                  # 1 cm = 0.01 m

unit:MilliM                                        # 毫米
  qudt:hasQuantityKind quantitykind:Length ;
  qudt:conversionMultiplier 0.001 .                 # 1 mm = 0.001 m

unit:KiloM                                         # 千米
  qudt:hasQuantityKind quantitykind:Length ;
  qudt:conversionMultiplier 1000.0 .                # 1 km = 1000 m
```

> 温度等有偏移的单位用 `conversionOffset`（如华氏度相对摄氏度）。

#### （3）缩放溯源——`qudt:scalingOf`
派生单位（如 `KiloM`）可声明它"缩放自"基准单位（`M`），刻画同一基准的不同尺度。QUDT 中 `scalingOf` 出现 **304 次**，是单位间派生关系的核心。

#### （4）SI 前缀——`qudt:Prefix` + `qudt:prefixMultiplier`
`cm`/`mm`/`km` 的 `c`/`m`/`k` 来自独立的 Prefix 资源，前缀自带 `prefixMultiplier`（缩放系数）。

```turtle
prefix:Centi
  a qudt:DecimalPrefix, qudt:Prefix ;
  qudt:prefixMultiplier 0.01 ;
  qudt:symbol "c" .
```

### 7.3 关键洞察：QUDT 本身就是一个三层模板结构

QUDT 的"量纲 → 基准单位 → 派生单位（前缀/缩放）"恰好是一个天然的模板层级，与本设计前面的属性模板机制同构：

```
QuantityKind（量纲）        ≈  类模板的结构原型
   │ hasQuantityKind / unitForQuantityKind
   ▼
Unit（基准单位，multiplier=1） ≈  属性模板的"原型实例"
   │ scalingOf / conversionMultiplier
   ▼
DerivedUnit（cm/mm/km）      ≈  从模板派生的带换算副本
```

→ **单位治理不是"要不要模板化"的问题，而是"引用现成模板本体 + 在本项目侧做轻量适配"的问题。**

### 7.4 治理方案：引用 QUDT + 单位注册表

**核心策略：不重新发明单位本体，引用 QUDT；本项目只维护一个"单位注册表"做映射与选择器。**

#### 7.4.1 扩展 Property.unit：从裸字符串到结构化引用

```ts
export interface Property {
  // ... 现有字段
  unit?: string;                          // ← 保留，向后兼容（裸字符串/符号）
  /** 新增：QUDT 单位 IRI 引用（规范身份） */
  unitRef?: string;                       // 如 'http://qudt.org/vocab/unit/M'
  /** 新增：所属量纲 IRI（由 unitRef 间接可得，冗余存储便于校验/展示） */
  quantityKindRef?: string;               // 如 'http://qudt.org/vocab/quantitykind/Length'
}
```

`unit` 保留为字符串以兼容旧文件；`unitRef` 提供规范身份与换算能力。

#### 7.4.2 单位注册表（本地映射与选择器）

从 QUDT 抽取常用单位（而非全部 2927 个）建一个本地注册表，供设计器选择：

```ts
export interface UnitSpec {
  qudtIri: string;           // 'http://qudt.org/vocab/unit/M'
  symbol: string;            // 'm'
  label: string;             // 'Meter'
  quantityKindIri: string;   // 'http://qudt.org/vocab/quantitykind/Length'
  quantityKindLabel: string; // 'Length'
  conversionMultiplier: number;  // 1.0（相对基准）
  conversionOffset?: number;     // 温度等有偏移
  scalingOf?: string;            // 基准单位 IRI（派生关系）
  ucumCode?: string;             // 'm'（医疗/科学常用 UCUM 编码）
}

/** 按量纲分组，便于设计器按"长度/质量/时间/货币"分类选择 */
export interface QuantityKindGroup {
  iri: string;               // '.../quantitykind/Length'
  label: string;             // 'Length'
  dimensionVector: string;   // 'A0E0L1I0M0H0T0D0'
  units: UnitSpec[];          // 该量纲下的常用单位
}

export const unitRegistry: QuantityKindGroup[] = [
  {
    iri: 'http://qudt.org/vocab/quantitykind/Length',
    label: 'Length', dimensionVector: 'A0E0L1I0M0H0T0D0',
    units: [
      { qudtIri:'.../unit/M',       symbol:'m',  label:'Meter',     conversionMultiplier:1.0,    scalingOf:'.../unit/M' },
      { qudtIri:'.../unit/CentiM',  symbol:'cm', label:'Centimeter',conversionMultiplier:0.01,   scalingOf:'.../unit/M' },
      { qudtIri:'.../unit/MilliM',  symbol:'mm', label:'Millimeter',conversionMultiplier:0.001,  scalingOf:'.../unit/M' },
      { qudtIri:'.../unit/KiloM',   symbol:'km', label:'Kilometer', conversionMultiplier:1000.0, scalingOf:'.../unit/M' },
    ],
  },
  // 质量、时间、温度、面积、体积、货币（QUDT 亦含货币单位）...
];
```

#### 7.4.3 换算能力（衍生收益）

有了 `conversionMultiplier`/`offset` 与 `quantityKindRef`，可做此前无法做的事：

```ts
/** 同量纲单位换算。不同量纲返回 null。 */
function convert(value: number, from: UnitSpec, to: UnitSpec): number | null {
  if (from.quantityKindIri !== to.quantityKindIri) return null;   // 量纲不同不可换算
  const base = value * from.conversionMultiplier + (from.conversionOffset ?? 0);
  return (base - (to.conversionOffset ?? 0)) / to.conversionMultiplier;
}
// convert(1, km, m) === 1000 ; convert(100, cm, m) === 1 ; convert(1, kg, USD) === null
```

### 7.5 与属性模板的嵌套关系

单位治理嵌入数据属性模板，形成"模板 → 单位"的纵向复用：

```
PropertyTemplate（数据属性模板）
   │ type='decimal', unitRef='.../unit/M'  ← 模板可预设单位
   ▼ applyPropertyTemplate
Property（实例）
   │ unitRef（继承自模板，可覆盖）
   ▼ unitRegistry 查询
UnitSpec → conversionMultiplier / quantityKind（换算与量纲校验）
```

> 即：属性模板可预设一个推荐单位（如 `length` 模板预设 `unit:M`），实例化时继承；用户可在同量纲内改选 `cm`/`mm`，换算能力随之生效。

### 7.6 序列化与解析

**序列化：** 把裸 `<ont:unit>kg</ont:unit>` 升级为带 IRI 的引用：

```xml
<owl:DatatypeProperty rdf:about=".../shipment_weight">
  <rdfs:range rdf:resource=".../XMLSchema#decimal"/>
  <ont:unit>kg</ont:unit>                                       <!-- 兼容旧解析器 -->
  <ont:unitRef rdf:resource="http://qudt.org/vocab/unit/KiloGM"/> <!-- 新：QUDT IRI -->
  <ont:quantityKindRef rdf:resource="http://qudt.org/vocab/quantitykind/Mass"/>
</owl:DatatypeProperty>
```

**解析：** 优先读 `ont:unitRef`；无则回退到 `ont:unit` 裸字符串（向后兼容）。

**可选增强：** 在本体头部引入 QUDT 命名空间声明，使单位 IRI 可被 SPARQL 直接查询：
```xml
xmlns:qudt="http://qudt.org/schema/qudt#"
xmlns:unit="http://qudt.org/vocab/unit/"
```

### 7.7 治理收益

| 维度 | 现状（裸字符串） | 引用 QUDT 后 |
|---|---|---|
| 单位身份 | `"kg"` 无法识别 | IRI 全局唯一，`kg`/`KG`/`千克` 归一 |
| 换算能力 | 无 | `convert(1, km, m)=1000` 可计算 |
| 量纲校验 | 无 | 不同量纲换算被拒绝（kg↔USD 返回 null） |
| 治理杂乱 | 各自手填 | 注册表按量纲分组，选择器统一来源 |
| 规范贴合 | 自造字符串 | 引用国际通用单位本体 |
| 模板化 | — | 单位嵌入属性模板，量纲/前缀分层天然模板化 |

### 7.8 范围与不做什么

- **不全量内置 2927 单位**：本地注册表只抽常用子集（长度/质量/时间/温度/面积/体积/货币/数据量），按需扩展。
- **不内置 QUDT schema**：不在本项目 RDF 里重定义 `qudt:Unit` 等类，只**引用** QUDT 的单位 IRI 作为取值。
- **不实现推理**：换算由本项目 TS 代码（`convert`）执行，不依赖 OWL 推理机——这是工具行为，非本体语义。

## 十、序列化与解析的统一策略

### 10.1 序列化双策略（数据属性 + 对象属性共用）

**判据：** 按 `templateRef` 分组扫描所有 `Property` 与 `Relationship`。

```
templateRef='name'     → Customer, Product, Store （3 处）→ 方案A 共享
templateRef='email'    → Customer                  （1 处）→ 方案B 独立
templateRef='contains' → Order→Product, Cart→Item  （2 处）→ 方案A 共享
templateRef=null       → 各类独占属性               （1 处）→ 方案B 独立
```

**合并前置校验（关键约束）：** 仅当 `range`/`unitRef`/`values`/`type` 一致才合并为方案 A；否则降级方案 B 并告警，避免合并丢失差异（单位不同则不可合并）。

**共享属性（方案 A）序列化：**
```xml
<owl:DatatypeProperty rdf:about=".../name">           <!-- IRI = .../name，不带类前缀 -->
  <rdfs:label>name</rdfs:label>
  <rdfs:domain rdf:resource=".../Customer"/>           <!-- 多 domain -->
  <rdfs:domain rdf:resource=".../Product"/>
  <rdfs:domain rdf:resource=".../Store"/>
  <rdfs:range rdf:resource=".../XMLSchema#string"/>
  <ont:propertyType>string</ont:propertyType>
  <ont:templateRef>name</ont:templateRef>              <!-- 溯源 -->
</owl:DatatypeProperty>
```

对象属性同理：
```xml
<owl:ObjectProperty rdf:about=".../contains">
  <rdfs:domain rdf:resource=".../Order"/>
  <rdfs:domain rdf:resource=".../Cart"/>
  <rdfs:range rdf:resource=".../Product"/>
  <rdfs:range rdf:resource=".../Item"/>
  <ont:cardinality>one-to-many</ont:cardinality>
  <ont:templateRef>contains</ont:templateRef>
</owl:ObjectProperty>
```

**独立属性（方案 B）序列化：** 保持现有 `{entityId}_{propName}` 格式，向后兼容。

### 10.2 解析反向重建

- 遇到 `ont:templateRef` → 记录溯源。
- 共享属性（多 `rdfs:domain`）→ 每个 domain 类各 push 一份 `Property`/`Relationship`，带相同 `templateRef`。
- 带前缀属性 → 按 domain 归属，`templateRef` 可选。
- 现有解析器每个属性只取一个 domain，需扩展为收集所有 domain 子元素。
- **单位**：优先读 `ont:unitRef`（QUDT IRI），无则回退 `ont:unit` 裸字符串。

### 10.3 类模板、注释属性与单位

- **类模板**：不进入 RDF，序列化仍生成各自独立 `owl:Class`。
- **注释属性**：从注册表驱动序列化，`ont:templateRef`/`ont:unitRef` 作为可选溯源注解。
- **单位**：以 `ont:unitRef`（QUDT IRI）引用外部 QUDT 本体，不在本体重定义单位类。

## 十一、向后兼容与迁移路径

### 11.1 解析旧文件（无 templateRef / 无 unitRef）

现有 RDF（如 `iq-lab-retail-step-3.rdf`）无 `ont:templateRef`/`ont:unitRef`，解析时每个属性按 domain 归属，`templateRef=undefined`（视为独立属性），`unit` 回退到裸字符串。**结果与现状完全一致，零破坏。**

### 11.2 渐进迁移四阶段

**阶段 1（立即可做，零风险）：** 引入 `PropertyTemplate` 类型 + 内置模板库 + `apply*` 动作 + 设计器"从模板添加"UI。序列化始终走方案 B。**设计期即享治理收益，RDF 输出不变。**

**阶段 2（可选，中等收益）：** 启用方案 A 序列化。扩展 parser 处理多 domain。提供"扫描同名属性 → 推荐提升为模板"一键向导（`promote*ToTemplate` 批量版）。**新本体享受 RDF 去重。**

**阶段 3（单位治理，独立收益）：** 引入 QUDT 单位注册表 + `unitRef` 字段 + 单位选择器 UI + 换算能力。可与阶段 1/2 并行，互不依赖。**获得换算与量纲校验能力。**

**阶段 4（收尾，工程整洁）：** 落地注释属性注册表，serializer/parser 从注册表驱动。落地类外观/结构模板。**消除散落硬编码。**

### 11.3 不强制迁移

旧文件继续按方案 B 工作、单位回退裸字符串；经过治理的本体享受方案 A 去重与单位 IRI。各路并存。

## 十二、风险与约束

| 风险 | 说明 | 缓解 |
|---|---|---|
| **合并丢失字段差异** | Customer 的 name 与 Product 的 name 单位/枚举不同，强行合并丢差异 | 序列化前校验：`range`/`unitRef`/`values`/`type` 一致才合并，否则降级方案 B 并告警 |
| **下游依赖 IRI 前缀** | 若有代码/查询依赖 `customer_name` 这种 IRI | 保留 `ont:templateRef` 溯源；查询改用 `rdfs:label` 或 `templateRef` |
| **解析器多 domain** | 现有 parser 每属性只取一个 domain | 扩展为收集所有 domain 子元素（阶段 2） |
| **对象属性共享的 range 合并** | 同一关系模板连不同类对，range 不同 | 同样校验 range 兼容性；不兼容则降级 |
| **模板库膨胀** | custom 模板无限增长 | 提供分类、搜索、弃用标记 |
| **QUDT 单位漂移** | QUDT 版本更新致 IRI 变动 | 注册表锁定具体版本快照；`unit` 符号冗余存储保降级 |
| **单位换算精度** | `conversionMultiplier` 浮点误差 | 关键场景用 `conversionMultiplierSN`（科学计数）或大数库 |
| **货币单位非 QUDT 强项** | 货币汇率随时间变，QUDT 货币系数仅参考 | 货币换算标注"参考汇率"，非实时；或货币单独走外部汇率源 |

## 十三、实施优先级与里程碑

```
ROI：统一属性模板（数据+对象）> 单位治理(引用QUDT) > 类模板 > 注释属性注册表 >> 数据类型(不做)
```

| 里程碑 | 内容 | 依赖 | 风险 |
|---|---|---|---|
| **M1：统一属性模板** | `PropertyTemplate` + 内置库 + `applyProperty/RelationshipTemplate` + 设计器 UI + `templateRef` 字段 | 无 | 低（阶段1零风险） |
| **M2：共享序列化** | 方案 A 双策略 + parser 多 domain + 合并校验 + 提升向导 | M1 | 中（改 RDF 输出） |
| **M3：单位治理** | QUDT 单位注册表 + `unitRef`/`quantityKindRef` + 选择器 UI + `convertValue` | 无（可与 M1 并行） | 低（引用外部本体） |
| **M4：类模板** | 外观模板 + 结构骨架模板 + UI | M1（结构骨架引用属性模板） | 低（不进 RDF） |
| **M5：注释属性注册表** | 注册表 + serializer/parser 驱动化 | M1（templateRef 需注册） | 低（工程整洁） |

**建议首落地单元为 M1**：一套机制覆盖数据属性 + 对象属性两个概念，ROI 最高，且阶段 1 零风险（不改 RDF 输出）。**M3 可与 M1 并行启动**，因为它只引用外部本体、不依赖属性模板机制（仅在第 7.5 节描述的"模板预设单位"处与 M1 交汇）。

| **注释属性** | ✅(中度) | 注册表（非副本） | 本身即全局 | 注释属性全局唯一 | 声明散落硬编码 |
| **数据类型** | ❌ | — | — | XSD标准枚举 | 无复用空间（叶子） |

**核心洞察：**
- 数据属性与对象属性**同构**，共用一套属性模板机制——首落地单元（M1）。
- 类模板是更高层抽象，组合属性模板，与已有 `designerTemplates` 形成三层。
- 单位治理**引用而非自建** QUDT 本体，量纲/前缀分层天然模板化；嵌入属性模板形成纵向复用（M3）。
- 注释属性做注册表，不做副本。
- 数据类型不模板化；枚举值集合治理归到类模板或独立字典。
