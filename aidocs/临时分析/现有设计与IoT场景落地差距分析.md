## 0. 一句话结论

现有 12 个模块 + PRD 构建的是一个**严格符合 GB/T 48000.3—2026 的"标准本体静态建模工作台"**（T-Box 概念模型 + A-Box 实例定义 + SHACL 校验 + RDF 序列化 + 扩展治理 + 可视化）；而沟通文档描述的是一个**以本体为语义中枢、IoT 驱动的动态运行时智能系统**（数据源映射、IoT 采集、时序数据、告警规则、服务触发、规则流/CEP、溯源、电梯困人派单、消防维保评估）。

**两者之间隔着一条"从建模台到运行时"的鸿沟。** 现有设计覆盖了沟的"左岸"（建模与静态校验），沟的"右岸"（运行时数据接入、推理、触发、闭环）几乎完全空白。本文按维度逐一拆解这条鸿沟。

## 1. 沟通文档诉求提炼

沟通文档共 8 个主题，可归纳为 **5 大运行时能力诉求**：

| # | 诉求主题 | 核心问题 | 涉及的本体能力 |
|---|---------|---------|--------------|
| A | **数据来源与实例化** | 实体实例数据从哪来？表单录入 / IoT 采集 / 第三方 API / NLP 抽取 / 算法推理，如何映射到本体实体？ | 数据源映射（R2RML / 可视化映射）、URI 生成策略、**Provenance 溯源本体** |
| B | **映射配置位置** | 映射关系配置在"知识映射模块"、规则文件还是代码内？ | 映射管理模块（可视化左右分屏）、R2RML、版本管理 |
| C | **告警规则** | 告警规则用公理/规则还是独立模块？如何与本体深度关联？ | 告警规则引擎、Alert 实体建模、本体概念引用、规则即数据 |
| D | **服务触发执行 / 规则流引擎** | 服务触发（ECA）如何基于本体匹配？规则流引擎（Drools）与本体的输入输出如何映射？ | 服务能力语义化（OWLS/SAWSDL）、事件语义化、规则流 ↔ 本体双向映射 |
| E | **楼控/电梯/消防落地场景** | 电梯困人→救援派单闭环、消防维保质量评估（时序因果链）在本体中如何配置与执行？ | 时序事件建模、CEP 引擎、双写架构（图谱负责决策、RDBMS 负责事务） |

此外，沟通文档反复强调三个**横切原则**：

- **"最新状态写图谱，历史数据留时序库"** —— 图谱不存全量时序，避免图膨胀。
- **"本体管是什么，规则引擎管怎么做，告警引擎管何时提醒"** —— 职责分离。
- **"双写/状态映射"** —— 图谱存概念与关系，业务系统存高频状态流转，二者通过 `hasExternalLink` 关联。

### 2.2 现有设计的明确边界（PRD §1.3 与各文档"本次不做"）

现有设计**反复声明**不做以下事项，这正是沟的所在：

| 明确不做 | 出处 | 与诉求的关系 |
|---------|------|------------|
| 大规模图谱推理（传递闭包、规则链） | PRD §1.3、模块 09 | 直接对应诉求 D（规则流引擎） |
| IoT 实时数据接入、时序数据 | 全部 12 模块均未涉及 | 直接对应诉求 A/E |
| 告警规则、通知动作（发短信/邮件） | 模块 09 仅有 VIOLATION/WARNING 级别，无外部动作 | 直接对应诉求 C |
| 服务触发执行（调 API、控制设备） | 无任何模块涉及 | 直接对应诉求 D |
| 复杂事件处理（CEP）、时序因果链验证 | 模块 09 明确排除 | 直接对应诉求 E（消防联动） |
| 数据源映射（R2RML / ETL / CDC） | 无任何模块涉及 | 直接对应诉求 A/B |
| Triplestore 双写 | 模块 08/09/10 均以 PostgreSQL 为唯一真相源 | 影响诉求 A/E 的图谱查询能力 |
| 实例自动生成（规则触发 makeInstance） | 模块 08 仅支持手工/受控导入 | 直接对应诉求 C/D/E（派单自动生成工单实例） |

### 2.3 关键洞察

> **现有设计是"建模台 + 静态校验器"，不是"运行时引擎"。** 它的运行时动作只有两个：① 实例创建/修改时触发局部校验（模块 08）；② 手动/导出前触发全量 SHACL 校验（模块 09）。这两个动作都是**同步、低频、面向数据质量**的，与沟通文档要求的**高频、实时、面向业务决策与动作执行**的运行时完全不同。

### 3.1 维度① 数据源映射（Data Source Mapping）—— 🔴 缺失

**诉求**：实体实例来自表单（PostgreSQL）、IoT（MQTT/Kafka）、第三方 API、NLP 抽取、算法推理。需要映射模块（可视化左右分屏 / R2RML / 代码内字典），明确"哪个数据源的哪个字段 → 哪个本体实体的哪个属性"，含转换规则、数据类型、主键→URI 策略、增量更新、版本管理。

**现状**：
- 模块 10（序列化交换）仅支持 **RDF 文件导入**（Turtle/JSON-LD/RDF-XML），且导入目标是"已有 RDF 三元组 → 本体实例"，**不是**"关系库表/CSV/MQTT 消息 → 本体实例"。
- 模块 08（实例）支持 Excel/JSON 批量导入，但那是**结构化文件的一次性导入**，不是持续的数据源映射。
- 无任何模块维护"数据源连接信息""字段映射规则""转换逻辑""增量策略"。

**差距**：需要一个全新的**数据源映射模块（Data Source Mapping）**，能力应包括：
- 数据源注册（DB 连接串 / MQTT broker / Kafka topic / HTTP API / CSV 路径）。
- 映射配置（目标实体/属性 ← 源表/字段，含转换表达式、URI 生成规则、数据类型映射）。
- 映射执行（全量 / 增量 CDC / 定时 / 按需）。
- 映射版本管理与变更历史。
- 可视化映射界面（左右分屏）。

> **与现有设计的关系**：此模块是模块 08（实例）的**生产端**——模块 08 现在只管"实例怎么存"，不管"实例从哪来"。建议作为独立新模块（如模块 13），消费 04/05/06 的 Schema 定义，产出写入 08 的实例表。

### 3.2 维度② IoT 动态采集 —— 🔴 缺失

**诉求**：传感器/设备通过 MQTT/Kafka 上报，流处理引擎（Flink）解析后更新本体实体属性（如 `Sensor.hasTemperature` 最新值）。

**现状**：12 个模块**完全没有**任何 IoT 接入、设备管理、消息消费、遥测（telemetry）概念。单位字典里有"温度/电压/功率"等物理量，但那是给"约束逻辑类的测量单位"用的，与 IoT 数据通道无关。

**差距**：需要**IoT 接入层**（新模块或独立服务），能力包括：
- 设备/传感器实体建模（SSN/SOSA 本体参考）—— 需在实体类型树扩展 `Sensor`、`Observation`、`Measurement` 等（属维度⑩）。
- 消息协议适配（MQTT / CoAP / Modbus / OPC UA / HTTP）。
- 遥测数据解析与属性更新（写"最新值"到本体实例）。
- 与维度③时序库联动。

### 3.3 维度③ 时序数据 —— 🔴 缺失

**诉求**：核心原则——**"最新状态写图谱，历史数据留时序库"**。本体中只更新属性最新值，历史时序存时序库，本体通过 `hasTimeSeriesEndpoint` 指向时序库查询接口。避免图膨胀。

**现状**：
- 无任何时序数据库选型、无时序表设计、无 `hasTimeSeriesEndpoint` 类属性。
- 模块 08 的 `ont_instance_data_value` 只存"当前值"，每次更新覆盖，**无法保留历史**——这意味着现有设计连"温度变化历史"都无法支撑，更别说消防联动的时间窗口匹配。

**差距**：
- 需引入时序库。**选型决策：TDengine（涛思）为首选，TimescaleDB 为备选**。理由见下"时序库选型论证"。

> **时序库选型论证（信创背景，v2.1 修订）**：
>
> | 维度 | **TDengine 涛思（首选）** | TimescaleDB（备选） |
> |------|--------------------------|---------------------|
> | **信创/国产化** | 北京涛思数据，纯国产，入选信创图谱 | 美国 Timescale Inc.，海外产品 |
> | **IoT 数据模型契合** | 超级表(STable)→设备类型、子表→设备实例、标签(TAGS)→设备静态属性、数据列→测点值；**与维度⑲物模型几乎 1:1 映射** | hypertable + partition by device_id，需自行组织 |
> | **写入性能** | 专为时序优化，单机百万级 TPS | 行存储底座，高并发需调优 |
> | **压缩比** | 列式 + 数据类型感知，IoT 场景 10-50× | 列式压缩，但行存储底座 |
> | **最新值缓存** | 原生缓存每子表最新值（免查库） | 需自建缓存/物化视图 |
> | **连续查询/降采样** | 内置 | 需 PG 物化视图 + 定时任务 |
> | **边缘部署** | 有 TDengine Edge（契合维度㉑边缘计算） | 无原生边缘版 |
> | **技术栈一致性** | 独立栈（类 SQL 语法） | PG 扩展，同栈 |
> | **跨库 JOIN** | 弱（时序库通病） | 强（PG 原生 JOIN） |
>
> **决策依据**：
> 1. **信创合规是硬约束**——国产化要求下 TimescaleDB 的"同栈"优势不成立。
> 2. **物模型契合是杀手级优势**——TDengine 的"超级表+子表+标签"模型与维度⑲物模型天然对齐：设备类型=超级表、设备实例=子表、静态属性=标签、动态测点=数据列。
> 3. **跨库 JOIN 弱项在本架构下不构成问题**——设备间的拓扑关联、维保历史走本体图谱（PostgreSQL），时序库只管"存数与聚合"，职责解耦，关联查询不走时序库。
> 4. **代价（诚实说明）**：引入独立技术栈，团队需学习；社区版与企业版功能差异（集群/副本在企业版）；需维护额外 JDBC 连接与数据同步策略。但这些是信创合规的必要代价。
- 实体/属性需扩展"时序端点"元数据：哪些属性是时序属性、指向哪个时序表/测量点。
- 模块 08 的数据值写入逻辑需分叉：**静态属性覆盖写，时序属性追加写 + 最新值快照**。

> **这是现有设计最大的结构性缺口之一**。没有时序能力，电梯/消防场景无从谈起。

### 3.4 维度④ Provenance 溯源 —— 🟡 需补充

**诉求**：引入 PROV-O（W3C Provenance Ontology），记录每个实例/属性值"怎么来的"——`wasGeneratedBy`（由传感器/表单/算法产生）、`wasAttributedTo`（操作人/网关）、`generatedAtTime`（产生时间）。NLP 抽取的数据还要带 `confidenceScore`（置信度）。

**现状**：
- 现有设计的"溯源"是**标准条款溯源**（`source_type=APPENDIX_C`、`source_reference=C.41`、`standard_iri`），回答的是"这个 Schema 元素来自国标哪一条"，**不是**"这条实例数据来自哪个数据源/谁在何时产生"。
- `ont_instance_data_value` 有 `unit_id`/`literal_symbol`/`sort_order`，但**没有** `provenance_source`/`generated_by`/`generated_at`/`confidence` 等字段。
- 审计字段（`create_by`/`update_by`/`create_time`）只记录平台操作人，不记录数据的生产来源（IoT 网关、外部 API、算法）。

**差距**：
- 实例值层面需补充 Provenance 元数据（数据来源类型、生产者、产生时间、置信度）。
- 是否引入完整 PROV-O 实体（`Activity`/`Agent`/`Entity`）需评估——对于楼控/电梯/消防场景，**轻量溯源字段**（数据来源类型 + 生产者标识 + 时间戳 + 置信度）可能比完整 PROV-O 图更务实，可作为一期方案。

---

### 3.5 维度⑤ 告警规则 —— 🔴 需改造 + 补充

**诉求**：告警规则配置在**独立模块**，但其**条件引用本体概念**（`Sensor.hasTemperature > 80`）、**生成的告警事件存入本体**（`Alert` 实体）。避免用 OWL 公理做实时告警（性能不可行）。告警规则即数据，可版本控制、可视化配置。

**现状**：
- 模块 07（公理规则）+ 模块 09（校验引擎）构成的是**数据质量校验规则**，不是**业务告警规则**。区别：
  - 模块 07/09 回答："这条实例数据**是否符合 Schema 约束**？"（如枚举值非法、日期倒序、单位不一致）。
  - 告警规则回答："这个**实时状态**是否**需要人关注**？"（如温度>80℃、电梯困人）。
- 模块 09 的 `severity` 有 VIOLATION/WARNING/INFO，但**没有外部动作**（发短信/邮件/Webhook），校验结果只是被动报告。
- 实体类型树**没有 `Alert` / `AlarmEvent` 类**——告警无法作为本体一等公民被查询、关联、溯源。
- 模块 07 的 `validation_mode` 枚举（OWL_CONSISTENCY/SHACL_CORE/SHACL_SPARQL/APPLICATION/COMPOSITE）是面向"约束校验"的，**不含**"阈值告警""模式匹配""时序窗口"等告警语义。

**差距**：
- **需新建告警规则模块**（独立于模块 07/09），配置项应包含：监控目标（本体实体/属性）、触发条件（阈值/模式/时序窗口）、告警级别、通知渠道、生成的 Alert 实体类型。
- **需在实体类型树补充 `Alert`/`AlarmEvent` 及其子类**（如 `TrappedPersonAlarm`），并定义其与设备、工单的对象属性（`detectedBy`/`triggersOrder`/`assignedTo`）。
- 告警规则引擎需独立于 SHACL 校验引擎，面向高频实时数据流。

### 3.6 维度⑥ 服务触发执行 —— 🔴 缺失

**诉求**：事件-条件-动作（ECA）。本体描述服务能力（OWLS/SAWSDL：输入/输出/前提/效果），触发引擎监听事件（如 `AlertGenerated`），基于本体语义匹配可用服务并调用（发邮件、调 API、控制设备）。

**现状**：**完全空白**。12 个模块无任何"服务注册""事件发布订阅""动作执行"能力。模块 09 的校验失败只能"阻断导出"，不能"触发动作"。

**差距**：需要**服务触发/动作执行层**（新模块或集成到告警/规则引擎），能力包括：
- 服务能力注册（服务名、输入输出契约、调用方式 REST/MQTT）。
- 事件总线（发布 `AlertGenerated`/`ThresholdExceeded` 等事件）。
- 事件-服务匹配与调度（可基于本体推理发现隐含能力，一期可用显式配置匹配）。
- 动作执行与结果回写（执行成功/失败记录为本体实例，如 `NotificationSent`）。

---

### 3.7 维度⑦ 规则流/CEP —— 🔴 缺失

**诉求**：规则流引擎（Drools / Easy Rules）编排复杂、多步骤、有分支的业务逻辑；CEP 引擎（Flink CEP / Node-RED）处理时序因果链（如消防联动：开阀→压力降→水流→压力开关→泵启动，5 分钟内）。规则引擎输入事实来自本体，输出动作和新事实映射回本体。

**现状**：
- 模块 07/09 明确**排除**大规模推理、传递闭包、规则链、CEP。
- `ReasonerAdapter.inferEntailments()` 直接抛 `UnsupportedOperationException`。
- 无任何 Drools/Flink/Node-RED 集成或预留。

**差距**：
- 沟通文档明确**倾向 Node-RED**（轻量、可视化、边缘友好），而非 Flink——这是重要的选型信号。
- 需引入**规则流/CEP 编排层**，能与本体实例双向映射（A-Box → 规则事实 → 动作/新事实 → A-Box）。
- 消防维保评估这类**时序因果链验证**是纯图数据库的弱项（图擅长拓扑，不擅长时间序列），必须由 CEP 引擎承接，图谱只提供"设备拓扑关系与维保任务上下文"。

> **关键提醒**：规则引擎选型（Node-RED vs Flink vs Drools）会显著影响架构。沟通文档已给出倾向 Node-RED 的明确信号，后续设计应据此决策，而非沿用 PRD 里"预留 ReasonerAdapter 接 GraphDB"的思路——那是面向推理的，不是面向 CEP/动作编排的。

---

### 3.8 维度⑧ 动态实例生成 —— 🔴 需改造

**诉求**：规则触发时**自动生成新实例**（如电梯困人 → 自动 `makeInstance(RescueOrder)` 并关联 `assignedTo` 维保员）。SWRL/Drools 规则的 `then` 部分能创建实例。

**现状**：
- 模块 08（实例）的写入路径是**纯手工/受控导入**——REST 接口由人调用，或附录 D 种子数据初始化。
- **没有任何"规则触发自动创建实例"的通道**。模块 09 是只读消费者，不写实例。
- `declaration_mode` 有 `REFERENCE_ONLY`（悬挂引用），但那是为附录 D 不一致兜底，不是为运行时动态生成设计。

**差距**：
- 模块 08 需开放**程序化/服务化写入入口**（供规则引擎/告警引擎/IoT 接入层调用），并支持事务、幂等、冲突处理。
- 需明确"谁有权在运行时创建实例"的治理策略（避免规则引擎无序生成垃圾实例）。

### 3.9 维度⑨ 双写架构 —— 🟡 需补充（可选）

**诉求**：图谱存"概念与关系"（决策），RDBMS 存"高频状态流转"（事务），通过 `hasExternalLink` 关联。图谱负责"思考"，业务库负责"记录执行"。

**现状**：
- 现有设计**刻意选择 PostgreSQL 为唯一真相源**，模块 08/09/10 都明确"不做 Triplestore 双写"。
- 这是一个**有意的简化决策**（符合"Prefer Simplicity"），但对于复杂图遍历查询（如沟通文档强调的"多跳关联查询：某维保员负责的楼宇里所有带特定品牌曳引机的电梯近一年困人记录"），关系库的 JOIN 性能会成为瓶颈。

**差距/权衡**：
- 一期可继续 PostgreSQL 单源（查询用递归 CTE + 图遍历），但需**预留**"是否引入 Triplestore/图数据库"的决策点。
- 至少应在实例/关系表上补一个 `external_link`（外部业务系统 ID/URL）字段，支撑双写映射。

> **注**：这不是必须立即改造，但应在架构文档中明确"单源→双源"的演进路径与触发条件（如实例规模超 10 万、多跳查询深度超 3）。

### 3.10 维度⑩ 事件/时序本体建模 —— 🟡 需补充

**诉求**：本体需建模"事件""时序""因果"概念——`AlarmEvent`/`DeviceEvent`（记录状态变化）、时间区间、事件序列、设备拓扑（哪个末端试水装置连哪个水流指示器，属于哪个维保任务）。

**现状**：
- 实体类型树（模块 04 预置 86 个类型）**完全基于 GB/T 48000.3 附录 B 的标准数字化实体**（标准实体/要素/层次/术语/信息单元/对象/特性/约束逻辑/行动/外部约束/制定程序），**没有任何"运行时事件""设备""传感器""告警""工单"概念**。
- 这并非设计缺陷——现有实体类型是**国标硬性要求**，且是标准数字化场景的正确定位。问题是：**楼控/电梯/消防是行业扩展场景，需要在国标核心之上做行业扩展**（这正是模块 11 扩展管理 + PRD §9 扩展原则的用途）。

**差距**：
- 需设计**行业扩展本体**（电梯扩展、消防扩展、楼控扩展），在核心实体类型之上扩展 `Elevator`/`Sensor`/`AlarmEvent`/`MaintenanceOrder` 等子类与属性。
- 这些扩展应走**扩展命名空间**（模块 11 管控），不污染核心。

### 3.11 维度⑪ Alert/工单实体建模 —— 🟡 需补充

**诉求**：`Alert`/`MaintenanceOrder`/`RescueOrder` 作为本体一等公民，含核心属性（severity/timestamp/status）、关键关系（`triggersOrder`/`assignedTo`/`causedBy`/`acknowledgedBy`/`resolvedAt`）、溯源信息（由哪条规则、哪个数据点触发）。

**现状**：无。属维度⑩的行业扩展范畴。

### 3.12 维度⑫ SPARQL 查询端点 —— 🔴 缺失（本体建模专家视角 · v2）

**诉求**：沟通文档（电梯场景深入沟通2）反复强调图查询的威力——"某维保员负责的楼宇里所有带特定品牌曳引机的电梯近一年困人记录"这类**多跳关联查询**用 SPARQL 极其自然。SPARQL 是 RDF 知识图谱的查询语言标准，也是本体推理与分析的核心入口。

**现状**：
- 模块 10（序列化）明确声明"**无 SPARQL 查询端点**"。
- 模块 09（校验）在内存构建 Jena Model 仅用于 SHACL 校验，**不暴露查询接口**。
- 模块 12（可视化）直接 SQL 查关系库，不走 SPARQL。
- 现有架构以 PostgreSQL 为唯一真相源，查询走 MyBatis-Plus SQL，**无法支撑图查询语义**。

**差距**：
- 若不引入 Triplestore，则复杂图查询只能靠 PostgreSQL 递归 CTE，**3 跳以上性能急剧下降**，且语义表达力远不如 SPARQL（路径查询、属性路径、CONSTRUCT 构造子图、联邦查询）。
- 即使一期维持 PostgreSQL 单源，也应**至少提供一层"图查询抽象"**（如 Apache Jena 的 RDF Connection over TDB，或 pggraph/AGE 扩展），为未来 SPARQL 端点留口。
- 建议明确"SPARQL 端点是否提供"是**架构分水岭**——若目标是真正的知识图谱应用（非仅建模台），SPARQL 端点是必备能力。

> **风险**：忽视此项会导致所有"图分析"诉求最终退化成 SQL JOIN 地狱，性能与可维护性双输。

### 3.13 维度⑬ 本体版本演化 —— 🔴 缺失（本体建模专家视角 · v2）

**诉求**：本体是**长期演化的活资产**，需要版本管理（v1.0 → v1.1 → v2.0）、差异比较（diff：新增/删除/修改了哪些类/属性/公理）、兼容性管理（向后兼容声明、迁移指南）、回滚、并行版本（不同项目用不同版本）。OWLGLEntology 级别的 `owl:versionIRI`/`owl:priorVersion`/`owl:backwardCompatibleWith` 是标准做法。

**现状**：
- 现有设计几乎没有本体版本概念。模块 11（扩展）有 `version` 字段但只是字符串标签，无 diff/兼容性/迁移。
- 模块 10（序列化）有 `ont_serialization_log` 审计，但那是**导出操作日志**，不是本体版本快照。
- 模块 04（实体类型）/05/06/07 的 `del_flag` 逻辑删除是**单线性变更**，无法回到历史版本，也无法对比两个版本。
- 无 `owl:versionIRI` 序列化支持。

**差距**：
- 当本体 Schema 变更（如给某实体加属性、改公理），已存在的实例如何处理？现有设计**无迁移策略**（类比 Flyway 管 DDL，本体需要管 Schema 演化的"本体迁移"）。
- 行业扩展（模块 11）尤其需要版本管理——医疗/电梯/消防本体随行业标准更新而演化。
- 建议引入**本体版本模型**：版本号、版本快照、diff 工具、兼容性声明、实例迁移规则、回滚。

### 3.14 维度⑭ 本体对齐/映射（Ontology Alignment） —— 🟡 缺失（本体建模专家视角 · v2）

**诉求**：沟通文档（数据关联沟通1）提到第三方系统接入需"本体对齐"——外部系统的 `City` 如何等价于本地 `UrbanArea`。跨本体映射是知识融合的核心：`owl:equivalentClass`/`owl:equivalentProperty`、桥接本体（bridge ontology）、实体消歧（同一设备在不同系统叫不同名）。

**现状**：
- 模块 04 有 `ont_entity_type_equivalent` 表，但那是**同一本体内部**的等价类声明，且模块 06 对象属性无等价属性表。
- **无跨本体对齐引擎**——无法声明"youming 的 `Elevator` ≡ 某行业标准的 `Lift` ≡ 某设备的 `DeviceType=ELEV`"。
- 无实体消歧/实体链接（entity linking）能力。
- 无本体对齐的可视化与校验工具。

**差距**：
- 多源数据融合（诉求①）天然需要本体对齐——不同数据源用不同术语描述同一现实实体，不对齐就会产生重复实例。
- 与医疗互操作（维度㉚）、IBMS 对接（维度㉘）强相关——这些外部系统都有自己的数据模型。
- 一期可先支持 `owl:equivalentClass/Property` 的存储与序列化，远期评估自动对齐算法（LIMES/SILK/LogMap）。

---

### 3.15 维度⑮ 受控词表/SKOS —— 🟡 缺失（本体建模专家视角 · v2）

**诉求**：行业知识体系需要**受控词表**（controlled vocabulary）——同义词、缩略语、上下位关系、分类法。W3C **SKOS**（Simple Knowledge Organization System）是标准。例如消防设备的分类树（探测器→感烟/感温/气体）、电梯品牌词典、医院科室分类。

**现状**：
- 模块 04 的"领域类别"只有 ICS/CCS 两个**静态国标分类**，无通用词表管理。
- 无 SKOS 模块（`skos:ConceptScheme`/`skos:Concept`/`skos:broader`/`skos:narrower`/`skos:exactMatch`）。
- 术语实体（`Term`）只有名称/定义，无同义词/缩略语/多语种映射。

**差距**：
- 受控词表是本体与业务系统之间的"语义桥梁"——IoT 物模型属性名、IBMS 子系统点位名、医疗术语都需要映射到规范词表。
- 缺少词表会导致实例命名混乱（同一设备不同源叫不同名），阻碍本体对齐（维度⑭）。
- 建议新增 SKOS 模块，支持概念scheme、概念层级、同义词、跨词表映射。

---

### 3.16 维度⑯ 推理物化/增量推理 —— 🟡 缺失（本体建模专家视角 · v2）

**诉求**：大规模图谱推理（如传递闭包：A→B→C→D 的可达性、子类层次推理）若每次查询都实时算，性能不可行。工业做法是**推理物化**（materialization）——把推理结果预先算好存入图，数据变更时**增量更新**受影响部分。

**现状**：
- 模块 09 全量在内存构建 Jena Model 执行 SHACL，**无物化、无增量**。
- `ReasonerAdapter.inferEntailments()` 直接抛异常。
- PRD §1.3 明确"不做大规模推理"，但沟通文档的"高危电梯自动标签""故障传播""多跳归因"都需要推理。

**差距**：
- 若要支撑"自动给高危设备打标签""故障影响面分析"等推理类诉求，必须有物化/增量推理机制。
- 这与 Triplestore 选型（维度⑨）耦合——GraphDB/gStore 内置推理物化，Jena TDB 需配合 RDFox/Pellet。
- 一期可维持"不推理"，但需明确**何时启动推理**的触发条件（实例规模、查询深度阈值）。

---

### 3.17 维度⑰ 多语言/国际化本体 —— 🟢 需补充（本体建模专家视角 · v2）

**诉求**：跨国企业/多语言园区的本体需要多语言标签（`rdfs:label@en`/`@zh`）、跨语言实体对齐（同一概念中英文名映射）、国际化数值/日期/单位格式。医疗领域更需跨语言术语（SNOMED CT 多语言版）。

**现状**：
- 模块 04/05/06 有 `*_label(entity/locale/label)` 表，**结构上支持多语言**，但仅作展示。
- PRD §9 提"前端中英文双语"，但本体层的多语言推理/查询未设计。
- 无跨语言实体对齐机制。

**差距**：相对低优先级（现有 label 表已预留），但需补齐运行时的多语言查询/序列化（如按 locale 输出 label）。

---

## 3.18-3.24 IoT 平台架构师视角补充（v2）

> 以下维度从**真实 IoT 平台落地经验**出发，针对 v1 仅泛泛提"IoT 接入"而未拆解的具体能力缺口。

### 3.18 维度⑱ 设备全生命周期建模 —— 🔴 缺失（IoT 平台视角 · v2）

**诉求**：设备不是静态资产，它有完整生命周期：采购 → 登记 → 安装 → 调试 → 运行 → 维保（多次）→ 维修 → 报废。每个阶段对应不同属性集、不同权限、不同关联（维保合同、责任人、历史工单）。电梯困人派单必须知道设备当前是否"在保"、维保合同是否有效。

**现状**：
- 实体类型树**无 `Device`/`Equipment` 基类**（国标核心只管标准数字化实体）。
- 无生命周期状态机（state machine）建模能力。
- 模块 08 实例的 `declaration_mode`（EXPLICIT/REFERENCE_ONLY）是引用模式，不是生命周期阶段。

**差距**：
- 需在行业扩展本体中定义 `Device` 抽象基类及其生命周期状态机（状态枚举 + 合法迁移 + 迁移条件）。
- 生命周期状态需参与告警/派单规则（如"报废设备不上报维保""过保设备告警升级"）。
- 与维度㉙工单闭环强耦合。

---

### 3.19 维度⑲ 物模型（Thing Model） —— 🔴 缺失（IoT 平台视角 · v2）

**诉求**：IoT 平台的核心抽象是**物模型**——每个设备类型有标准化的"属性（property）/服务（service）/事件（event）"三元组描述。例如电梯物模型：属性={楼层/载重/门状态}、服务={召唤/锁梯/检修}、事件={困人/超载/故障}。阿里云 IoT、华为 IoT、AWS IoT 都基于物模型。**物模型必须与本体实体类型对齐**，否则 IoT 数据无法语义化。

**现状**：
- 现有数据属性（模块 05）是**标准数字化属性**（标准编号/发布日期/约束类型），与 IoT 设备点位（温度测点/开关量）语义不同。
- 无物模型抽象层，IoT 属性与本体数据属性之间**无映射规范**。
- 无"事件"作为一等公民（IoT 事件 ≠ 校验违规）。

**差距**：
- 需设计**物模型层**：设备类型 → 属性/服务/事件定义，并与本体实体类型/数据属性/对象属性双向映射。
- 物模型是 IoT 接入层（维度②）与本体之间的**契约层**——没有它，IoT 数据进图谱就是"裸数据"，失去语义。
- 建议物模型作为行业扩展本体的子模块，复用模块 05 的值域规范。

---

### 3.20 维度⑳ 数字孪生（Digital Twin） —— 🟡 缺失（IoT 平台视角 · v2）

**诉求**：智慧园区/医院/工厂普遍要求数字孪生——物理设备在虚拟空间有对应实体，实时同步状态，支持仿真、预测、可视化。电梯困人场景中，数字孪生可实时显示电梯在井道中的位置、门状态、载重。

**现状**：无孪生实体概念，无"物理↔虚拟"映射关系。

**差距**：
- 数字孪生 = 本体实体（虚拟）+ IoT 实时数据（物理状态）+ 同步机制。
- 与维度⑲物模型、维度②IoT 接入、维度③时序强耦合。
- 一期可作为可视化（模块 12）的增强方向，远期可结合 BIM（维度㉕）做三维孪生。

---

### 3.21 维度㉑ 边缘计算/云边协同 —— 🟡 缺失（IoT 平台视角 · v2）

**诉求**：沟通文档（规则引擎选型沟通1）明确提到 Node-RED 适合**边缘部署**。真实 IoT 架构是分层的：边缘网关（数据预处理、本地规则、断网缓存）↔ 云端（全局分析、长期存储、跨域协同）。电梯/消防场景的毫秒级响应必须在边缘完成，不能全靠云端。

**现状**：无边缘层概念，假设全集中云端。

**差距**：
- 需设计边缘节点实体、边缘规则下发机制、断网续传（数据缓存与补偿）、云边数据同步策略。
- 与维度⑦ CEP 选型（Node-RED 边缘 + Flink 云端混合）耦合。
- 建议：边缘负责实时控制与简单告警，云端负责复杂分析与持久化。

---

### 3.22 维度㉒ 下行控制/反向控制 —— 🔴 缺失（IoT 平台视角 · v2）

**诉求**：IoT 不是单向数据上报，还有**下行控制**——服务触发执行（诉求⑥）需要下发命令到设备（如远程锁梯、启动消防泵、调节空调温度）。这涉及命令编排、安全联锁、确认回执、权限校验、幂等性。

**现状**：
- v1 只提"服务触发执行"，但侧重"调 API/发通知"，**未明确设备控制通道**。
- 现有设计是纯上行数据消费，无下行控制链路。

**差距**：
- 下行控制比上行采集**复杂得多**——必须保证命令可靠送达、执行确认、失败重试、安全联锁（如"启泵前必须确认无人在泵房"）。
- 命令模板、命令优先级、命令超时、并发冲突都需要建模。
- 与维度⑥服务触发、维度㉙工单闭环强相关。

> **关键风险**：消防泵启动这类**安全攸关**的下行控制，必须有双人确认、联锁、审计。现有设计完全无此能力。

---

### 3.23 维度㉓ 告警风暴抑制/去重/根因 —— 🟡 缺失（IoT 平台视角 · v2）

**诉求**：真实 IoT 场景下，一次网络抖动可能导致数百个设备同时离线告警，一个故障可能触发连锁告警（如停电→所有设备掉线）。必须有**告警去抖（debounce）、聚合（aggregate）、关联（correlate）、根因分析（root cause）**，否则运维人员会被告警淹没。

**现状**：
- 模块 09 的 `severity`（VIOLATION/WARNING/INFO）是校验级别，无告警去重/风暴抑制。
- v1 的维度⑤告警规则只提"生成 Alert 实体"，未提抑制与根因。

**差距**：
- 告警引擎需内置：时间窗口去抖、同类聚合、拓扑关联（同一母线下的设备掉线合并为一个根因告警）、根因推理（A 故障导致 B/C 告警，只报 A）。
- 与维度㉔设备拓扑、维度⑯推理物化耦合。

---

### 3.24 维度㉔ 设备拓扑与故障传播 —— 🟡 缺失（IoT 平台视角 · v2）

**诉求**：设备不是孤立的，它们有**拓扑关系**——供电链路（变压器→配电柜→楼层配电箱→设备）、网络链路、管路链路（消防泵→管道→阀门→喷头）。故障会沿拓扑传播（上游停电导致下游全断）。影响面分析需要图遍历。

**现状**：对象属性（模块 06）可表达拓扑，但**无故障传播引擎、无供电/管路链路专有拓扑类型**。

**差距**：
- 需建模链路拓扑（供电链/水力链/网络链），区分"上下游"语义。
- 需故障传播推理引擎（基于拓扑 + 告警，推算影响面与根因）。
- 与维度⑯推理物化、维度㉓告警根因强耦合。

---

## 3.25-3.29 智慧园区架构师视角补充（v2）

> 智慧园区（产业园/写字楼/商业综合体）是楼控、消防、电梯三大系统的**集成承载场景**。以下维度针对园区级集成能力缺口。

### 3.25 维度㉕ 空间/BIM/GIS 本体 —— 🔴 缺失（园区视角 · v2）

**诉求**：园区一切对象都依附于**空间**——楼宇→楼层→区域→房间，BIM 构件（墙/门/窗/管井），GIS 坐标（经纬度/海拔）。电梯困人派单必须知道电梯在哪个楼哪个单元；消防联动必须知道喷头属于哪个防火分区；能耗分析必须按空间分项。

**现状**：
- 实体类型树**无任何空间实体**（`Building`/`Floor`/`Room`/`FireZone`/`Space`）。
- 无 BIM 构件本体（IFC 对齐）、无 GIS 坐标属性、无空间包含关系（`contains`/`locatedIn`）。
- 现有"标准化对象"是抽象的，不承载空间语义。

**差距**：
- **这是园区场景最致命的缺口之一**——没有空间本体，所有"位置""区域""分区"都无法语义化表达。
- 需设计空间实体类型树（园区→楼→层→区→室），支持 BIM IFC 实体对齐与 GIS 坐标。
- 空间是所有设备/人员/事件的"锚点"，必须先建。
- 与维度㉘ IBMS、维度㉖ 能耗、消防防火分区强耦合。

---

### 3.26 维度㉖ 能源管理/碳排放 —— 🟡 缺失（园区视角 · v2）

**诉求**：园区核心 KPI 是能耗（电/水/气/冷/热）与碳排放。需要能耗计量（分项计量：照明/空调/动力/特殊）、分时统计、峰谷平分析、碳排核算（按能源因子换算）、节能优化（基于占用率/时段的策略）。

**现状**：无能源实体、无计量表计本体、无碳排计算模型。

**差距**：
- 需扩展能源本体：`EnergyMeter`（表计）、`EnergyConsumption`（能耗记录）、`CarbonEmission`（碳排）、能源类型字典。
- 能耗是典型时序数据（维度③），与空间（维度㉕）绑定（按楼层/区域分项）。
- 碳排计算依赖能源因子字典（单位字典模块 02 可扩展，但缺碳排因子数据）。

---

### 3.27 维度㉗ 安防/门禁/视频联动 —— 🟡 缺失（园区视角 · v2）

**诉求**：园区安防含门禁（刷卡/人脸/二维码）、视频监控（结构化：人脸/车牌/行为）、入侵报警、周界防范。需要事件融合（刷卡+视频+消防联动），如"消防告警→自动释放门禁→视频弹窗"。

**现状**：无安防实体、无事件融合引擎、无视频结构化数据接入。

**差距**：
- 需扩展安防本体：`AccessControlPoint`/`Camera`/`Credential`/`SecurityEvent`。
- 视频结构化数据（AI 识别结果）需作为事件接入，与告警（维度⑤）、服务触发（维度⑥）联动。
- 与维度㉜安全合规强相关（人脸/车牌数据属敏感个人信息）。

---

### 3.28 维度㉘ IBMS 子系统标准化对接 —— 🔴 缺失（园区视角 · v2）

**诉求**：智慧园区的现实是**异构子系统林立**——暖通（BACnet/Modbus）、给排水、照明（DALI/KNX）、电梯、消防（火灾报警主机私有协议）、安防、停车、能耗。IBMS（智能建筑管理系统）的核心是把这些子系统的数据**标准化接入**并联动。每个子系统有自己的点位表、数据模型。

**现状**：
- 无子系统适配层、无协议适配器（BACnet/Modbus/OPC UA/KNX/Matter）。
- 无"点位（point）"抽象——子系统点位如何映射到本体属性是 IBMS 落地的核心难题。
- 模块 02 单位字典只是数值单位，不是子系统点位。

**差距**：
- 需设计**点位映射层**：子系统点位（如"BACnet AV-1"）→ 本体属性（如 `某空调.送风温度`）。
- 需协议适配器框架（南北向驱动），与维度⑲物模型对齐。
- 这是 IBMS 落地最重的一块工程，往往占园区项目 40% 工作量。

---

### 3.29 维度㉙ 巡检/工单闭环 —— 🔴 缺失（园区视角 · v2）

**诉求**：v1 维度⑪只提了"工单实体"，但真实场景是**完整闭环**：巡检计划（周期/路线/项）→ 派单 → 现场执行（扫码/拍照/填表）→ 提交验收 → 不合格返工 → 归档统计。电梯困人救援、消防维保评估、设备定期巡检都走这条闭环。

**现状**：
- 无巡检计划实体、无工单流程引擎、无移动端执行支持、无验收/归档。
- 模块 09 校验不是业务流程。

**差距**：
- 需扩展工单/巡检本体：`InspectionPlan`/`WorkOrder`/`InspectionItem`/`ExecutionRecord`/`Acceptance`。
- 需轻量流程引擎（状态机驱动工单流转），与维度⑥服务触发、维度⑧动态实例生成集成。
- 移动端（App/小程序）是巡检落地必备，现有前端只覆盖 PC。

---

## 3.30-3.31 智慧医院架构师视角补充（v2）

> 智慧医院是高合规、高复杂度场景，本体需对齐医疗行业标准并支撑患者安全与药品合规。

### 3.30 维度㉚ 医疗互操作标准对接 —— 🟡 缺失（医院视角 · v2）

**诉求**：智慧医院的本体必须与医疗行业标准对齐——**HL7/FHIR**（医疗信息交换）、**ICD-10/11**（疾病分类）、**SNOMED CT**（临床术语）、**LOINC**（检验指标）、**药品 ATC 编码**。否则本体无法与 HIS/EMR/LIS/PACS 等医院系统互操作。

**现状**：完全无医疗术语标准对接，领域类别仅 ICS/CCS（标准分类，非医疗）。

**差距**：
- 需医疗扩展本体，对齐 FHIR 资源（Patient/Observation/Condition/Medication）。
- 需医疗受控词表（维度⑮ SKOS 的医疗实例），导入 ICD/SNOMED。
- 与维度⑭本体对齐强耦合（医疗术语 ↔ 本地实体）。

---

### 3.31 维度㉛ 医疗设备/患者/合规冷链 —— 🟡 缺失（医院视角 · v2）

**诉求**：
- **医疗设备**：CT/MRI/监护仪/输液泵的生命周期与维保（比通用设备更严，需计量校准）。
- **患者实体**：患者位置（床位）、诊疗关联、隐私保护。
- **合规冷链**：疫苗/血液/试剂的温控全链路溯源（温度异常→告警→处置→记录，符合 GSP）。
- **院感防控**：器械消毒追溯、隔离区管理。

**现状**：无医疗扩展本体，无患者/冷链/院感实体。

**差距**：
- 医疗是高度合规场景，冷链温度异常可能涉及药品安全责任，**溯源（维度④）必须完整**。
- 与维度㉙ 工单闭环（校准/维保）、维度⑤ 告警（温度超限）、维度㉜ 安全合规强耦合。

---

## 3.32-3.35 横切基础设施视角补充（v2）

> 以下维度**不属于任何单一业务场景**，但所有场景都依赖它们。这是最容易被遗漏、也最容易在后期成为瓶颈的"非功能性"差距。

### 3.32 维度㉜ 安全与合规（横切） —— 🔴 需补充（v2）

**诉求**：
- **等保 2.0 / 数据安全法 / 个人信息保护法**：园区/医院涉及大量个人信息（人脸/车牌/患者数据），必须数据分级分类、脱敏、加密、审计、最小化采集。
- **设备身份认证**：IoT 设备接入必须双向认证（证书/Token），防止伪设备注入。
- **命令鉴权**：下行控制（维度㉒）必须校验权限，防止越权操控（如非授权人员远程开门）。
- **操作审计**：谁在何时对哪个实体/规则做了什么，全链路留痕。
- **医疗合规**：HIPAA/等保三级/电子签名。

**现状**：
- PRD §10 仅有 RBAC 四角色（管理员/建模/审核/访客）+ `@SysLog`，**远不足**支撑数据级权限/字段级脱敏/设备认证。
- 无数据分级分类、无脱敏规则、无字段级权限。
- 无 IoT 设备认证机制（接入层未设计）。

**差距**：
- 需补充：数据分级分类标签、动态脱敏、字段级权限、IoT 设备证书/Token 管理、命令二次确认（高风险操作）、细粒度审计（不只是操作日志，还有数据访问日志）。
- 这是**合规红线**，医疗/金融场景不过关就无法上线。

---

### 3.34 维度㉞ 可观测性与运维（横切） —— 🟡 缺失（v2）

**诉求**：运行时系统必须有完善的可观测性——**指标**（metrics：实例数/告警数/规则执行耗时/查询 QPS）、**日志**（logs：结构化日志/链路日志）、**追踪**（traces：一次告警从 IoT 上报到派单的全链路）。规则引擎执行情况需要监控（哪些规则触发频繁、哪些规则从未触发）。

**现状**：模块 09 有 `ont_validation_report`，但那只是校验报告，**不是系统级可观测**。无 metrics/tracing 基础设施。

**差距**：
- 需接入 Prometheus + Grafana（指标）、ELK/Loki（日志）、Jaeger/SkyWalking（追踪）。
- 规则/映射/CEP 执行需埋点，便于排查"为什么这条告警没触发"。
- 这是运维落地的基础，否则线上问题无从排查。

---

### 3.35 维度㉟ 事件驱动架构 EDA（横切） —— 🔴 缺失（v2）

**诉求**：IoT/告警/触发/CEP 本质都是**事件驱动**的。需要事件总线（Kafka/RabbitMQ/Redis Streams）、CDC（捕获 PostgreSQL 变更下发事件）、事务发件箱模式（Transaction Outbox，保证 DB 写入与事件发布一致性）、事件 schema 演化管理。

**现状**：
- 现有设计是**同步校验为主**——模块 09 同步执行 SHACL，模块 10 同步导入导出。
- AGENTS.md 提到 Redis 已部署，但仅作缓存，未作消息总线。
- 无事件基础设施。

**差距**：
- EDA 是连接 IoT 接入、告警、触发、CEP 各模块的**神经系统**。
- 没有事件总线，模块间只能同步 RPC 调用，无法解耦、无法削峰、无法回放。
- 建议引入 Kafka（或复用 Redis Streams 做轻量起步）作为事件骨干。

---

### 3.36 维度㉱ AI/LLM 增强（横切） —— 🟢 需补充（远期 v2）

**诉求**：沟通文档（数据关联沟通1）提到 NLP 抽取作为数据来源之一。LLM 时代，本体平台可增强：①自然语言建模（"创建一个电梯实体"→自动生成 Schema）；②图谱问答（GraphQA，用自然语言查图谱）；③文档抽取补全（从设备手册自动抽取属性）；④时序异常检测（AI 识别异常模式）；⑤规则推荐（基于历史数据推荐告警阈值）。

**现状**：完全未涉及。PRD §1.3 明确"不做标准文本自动解析"。

**差距**：
- 一期不做合理（优先建基础设施），但应在架构中**预留 LLM 接入点**——本体是 LLM 理解领域知识的最佳载体（RAG over ontology）。
- 远期可作为差异化亮点。与维度⑭本体对齐、维度⑮ SKOS 协同（词表提升 LLM 准确性）。

## 4. 用落地场景检验设计缺口

沟通文档给了两个高价值场景，v2 再补充园区/医院两个场景，用以反推设计完整性。

### 4.1 场景一：电梯困人 → 救援派单闭环（v1）

**完整链路**：电梯 IoT 上报困人 → 流引擎写 `TrappedPersonAlarm` 实例 → 规则引擎查询图谱（电梯位置+值班维保员）→ 自动生成 `RescueOrder` 实例并 `assignedTo` → 调工单系统 API 派单 → 推送 App → 工单状态回写图谱。

| 链路环节 | 需要的能力 | 现有设计 | 缺口 |
|---------|-----------|---------|------|
| IoT 上报困人 | ②IoT 接入 + ③时序 | 无 | 🔴 |
| 写 Alarm 实例 | ⑩Alarm 实体类型 + ⑧动态生成 | 无 Alarm 类型；模块 08 不支持规则触发生成 | 🔴 |
| 规则引擎查询图谱 | ⑦规则引擎 + 图查询 | 模块 09 是校验不是决策；无规则引擎 | 🔴 |
| 生成 RescueOrder 实例 | ⑧动态生成 + ⑩工单实体 | 无 | 🔴 |
| 调工单系统 API | ⑥服务触发 | 无 | 🔴 |
| 推送 App | ⑥服务触发（通知） | 无 | 🔴 |
| 工单状态回写 | ⑨双写/external_link + ④溯源 | 无 external_link 字段 | 🟡 |
| 历史归因分析（某批次曳引机困人） | 图多跳查询 + 时序 | 无时序；PostgreSQL 单源多跳性能存疑 | 🟡 |

**结论**：电梯困人闭环**链路的 8 个环节中，6 个完全缺失**。现有设计无法支撑此场景。

### 4.2 场景二：消防维保质量评估（时序因果链）

**规则**：末端试水开启 → 压力变化 → 水流指示器启动 → 压力开关启动 → 泵启动，且总耗时 ≤ 5 分钟。

| 能力需求 | 现有设计 | 缺口 |
|---------|---------|------|
| 设备拓扑（试水阀↔水流↔压力开关↔泵） | 对象属性可表达拓扑，但缺设备实体类型 | 🟡 行业扩展 |
| 维保任务上下文（时间窗口） | 无时序/任务实体 | 🔴 |
| 时序事件序列捕获 | ③时序 + ⑦CEP | 🔴 完全缺失 |
| 时间窗口匹配（5 分钟） | 无窗口计算能力 | 🔴 |
| 评估结果（Pass/Fail）实例回写 | ⑧动态生成 + ⑩评估实体 | 🔴 |
| 规范可调（改 300 秒→180 秒） | 规则需外部化、可配置 | 🔴 |

**结论**：沟通文档自身已点明"纯图数据库不擅长时序计算，必须图谱 + CEP 混合架构"。现有设计**既无 CEP，也无时序**，此场景无法落地。

### 4.3 场景三：园区能耗异常定位（v2 园区视角）

**场景**：某园区本月电费异常升高，需定位原因。排查路径：总表能耗↑ → 哪栋楼↑ → 该楼哪层/哪个区域↑ → 该区域哪类负荷（空调/照明/动力）↑ → 是设备故障还是使用异常 → 是否涉及某次维保后参数变更。

| 能力需求 | 现有设计 | 缺口 |
|---------|---------|------|
| 空间层级（园→楼→层→区） | 无空间本体 | 🔴 ㉕ |
| 能耗表计与分项计量 | 无能源实体 | 🔴 ㉖ |
| 能耗时序数据（小时/日维度） | 无时序库 | 🔴 ③ |
| 多跳归因查询（空间→设备→负荷→工单） | 无 SPARQL，SQL JOIN 性能差 | 🔴 ⑫ |
| 关联维保历史（参数变更溯源） | 无工单闭环 | 🔴 ㉙ |
| 异常检测（识别"异常升高"） | 无 AI/统计能力 | 🟢 ㉱ |

**结论**：园区能耗归因需要**空间 + 能源 + 时序 + 图查询 + 工单**五项能力协同，现有设计全缺。

### 4.4 场景四：医院疫苗冷链温度异常处置（v2 医院视角）

**场景**：冷链冰箱温度连续 2 小时 > 8℃（疫苗失效临界），系统需：告警 → 自动通知值班 → 派工单 → 记录处置（转移疫苗/维修）→ 全链路溯源留证（合规 GSP 要求）→ 评估疫苗是否报废。

| 能力需求 | 现有设计 | 缺口 |
|---------|---------|------|
| 冷链设备/疫苗实体 | 无医疗本体 | 🟡 ㉛ |
| 温度时序（2 小时窗口判断） | 无时序 | 🔴 ③ |
| 告警（阈值+持续时长） | 无告警引擎 | 🔴 ⑤ |
| 工单派发与处置记录 | 无工单闭环 | 🔴 ㉙ |
| 全链路溯源（合规留证） | 无 Provenance | 🟡 ④ |
| 通知（值班/负责人） | 无服务触发 | 🔴 ⑥ |
| 数据安全（疫苗/患者隐私） | RBAC 不足 | 🔴 ㉜ |

**结论**：冷链合规场景中，**溯源（维度④）从 v1 的"中优先级"升级为"强制"**——没有完整溯源，合规审计无法通过。

### 5.3 🔄 需要补充设计的横切关注点

- **URI 生成策略**：实例 URI 从外部主键稳定生成（`domain/ontology/{Class}/{PK}`）；模块 03/08 IRI 生成延伸到"外部数据源主键→实例 URI"。
- **增量更新与 CDC**：映射模块必须支持增量，否则全量同步在大规模 IoT/业务数据下不可行；与 EDA（模块 26）耦合。
- **版本管理一致性**：本体 Schema（模块 14）、映射规则、告警规则、CEP 规则、物模型都需版本控制——建议统一版本模型，避免各自为政。
- **性能与规模分层指标**：建模台（现有 PRD §9）vs 运行时（IoT 吞吐/告警延迟/规则执行/查询 QPS）量级完全不同，需分别定义。
- **可解释性与审计**：每条告警能追溯到触发规则与源数据；每次服务调用/下行控制留痕；医疗/安全攸关场景强制。
- **数据质量治理**：多源数据接入后，脏数据/重复实例/命名不一致会指数级放大；需数据质量规则与实体合并（entity merge）能力（与模块 15 对齐、模块 16 词表协同）。
- **配置即数据 vs 代码**：告警/CEP/映射规则应可配置（沟通文档原则），但 Node-RED 流程属"可视化代码"，需纳入版本管理与 CI/CD。

## 6. 实施路线图建议（v2）

> **v2 路线图关键调整**：
> 1. **横切地基前置到 M6.5**——安全/EDA/可观测是运行时地基，不能等到最后；尤其安全合规则是红线。
> 2. **空间本体提到 M7 最前**——空间是所有园区/医院场景的锚点，没有它设备/人都无处安放。
> 3. **物模型与设备生命周期先于 IoT 接入**——先定义"设备是什么、有什么属性/服务/事件"，再接入数据，否则裸数据无语义。
> 4. **工单闭环提到 M8**——它是告警/触发的"动作出口"，没有工单闭环，告警只能"看"不能"办"。
> 5. **医疗扩展放 M10**——医疗合规复杂度高，建议在通用能力验证后再切入。

## 7. 关键风险与原则

### 7.1 必须坚守的原则（v2 增补）

1. **职责分离**（沟通文档核心论断）：
   - 本体（T-Box）管"是什么"——领域知识与概念模型。
   - 规则引擎/CEP 管"怎么做"——业务流程与时序编排。
   - 告警引擎管"何时提醒"——实时监控。
   - 服务触发管"做什么动作"——执行。
   - **不要把告警/触发/CEP 塞进 SHACL 校验引擎（模块 09），也不要用 OWL 公理做实时告警。**

2. **核心 Schema 锁定 + 行业扩展隔离**（现有 PRD §3.3 已立）：
   - 楼控/电梯/消防/医疗的设备、告警、工单实体**必须走扩展命名空间**（模块 11），不得污染国标核心实体类型树。

3. **最新状态写图谱，历史留时序库**：
   - 图谱/关系库只存最新值 + 关系；时序历史进 TDengine；本体属性指向时序端点。避免图膨胀。

4. **图谱决策 + 业务库事务（双写/状态映射）**：
   - 工单流转、签到、照片上传等高频事务留业务系统；图谱存"概念与关系"用于决策与归因；`hasExternalLink`/`external_link` 桥接。

5. **规则/告警即数据**：
   - 告警规则、CEP 规则、映射规则都应可配置、可版本控制、可视化，而非硬编码。

6. **横切地基先行（v2）**：
   - 安全合规、事件驱动骨干（EDA）、可观测性**必须先于业务模块建设**——它们是运行时地基，后置会导致反复返工与合规风险。

7. **空间本体优先（v2）**：
   - 园区/医院一切对象依附于空间——空间本体（园/楼/层/区/室 + BIM/GIS）必须先于设备/业务实体建模，否则对象无处安放。

8. **物模型作为 IoT 与本体的契约层（v2）**：
   - IoT 数据进图谱前，必须先经物模型层（属性/服务/事件定义）语义化，避免裸数据污染图谱。

9. **下行控制安全联锁（v2）**：
   - 任何设备控制命令必须经权限校验 + 联锁 + 确认回执；安全攸关操作（启泵/锁梯/开门）强制双人确认与审计。

10. **本体版本化与实例迁移（v2）**：
    - 本体 Schema 是活资产，必须版本管理 + 兼容性声明 + 存量实例迁移规则，类比 Flyway 管 DDL。

### 7.2 主要风险（v2 增补）

| 风险 | 影响 | 对策 |
|------|------|------|
| **把运行时能力塞进现有 12 模块** | 职责混淆，模块 09 校验引擎被滥用为告警/决策引擎，性能与可维护性崩溃 | 明确新建独立模块（13-39），模块 09 保持只读校验定位 |
| **时序数据进图谱导致图膨胀** | 图谱/关系库膨胀，查询崩溃 | 坚持"最新值+时序端点"策略，时序进 TDengine |
| **规则引擎选型摇摆** | Node-RED vs Flink vs Drools 影响整个 M8-M10 架构 | 沟通文档已倾向 Node-RED（轻量/可视化/边缘友好），一期定 Node-RED，保留 Flink 作大规模演进 |
| **IoT 高频数据压垮写入链路** | 实例模块写入成为瓶颈 | IoT 接入层聚合/降采样；时序写与实例最新值写分离 |
| **行业扩展本体设计失控** | 扩展实体泛滥，破坏核心一致性 | 严格走模块 11 扩展合法性校验（5 条规则），扩展命名空间强制 |
| **Provenance 过度设计** | 完整 PROV-O 图增加复杂度 | 一期字段级轻量溯源，远期按需演进 |
| **双写一致性** | 图谱与业务库状态不一致 | 一期 external_link 单向引用 + 异步回写；明确最终一致性边界 |
| **横切基础设施后置（v2）** | 安全/EDA/可观测若放到最后，运行时模块无地基可依，反复返工 | 横切层前置到 M6.5，先建地基再起上层 |
| **空间本体缺失导致场景悬空（v2）** | 设备/人员/事件无处安放，所有园区/医院场景无法落地 | 空间本体作为 M7 首要交付，先于设备/业务实体 |
| **物模型与本体脱节（v2）** | IoT 数据进图谱成"裸数据"，失去语义价值 | 物模型层（模块 20）作为 IoT 接入与本体之间的强制契约层 |
| **下行控制安全风险（v2）** | 越权操控设备（如远程开门/启泵）造成安全事故 | 命令二次确认 + 联锁 + 权限校验 + 审计，安全攸关操作强制双人 |
| **告警风暴淹没运维（v2）** | 一次故障触发数千告警，运维瘫痪 | 告警引擎内置去抖/聚合/关联/根因收敛（模块 23） |
| **多源数据质量失控（v2）** | 脏数据/重复实例/命名不一致指数级放大 | 数据质量规则 + 实体合并 + SKOS 词表治理 + 本体对齐协同 |
| **医疗/安全合规不达标（v2）** | 等保/数据安全/GSP 不过关无法上线 | 安全合规（模块 36）作为红线最先建设；冷链溯源强制完整 |
| **本体版本演化断裂（v2）** | Schema 变更后存量实例无法迁移，历史数据失配 | 本体版本模型（模块 14）+ 实例迁移规则，类比 Flyway 管 DDL |
| **系统复杂度爆炸（v2）** | 39 个模块协同，集成与运维成本陡增 | 严格分层 + 清晰边界 + 可观测性 + 渐进式交付（每里程碑可独立验收） |

### 7.3 与现有 PRD 边界声明的关系

PRD §1.3"非目标"声明了三条：不做标准文本解析、不做大规模图谱推理、不做协同制定流程。这三条**本身没错**，但它们**没有覆盖**沟通文档提出的运行时能力（IoT/告警/触发/CEP/数据源映射）。

建议在 PRD 或新增的"运行时设计文档"中：
- **保留**现有 12 模块的建模台定位与非目标声明（它们对"标准数字化建模"场景是正确的）。
- **新增**一节明确"运行时智能能力（IoT 接入/告警/触发/CEP/数据源映射）属第二阶段（M7-M10），由独立模块承接，不在现有 12 模块范围内"。
- 避免**误把现有 12 模块当成能直接支撑电梯/消防场景的系统**——那是沟的右岸，还没建。

## 9. 总结

| 维度 | 结论 |
|------|------|
| **现有设计是什么** | GB/T 48000.3—2026 合规的标准本体**静态建模工作台**（T-Box + A-Box + SHACL + RDF + 扩展治理 + 可视化） |
| **沟通文档要什么** | 以本体为语义中枢的**IoT 驱动动态运行时智能系统**（数据接入 + 时序 + 告警 + 触发 + CEP + 溯源 + 电梯/消防/园区/医院闭环） |
| **v1 差距** | 11 维度（6 缺失 + 5 需补充/改造），8 个新模块 |
| **v2 增量差距** | 多角色评审新增 **25 个维度**（本体6 + IoT7 + 园区6 + 医院2 + 横切5），新模块扩展至 **27 个** |
| **v2 核心发现** | v1 遗漏了：①本体层基础能力（SPARQL/版本/对齐/SKOS/推理）；②IoT 真实落地七要素（设备生命周期/物模型/孪生/边缘/下行控制/告警风暴/故障传播）；③园区五要素（空间/能源/安防/IBMS/工单闭环）；④医疗五要素（FHIR/设备/患者/冷链/院感）；⑤横切四要素（安全/可观测/EDA/AI）。**这些是"将来开发还是不全面"的主要根源** |
| **需要完善的** | 模块 04（对齐）/08（写入+溯源）/07（边界）/09（定位）/10（版本+多语言）+ PRD §1.3/§9 |
| **需要补充的** | 26 个新模块，分 5 层（本体增强/数据接入/运行时智能/行业扩展/横切基础设施） |
| **需要改造的** | 模块 08、07、09、10、04 + PRD 边界声明与非功能需求 |
| **实施路径** | M6.5 横切地基 → M7 数据接入+空间 → M8 事件告警+工单 → M9 CEP+IBMS → M10 场景闭环+智能增强 |
| **最关键决策** | ①规则引擎 Node-RED（沟通文档信号）；②时序库 TDengine 涛思（信创+物模型契合，详见 §3.3）；③告警/触发/CEP/EDA 独立成模块，不污染校验引擎；④行业扩展走模块 11，不污染核心；⑤横切地基（安全/EDA）先行业务模块；⑥空间本体先于设备/业务实体；⑦物模型作为 IoT-本体契约层；⑧下行控制强制安全联锁 |

> **一句话（v2）**：现有设计是一座合格的"标准本体建模工厂"，但沟通文档与真实园区/医院/楼控场景要的是一座"会感知、会决策、会行动、可演进、合合规的智能城市"。工厂已建好（M1-M6），城市还缺：**地基**（安全/EDA/可观测）、**供电**（数据接入）、**神经**（IoT/时序/物模型）、**骨架**（空间本体）、**免疫系统**（告警/风暴抑制）、**肌肉**（服务触发/下行控制）、**大脑皮层**（CEP/规则流）、**循环系统**（工单闭环）、**皮肤**（IBMS/安防/能源）、**记忆**（版本/溯源/孪生）、**语言**（SPARQL/对齐/SKOS）、**灵魂**（AI/LLM，远期）。
>
> v1 只看到了"神经和肌肉"，v2 补齐了"地基、骨架、循环、皮肤、记忆、语言"。**唯有把这 12 类逐项补齐且各司其职，通过本体协同，才能避免"开发完还是不全面"的困局。** 本次仅分析，未做任何开发。
