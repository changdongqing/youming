## 1. 结论

下一阶段建议优先开发 **模块18“数据源映射”**，并以本系统现有的用户、部门、岗位数据作为第一套完整落地场景；完成关系数据库到本体实例的稳定映射链路后，再开发 **模块20“IoT 物模型与本体映射”**。

建议的总体顺序为：

```text
现有基础能力稳定性门禁
  → 运行时实例写入底座
  → 通用关系数据库映射
  → 用户/部门/岗位自举建模
  → IoT物模型与本体映射
  → IoT动态接入与时序数据
  → 告警、服务触发和CEP闭环
```

不建议当前直接开始 MQTT、设备遥测或告警开发。数据源映射阶段应先建立一条可复用的运行时链路：

```text
外部数据
  → 映射配置
  → 数据转换与IRI生成
  → 幂等实例写入
  → 来源追踪
  → EDA事件
  → SHACL校验
  → SPARQL查询与可视化
```

用户、部门、岗位并不是简单的演示数据，而是用于验证平台能否从“静态本体建模工作台”演进为“语义数据运行时平台”的首个自举场景。

## 2. 当前能力与开发时机判断

当前仓库已经完成以下关键基础能力：

| 已有能力 | 当前落地 | 对数据源映射的作用 |
|---|---|---|
| 本体Schema和实例管理 | 模块01～12 | 提供实体类型、数据属性、对象属性及实例承载能力 |
| SPARQL查询端点 | V17、模块13 | 用于映射完成后的语义查询验收 |
| 本体版本演化 | V18、模块14 | 映射配置可以声明兼容的本体版本范围 |
| EDA事件骨干 | V19、模块26 | 映射作业和实例变化可通过Outbox可靠发布事件 |
| 安全与合规 | V20、模块36 | 支撑数据源凭证、敏感字段、权限和审计 |
| UPMS业务数据 | `sys_user`、`sys_dept`、`sys_post` 等 | 可作为第一套真实数据映射来源 |

模块14详细设计已经明确：

- 数据源映射配置需要声明兼容的本体版本范围；
- 发生 breaking 版本变化时，映射配置应执行兼容性检查。

模块26和模块36已经分别提供：

- 可靠领域事件骨干；
- 数据最小化和敏感载荷控制；
- 凭证、安全策略和审计能力。

因此，旧路线图中 M6.5 的主要运行时地基已经具备，当前进入模块18是合适的。

### 2.1 需要先处理的现状约束

当前实例管理仍以人工建模为中心：

- `OntEntityInstanceServiceImpl#createInstance()` 当前将来源固定为 `EXTENSION`；
- V10 中实例 `source_type` 只允许 `APPENDIX_D/EXTENSION`；
- 实例和值没有形成完整的“外部数据源记录身份”；
- 缺少映射版本、同步作业、同步游标、内容摘要、失败重试等运行时信息；
- 现有实例接口面向前端CRUD，不适合直接承载映射、IoT、规则和告警的批量写入。

因此，数据源映射不能只增加配置表和管理页面，必须先补齐程序化、幂等、可溯源的实例摄入能力。

### 2.2 稳定性门禁

在正式开发模块18之前，建议安排一个短周期的稳定性门禁，而不是新增业务功能：

- 对模块13 SPARQL执行集成回归；
- 对模块14版本发布、迁移、恢复执行集成回归；
- 对模块26 Outbox、Relay、Inbox幂等、死信和回放补关键测试；
- 对模块36安全策略、脱敏、加密、审计链和设备凭证补关键测试；
- 验证以上模块在 `pig-boot` 单体运行形态下能够协同工作。

模块18将直接依赖这些能力，先建立稳定基线可以避免在映射开发期间反复排查基础设施问题。

## 3. 下一阶段定位：数据源映射与组织账号自举建模

建议将下一阶段定义为：

> **M7-A：数据源映射与组织账号自举建模**

目标链路如下：

```text
youming业务数据库
  ├── sys_user
  ├── sys_dept
  ├── sys_post
  ├── sys_user_dept
  └── sys_user_post
          ↓
数据源映射模块
          ↓
组织与账号扩展本体
          ↓
Ontology实例、数据属性值和对象关系
          ↓
SHACL校验、SPARQL查询和图谱可视化
```

这一阶段应交付的不是针对三张表编写一次性同步代码，而是一套可以继续服务于其他业务系统、第三方数据库和IoT设备档案的通用映射能力。

## 4. 迭代一：运行时实例写入底座

### 4.1 建立统一实例摄入服务

建议在现有人工CRUD服务之外增加内部程序化写入服务，例如：

```java
OntologyInstanceIngestionService
```

统一处理：

- 根据外部稳定键创建或更新实例；
- 数据属性批量覆盖或合并；
- 对象关系批量建立和解除；
- 单条和批次事务控制；
- 幂等控制；
- 类型、值域、基数、单位和域/值域检查；
- 来源和映射作业记录；
- 安全策略和数据访问审计；
- 实例变化事件发布。

后续模块应统一调用该服务：

```text
模块18 数据源映射
模块19 IoT接入
模块23 告警
模块24 服务触发
规则引擎和第三方API导入
```

这些模块不应分别直接操作：

- `ont_entity_instance`
- `ont_instance_data_value`
- `ont_instance_object_relation`

否则会形成多套IRI、幂等、校验、安全和事件规则。

### 4.2 建立外部记录身份

建议增加独立的来源绑定模型：

```text
数据源 + 映射配置 + 源对象 + 源记录主键
                      ↓
                  本体实例ID
```

至少记录：

- `source_id`：数据源；
- `mapping_id`：映射配置；
- `source_object`：源表、视图或对象名称；
- `source_record_key`：源记录稳定主键；
- `instance_id`：目标本体实例；
- `source_version`：源数据或消息版本；
- `source_updated_at`：源记录更新时间；
- `last_sync_at`：最近同步时间；
- `content_hash`：映射输入摘要；
- `sync_status`：同步状态。

建议建立逻辑唯一约束：

```text
(mapping_id, source_object, source_record_key)
```

其作用包括：

- 重复同步不会创建重复实例；
- 源记录更新时可以定位既有实例；
- 源记录删除时可以执行删除策略；
- IRI模板演化后仍能追踪原始记录；
- 可以按源记录进行失败重试和审计。

### 4.3 扩展实例来源

实例来源建议扩展为：

```text
MANUAL
APPENDIX_D
EXTENSION
DATA_MAPPING
IOT
RULE
IMPORT
API
```

第一期不要求完整实现 PROV-O，但至少应记录：

- 来源数据源；
- 来源表、API或设备；
- 来源主键或消息ID；
- 映射规则及版本；
- 同步作业；
- 生成时间；
- 原始值摘要；
- 转换结果；
- 可选置信度。

## 5. 迭代二：通用关系数据库映射V1

### 5.1 V1范围

第一版建议只做关系数据库映射，优先支持 PostgreSQL。

第一版不同时建设：

- REST API映射；
- Excel批量映射；
- MQTT/Kafka遥测接入；
- 完整R2RML标准实现；
- 图数据库映射；
- 任意脚本执行；
- 数据库日志级实时CDC。

优先把关系表到本体实例、数据属性和对象属性的语义映射做正确、做稳定。

### 5.2 数据源管理

应支持：

- 数据源注册；
- 连接测试；
- Schema、表、视图、列、主键和外键发现；
- 凭证加密；
- 数据源访问权限；
- 只读账号约束；
- 可访问Schema和表白名单；
- 连接使用情况审计。

仓库已有 `pig-common-datasource` 和代码生成模块的数据源能力，可以复用底层动态数据源技术，但不建议让Ontology直接依赖代码生成模块的业务实现。

详细设计阶段需要在以下方案中作出决定：

1. 将数据源注册能力抽取为公共基础模块，代码生成和Ontology共同使用；
2. Ontology建立独立的数据源配置，但复用公共动态数据源基础设施；
3. Ontology仅保存公共数据源引用，不保存重复连接信息。

长期优先考虑公共数据源注册中心；如果一期需要控制改造范围，可以采用独立配置加抽象接口，但应避免将连接实现写死。

### 5.3 实体映射

配置关系：

```text
源表或视图 → 本体实体类型
```

至少包含：

- 目标本体工程；
- 兼容本体版本范围；
- 目标实体类型；
- 源对象和源主键；
- 数据过滤条件；
- IRI模板；
- 标签生成规则；
- 删除策略；
- 启停状态；
- 映射版本。

IRI应根据稳定业务键生成，例如：

```text
{namespace}user-account/{user_id}
{namespace}department/{dept_id}
{namespace}position/{post_id}
```

不能使用用户名、姓名、部门名称等可能变化的字段作为实例身份。

### 5.4 数据属性映射

配置关系：

```text
源字段 → 本体数据属性
```

第一期转换函数应控制在安全、确定、可审计范围：

- 字符串裁剪；
- 数值类型转换；
- 日期格式转换；
- 布尔和状态码转换；
- 枚举字典转换；
- 空值处理；
- 默认值；
- 简单字符串拼接。

第一版不建议允许执行任意JavaScript、Groovy、SpEL或任意SQL表达式，避免安全、性能和可重放性问题。

### 5.5 对象属性映射

必须支持：

1. 外键生成的对象关系；
2. 中间关联表生成的对象关系；
3. 自关联层次关系；
4. 目标实例暂未存在时的延迟解析。

组织管理场景示例：

```text
sys_dept.parent_id
  → parentOrganizationUnit

sys_user.dept_id
  → primaryDepartment

sys_user_dept
  → memberOfDepartment

sys_user_post
  → assignedPosition
```

对象关系映射是Ontology数据接入区别于普通字段ETL的关键能力，不能仅实现平面字段复制。

### 5.6 映射预览和发布

映射正式执行前应提供：

- 抽样读取；
- IRI生成预览；
- 数据属性预览；
- 对象关系预览；
- 类型转换错误；
- 空值和默认值处理结果；
- 缺失引用；
- 重复IRI；
- 敏感字段提示；
- SHACL预校验；
- 预计新增、更新、跳过和失败数量。

映射配置应具有草稿、已发布、已停用等状态。正式同步只能使用已发布版本，不能直接执行正在编辑的草稿。

## 6. 迭代三：用户、部门、岗位自举建模

### 6.1 不直接复制数据库概念

不建议将本体实体类型设计为：

```text
SysUser
SysDept
SysPost
```

这些名称反映的是pig数据库实现，而不是稳定业务语义。直接照搬会导致本体与具体系统表结构强耦合。

建议使用：

| 业务表 | 推荐实体类型 | 语义说明 |
|---|---|---|
| `sys_user` | `UserAccount`或`PlatformUserAccount` | 系统账号，不直接等同于自然人 |
| `sys_dept` | `OrganizationalUnit` | 组织单元或部门 |
| `sys_post` | `Position` | 岗位，不等同于RBAC角色 |
| `sys_user_dept` | 对象属性断言 | 账号与所属部门关系 |
| `sys_user_post` | 对象属性断言 | 账号与岗位关系 |

### 6.2 UserAccount与Person边界

`sys_user`代表的是系统账号，不一定等同于现实世界中的自然人。

第一期应优先映射为：

```text
UserAccount
```

以后接入HR或人员主数据后，再扩展：

```text
Person --hasAccount--> UserAccount
Person --holdsPosition--> Position
Person --memberOf--> OrganizationalUnit
```

这样可以避免因为当前数据库把账号和部分人员信息放在同一张表，就在本体中错误地声明“账号等同于人员”。

### 6.3 推荐数据属性

#### UserAccount

- `externalId`
- `username`
- `displayName`
- `accountStatus`
- `email`
- `phone`
- `createdAt`
- `updatedAt`

明确禁止映射：

- `password`；
- `salt`；
- 认证密钥；
- 不必要的第三方OpenID；
- 密码修改和认证过程中的敏感信息。

手机号、邮箱应接入模块36的数据分级、脱敏和访问审计。

#### OrganizationalUnit

- `externalId`
- `organizationCode`，如果源系统具备；
- `organizationName`
- `sortOrder`
- `status`
- `createdAt`
- `updatedAt`

#### Position

- `externalId`
- `positionCode`
- `positionName`
- `description`
- `sortOrder`

### 6.4 推荐对象属性

| 对象属性 | 主体 | 客体 | 数据来源 |
|---|---|---|---|
| `parentOrganizationUnit` | OrganizationalUnit | OrganizationalUnit | `sys_dept.parent_id` |
| `primaryDepartment` | UserAccount | OrganizationalUnit | `sys_user.dept_id` |
| `memberOfDepartment` | UserAccount | OrganizationalUnit | `sys_user_dept` |
| `assignedPosition` | UserAccount | Position | `sys_user_post` |

当前数据库中没有直接的岗位—部门关系，因此不能仅根据“某部门用户拥有某岗位”推断“岗位属于该部门”。如业务确实需要该关系，应先明确业务事实来源，再增加相应表或映射规则。

## 7. 迭代四：同步作业、增量和EDA

### 7.1 同步模式

第一期建议实现：

- 手工全量同步；
- 定时增量同步；
- 预览执行；
- 正式执行；
- 指定记录重跑；
- 失败记录重试；
- 作业取消；
- 断点恢复。

增量同步第一期可以采用：

```text
update_time + 主键游标
```

暂时不必立即接入Debezium或数据库日志CDC。应先验证映射语义、幂等、删除策略和错误恢复，再演进实时CDC。

### 7.2 同步依赖顺序

组织账号场景应按依赖执行：

```text
1. 部门实例
2. 岗位实例
3. 用户账号实例
4. 部门父子关系
5. 用户—部门关系
6. 用户—岗位关系
```

关系映射遇到目标实例尚未创建时，应：

- 延迟到第二阶段解析；或
- 写入待解析队列；或
- 进入可重试错误记录。

不能静默丢弃关系。

### 7.3 EDA事件

建议发布：

```text
MAPPING_JOB_STARTED
MAPPING_JOB_COMPLETED
MAPPING_JOB_FAILED
INSTANCE_INGESTED
INSTANCE_UPDATED_FROM_SOURCE
RELATION_RESOLVED
MAPPING_RECORD_REJECTED
```

事件载荷必须遵循数据最小化原则，不得包含：

- 密码和盐；
- 数据源凭证明文；
- 未脱敏敏感字段；
- 无必要的完整源记录。

### 7.4 删除策略

实体映射应显式配置：

- `IGNORE`：忽略源删除；
- `MARK_INACTIVE`：将本体实例标记为失效；
- `SOFT_DELETE`：软删除映射生成实例；
- `BLOCK_AND_REVIEW`：进入人工确认。

用户、部门和岗位第一期建议采用 `MARK_INACTIVE`。不建议直接物理删除本体实例，因为实例可能仍被历史关系、审计记录、本体版本或业务场景引用。

## 9. M7-A验收标准

### 9.1 功能验收

1. 能配置 `sys_user`、`sys_dept`、`sys_post` 到本体实体类型的映射；
2. 能通过 `sys_user_dept`、`sys_user_post` 生成对象属性关系；
3. 能通过 `sys_dept.parent_id` 生成部门层次关系；
4. 同一批数据重复执行不会产生重复实例；
5. 修改用户名显示信息或部门名称后更新原实例，不创建新实例；
6. 源数据删除或停用时按配置策略处理；
7. 缺失部门、岗位或关系目标时进入错误明细；
8. 映射规则绑定本体版本，不兼容版本时阻断执行；
9. 同步作业可重试、可恢复、可审计；
10. 手机号和邮箱受安全策略控制；
11. 密码、盐和凭证信息不进入本体、日志和事件；
12. 实例变化能够通过EDA可靠发布领域事件。

### 9.2 语义验收

通过SPARQL能够查询：

- 某用户账号属于哪些部门；
- 某用户账号的主部门；
- 某用户账号分配了哪些岗位；
- 某部门有哪些下级部门；
- 某部门及其子部门有哪些用户账号；
- 某岗位关联了哪些用户账号；
- 某个实例来自哪个数据源、源对象和源记录；
- 某次映射作业创建或更新了哪些实例。

### 9.3 性能与可靠性基线

第一期不追求IoT级吞吐，但应满足：

- 万级组织账号实例可稳定同步；
- 重复同步保持幂等；
- 单条失败不阻断整个批次；
- 作业可以断点恢复；
- 同步过程不长时间锁定业务表；
- 失败记录可以定位到具体映射、源记录和目标属性；
- 同步结果具备可观测指标和审计日志。

## 10. 下一阶段之后：IoT物模型与本体映射

完成 M7-A 后，建议进入：

> **M7-B：IoT物模型与Ontology映射**

这一阶段先建设静态语义契约，不立即建设完整MQTT实时接入。

### 10.1 物模型核心对象

- 产品 `Product`；
- 设备类型 `DeviceType`；
- 设备实例 `Device`；
- 属性 `Property`；
- 服务 `Service`；
- 事件 `Event`；
- 参数 `Parameter`；
- 数据类型；
- 单位；
- 访问模式；
- 约束范围；
- 物模型版本。

### 10.2 物模型到本体的映射

| 物模型对象 | 本体目标 |
|---|---|
| 产品或设备类型 | EntityType |
| 设备实例 | EntityInstance |
| 物模型属性 | DataProperty |
| 设备关联 | ObjectProperty |
| 设备事件 | 事件实体类型或事件实例 |
| 服务定义 | Action或Service语义实体 |
| 服务参数 | DataProperty或参数实体 |
| 单位 | 现有单位字典 |
| 枚举值 | 枚举值域，后续可接SKOS |

需要校验：

- 数据类型兼容；
- 单位维度兼容；
- 属性读写方向；
- 值域和基数；
- 事件参数完整性；
- 本体版本兼容性；
- 物模型版本兼容性。

### 10.3 物模型应先于IoT动态接入

如果先接入MQTT再补物模型，系统得到的只是缺乏语义的裸数据：

```json
{
  "deviceId": "D001",
  "temperature": 28.6,
  "status": 1
}
```

系统无法确定：

- `temperature`的业务含义；
- 单位；
- 对应的本体属性；
- `status=1`的枚举语义；
- 数据是否可写；
- 是否属于时序属性；
- 是否应该产生语义事件。

正确顺序应为：

```text
定义物模型
  → 映射到本体
  → 注册产品和设备
  → 接入遥测
  → 最新状态写本体实例
  → 历史数据写时序库
  → 语义事件进入EDA
```

## 12. 模块15、16、17的优先级判断

当前不建议将以下模块插到数据源映射之前：

- 模块15 本体对齐；
- 模块16 SKOS受控词表；
- 模块17 推理物化。

原因是单一数据源的用户、部门、岗位映射暂不依赖这些能力。它们更适合在以下场景出现时建设：

- 多个业务系统同时接入；
- 同一人员或设备跨源身份消歧；
- 不同行业术语和编码体系治理；
- 跨本体等价类、等价属性对齐；
- 故障传播、层次闭包等推理物化需求。

因此当前优先模块18具有更直接的业务价值，也能更全面地验证已完成的实例、校验、SPARQL、版本、EDA和安全能力。

## 13. 最终建议

下一阶段应正式立项：

> **模块18：数据源映射与组织账号自举建模**

核心交付不是一次性导入三张业务表，而是建立可复用的：

1. 数据源连接机制；
2. 实体、数据属性和对象属性映射机制；
3. 稳定IRI生成机制；
4. 程序化实例摄入机制；
5. 幂等、增量和删除处理机制；
6. 来源追踪和安全审计机制；
7. 映射版本与本体版本兼容机制；
8. 映射预览、同步作业和错误恢复机制。

用户、部门、岗位是第一套验证数据。完成该阶段后，再开发物模型映射，后续设备档案、空间关系、IoT最新状态和业务事件都可以复用同一套实例摄入、IRI、溯源、版本、安全和EDA基础。
