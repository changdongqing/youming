## 三、需修正问题（P1）

### P1-01：前端分页接口未使用，页面假分页

**位置：** `web/src/views/ontology/data-property/index.vue:355-384`，`web/src/api/ontology/data-property.ts:12-18`

**问题：**

API 层定义了 `fetchDataPropertyPage` 分页查询函数，但页面 `loadList()` 在"全部属性"模式下调用的是 `fetchDataPropertyList`（不分页 list 接口），然后在前端伪造分页：

```typescript
const response = await fetchDataPropertyList(params);       // 调的是 /list 不分页接口
pagedData.value = (response.data || []) as DataPropertySummary[];
pagination.total = pagedData.value.length;                  // total = 当前数组长度，非实际总数
```

**影响：**
- 分页器 `pagination.total` 恒等于已加载数组长度，翻页按钮无效（前端未做切片）；
- 全部数据一次性加载到前端，数据量增长后有性能和内存风险；
- `params` 中传递的 `current/size` 被 `/list` 接口忽略，查询条件 `name/baseType/isBuiltin` 虽生效但无法分页；
- 与设计 §6.1 "`/ontology/data-properties` 返回 `IPage`，管理分页"不一致。

**修复方案：** 改用 `fetchDataPropertyPage` 并正确处理 `IPage` 响应结构（`response.data.records` + `response.data.total`）。

### P1-03：后端摘要查询 N+1 性能问题

**位置：** `server/.../service/impl/OntDataPropertyServiceImpl.java:523-554`（`toSummary` 方法）

**问题：**

```java
private OntDataPropertySummaryVO toSummary(OntDataProperty prop) {
    // ...
    List<OntDataPropertyLabel> labels = labelMapper.selectList(...);       // 查询1：标签
    OntEntityType domainType = entityTypeMapper.selectById(...);            // 查询2：定义域
    List<OntEntityTypeLabel> domainLabels = entityTypeLabelMapper.selectList(...); // 查询3：定义域标签
    long enumCount = enumMapper.selectCount(...);                           // 查询4：枚举计数
    OntUnitCategory category = unitCategoryMapper.selectById(...);          // 查询5：单位分类（可选）
    // ...
}
```

`pageSummary` 和 `listSummary` 对每条记录调用 `toSummary`，分页 10 条时产生 **40~50 次 DB 往返**。设计 §6.1 明确要求"分页先查主表，再批量查询标签、定义域，禁止逐行 N+1 查询"。

**影响：**
- 分页列表加载慢，数据量增长后性能急剧下降；
- 直接违反设计文档明确禁止 N+1 的要求。

**修复方案：** 在 `pageSummary`/`listSummary` 中先查主表，收集全部 ID 后批量查询标签、定义域、枚举计数，在内存中组装 VO。

## 四、需修正问题（P2）

### P2-01：Service 层缺少 preferred_alias 跨列冲突校验

**位置：** `server/.../service/impl/OntDataPropertyServiceImpl.java:375-430`（`validateSemanticFields`）

**问题：**

设计 §3.1 约束 4 要求："`preferred_alias` 在同一工程和命名空间内不得与其他有效记录的 `iri_local_name/preferred_alias` 冲突；跨列冲突由 Service 校验，迁移断言兜底。"

当前 `validateSemanticFields` 校验了 IRI 唯一、IRI 本地名唯一、定义域内 name 唯一，但**未校验 `preferred_alias`**：
- 新建扩展属性时设置 `preferredAlias = "unit"`（与内置 C.41 的 iri_local_name 冲突）不会被拦截；
- 数据库唯一索引 `uk_ont_data_property_preferred_alias` 只覆盖 `preferred_alias` 自身列冲突，不覆盖"别名与另一个属性的 iri_local_name 相同"的跨列冲突。

**影响：**
- 扩展属性可创建与其他属性 `iri_local_name` 同名的 `preferred_alias`，导致序列化时 IRI 歧义；
- V7 迁移断言只检查内置种子间的冲突，不检查扩展属性。

**修复方案：** 在 `validateSemanticFields` 增加 `preferred_alias` 跨列冲突校验（别名不为空时，检查同工程同命名空间下是否有其他记录的 `iri_local_name` 或 `preferred_alias` 等于该值）。

### P2-02：内置属性更新路径 saveLabel 空值覆盖风险

**位置：** `server/.../service/impl/OntDataPropertyServiceImpl.java:290-300, 563-575`

**问题：**

内置属性更新路径：
```java
if (BUILTIN.equals(old.getIsBuiltin())) {
    // ... 更新 sortOrder/remarks
    saveLabel(old.getId(), ZH, request.getLabel());  // request.getLabel() 可能为 null
    return R.ok(...);
}
```

`saveLabel` 实现：
```java
private void saveLabel(Long dataPropertyId, String locale, String label) {
    int updated = labelMapper.update(null, Wrappers.<OntDataPropertyLabel>lambdaUpdate()
        .eq(OntDataPropertyLabel::getDataPropertyId, dataPropertyId)
        .eq(OntDataPropertyLabel::getLocale, locale)
        .set(OntDataPropertyLabel::getLabel, label));   // label=null 时覆盖为 null
    // ...
}
```

虽然 `OntDataPropertyUpdateDTO.label` 有 `@NotBlank` 校验，正常请求不会为 null。但如果未来移除校验或存在绕过路径，`saveLabel` 会以 null 覆盖已有中文标签，且后续 `ck_ont_data_property_label_text CHECK (btrim(label) <> '')` 会抛出数据库异常而非业务错误。

**影响：** 边界场景下内置属性中文标签被破坏；防御性不足。

**修复方案：** `saveLabel` 增加 null/blank 防御，空值时跳过标签更新。

### P2-03：hasSemanticChanges 对内置属性 definition/formatHint 过度限制

**位置：** `server/.../service/impl/OntDataPropertyServiceImpl.java:485-503`

**问题：**

设计 §5.3 规定"内置属性仅允许修改 `sortOrder/remarks`"，`hasSemanticChanges` 据此将 `definition`、`formatHint`、`preferredAlias` 等全部视为语义字段修改而拒绝。

这一实现**严格符合设计**，但存在实务问题：
- 内置属性更新 DTO 的 `definition`/`formatHint` 字段本身允许传入（DTO 无内置属性特判），前端编辑表单中"定义"和"格式提示"输入框在内置模式下也未禁用（仅 `formatHint` 无 disabled），导致用户可填入但提交时被拒，体验不一致；
- `definition` 在国标溯源中是可维护的治理内容（设计 §2.1"用户扩展可维护"），严格禁止修改定义文案可能过于刚性。

**影响：** 体验不一致；治理灵活性受限。不阻断功能，属优化项。

**修复方案：** 前端内置编辑模式下禁用 `definition` 输入框（与 `formatHint` 统一处理），或后端对内置属性放宽 `definition` 更新。本次选择前端统一禁用，保持后端与设计一致。
