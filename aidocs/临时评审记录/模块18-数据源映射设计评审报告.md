## 一、评审总体结论

**总评分：8.5 / 10 —— 设计质量优秀，可进入实现阶段，但存在若干必须在编码前修正的问题。**

这套设计文档体系展现出以下突出优点：

1. **架构分层清晰**：18-00 总体架构明确了 Controller→Application→Connector/Compiler/Ingestion→Repository 的单向依赖链，禁止跨层调用，这在后端工程中属于成熟做法。
2. **安全边界意识极强**：全文贯穿"失败关闭"原则，凭证加密用 AES-256-GCM + AAD 绑定，不回显密码、不保存源整行、事件载荷最小化，威胁模型表格完备。
3. **Ontology 建模判断正确**：UserAccount ≠ Person、Position ≠ RBAC Role、不推断岗位属于部门——这三条建模克制避免了常见的过度本体化错误。
4. **幂等设计扎实**：来源绑定唯一键 + 内容哈希 + 属性所有权 + 冲突策略四层保证，不依赖"先查再插"的脆弱假设，并发用 `ON CONFLICT` 兜底。
5. **文档间权威边界明确**：18-00 声明冲突时以总体架构为准，具体功能以子文档为准，表归属清单统一在 18-00 §7.1。

**主要扣分项**（详见下文各节）：

- 权限注解名称存在拼写不一致（`ontology_ontology_mapping_publish` 多了一层 `ontology_` 前缀）。
- 18-04 声称数据属性ID范围 954001~954015，但实际列表到 954017，范围声明有误。
- 单记录事务粒度（每条 `REQUIRES_NEW`）在万级数据量下可能成为性能瓶颈，缺少降级路径。
- 前端组件拆分精细但缺少 `RelationMappingEditor.vue`（独立编辑组件），关系映射仅通过 Wizard 配置可能在复杂场景受限。

## 二、模块必要性评审

### 2.1 模块18整体是否必须？——**必须**

| 评审维度 | 判断 | 理由 |
|---|---|---|
| 平台能力缺口 | 必须 | 当前平台实例全靠人工 CRUD（`OntEntityInstanceService`），无法从外部业务系统自动、受控、可追溯地批量生成语义实例。交叉验证确认不存在 `OntologyInstanceIngestionService`，摄入能力是全新建设。 |
| 上游设计一致性 | 必须 | 模块03~14 已完成 T-Box（Schema）建模和实例管理，模块26 EDA 和模块36 安全已提供事件骨干和安全决策，但从"外部数据 → A-Box"的运行时摄入通道仍是空白。 |
| 业务场景验证 | 必须 | 18-09 以 youming 自身 UPMS（sys_user/sys_dept/sys_post）作为首个自举场景，这是一个极其务实的"吃自己狗粮"策略，能立即验证整个映射链路的可用性。 |
| 后续模块依赖 | 必须 | 模块19 IoT接入、模块20 物模型均需复用18-01的摄入服务和来源绑定思想。如果不建18，19/20需要各自复制实例校验逻辑，违反DRY。 |

| 子模块 | 是否必须 | 评审意见 |
|---|---|---|

| 18-07 同步作业 | 必须 | 游标恢复 + 租约 + 取消 + 错误率阈值 + 删除检测——这些是生产作业的必要能力。 |
| 18-08 安全/EDA/可观测 | 必须 | 确保映射不成为模块36的安全旁路。INGEST动作扩展、异步授权快照、事件最小化——都是横切必要约束。 |

| 18-10 前端控制台 | 必须 | 用户"无需编辑JSON或SQL即可完成受控映射"——这是产品可用性的必要条件。纯后端API无法交付给业务用户。 |

## 四、模块设计合理性评审

### 4.1 后端架构设计（Java高级工程师视角）

#### 4.1.1 分层与依赖 —— ⭐优秀

```
controller/  → application/ → connector/compiler/transform/ingestion/job → repository/
```

- 禁止 Controller 直接调用 Mapper ✅
- 禁止 Connector 直接写 Ontology 表 ✅
- 禁止映射 Worker 绕过摄入服务 ✅

这三条硬约束在 `18-00 §5.1` 明确列出，是工程纪律的关键。从现有代码看，pig 上游本身遵循 Controller→Service→Mapper 模式，本设计在此基础上增加了 ingestion 层作为统一写入入口，合理且不破坏现有结构。

#### 4.1.2 OntologyInstanceIngestionService 接口设计 —— ⭐优秀，有改进建议

```java
public interface OntologyInstanceIngestionService {
    IngestionResult upsertEntity(EntityIngestionCommand command);
    RelationIngestionResult upsertRelation(RelationIngestionCommand command);
    DeactivationResult deactivateEntity(SourceIdentity sourceIdentity, DeleteStrategy strategy, IngestionContext context);
    BatchIngestionResult ingestBatch(List<EntityIngestionCommand> commands, IngestionContext context);
}
```

**优点：**
- 使用 Java `record` 定义命令对象，不可变且线程安全。
- `SourceIdentity` 用规范化复合键 + SHA-256 摘要，设计稳定。
- 明确声明为"内部SPI，V1不创建公网批量写API"——安全意识强。

**改进建议：**
- `ingestBatch` 方法缺少分页/流式接口签名。万级记录全量加载到 `List` 可能 OOM。建议增加 `Stream<EntityIngestionCommand>` 或 `Iterator` 重载，或在接口注释中声明调用方必须分页传入。
- `deactivateEntity` 的 `DeleteStrategy` 参数是枚举还是接口？文档中 `DeleteStrategy` 用法不一致：18-01 §10 描述为策略枚举（`IGNORE/MARK_INACTIVE/SOFT_DELETE/BLOCK_AND_REVIEW`），18-04 §3 表中 `delete_strategy` 字段也是这些值。建议明确为枚举。

#### 4.1.3 事务粒度 —— ⚠️ 需关注

18-07 §7 声明：

> V1采用每条记录 `TransactionTemplate + REQUIRES_NEW` 事务，保证单条失败不回滚同页已成功记录。

**评估：**
- 正确性角度：这是最安全的隔离级别，单条失败不影响同批其他记录。
- 性能角度：每条记录一个独立事务，PostgreSQL 下每个事务有 commit/fsync 开销。万级数据（18-07 §17 验收测试为10000条UPMS）按每条独立事务计算，约 10000 次提交。
- 文档已预留降级路径："后续只有在压测证明事务开销成为瓶颈后，才允许引入批内保存点优化"——这个决策方向正确。
- **建议**：在配置项中增加 `job.batch-commit-size` 默认为1，允许后续调优时改为批内保存点模式而无需改接口。

#### 4.1.4 Connector SPI —— ⭐优秀

```java
public interface DataSourceConnector extends AutoCloseable {
    String type();
    ConnectionTestResult test(ConnectionRequest request);
    List<SourceSchema> listSchemas(MetadataRequest request);
    List<SourceObject> listObjects(ObjectQuery query);
    SourceObjectMetadata describeObject(ObjectRef ref);
    SourcePage scan(SourceScanPlan plan, SourceCursor cursor);
    Optional<SourceRow> findByKey(SourceLookupPlan plan, SourceRecordKey key);
}
```

- `AutoCloseable` 继承正确，连接池生命周期管理清晰。
- `scan` 返回 `SourcePage` 支持游标分页，不返回全量 `List<SourceRow>`，内存安全。
- `findByKey` 用于增量重试和关系绑定查询，接口职责分明。
- V1唯一实现 `PostgreSqlDataSourceConnector`，但SPI预留了扩展性。

#### 4.1.5 SQL安全设计 —— ⭐优秀

18-02 §8 的安全措施非常全面：

1. 标识符来自元数据快照 + 双引号转义 + 白名单 ✅
2. 过滤DSL结构化 + PreparedStatement参数化 + 禁止RAW/SUBQUERY/UNION ✅
3. 只读连接 + `BEGIN READ ONLY` + `statement_timeout` + `lock_timeout` ✅
4. 数据库账号也必须只读 ✅（"应用层只读不能替代数据库权限"——这条认知非常专业）

#### 4.1.6 乐观锁 —— ⭐合理

```sql
UPDATE ont_mapping_version
SET ..., revision = revision + 1
WHERE id = :id AND revision = :expectedRevision AND version_status = 'DRAFT';
```

更新0行返回 `ONT-MAP-011 VERSION_CONFLICT`，前端必须带 revision，冲突后重新加载。这是标准的乐观锁模式，与 pig 上游 `@Version` 注解的思路一致但更受控（显式 revision 字段而非 JPA 自动版本）。

### 4.2 数据库设计评审

#### 4.2.1 表结构总体评估 —— ⭐优秀

15张新建表 + 多张改造表，覆盖了数据源、元数据、映射工程/版本/实体/字段/关系、校验报告/问题、作业/记录、来源绑定/值provenance/关系provenance、待解析关系——每个表都有明确职责，无冗余。

#### 4.2.2 唯一索引设计 —— ⭐优秀

所有唯一索引使用 `WHERE del_flag = '0'` 条件索引，允许逻辑删除后重建。这是 pig 上游的既有模式（如 `sys_user` 的 `uk_user_username` 也是 partial index），与本仓库一致。

特别值得肯定的设计：

```sql
-- 来源绑定唯一键：映射工程+实体映射码+源记录键哈希
CREATE UNIQUE INDEX uk_ont_binding_identity
  ON ont_source_instance_binding
  (mapping_project_id, entity_mapping_code, source_record_key_hash)
  WHERE del_flag = '0';
```

使用哈希控制索引长度（`varchar(64)` 而非 `varchar(1024)`），命中后再比较完整键——这是处理长键唯一约束的标准做法。

#### 4.2.3 延迟外键处理 —— ⭐正确

18-07 §4.1 明确列出6组延迟外键，在全部表创建后追加。这正确处理了表间循环引用：

```
ont_mapping_project.last_job_id → ont_mapping_job
ont_source_instance_binding.first_seen_job_id/last_seen_job_id → ont_mapping_job
ont_instance_value_provenance.last_job_id → ont_mapping_job
ont_instance_relation_provenance.last_job_id → ont_mapping_job
ont_pending_relation.first_job_id/last_job_id → ont_mapping_job
```

#### 4.2.4 `assertion_origin` 列改造 —— ⭐合理但需补充

18-05 §9 正确识别了关系主表缺少来源标识的问题。当前 `ont_instance_object_relation` 无 `assertion_origin` 列（交叉验证确认），增加该列并回填历史数据是正确的。

**建议补充：**

```sql

  WHERE id IN (SELECT instance_id FROM ont_source_instance_binding 
               WHERE entity_mapping_code LIKE 'APPENDIX_D%')
```

## 十、最终建议

### 10.1 可以进入实现阶段

这套设计文档已经达到了进入编码实现阶段的成熟度。建议按以下步骤推进：

1. **先修正P0问题**（权限注解统一、ID范围修正）——预计0.5天。
2. **补充P1关键项**（DATETIME Java类清单、assertion_origin回填SQL、V21建表顺序总览）——预计1天。
3. **按18-00 §15交付顺序开始阶段1**（18-01摄入底座 + V21核心改造）。

### 10.2 实现期间注意事项

1. V21迁移脚本应先在本地 `youmingdb` 上用 Flyway dry-run 验证建表顺序和外键约束。
2. `OntologyInstanceIngestionService` 的并发幂等测试（18-01 §14 第1条"并发摄入100次"）应在阶段1就完成，作为后续所有功能的基础保障。
3. DATETIME类型扩展涉及多模块，建议在阶段1的V21中一次性完成DDL改造，避免后续多次ALTER。
4. 前端开发可与后端阶段3-4并行启动API mock，但实际联调依赖后端阶段4完成。
5. 18-09的UPMS自举场景应在阶段6作为端到端验收的关键里程碑，不合格不发布。

### 10.3 长期演进建议

1. **CDC能力**（V1.1）：18-00 §3.2 明确CDC留作V1.1，不阻塞首期。建议在V1实现期间记录CDC需求点，为V1.1预留扩展接口。
2. **多数据库连接器**：Connector SPI已预留，后续MySQL/Oracle/REST连接器可按SPI扩展。
3. **R2RML导出**：18-00 §3.2 提及"可在后续增加兼容导出器"，建议在V1.x实现。
4. **图谱可视化**：18-09 §12 可视化验收当前依赖现有图谱模块，后续可增强映射关系专用视图。
